### 📖 5.1 인증과 인가

  - 예: 영업팀은 영업 실적을 조회할 수 있지만 정산 내역은 조회할 수 없다

```

   v
[인증] 누구인가?            --> seoyeon 맞음 (비밀번호 통과)
   v

```

### 📖 5.2 역할 기반 접근통제(RBAC)

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- **RBAC**(Role-Based Access Control · 롤 베이스드 액세스 컨트롤, 역할 기반 접근통제)
  - 사용자에게 권한을 직접 주지 않고, **역할**에 권한을 주고 사용자에게 역할을 준다
  - 사용자 → 역할 → 권한 순서로 따라가서 허용 여부를 정한다
- **역할**(role · 롤)
  - 하는 일이 같은 사람들의 묶음
  - 예: 영업(sales) · 재무(finance) · 계정 관리자(account_admin)
- **권한**(permission · 퍼미션)
  - 「자원 하나에 행위 하나」를 허용하는 것
  - 오늘은 `자원:행위` 모양으로 쓴다. 예: `SALES:QUERY` 는 영업 실적 조회

```
[사용자]          [역할]                 [권한]
seoyeon   ----->  sales           ----->  SALES:QUERY, SALES:CHANGE
junho     ----->  finance         ----->  SALES:QUERY, SETTLE:QUERY
gaeun     ----->  account_admin   ----->  ACCOUNT:QUERY, ACCOUNT:CHANGE
```

권한을 「준다」는 것은 그 사람이 할 수 있는 일을 파일에 적어 두는 것입니다. 영업팀이 30명이라고 할 때 두 방식을 파일 모양으로 비교하면 이렇습니다.

```
[직접 주기] 사용자 한 명마다 권한 목록을 적는다 (30명이면 30곳)

   "seoyeon": {"permissions": ["SALES:QUERY", "SALES:CHANGE"]},
   "minsu":   {"permissions": ["SALES:QUERY", "SALES:CHANGE"]},
   ...                          ← 영업팀 30명 모두 같은 내용을 되풀이해 적는다

   영업팀 권한이 바뀌면      30곳을 하나씩 고친다
   부서를 옮긴 직원은        옛 권한을 지우는 것을 잊기 쉽다

[역할로 주기] 권한 목록은 역할 한 곳에만 적고, 사용자에게는 역할 이름만 적는다

   roles.json  "sales": ["SALES:QUERY", "SALES:CHANGE"]        ← 권한은 여기에 한 번만 적는다
   users.json  "seoyeon": {"role": "sales"},                   ← 30명은 역할 이름만 적는다
               "minsu":   {"role": "sales"},
               ...

   영업팀 권한이 바뀌면      roles.json 의 sales 한 곳만 고친다
   부서를 옮긴 직원은        그 직원의 role 한 칸만 바꾼다
```

- 영업팀 30명 중 1명이 재무팀으로 옮길 때 고칠 곳을 세면, 직접 주기는 영업 권한 두 개(`SALES:QUERY` · `SALES:CHANGE`)를 빼고 재무 권한 두 개(`SALES:QUERY` · `SETTLE:QUERY`)를 넣어서 **네 군데**이고 하나라도 빼먹으면 옛 권한이 남습니다. 역할로 주기는 그 직원의 역할 하나(`sales` → `finance`)만 바꾸는 **한 군데**입니다.

### 📖 5.3 권한 매트릭스와 최소권한

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- **권한 매트릭스**(permission matrix · 퍼미션 매트릭스)
  - 역할을 줄에, 권한을 칸에 놓고 허용(○)과 아님을 표시한 표
  - 누가 무엇을 해도 되는지를 한눈에 확인하는 데 쓴다
- **최소권한**(least privilege · 리스트 프리빌리지)
  - 일에 필요한 만큼만 허용한다(10/19(월) 오전)
  - 매트릭스에서는 ○ 가 적을수록 좋다. 필요 없는 ○ 는 사고가 났을 때 피해 범위가 된다
- **기본 거부**(default deny · 디폴트 디나이)
  - 매트릭스에 ○ 가 없으면 모두 거부한다(10/15(목) 방화벽과 같은 생각)

표에 나오는 자원과 행위입니다.

- 자원
  - `SALES`: 영업 실적
  - `SETTLE`: 정산 내역
  - `ACCOUNT`: 직원 계정과 그 권한 설정
- 행위
  - `QUERY`: 조회
  - `CHANGE`: 변경
- 역할 `batch` 는 **서비스 계정**(사람이 아니라 프로그램이 자동으로 쓰는 계정)의 역할입니다. `batch-night` 가 매일 02:00 에 정산을 집계합니다

A사가 정한 권한 매트릭스(초안)입니다.

| 역할 | `SALES:QUERY` | `SALES:CHANGE` | `SETTLE:QUERY` | `ACCOUNT:QUERY` | `ACCOUNT:CHANGE` |
|---|---|---|---|---|---|
| `sales`(영업) | ○ | ○ | | | |
| `finance`(재무) | ○ | | ○ | | |
| `account_admin`(계정 관리자) | | | | ○ | ○ |
| `batch`(정산 집계 서비스 계정) | | | ○ | | |
| `auditor`(감사) | ○ | | ○ | ○ | |

- `auditor`(감사 담당)의 **감사**(audit · 오딧)는 규칙대로 일이 처리됐는지 나중에 기록으로 확인하는 일입니다. 이 역할은 자료를 조회만 하고 바꾸지는 않습니다.
- 역할이 하는 일: `sales` 영업 실적을 조회하고 고친다 · `finance` 정산 내역을 조회한다 · `account_admin` 직원 계정과 권한을 설정한다 · `batch` 정산을 자동으로 집계한다 · `auditor` 자료를 조회하며 확인한다.

#### 매트릭스에서 요청 하나 판정하기

읽는 법은 역할 줄과 권한 칸이 만나는 곳을 보는 것입니다.

- 예 ①: `sales` 줄 × `SALES:QUERY` 칸 = ○ → 영업은 영업 실적을 조회해도 됩니다.
- 예 ②: `sales` 줄 × `SETTLE:QUERY` 칸 = 빈칸 → 영업이 정산 내역을 조회하면 거부입니다.

요청 하나는 세 단계로 판정합니다. 본보기는 문제에 없는 요청입니다.

| 단계 | 하는 일 | 본보기: gaeun 의 직원 계정 조회(`ACCOUNT:QUERY`) |
|---|---|---|
| ① 역할 찾기 | 사용자의 역할을 인사팀 표에서 찾는다 | gaeun 의 역할은 `account_admin` |
| ② 칸 찾기 | 그 역할 줄과 요청한 권한 칸이 만나는 곳을 본다 | `account_admin` 줄 × `ACCOUNT:QUERY` 칸 |
| ③ ○ 확인 | ○ 가 있으면 허용, 없으면 거부 | ○ 있음 → 허용 |

- 다른 본보기: `auditor` 가 `ACCOUNT:CHANGE` 를 하려는 경우 그 칸에 ○ 가 없으므로 거부입니다(10/15(목) 방화벽의 기본 거부와 같습니다).

| `config/roles.json` | 역할 → 권한 목록 | `"역할": ["자원:행위", …]` |

- 설정을 코드와 나눠 파일에 두면, 직원이 바뀌어도 코드는 그대로 두고 파일만 고칩니다.
- JSON 의 참 · 거짓은 소문자 `true` · `false` 로 씁니다. 파이썬의 `True` · `False` 와 다릅니다.
- 마지막 항목 뒤에는 쉼표를 쓰지 않습니다.
- 글자와 이름은 큰따옴표 `"` 로만 감쌉니다. 작은따옴표 `'` 는 JSON 오류입니다.
- 파일이 JSON 규칙에 맞는지는 `python -m json.tool config/users.json` 처럼 확인합니다. `-m json.tool` 은 파이썬에 들어 있는 JSON 검사 도구를 실행하라는 뜻입니다. 맞으면 내용이 다시 정리되어 출력되고, 틀리면 `Expecting …` 오류와 줄 번호가 나옵니다.

#### 매트릭스의 ○ 는 파일에서 어떻게 적히나

- 매트릭스의 ○ 는 사람이 보기 쉽게 그린 표시입니다. 파일에는 「○」 글자로 저장하지 않고, `roles.json` 목록에 적힌 **권한 하나가 ○ 한 칸**입니다. 빈칸은 아예 적지 않으므로 목록에 없으면 거부(기본 거부)입니다.
  - 예: `sales` 줄의 ○ 두 칸(`SALES:QUERY` · `SALES:CHANGE`) → `"sales": ["SALES:QUERY", "SALES:CHANGE"]`

두 파일은 역할 이름으로 이어집니다. seoyeon 이 무엇을 해도 되는지는 두 파일을 차례로 보면 압니다.

| 순서 | 파일 | 찾는 것 | 결과 |
|---|---|---|---|
| ① | `users.json` | `"seoyeon"` 줄 | `"role": "sales"` |
| ② | `roles.json` | `"sales"` 줄 | `["SALES:QUERY", "SALES:CHANGE"]` |
| ③ | 결과 | | seoyeon 은 영업 실적 조회 · 변경만 해도 됨 |

- 두 파일을 잇는 열쇠는 **역할 이름**입니다. `users.json` 의 `role` 과 `roles.json` 의 이름이 같은 글자여야 하고, `"Sales"` · `"sale"` 처럼 다르면 `roles.json` 에서 못 찾습니다.
- 권한은 `roles.json` 에 역할마다 한 번만 적고, 영업팀 30명은 `users.json` 에 역할 이름만 적습니다.
- 쉼표 하나 · 따옴표 하나만 틀려도 판정 코드가 파일을 읽지 못합니다. 그때 `python -m json.tool` 이 틀린 줄 번호와 함께 오류를 알려 줍니다(아래는 Python 3.9 에서 확인한 문구이고, 버전에 따라 조금 다를 수 있습니다. 줄 번호는 내 파일에 따라 다릅니다).

| 틀린 곳 | `json.tool` 이 보여 주는 오류(예) |
|---|---|
| 줄 끝 쉼표가 빠짐 | `Expecting ',' delimiter: line 3 …` |
| 작은따옴표 `'seoyeon'` | `Expecting property name enclosed in double quotes: line 2 …` |
| 마지막 줄 뒤에 쉼표 | `Expecting property name enclosed in double quotes: line 4 …` |
| 파이썬식 `True` | `Expecting value: line 2 …` |

> ✍️ **여기부터 문제입니다.** 위는 읽을거리였고, 아래에서 직접 합니다.

```
   v 있음
[4] "자원:행위" 가 역할의 권한에 있나?
      없으면 --> 거부: 권한 없음
   v 있음
허용
```

- 위에서부터 검사하다가 하나라도 걸리면 그 자리에서 거부를 리턴하고 끝납니다(10/19(월) 오전의 필수 조건과 같은 방식).
- 네 검사를 모두 지나야만 허용입니다. 검사 하나를 빼먹으면 그 경우는 **잘못 허용됩니다.** 이것이 2과목 10/21(수) 오전에 본 열림 기본 값(fail-open)과 같은 위험입니다.

#### 걸리면 바로 끝내는 이유

뒤 검사는 앞 검사를 통과한 요청에만 할 수 있습니다. 앞에서 걸러 주지 않으면 코드가 멈춥니다.

| 검사 | 앞에서 걸러 주지 않으면 |
|---|---|
| [2] 재직 | 사용자 파일에 없는 사용자의 `employed` 를 꺼내려다 `KeyError` 로 멈춤. 예: `USERS["minsu"]["employed"]` → `KeyError: 'minsu'` |
| [4] 권한 | 역할 파일에 없는 역할의 목록을 꺼내려다 `KeyError` 로 멈춤. 예: `ROLES["intern"]` → `KeyError: 'intern'` |

- 하나만 걸려도 결론은 거부라서 남은 검사를 더 볼 필요가 없습니다. 끝까지 다 지난 요청만 허용하는 것이 기본 거부입니다.

#### 거부 이유 네 가지 — 감사 때 하는 말

| 거부 이유 | 어디서 막혔나 | 감사 때 하는 말 · 고칠 곳 |
|---|---|---|
| 등록되지 않은 사용자 | `users.json` 에 없음 | 등록 누락인지, 없는 계정의 접속 시도인지 |
| 퇴사한 계정 | `"employed": false` | 막는 게 맞음. 남은 계정은 회수 |
| 역할이 없음 | `roles.json` 에 없음 | 설정 누락 → `roles.json` 에 역할을 정해 넣음 |
| 권한 없음 | 목록에 그 권한 없음 | 정상 차단. 한 계정에 몰리면 사건 신호 |

- 네 이유는 사용자 → 역할 → 권한을 찾아가다 막힐 수 있는 네 곳입니다. 이름은 수업에서 붙였습니다.
- 「거부」 하나로만 남기면 설정을 고칠 일과 사건 신호가 섞여 구분할 수 없습니다.

**이 시간에 나오는 말** (이미 배운 방법입니다)

- `with open(파일, encoding="utf-8") as f:` 와 `json.load(f)` 로 JSON 파일을 딕셔너리로 읽습니다(9/28(월)).
- `값 in 딕셔너리` 는 딕셔너리에 그 키가 있는지, `값 not in 딕셔너리` 는 없는지 검사합니다. 예: `role not in ROLES`. `값 not in 리스트` 는 목록에 없는지 검사합니다(10/15(목)).
- `return 값1, 값2` 로 두 값을 함께 리턴하고, `ok, reason = 함수(…)` 로 나눠 받습니다(10/16(금) 4교시).
- `f"{resource}:{action}"` 처럼 f-문자열로 글자를 합칩니다(9/23(수)).
- `from rbac import check_permission` 처럼 내가 만든 파일의 함수를 불러옵니다(10/6(화) `from llm_client import call_llm`).
- `if not 값:` 은 값이 거짓(`False`)일 때 실행됩니다(10/19(월) `not account["employed"]`).
- 함수 첫 줄의 `""" … """` 는 **독스트링**(docstring · 닥스트링)이라 부르는 설명 글입니다. 함수가 무엇을 받고 리턴하는지 한 번에 적은 것이고 실행에는 영향이 없습니다.

`rbac.py` 가 시작할 때 읽어 두는 `ROLES` · `USERS` 는 이런 모양이고, 함수는 `ok, reason` 으로 나눠 리턴합니다.

```python
print(ROLES["sales"])                 # ['SALES:QUERY', 'SALES:CHANGE']
print(USERS["seoyeon"])               # {'role': 'sales', 'employed': True}   ← JSON 의 소문자 true 가 파이썬의 True 가 됨
print(USERS["seoyeon"]["employed"])   # True

ok, reason = check_permission("minsu", "SALES", "QUERY")
print(ok, reason)                     # False 등록되지 않은 사용자
```

```python
is_open = False                           # 예시 값
if not is_open:                           # is_open 이 거짓이면
    print("닫혀 있음")                      # 닫혀 있음
```

- 예시의 `is_open` 자리에 `USERS[user]["employed"]` 를 넣으면 `[2]` 가 됩니다.

### <mark>✍️ 문제 6-1 · 권한 판정 함수 `check_permission` 직접 쓰기</mark>

**📍 이런 상황이 있습니다**

- 판정 함수의 첫 검사(등록되지 않은 사용자)는 미리 써 두었습니다. 담당자는 나머지 세 검사를 직접 써서, 모든 실패 경로가 거부되고 이유가 서로 다르게 남게 해야 합니다.
- 현업의 접근통제 코드는 이렇게 검사를 위에서부터 차례로 걸고, 끝까지 지난 경우에만 허용합니다.

**🎯 할 일**

1. 아래 코드로 `rbac.py` 를 만들고, `# ←` 가 있는 <mark>다섯 곳</mark>을 채웁니다.

**준비** — 아래 `rbac.py` 는 5교시(문제 5-1)에 쓴 두 파일 `config/users.json` 과 `config/roles.json` 을 **읽습니다.** 그 파일이 없으면 코드가 시작하자마자 멈춥니다. 터미널이 `…/access_control` 위치인지 확인한 뒤(아니면 `cd access_control` 로 들어갑니다) 두 파일이 있는지 봅니다.

**`rbac.py`**

```python
import json                                                      # JSON 파일을 읽는 모듈을 불러온다

with open("config/roles.json", encoding="utf-8") as f:           # 역할 파일을 연다
    ROLES = json.load(f)                                         # 역할 → 권한 목록 딕셔너리로 읽는다
with open("config/users.json", encoding="utf-8") as f:           # 사용자 파일을 연다
    USERS = json.load(f)                                         # 사용자 → 정보 딕셔너리로 읽는다


def check_permission(user, resource, action):                    # 사용자 · 자원 · 행위를 받는 함수
    """(허용 여부, 이유)를 리턴한다. 허용 목록에 없으면 모두 거부한다."""   # 함수 첫 줄의 """ … """ 는 함수 설명 글이고 실행에는 영향이 없다
    if user not in USERS:                                        # 사용자 파일에 없는 계정이면
        return False, "등록되지 않은 사용자"                       # 바로 거부하고 함수를 끝낸다
    # [2]-1. USERS[user]["employed"] 가 참이 아니면 "퇴사한 계정" 을 이유로 거부한다   # ←

    # [3]-1. 이 사용자의 역할 USERS[user]["role"] 을 role 에 담는다   # ←
    # [3]-2. role 이 ROLES 에 없으면 "역할이 없음" 을 이유로 거부한다   # ←

    # [4]-1. resource 와 action 을 "자원:행위" 모양 글자로 합쳐 permission 에 담는다   # ←
    # [4]-2. permission 이 ROLES[role] 목록에 없으면 "권한 없음" 을 이유로 거부한다   # ←

    return True, "허용"                                          # 모든 검사를 지나면 허용한다
```

**`day01_6-1_run.py`**

```python

REQUESTS = [                                                     # 판정할 요청 목록. (사용자, 자원, 행위)
    ("seoyeon", "SALES", "QUERY"),                               # 영업이 영업 실적 조회
    ("seoyeon", "SETTLE", "QUERY"),                              # 영업이 정산 조회 (10/19(월) 사건)
    ("junho", "SETTLE", "QUERY"),                                # 재무가 정산 조회
    ("junho", "SALES", "CHANGE"),                                # 재무가 영업 실적 변경
    ("dami", "SALES", "QUERY"),                                  # 퇴사자가 영업 실적 조회
    ("minsu", "SALES", "QUERY"),                                 # 사용자 파일에 없는 계정
    ("gaeun", "ACCOUNT", "CHANGE"),                              # 계정 관리자가 권한 변경
    ("batch-night", "SETTLE", "QUERY"),                          # 서비스 계정이 정산 집계
    ("tester", "SALES", "QUERY"),                                # 역할 파일에 없는 역할(intern)
]

for user, resource, action in REQUESTS:                          # 요청을 하나씩 꺼낸다
    ok, reason = check_permission(user, resource, action)        # 판정 결과와 이유를 나눠 받는다
    print(user, resource, action, "->", ok, reason)              # 사용자 · 자원 · 행위 -> 결과 이유 를 출력한다
```

- 주석의 `[2]` · `[3]` · `[4]` 는 6.1 그림의 검사 번호입니다. `[1]` 은 미리 써 두었습니다.
- 주석 줄은 그대로 두고, **각 주석 바로 아래 줄**에 씁니다.
- `# ←` 주석이 모두 앞 공백 4칸에서 시작하므로, 그 아래에 쓰는 줄도 4칸으로 시작합니다. `if` 안쪽의 `return` 줄만 4칸 더 들어간 8칸입니다.

- 출력 한 줄의 모양은 `사용자 자원 행위 -> True(또는 False) 이유` 이고, 요청이 아홉 건이라 아홉 줄이 나옵니다.

#### 🐍 문법 상자 · 1부 · 2부에서 쓰는 모양 (예시 값 · 읽기만 합니다)

키를 글자로 만들어 건수 세기 — 예시 사용자 `minsu`

```python
counts = {}

```

| 읽은 기록(예시) | 만든 키 | 센 뒤 `counts` |
|---|---|---|
| minsu 허용 | `"minsu 허용"` | `{'minsu 허용': 1}` |
| minsu 허용 | `"minsu 허용"` | `{'minsu 허용': 2}` |
| minsu 거부 | `"minsu 거부"` | `{'minsu 허용': 2, 'minsu 거부': 1}` |

역할마다 빈 목록을 먼저 만들고 쌓기 — 예시 역할 `hr`

```python
if role not in used:                          # 이 역할이 처음이면
    used[role] = []                           # 빈 목록부터
used[role].append(f"{resource}:{action}")     # 쓴 권한을 더함
```

| 읽은 허용 기록(예시) | 쌓은 뒤 `used` |
|---|---|
| hr · STAFF:QUERY | `{'hr': ['STAFF:QUERY']}` |
| hr · PAY:QUERY | `{'hr': ['STAFF:QUERY', 'PAY:QUERY']}` |

- 빈 목록 없이 바로 `append` 하면 `KeyError` 가 납니다.

`items()` 와 `used.get(역할, [])` — 기록에 없는 역할은 빈 목록

```python
ROLES = {"hr": ["STAFF:QUERY", "PAY:QUERY"], "guest": ["NEWS:QUERY"]}   # 예시
used  = {"hr": ["STAFF:QUERY"]}
for role, perms in ROLES.items():
    print(role, perms, used.get(role, []))
# hr ['STAFF:QUERY', 'PAY:QUERY'] ['STAFF:QUERY']
# guest ['NEWS:QUERY'] []          ← 기록에 없는 역할은 빈 목록
```

### <mark>✍️ 문제 7-1 · 접속 기록을 다시 판정하며 쓰이지 않는 권한 찾기</mark>

**📍 이런 상황이 있습니다**

- 보안 담당이 「RBAC 를 지난주에 켰다면 무엇이 막혔을지」 숫자로 알고 싶어 합니다. 막혀야 할 것이 막히는지와 정상 업무가 막히지 않는지를 모두 봐야 합니다.
- 같은 기록으로 「매트릭스의 ○ 중 실제로 쓰이지 않는 것」도 찾아 달라고 합니다. 쓰이지 않는 권한은 줄일 후보지만, 하루 기록에 안 보였다고 모두 지우면 정상 업무가 막힐 수 있습니다.
- 현업에서는 새 규칙을 켜기 전에 과거 기록에 적용해 보고 결과를 숫자로 보고하고, 이 점검을 정기적으로 돌려 「쓰이지 않은 권한 목록」을 만든 뒤 담당자 확인을 거쳐 회수합니다.

**🎯 할 일**

1. `access_log.py` 와 `day01_7-1_audit.py` 를 만듭니다(7.1).
2. `day01_7-1_audit.py` 의 <mark>1부 반복문</mark>(건수 세기 · 거부 출력 · 쓴 권한 모으기)과 <mark>2부</mark>(쓰이지 않은 권한 출력)를 직접 씁니다.
3. 실행해서 <mark>거부된 기록</mark>, <mark>사용자별 허용 · 거부 건수</mark>, <mark>쓰이지 않은 권한</mark>을 읽습니다.
4. 쓰이지 않은 권한 중 <mark>줄일 것과 남길 것</mark>을 이유와 함께 나눕니다.

**`day01_7-1_audit.py`**

```python
from rbac import check_permission, ROLES, USERS                  # 판정 함수와 역할 · 사용자 정보를 불러온다
from access_log import LOG                                       # access_log.py 의 기록 목록을 불러온다

allowed = 0                                                      # 허용 건수
denied = 0                                                       # 거부 건수
counts = {}                                                      # "사용자 허용" · "사용자 거부" → 건수
used = {}                                                        # 역할 → 실제로 쓴 권한 목록

# ← 1부: 기록을 하나씩 다시 판정하며 건수와 쓴 권한 모으기
# 1. LOG 에서 (번호, 시각, 사용자, 자원, 행위)를 하나씩 꺼낸다
# 2. check_permission 으로 판정해 ok, reason 으로 나눠 받는다
# 3. ok 이면 allowed 를 1 늘리고, counts 의 "사용자 허용" 을 1 늘리고, 그 사용자의 역할을 role 에 담는다
# 4. 같은 허용 기록에서, used 에 role 이 아직 없으면 used[role] = [] 로 빈 목록을 먼저 만들고,
#    used[role] 목록에 "자원:행위" 글자를 더한다
# 5. 아니면 denied 를 1 늘리고, "[거부]" 와 번호 · 시각 · 사용자 · 자원 · 행위 · 이유를 출력하고,
#    counts 의 "사용자 거부" 를 1 늘린다

print("허용", allowed, "거부", denied)                           # 전체 건수를 출력한다
print(counts)                                                    # 사용자별 건수를 출력한다

# ← 2부: 쓰이지 않은 권한 출력하기
# 6. ROLES 에서 역할과 권한 목록을 하나씩 꺼낸다
# 7. 그 목록의 권한을 하나씩 꺼내, used.get(역할, []) 에 없으면 "쓰이지 않음", 역할, 권한 을 출력한다
```

- 키는 `user + " 허용"` 처럼 사용자 이름과 글자를 합쳐 만듭니다. 글자와 글자는 `+` 로 이어 붙입니다(`"seoyeon" + " 허용"` 은 `seoyeon 허용`).
- `for log_id, time, user, resource, action in LOG:` 처럼 반복문의 이름은 기록 한 줄의 값 개수(다섯 개)만큼 쓰고, 아래 코드에서는 같은 이름을 씁니다.
- 거부 줄은 `print("[거부]", log_id, time, user, resource, action, "-", reason)` 모양으로 출력합니다.
- `used.get(role, [])` 는 그 역할이 기록에 한 번도 없을 때 빈 목록을 리턴합니다. 그러면 그 역할의 권한은 모두 「쓰이지 않음」이 됩니다.
- 거부된 기록은 쓴 권한으로 모으지 않습니다. 거부된 요청은 권한을 쓴 것이 아니기 때문입니다.
- 딕셔너리 안에 목록을 만들어 쌓는 모양은 이렇습니다: `if role not in used:` 다음 줄에 `used[role] = []` 로 빈 목록을 먼저 만들고, 그다음 줄에 `used[role].append(값)` 으로 더합니다(10/15(목) `.append`).
- 코드는 `# ← 1부` 주석 아래, `print("허용", …)` 줄 **위**에 씁니다. 2부 코드는 `# ← 2부` 주석 아래에 씁니다. 들여쓰기 구조는 아래와 같습니다.

```
for … in LOG:                  # 1부: 들여쓰기 없음
    ok, reason = …             # 4칸
    if ok:                     # 4칸
        …                      # 허용일 때: 8칸 (그 안의 if role not in used: 안쪽은 12칸)
    else:                      # 4칸
        …                      # 거부일 때: 8칸

for … in ROLES.items():        # 2부: 들여쓰기 없음
    for … in …:                # 4칸
        if …:                  # 8칸
            print(…)           # 12칸
```

- 맞게 썼다면 1부 끝에 `허용 7 거부 8` 이 나오고, 2부에서 `쓰이지 않음` 줄이 7개 나옵니다.

**관제에서는** — 「로그인은 정상인데 맡지 않은 자원에 접근」한 기록은 인가 쪽 문제로 분류하고 매트릭스와 대조합니다. 퇴사자 계정이 살아 있는 것은 감사에서 가장 자주 지적되는 항목이라 인사 목록과 계정 목록을 정기적으로 대조하고, 역할 파일에 없는 역할을 가진 사용자는 설정 누락의 신호입니다.

- (다) 허용되면 안 되는 요청은 네 건입니다: `seoyeon` 의 정산 조회(영업에는 정산 권한이 없음), `junho` 의 영업 실적 변경(재무에는 변경 권한이 없음), `dami` 의 영업 실적 조회(퇴사자), `tester` 의 영업 실적 조회(역할 `intern` 이 역할 파일에 없음). 검사가 [1] 하나뿐이면 [2] ~ [4] 의 경우가 모두 마지막 `return True` 까지 내려가 허용됩니다. 10/19(월) 사건(영업 계정의 정산 조회)도 다시 통과합니다. 2과목 10/21(수) 오전의 **열림 기본 값(fail-open)** 과 같은 문제입니다. 확인하지 못한 경우를 통과시키면 그 틈이 그대로 공격 경로가 됩니다.
- (라) 판정은 둘 다 거부지만 **이유가 달라집니다.** 지금 순서([2] → [3])면 「퇴사한 계정」으로 남습니다. 순서를 바꾸면([3] → [2]) 역할 `none` 이 역할 파일에 없어서 [3] 에서 먼저 걸려 「역할이 없음」으로 남고, 퇴사자라는 진짜 이유가 기록에서 사라집니다. 사람 자체를 먼저 확인하고(있나 · 재직 중인가) 그다음 역할 · 권한을 보는 순서가 이유를 정확하게 남깁니다.
- (마) 한 예: **검사 [4](권한 확인) 뒤, 허용 직전에 [5] 시간 검사를 둡니다.** 시간 조건은 역할 권한이 맞는 요청에만 의미가 있고, 맨 뒤에 두면 앞의 거부 이유(등록되지 않은 사용자 · 퇴사한 계정 · 역할이 없음 · 권한 없음)를 가리지 않습니다. 이유는 「근무 시간 아님」처럼 따로 남깁니다. 함수가 시각을 알아야 하므로 `check_permission(user, resource, action, hour)` 처럼 값을 하나 더 받는다고 가정하는 것이 전제입니다. 순서와 이유가 이어지면 맞습니다.
- (한 줄) 예: 「`check_permission` 은 없는 사용자 · 퇴사자 · 정해지지 않은 역할 · 권한 없는 요청을 모두 거부하고 이유를 따로 남기며, 네 검사를 모두 지난 요청만 허용합니다.」

**왜** — 접근통제 함수는 「허용할 조건을 모두 확인한 뒤에만 허용」해야 합니다. 맨 끝의 `return True` 앞에 빠진 검사가 있으면 그 경우는 모두 허용됩니다.

**자주 틀리는 곳** — `return` 을 빼고 `False, "퇴사한 계정"` 만 써서 검사가 아무 일도 안 하는 경우가 많습니다. `f"{resource}:{action}"` 에서 `f` 를 빼면 글자 그대로 `{resource}:{action}` 이 되어 모두 「권한 없음」이 됩니다. `role` 을 담기 전에 `role not in ROLES` 를 써서 `NameError` 가 나는 경우도 있습니다. 들여쓰기가 `if` 와 맞지 않으면 `IndentationError` 가 납니다.

**관제에서는** — 거부 이유가 구분돼 있으면 「권한 없음」이 몰리는 계정(사건 신호)과 「역할이 없음」이 몰리는 계정(설정 누락)을 나눠 볼 수 있습니다.
