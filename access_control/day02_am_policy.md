### 📖 2.1 입사 · 이동 · 퇴사와 사용자 파일

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

| 인사 변경 | 사용자 파일에서 하는 일 | 함수 |
|---|---|---|
| 입사 | 사용자 항목을 **새로 만들고** 역할을 적는다 | `assign_role` |
| 부서 이동 | 역할 칸의 값을 새 역할로 **바꾼다**(예: `sales` → `finance`). 이전 역할은 남지 않는다 | `assign_role` |
| 퇴사 | 그 사람 항목 안의 `employed` 값만 `false` 로 바꾼다. 항목(`"junho": {…}`) 자체는 파일에서 **삭제하지 않고 남겨 둔다** | `revoke_access` |

- **사용자 항목**: `users.json` 에서 사람 한 명을 나타내는 한 덩어리입니다. 예: `"junho": {"role": "finance", "employed": true}` 전체
- **부여**(assign · 어사인): 사용자에게 역할을 주는 것. 역할 파일(`roles.json`)에 없는 역할 이름이면 부여하지 않고 거부한다
- **회수**(revoke · 리보크): 사용자의 접근을 없애는 것. 오늘은 `employed` 값을 `false` 로 바꿔서 어제의 `check_permission` 이 「퇴사한 계정」으로 거부하게 한다
- 사용자 한 명은 역할 하나만 가집니다(`"role": "sales"`). 이동하면 그 칸의 값을 `finance` 로 **바꾸므로**, 이전 역할 `sales` 의 권한은 더 이상 갖지 않고 새 역할 `finance` 의 권한만 갖습니다.
- 만약 이전 역할을 지우지 않고 새 역할을 하나 더 붙이면(`sales` 와 `finance` 를 둘 다 가지면) 두 역할의 권한을 모두 갖게 되어 권한이 계속 쌓입니다. 오늘 만드는 함수는 이렇게 하지 않습니다.
- 퇴사자의 항목을 삭제하지 않고 남겨 두는 이유가 두 가지 있습니다.
  - 삭제하면 그 사람의 요청이 「등록되지 않은 사용자」로 나와서, 퇴사자와 처음부터 없던 계정을 구분할 수 없습니다.
  - 3교시에서 예외 목록을 점검할 때 예외를 가진 사람이 재직 중인지 사용자 항목에서 찾습니다. 항목이 없으면 찾지 못해 오류가 납니다.
- 두 함수는 어제의 `check_permission` 처럼 `(성공 여부, 이유)` 를 리턴합니다.

### 📖 2.2 함수가 딕셔너리를 바꾸는 방식

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

**🐍 문법 상자 — 딕셔너리 칸 바꾸기**

| 하려는 일 | 코드 |
|---|---|
| 새 칸을 만들거나 같은 이름의 칸을 덮어쓰기 | `users["minsu"] = {"role": "sales", "employed": True}` |
| 칸 안의 값 하나만 바꾸기 | `users["junho"]["employed"] = False` |
| 그 이름의 칸이 있는지 묻기 | `"minsu" in users` · `"salse" not in ROLES` |

- 파이썬에서는 참이 `True`, 거짓이 `False` 입니다. 파일(JSON)에 적을 때만 소문자 `true` · `false` 입니다.
- 딕셔너리를 함수에 넘기면, 함수는 **같은 딕셔너리**를 받습니다. 그래서 함수 안에서 바꾼 값이 함수 밖에도 남습니다.

```python
users = {"junho": {"role": "finance", "employed": True}}         # 사용자 딕셔너리 하나

def retire(d):                                                   # 딕셔너리를 받아 junho 를 퇴사 처리하는 함수
    d["junho"]["employed"] = False                               # 받은 딕셔너리 안의 값을 바꾼다

retire(users)                                                    # 함수에 딕셔너리를 넘긴다
print(users)                                                     # 함수 밖의 딕셔너리를 출력한다
```

```
{'junho': {'role': 'finance', 'employed': False}}
```

- 위 예에서 함수 안의 `d` 와 바깥의 `users` 는 이름만 다르고 **같은 딕셔너리 하나**입니다. 그래서 함수 안에서 바꾼 값이 바깥에도 남습니다.
- 오늘도 같습니다. `rbac.py` 가 읽어 둔 `USERS` 를 `assign_role(USERS, …)` 에 넘기면, `check_permission` 도 같은 `USERS` 를 보므로 바뀐 사용자로 판정합니다. 바뀐 딕셔너리를 따로 리턴하지 않아도 됩니다.
- 함수 안에서 `users = {...}` 처럼 **새 딕셔너리를 만들어 이름에 담으면** 바깥은 바뀌지 않습니다. 오늘은 `users[name] = …` 처럼 받은 딕셔너리의 칸을 바꿉니다.
- 오늘은 컴퓨터 메모리(프로그램이 실행되는 동안 값을 담아 두는 곳)에 읽어 둔 딕셔너리만 바꿉니다. 어제 만든 `config/users.json` 파일을 고치지 않기로 했기 때문에 저장하지 않으며, 프로그램이 끝나면 바꾼 내용도 사라집니다.

### 📖 3.2 글자를 시각으로 바꿔 비교하기

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

**🐍 문법 상자 — `datetime.strptime` 의 형식 글자**

9/23(수)에는 `datetime.strptime(글자, "%H:%M")` 으로 시 · 분을 읽었습니다. 오늘은 날짜까지 함께 읽습니다.

| 형식 | 뜻 | 예 |
|---|---|---|
| `%Y` | 네 자리 연도 | `2026` |
| `%m` | 두 자리 월 | `10` |
| `%d` | 두 자리 일 | `22` |
| `%H:%M` | 시:분(24시간) | `18:00` |

```python
from datetime import datetime                                    # 날짜 · 시각을 다루는 모듈에서 datetime 을 불러온다

now = datetime.strptime("2026-10-22 14:00", "%Y-%m-%d %H:%M")    # 글자를 시각으로 바꾼다
expires = datetime.strptime("2026-10-22 18:00", "%Y-%m-%d %H:%M")  # 만료 시각도 시각으로 바꾼다
print(now < expires)                                             # 지금이 만료 전인가?
print(now >= expires)                                            # 지금이 만료 시각 이후인가?
```

```
True
False
```

- 글자 그대로 `"2026-10-22 14:00" < "2026-10-22 18:00"` 를 비교해도 결과가 맞아 보이지만, 형식이 하나라도 다르면(`"2026-10-22 9:00"`) 틀립니다. 글자 비교는 앞에서부터 한 글자씩 보기 때문에 `9:00` 이 `18:00` 보다 크다고 나옵니다. 시각은 **시각으로 바꾼 뒤** 비교합니다.
- 골격과 실행 파일에 나오는 `TIME_FORMAT` 은 `exception_policy.py` 위쪽에 적혀 있는 형식 글자 `"%Y-%m-%d %H:%M"` 입니다.
- **오늘은 지금 시각을 `2026-10-22 14:00` 으로 고정합니다.** 실제 운영에서는 `datetime.now()` 를 쓰지만, 그러면 실행할 때마다 결과가 달라져 정답과 비교할 수 없기 때문입니다. 함수가 지금 시각을 `now` 로 받게 만들면 고정 시각과 `datetime.now()` 를 모두 쓸 수 있습니다.

### <mark>✍️ 문제 3-1 · 지금 유효한 예외를 찾는 함수 만들고, 회수할 예외 읽기</mark>

**📍 이런 상황이 있습니다**

- `seoyeon` 은 영업 역할이라 정산 조회 권한이 없습니다. 그런데 오늘 18시까지 월말 정산 대조를 도와야 해서, 역할은 그대로 두고 이 사람에게만 정산 조회를 잠깐 허용했습니다. 이것이 예외입니다. 정산 포털은 요청을 받을 때마다 「이 사람에게 지금 유효한 예외가 있나?」를 확인해야 하므로, 그 확인을 하는 함수가 필요합니다.

**`day02_3-1_run.py`** — 그대로 붙여 넣습니다. 학생이 쓰는 줄은 없습니다. 단계 1(판정)은 `find_exception` 으로 여섯 건을 판정하고, 단계 2(점검)는 3.3 의 순서대로 예외 목록을 하나씩 점검해 회수할 것을 찾습니다.

```python
import json                                                      # 사용자 파일을 읽는 데 쓴다
from datetime import datetime                                    # 지금 시각을 만드는 데 쓴다
from exception_policy import find_exception, EXCEPTIONS, TIME_FORMAT   # 판정 함수 · 예외 목록 · 시각 형식을 불러온다

NOW = datetime.strptime("2026-10-22 14:00", TIME_FORMAT)         # 오늘 실습의 지금 시각(고정)

CHECKS = [                                                       # 단계 1 에서 판정할 (사용자, "자원:행위") 목록
    ("seoyeon", "SETTLE:QUERY"),                                 # 오늘 18시까지 예외
    ("junho", "SALES:CHANGE"),                                   # 10/20 에 끝난 예외
    ("dami", "SALES:QUERY"),                                     # 퇴사자에게 남은 예외
    ("batch-night", "SALES:QUERY"),                              # 내일 아침까지 예외
    ("gaeun", "SETTLE:QUERY"),                                   # 오늘 12시에 끝난 예외
    ("seoyeon", "ACCOUNT:CHANGE"),                               # 예외가 없는 권한
]

print("--- 단계 1: 판정 - 지금 유효한 예외가 있나")                 # 단계 1 시작을 알리는 줄
for user, permission in CHECKS:                                  # 하나씩 꺼낸다
    print(user, permission, "->", find_exception(user, permission, NOW))   # 사용자 권한 -> (결과, 번호) 를 출력한다

with open("config/users.json", encoding="utf-8") as f:           # 어제 만든 사용자 파일을 연다
    USERS = json.load(f)                                         # 사용자 → 정보 딕셔너리로 읽는다

print("--- 단계 2: 점검 - 예외 목록에서 회수할 것")                 # 단계 2 시작을 알리는 줄
for exc in EXCEPTIONS:                                           # 예외를 하나씩 꺼낸다
    expires = datetime.strptime(exc["expires"], TIME_FORMAT)     # 만료 시각을 시각으로 바꾼다
    if NOW >= expires:                                           # 이미 만료됐으면
        print("[회수] 만료됨", exc["id"], exc["user"], exc["permission"], exc["expires"])   # 만료된 예외를 출력한다
    elif not USERS[exc["user"]]["employed"]:                     # 만료 전인데 재직 중이 아니면(`not` 은 참 · 거짓을 뒤집음)
        print("[회수] 퇴사자", exc["id"], exc["user"], exc["permission"], exc["expires"])   # 퇴사자의 예외를 출력한다
    else:                                                        # 둘 다 아니면
        print("[유지]", exc["id"], exc["user"], exc["permission"], exc["expires"])   # 유지할 예외를 출력한다
```

- 채우기 전에 실행해도 오류 없이 실행됩니다. 단계 1 은 여섯 줄 모두 `None` 이고, 단계 2 는 예외 목록만 읽으므로 그대로 나옵니다.

### 📖 4.1 판정 순서

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

```
+------------------------------------------------+
| evaluate_access(사용자, 자원, 행위, 지금 시각) |
+------------------------------------------------+
   |
   v
+----------------------------------------+
| [역할 판정] check_permission 으로 판정 |
+----------------------------------------+
   |
   +--> 허용 --> 허용: 역할 권한
   |
   +--> 거부(그 밖의 이유: 없는 사용자 · 퇴사 · 역할이 없음) --> 거부: 그 이유 그대로   (골격의 3번)
   |
   v  거부(권한 없음)일 때만 아래로
+-------------------------------------------------------+
| [예외 판정] find_exception 으로 지금 유효한 예외 찾기 |
+-------------------------------------------------------+
   |
   +--> 있음 --> 허용: 예외 N번
   |
   +--> 없음 --> 거부: 권한 없음
```

- `check_permission` 은 어제 만든 그대로 불러 씁니다. 고치지 않습니다. 이 함수는 `(True 또는 False, 이유)` 를 리턴하고, 이유는 「권한 없음」 · 「퇴사한 계정」 · 「등록되지 않은 사용자」 · 「역할이 없음」 중 하나입니다.
- 오늘의 `policy.py` 는 어제의 역할 파일(`roles.json`)과 사용자 파일(`users.json`)을 그대로 씁니다. 2교시의 `assign_role` 과 `revoke_access` 는 메모리의 사용자 딕셔너리만 바꾸고 파일에는 저장하지 않으므로, `policy.py` 는 인사 변경 전의 사용자로 판정합니다.
- **서비스 계정**은 사람이 아니라 프로그램이 쓰는 계정입니다(`batch-night`). 사람이 로그인하지 않고, 키나 비밀번호를 설정 파일에 두고 접속하는 경우가 많습니다.
- `[역할 판정]` 에서 「권한 없음」일 때만 예외를 봅니다. 사용자 자체가 거부 대상인 경우는 예외 검사까지 가지 않습니다.

### 📖 4.2 허용 방식별로 세기

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- 판정 결과는 세 갈래로 셉니다: **역할로 허용**(이유가 「역할 권한」) · **예외로 허용**(이유가 「예외 N번」) · **거부**.
- 허용을 둘로 나눠 세는 이유는 **예외로 열린 일이 얼마나 되는지** 숫자로 보기 위해서입니다. 예외가 많아지면 역할 설계가 실제 업무와 맞지 않는다는 신호입니다. 현업에서는 예외 허용 건수를 따로 세어 매주 보고합니다.
- 세는 모양은 어제 7-1 과 같습니다: `counts[키] = counts.get(키, 0) + 1`.
- 요청마다 시각이 다르면 `"2026-10-22 " + 시각` 으로 날짜 글자와 시각 글자를 이어 붙인 뒤 `strptime` 으로 시각을 만듭니다(3.2).
- **만료 뒤 시도**: 거부 이유가 「권한 없음」인데 같은 사람 · 같은 권한의 예외가 예외 목록에 있으면, 예외가 끝난 뒤에도 다시 시도한 것입니다. 퇴사자(`dami`)처럼 사람이 거부 대상인 경우는 예외가 남아 있어도 만료 뒤 시도로 보지 않습니다.
- 순서는 「역할 권한으로 허용」을 먼저 검사하고, 그다음 「그 밖의 허용」(예외)을 검사합니다. 거꾸로 하면 역할로 허용된 요청이 예외로 세어집니다.

### 📖 4.3 파일 사이의 흐름을 그림으로 그리기

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- 파일이 여러 개가 되면 「어느 파일이 어느 파일의 무엇을 부르는가」를 머릿속에만 두기 어렵습니다. 글자로 그림을 그리면 한 곳이 고장 났을 때 어느 화살표에서 멈추는지 바로 보입니다.
- 그림 규칙: 파일은 상자(`+---+` 와 `| 파일 이름 |`)로 그리고, 시작 파일을 맨 위에 둡니다. 상자 아래로 `|` 와 `v` 로 이어 가고, `+-->` 옆에 **부르는 함수 이름**을 씁니다. 파일이 읽는 설정 파일은 `읽음` 아래에 적습니다. 그림에는 파일 이름 · 부르는 함수 · 읽는 설정 파일만 넣고, 그 밖의 가져오기(`datetime` 등)는 그리지 않습니다. 오른쪽 선이 한글 때문에 조금 안 맞아도 괜찮습니다.
- **파일 맨 위에서 설정 파일을 읽는 줄(`with open(…)`)은 그 파일을 불러오는(`import`) 순간 실행됩니다.** 그래서 설정 파일이 깨져 있으면 함수를 부르기도 전에, 그 파일을 불러오는 화살표에서 멈춥니다.
- 아래는 2교시의 파일들로 그린 본보기입니다. 4교시 문제에서는 4교시 파일들로 직접 그립니다.

```
+------------------+
| day02_2-1_run.py |
+------------------+
   |
   +--> 1. check_permission() 호출
   |       |
   |       v
   |    +---------+
   |    | rbac.py |
   |    +---------+
   |       |  읽음 (rbac.py 를 불러올 때 한 번)
   |       v
   |    config/users.json · config/roles.json
   |
   +--> 2. assign_role() · revoke_access() 호출  (USERS 를 넘김)
           |
           v
        +---------------+
        | role_admin.py |
        +---------------+
           |  가져옴
           v
        rbac.py 의 ROLES
```

> ✍️ **여기부터 문제입니다.** 위는 읽을거리였고, 아래에서 직접 합니다.

### <mark>✍️ 문제 4-1 · 최종 판정 함수 `evaluate_access` 만들고, 오늘 요청 아홉 건의 결과와 만료 뒤 시도 읽기</mark>

**📍 이런 상황이 있습니다**

- 지금은 역할을 확인하는 함수(`check_permission`)와 예외를 확인하는 함수(`find_exception`)가 따로 있습니다. 정산 포털 개발팀은 요청 하나를 넣으면 「허용인지 거부인지」와 「이유」가 한 번에 나오는 함수 하나를 원합니다. 두 확인을 4.1 의 순서대로 합칩니다.
- 보안 담당은 하루가 끝나면 세 가지를 알고 싶어 합니다. 오늘 예외로 허용된 요청이 몇 건인지, 예외 번호마다 몇 번 쓰였는지, 이미 끝난 예외로 다시 시도한 요청이 있는지입니다. 오늘 요청 아홉 건을 그 시각대로 판정하면서 이 숫자를 셉니다.
- 현업에서는 이 집계를 하루가 끝날 때 자동으로 만들어 보안 담당에게 보냅니다. 또 접근통제 제품에는 이렇게 여러 규칙을 정해진 순서로 합쳐 결과 하나를 내는 부분(PDP · 피디피, 판단 지점)이 따로 있습니다.

**🎯 할 일**

1. `policy.py` 를 만들고 `evaluate_access` 본문을 직접 씁니다.
2. `day02_4-1_run.py` 를 실행해서 <mark>아홉 건의 결과</mark>, <mark>만료 뒤 시도</mark>, <mark>예외 번호별 사용 건수</mark>를 읽습니다.

**`policy.py`**

```python
from rbac import check_permission                                # 어제 만든 역할 판정 함수를 불러온다
from exception_policy import find_exception                      # 3교시에 만든 예외 판정 함수를 불러온다


def evaluate_access(user, resource, action, now):                # 사용자 · 자원 · 행위 · 지금 시각을 받는 함수
    """(허용 여부, 이유)를 리턴한다. 역할 권한 → 유효한 예외 → 거부 순서로 본다."""
    # ← 아래를 직접 씁니다 (주석은 두고 각 주석 바로 아래 줄에 씁니다)
    # 1. check_permission 으로 판정해 ok, reason 으로 나눠 받는다
    # 2. ok 이면 True, "역할 권한" 을 리턴한다
    # 3. reason 이 "권한 없음" 이 아니면 False 와 그 reason 을 그대로 리턴한다
    # 4. find_exception 에 user, "자원:행위" 글자(f"{resource}:{action}"), now 를 넣어 found, exc_id 로 나눠 받는다
    # 5. found 이면 True, f"예외 {exc_id}번" 을 리턴한다
    # 6. 여기까지 왔으면 False, "권한 없음" 을 리턴한다
```
**`day02_4-1_run.py`** — 그대로 붙여 넣습니다. 학생이 쓰는 줄은 없습니다. 오늘 요청 아홉 건을 그 시각대로 `evaluate_access` 로 판정하고, 4.2 의 순서로 방식별 건수와 예외 번호별 사용 건수를 세고, 예외가 끝난 뒤의 시도를 알립니다.

```python
from datetime import datetime                                    # 요청 시각을 만드는 데 쓴다
from policy import evaluate_access                               # 방금 만든 최종 판정 함수를 불러온다
from exception_policy import EXCEPTIONS                          # 예외 목록을 불러온다

TODAY_LOG = [                                                    # 오늘 정산 포털 요청 기록. (시각, 사용자, 자원, 행위)
    ("09:10", "seoyeon", "SETTLE", "QUERY"),                     # 예외 1번 기간 안
    ("10:00", "dami", "SALES", "QUERY"),                         # 퇴사자(예외 3번이 남아 있음)
    ("11:40", "gaeun", "SETTLE", "QUERY"),                       # 예외 5번 기간 안
    ("12:30", "gaeun", "SETTLE", "QUERY"),                       # 예외 5번이 12:00 에 끝난 뒤
    ("13:00", "junho", "SETTLE", "QUERY"),                       # 역할 권한으로 허용되는 요청
    ("14:00", "batch-night", "SALES", "QUERY"),                  # 예외 4번 기간 안
    ("15:00", "junho", "SALES", "CHANGE"),                       # 예외 2번은 10/20(화) 에 끝남
    ("16:20", "seoyeon", "SETTLE", "QUERY"),                     # 예외 1번 기간 안
    ("18:05", "seoyeon", "SETTLE", "QUERY"),                     # 예외 1번이 18:00 에 끝난 뒤
]

counts = {}                                                      # "역할로 허용" · "예외로 허용" · "거부" → 건수
used = {}                                                        # "예외 N번" → 오늘 쓰인 건수

for time, user, resource, action in TODAY_LOG:                   # 기록을 하나씩 꺼낸다
    now = datetime.strptime("2026-10-22 " + time, "%Y-%m-%d %H:%M")   # 오늘 날짜와 그 요청의 시각을 시각으로 바꾼다
    ok, reason = evaluate_access(user, resource, action, now)    # 그 시각으로 최종 판정을 받는다
    print(time, user, resource, action, "->", ok, reason)        # 결과를 출력한다
    if ok and reason == "역할 권한":                               # 역할로 허용이면
        counts["역할로 허용"] = counts.get("역할로 허용", 0) + 1     # 역할로 허용된 건수를 1 늘린다
    elif ok:                                                     # 그 밖의 허용은 예외로 허용
        counts["예외로 허용"] = counts.get("예외로 허용", 0) + 1     # 예외로 허용된 건수를 1 늘린다
        used[reason] = used.get(reason, 0) + 1                   # 그 예외 번호의 사용 건수를 1 늘린다
    else:                                                        # 거부면
        counts["거부"] = counts.get("거부", 0) + 1                 # 거부된 건수를 1 늘린다
        if reason == "권한 없음":                                 # 거부 이유가 「권한 없음」일 때만
            for exc in EXCEPTIONS:                               # 예외 목록을 하나씩 꺼낸다
                if exc["user"] == user and exc["permission"] == resource + ":" + action:   # 같은 사람 · 같은 권한의 예외가 있으면
                    print("[만료 뒤 시도]", time, user, resource, action, "- 만료된 예외", exc["id"], exc["expires"])   # 만료 뒤 시도로 알린다

print(counts)                                                    # 방식별 건수를 출력한다
print("예외 사용", used)                                          # 예외 번호별 사용 건수를 출력한다
```
- `evaluate_access` 의 들여쓰기: 본문은 모두 함수 안이라 4칸으로 쓰고, 2번 `if` 아래 `return` 과 3번 `if` 아래 `return` 은 4칸 더(8칸) 들어갑니다. 5번 `if` 아래 `return` 도 8칸입니다.
- `evaluate_access` 를 채우기 전에 실행하면 `TypeError: cannot unpack non-iterable NoneType object` 오류가 납니다. 함수가 아무것도 리턴하지 않아 `ok, reason` 으로 나눠 받지 못하기 때문입니다. 본문을 채운 뒤에 실행합니다.

- (나) `SALES CHANGE` 는 **허용에서 거부**(`권한 없음`)로, `SETTLE QUERY` 는 **거부에서 허용**으로 바뀌었습니다. `seoyeon` 의 역할이 `sales` 에서 `finance` 로 바뀌었고, `finance` 에는 `SALES:QUERY` 와 `SETTLE:QUERY` 만 있고 `SALES:CHANGE` 가 없기 때문입니다. 역할 값 하나만 바꿨는데 권한 전체가 바뀐 것입니다. 이동한 사람에게 이전 역할의 권한(영업 실적 변경)이 남아 있으면 새 업무에 필요 없는 권한이 계속 쌓입니다. 계정이 도용되거나 실수가 생기면 영향받는 범위가 넓어지고, 일에 필요한 만큼만 준다는 최소권한과도 어긋납니다.
- (다) 사흘 동안 `junho` 의 사용자 항목은 아직 재직(`employed` 가 `true`)이라서 정산 조회가 계속 허용됩니다. 나간 사람이 자료를 내려받거나 변경할 수 있고, 로그에는 정상 사용자의 행동으로 남아서 나중에 가려내기 어렵습니다. 간격을 줄이는 방법은 여러 가지가 있습니다. ① 인사 시스템이 퇴사가 확정되는 즉시 보안 담당에게 알리게 한다 ② 퇴사 예정일을 미리 받아 그 시각에 맞춰 회수한다 ③ 인사 명단과 계정 목록을 매일 대조해 어긋난 계정을 찾는다 ④ 퇴사 당일 회수 확인을 체크리스트에 넣는다. 두 가지 이상이고 핵심이 같으면 맞습니다.

**왜** — 사람이 바뀔 때마다 파일을 손으로 고치면 오타와 빠뜨림이 생깁니다. 함수로 처리하면 「없는 역할은 거부」 같은 검사가 늘 같은 순서로 들어갑니다. 역할 값 하나만 바꾸면 권한이 통째로 바뀌므로, 이동한 사람에게 이전 권한이 남지 않게 새 역할로 **바꿉니다.**(역할을 하나 더 붙이지 않습니다.) 퇴사자 항목을 삭제하지 않고 `employed` 값만 바꾸면, 거부 이유가 「퇴사한 계정」으로 남아서 처음부터 없던 계정과 구분됩니다.

**자주 틀리는 곳** — `if role in ROLES:` 로 `not` 을 빼먹어 정상 역할을 모두 거부하는 경우가 가장 많습니다. 사용자 항목을 먼저 바꾸고 역할을 검사해서, 오타 역할이 이미 들어간 뒤에 거부하는 경우도 많습니다(`hana 가 사용자에 들어갔나` 가 `True`). `False` 를 소문자 `false` 로 써서 `NameError` 가 나는 경우도 있습니다(소문자는 JSON 파일에서만 씁니다). `return` 을 빼먹으면 통보 처리 줄이 `None` 으로 나옵니다. 함수 안에서 `users = {…}` 로 새 딕셔너리를 만들어 담으면 바깥의 `USERS` 는 바뀌지 않아서, 부여 결과는 `(True, '부여')` 인데 `minsu` 와 `seoyeon` 의 변경 후 판정이 변경 전과 같습니다.

**관제에서는** — 인사 통보와 계정 상태를 정기적으로 대조합니다. 퇴사 당일에 접근을 회수하지 않으면 퇴사자 계정을 쓸 수 있는 시간이 생기고, 이동한 사람은 이전 역할의 권한이 남지 않았는지 확인합니다. 부여와 회수는 누가 언제 했는지 기록으로 남겨 감사에 대비합니다.
