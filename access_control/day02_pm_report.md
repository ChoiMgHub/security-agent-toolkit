## 5교시 · 설정 파일이 고장 나도 거부하기

### 문제 5-1 · 설정 파일을 안전하게 읽는 함수 `load_json` 만들고, 고장 두 가지로 시험하기

- (가) 실행한 출력 전체를 붙여 넣고, 경고 두 줄이 각각 어떤 오류 때문에 나왔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체 ② 경고 두 줄이 각각 어떤 오류 때문에 나왔는지
  - 답:

오전에는 설정 파일을 바로 읽다가 JSON 문법이 잘못되면 요청을 판정하기 전에 프로그램이 멈출 수 있다는 점을 살펴봤다. 오후에는 이런 상황을 다루기 위해 `config_loader.py`에 안전하게 읽는 함수 `load_json`을 만들고, 정상 파일·없는 경로·깨진 JSON을 차례로 읽어 봤다. 작업 위치는 `~/Documents/Aleph_Choi/security-agent-toolkit/access_control`이었고, `vim`으로 파일을 작성한 뒤 다음 출력을 직접 확인했다.

```text
config/users.json -> 사용자 6 명을 읽음, 판정을 계속한다
[경고] 설정 파일 없음: config/users_typo.json
config/users_typo.json -> 사용자 0 명, 등록된 사용자가 없다
[경고] 설정 파일 깨짐: config/users_broken.json
config/users_broken.json -> 사용자 0 명, 등록된 사용자가 없다
```

경고 두 줄의 원인은 다음과 같다.

| 경고 | 오류 종류 | 원인 |
|---|---|---|
| 설정 파일 없음 | `FileNotFoundError` | `config/users_typo.json`이라는 파일이 없는 경로를 읽으려고 함 |
| 설정 파일 깨짐 | `json.JSONDecodeError` | `config/users_broken.json`의 내용을 JSON 문법으로 해석하지 못함. 교재는 마지막 항목 뒤에 쉼표가 남은 파일로 이 상황을 만들도록 안내함 |

정상 파일에서는 사용자 여섯 명을 읽었고, 오류가 난 두 경우에는 경고를 출력한 뒤 기본값 `{}`를 반환했다. 없는 파일을 처리한 다음에도 깨진 파일의 결과까지 출력됐으므로, 준비한 오류 상황 때문에 프로그램이 중단되지는 않았음을 확인했다. 이번에는 경고가 나오는 것까지 시험하려던 동작이었다.

함수 호출은 `users = load_json(path, {})` 형태였다. `path`는 읽을 경로이고, `default`에는 호출할 때 전달한 `{}`가 들어간다. `try`에서 읽기를 시도하고, 오류 종류에 맞는 `except`에서 경고와 기본값 반환을 수행하는 구조로 설명받았다. 경고만 출력하고 `return default`를 빠뜨리면 `None`이 반환될 수 있어서 뒤의 사용자 검사에도 문제가 생긴다. 이 오류를 실제로 겪었다는 뜻은 아니고, 코드에서 기본값 반환이 필요한 이유다.

이번 실습에서는 새 읽기 함수를 시험했으며 오전의 `rbac.py`나 `policy.py`에 연결하지 않았다. 출력의 ‘판정을 계속한다’도 시험 파일의 안내 문구다. 실제 접근 요청을 넣어 모든 사용자의 거부까지 확인한 것은 아니다. 또한 파일을 자동으로 고친 것이 아니라 읽기 실패에 대해 준비한 대응을 수행한 것이다.

- (나) 🔍 실패했을 때 프로그램을 멈추지 않고 빈 설정을 리턴하는 것이, 오류로 멈추는 것보다 왜 안전한가요? 「멈춘 뒤 현장에서 생기는 일」을 넣어 적어 주세요.
  - 쓸 내용: ① 빈 설정을 리턴하는 이유 ② 멈춘 뒤 현장에서 생기는 일
  - 답:

설정을 읽지 못했다면 누구에게 어떤 권한이 있는지 확인할 근거가 부족하다. 이때 빈 사용자 설정 `{}`를 반환하고 그 값을 사용자 판정에 사용하도록 연결하면, 등록된 사용자가 없으므로 기존 판정의 사용자 확인 단계에서 모든 요청을 거부하는 방향으로 처리할 수 있다. 실패했을 때 접근이 닫히는 쪽으로 동작하는 것을 `fail-closed`라고 배웠다.

반대로 판정 프로그램이 오류로 멈춰 정산 업무를 못 하게 되면, 현장에서 급한 업무를 처리하려고 판정 기능을 끄거나 건너뛰자는 요구가 생길 수 있다. 그 결과 모두 통과시키게 되면 권한을 확인하지 않은 요청까지 허용될 위험이 있다. 이렇게 실패 시 접근이 열리는 방향을 `fail-open`이라고 한다.

프로그램이 멈췄다는 사실 자체가 자동으로 모두 허용한다는 뜻은 아니다. 연결된 시스템이나 현장의 대응이 어떻게 되는지가 중요하다. 수업에서는 급한 상황에서 판정을 우회하지 않도록, 경고를 남기면서 접근은 막는 동작을 미리 준비하는 이유를 설명받았다.

빈 설정으로 거부하더라도 정상 사용자들의 업무는 막힐 수 있다. 그래서 ‘프로그램이 계속 실행된다’와 ‘업무가 정상 처리된다’는 구분해야 한다. 확인할 수 없는 접근은 막되, 담당자가 문제를 알고 정상 설정으로 복구할 수 있어야 한다.

여기서 모두 거부로 연결되는 것은 빈 **사용자** 설정이다. 예외 목록만 빈 `[]`가 됐다고 역할 권한까지 없어지는 것은 아니다. 사용자는 딕셔너리라 `{}`, 예외는 목록이라 `[]`처럼 원래 자료 형태에 맞는 기본값을 사용해야 한다는 점도 복습할 것이다.

- (다) 🔍 설정 파일이 깨져서 모두 거부되면 정산 업무가 멈춥니다. 운영자가 이 상황을 빨리 알고 복구하려면 판정 프로그램에 무엇을 더하겠습니까? 두 가지 이상 적고, 그중 가장 먼저 할 것을 고른 이유를 적어 주세요.
  - 쓸 내용: ① 더할 것 두 가지 이상 ② 가장 먼저 할 것과 그 이유
  - 답:

내가 운영에 더할 기능으로는 다음 세 가지를 생각했다.

1. **오류 로그와 담당자 알림**: 발생 시각, 문제가 생긴 설정 경로, 오류 종류를 기록하고 담당자가 빠르게 알 수 있도록 알림을 보내게 하겠다.
2. **현재 설정 상태 표시**: 정상 설정을 읽었는지, 읽기 실패로 빈 기본값을 사용 중인지 확인할 수 있는 상태 화면이나 명령을 두겠다.
3. **검증된 설정 사본과 복구 절차**: 정상 동작을 확인한 설정을 보관하고, 변경 이력을 확인한 뒤 검증해서 되돌릴 수 있도록 하겠다.

가장 먼저 할 것은 담당자 알림이다. 모두 거부되는 상황을 빨리 알아야 원인을 확인하고 복구를 시작할 수 있기 때문이다. 문제를 늦게 알면 업무 중단이 길어지고 현장에서 판정을 끄자는 요구가 커질 수도 있다.

복구할 때도 오래된 사본을 확인 없이 적용하지는 않겠다. 그 사이 반영한 퇴사나 권한 회수가 빠져 있을 수 있으므로 현재 정책과 맞는 설정인지 확인해야 한다.

이 내용은 문제에서 묻는 운영 개선에 대한 내 제안이다. 이번 실습에서 로그 파일 저장, 담당자 알림, 상태 화면이나 자동 복구 기능을 구현한 것은 아니다. 실제로 확인한 범위는 정상 읽기와 두 오류 상황의 경고·기본값 반환이다.

## 6교시 · 테스트 케이스 설계

### 문제 6-1 · 꼭 지켜야 할 네 가지를 테스트로 설계하고, 팀원의 제안을 시험하기

- (가) `test_policy_extra.py` 를 실행한 출력 전체를 붙여 넣고, 실패한 줄 번호와 `AssertionError:` 뒤에 나온 글자를 적어 주세요.
  - 쓸 내용: ① `test_policy_extra.py` 출력 전체 ② 실패한 줄 번호 ③ `AssertionError:` 뒤의 글자
  - 답:

`test_policy.py`와 `test_policy_extra.py`를 `vim`으로 작성해 실행했다. 보고서에서 요구하는 추가 테스트의 최종 출력은 다음과 같다.

```text
5 통과
Traceback (most recent call last):
  File "c:\Users\User\Documents\Aleph_Choi\security-agent-toolkit\access_control\test_policy_extra.py", line 14, in <module>
    assert ok == True, "6. 만료 정각에도 허용되어야 한다(팀원 제안)"
           ^^^^^^^^^^
AssertionError: 6. 만료 정각에도 허용되어야 한다(팀원 제안)
```

실패한 곳은 `test_policy_extra.py`의 **14번째 줄**이고, `AssertionError:` 뒤의 글자는 **`6. 만료 정각에도 허용되어야 한다(팀원 제안)`**이다. 그전에 `5 통과`가 출력됐으므로, 퇴사한 `dami`가 예외가 있어도 거부되는 5번 검사를 통과한 것도 확인했다.

추가 테스트와 별도로 기본 테스트에서는 한 번 수정하는 과정을 거쳤다. 처음 실행했을 때는 다음처럼 2번 검사에서 멈췄다.

```text
Traceback (most recent call last):
  File "c:\Users\User\Documents\Aleph_Choi\security-agent-toolkit\access_control\test_policy.py", line 17, in <module>
    assert ok == False and reason == "권한 없음", "2. 권한 없음"
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
AssertionError: 2. 권한 없음
```

이 출력만 봤을 때는 실제 반환값이 무엇인지 확정할 수 없었다. 나는 두 테스트 파일의 코드를 AI에게 공유했고, 2번에서 결과를 변수에 받는 줄에 `=` 대신 `==`를 쓴 부분을 확인받았다.

수정 전:

```python
ok, reason == evaluate_access("seoyeon", "ACCOUNT", "CHANGE", at("2026-10-22 14:00"))
```

수정 후:

```python
ok, reason = evaluate_access("seoyeon", "ACCOUNT", "CHANGE", at("2026-10-22 14:00"))
```

`=`는 값을 저장하고 `==`는 같은지 비교한다. 수정 전에는 함수가 호출돼도 새 결과를 `ok`, `reason`에 저장하지 않아, 1번에서 받았던 `True`, `"역할 권한"`이 그대로 남아 있었다. 그 값을 2번의 ‘거부이며 권한 없음이어야 한다’는 조건과 비교해서 실패한 것이었다. 따라서 이 실패만으로 정책이 해당 요청을 잘못 허용했다고 판단하면 안 됐다.

나는 안내에 따라 `==`를 `=`로 바꾸고 다시 실행해 다음 출력을 직접 확인했다.

```text
[경고] 설정 파일 없음: config/no_such.json
테스트 4개 모두 통과
```

없는 파일 경고는 4번이 일부러 없는 경로를 읽어서 나온 정상적인 경고였다. 기본 테스트의 최종 결과는 네 가지 모두 통과였고, 추가 테스트는 다시 실행해도 5번 통과 뒤 6번이 실패했다. 두 파일의 실패를 같은 원인으로 묶지 않고 구분해야 했다.

- (나) 🔍 그 실패는 코드가 틀렸다는 뜻인가요, 제안이 우리가 정한 만료 규칙과 다르다는 뜻인가요? 근거를 적어 주세요.
  - 쓸 내용: ① 코드가 틀렸는지, 제안이 정책과 다른지 ② 우리가 정한 만료 규칙과 3번 테스트 결과를 근거로 한 이유
  - 답:

추가 테스트 6번의 실패는 **팀원의 제안이 현재 만료 규칙과 다르다는 뜻**이다.

우리가 정한 규칙은 ‘현재 시각이 만료 시각보다 앞일 때만 예외가 유효하고, 만료 정각부터는 거부한다’는 것이다. 코드의 비교는 `now < expires`다. 만료가 18시라면 17:59에는 기간이 남지만, 18:00 정각에는 `18:00 < 18:00`이 거짓이 되어 예외를 사용할 수 없다.

| 구분 | 17:59 | 18:00 |
|---|---|---|
| 기존 정책 | 예외로 허용 | 거부 |
| 팀원 제안이 요구한 정각의 결과 | 이 항목에서 묻지 않음 | 허용 |
| 내가 확인한 기본 3번 테스트 | 예외 1번 허용 검사 통과 | 거부 검사 통과 |

처음 기본 테스트는 2번에서 멈춰 그 아래의 3번을 확인하지 못했다. 하지만 대입 기호를 수정한 뒤에는 내가 작성한 네 가지 테스트가 모두 통과했다. 따라서 3번에서 17:59 허용과 18:00 거부를 검사한 결과도 최종 실행에서 확인했다.

추가 테스트 6번은 같은 정각에 `ok == True`여야 한다고 요구한다. 프로그램이 현재 정책대로 거부했기 때문에 그 기대와 맞지 않아 실패한 것이다. 실패 표시를 없애려고 `<`를 `<=`로 바꾸면 기존 정책 자체를 바꾸게 된다. 이번에는 정책을 고치는 문제가 아니라 두 규칙의 차이를 판단하는 문제였다.

실행이 끝난 뒤에도 문제 6-1이 아직 충분히 이해되지 않아 더 쉬운 설명과 정리를 다시 요청했다. ‘접근이 거부됨’과 ‘테스트가 실패함’은 다른 의미로 읽어야 한다. 거부돼야 하는 요청이 실제로 거부되면 테스트는 통과하고, 기대와 실제 결과가 다르면 실패한다.

기본 2번의 처음 실패는 내 테스트 코드가 결과를 저장하지 못한 실수였고, 추가 6번의 실패는 제안과 정책의 불일치였다. 같은 `AssertionError`라도 먼저 어느 규칙과 값을 비교했는지 확인해야 한다는 설명을 받았다.

- (다) 🔍 정책 코드를 바꿀 때마다 `test_policy.py` 의 1 ~ 4번 테스트를 돌리지 않으면 어떤 사고가 날 수 있나요? 네 개 중 하나를 골라, 그 테스트가 막아 주는 사고를 구체적인 장면으로 적어 주세요.
  - 쓸 내용: ① 고른 테스트 ② 그 테스트가 막아 주는 사고 장면
  - 답:

나는 **3번 만료 경계 테스트**를 골랐다.

예를 들어 누군가 예외 판정 코드를 수정하다 `now < expires`를 `now <= expires`로 바꿨다고 가정해 보자. 그러면 18:00까지인 예외가 18:00 정각에도 유효하다고 판단된다. 사용자가 그 정각에 정산 조회를 요청하면 원래 정책상 거부해야 하지만 허용될 수 있다.

만료에서 떨어진 시각만 확인하면 `<`와 `<=`가 같은 결과를 낼 수 있어 이 실수를 놓칠 수 있다. 그래서 3번은 만료 1분 전인 17:59에 예외 1번으로 허용되는지와, 정각인 18:00에 거부되는지를 각각 새로 판정해 검사한다. 이 테스트를 변경 후 다시 실행하면 비교 기호 하나로 기간 규칙이 달라진 것을 알아차릴 수 있다.

위 변경으로 달라지는 것은 만료 시각과 정확히 같은 순간이다. 이 변경 하나만으로 18:05나 밤늦게까지 계속 허용되는 것은 아니다. 실제로 내가 정책 코드를 이렇게 바꿨다는 뜻은 아니고, 테스트가 막아 줄 수 있는 실수의 예다.

내가 이번에 작성한 테스트는 정해 둔 입력과 기대 결과를 자동으로 비교하는 체크리스트였다. 정책을 바꾼 뒤 전에 지키던 동작이 유지되는지 다시 확인하는 데 사용할 수 있다. 다만 네 가지가 통과했다고 모든 사용자·시각·자원이나 모든 오류 상황까지 확인한 것은 아니다.

특히 4번은 `load_json`으로 없는 파일을 읽은 결과에 `seoyeon`이 없다는 것을 확인한다. 그 검사로 확인한 범위는 반환된 값에 해당 사용자가 없다는 점이다. 설정 고장부터 최종 접근 거부까지 연결한 동작 전체를 시험한 것은 아니어서, 이 범위도 구분해 복습할 것이다.

## 오후 수업을 마치며 남기는 복습 메모

오후에는 설정을 못 읽는 상황에 어떻게 대응할지와, 접근 정책이 정한 규칙을 지키는지 자동으로 확인하는 방법을 배웠다. Windows의 VS Code 터미널을 사용했고 프롬프트에는 `UCRT64`가 표시됐다.

5교시에는 정상 설정과 두 고장 상황을 직접 실행해 경고와 결과를 확인했다. 6교시에는 기본 테스트 2번에서 `AssertionError`를 겪었고, 코드를 공유해 AI의 설명을 받은 뒤 `==`를 `=`로 수정했다. 재실행으로 기본 네 가지 통과와 추가 5번 통과·6번 실패를 확인했다. 수정 후에도 문제의 의미가 충분히 이해되지 않아 다시 쉽게 정리해 달라고 요청했다.

나중에 복습할 때 다시 확인할 것은 다음과 같다.

- `=`는 값을 저장하고 `==`는 비교한다. 판정 결과를 변수에 받는 줄과 그 값을 검사하는 줄은 역할이 다르다.
- `assert`의 조건이 참이면 다음 줄로 가고, 거짓이면 설명을 담은 `AssertionError`로 그 자리에서 멈춘다. 쉼표 뒤는 두 번째 조건이 아니라 실패 설명이며, 두 조건을 함께 확인할 때는 `and`를 쓴다.
- `print`는 값을 보여 주고 사람이 판단하게 하지만, `assert`는 정해 둔 기대와 맞는지를 코드로 검사한다. 기대 결과는 현재 출력에 무조건 맞추는 것이 아니라 정책을 근거로 정해야 한다.
- 테스트는 첫 실패에서 멈출 수 있다. 처음 2번에서 실패했을 때는 뒤의 검사까지 통과한 것이 아니었고, 수정 후 최종 실행에서 모두 확인했다.
- 네 가지 테스트 상황 중 만료 경계는 두 시각을 검사한다. 상황의 수와 `assert` 문장 수가 반드시 같은 것은 아니다.
- 5교시는 지정한 오류에 대응해 기본값을 반환하는 기능이고, 6교시는 기대와 다른 동작을 발견해 멈추는 시험이다. 목적이 달라 오류가 났을 때의 동작도 다르다.

실행에 성공한 사실과 내가 혼자 원리를 설명할 수 있는지는 별개로 남겨 두고 싶다. 이번에는 정상 출력과 오류·수정 과정을 확인했고, 개념과 결과를 이해하기 위한 설명은 AI의 도움을 여러 번 받았다. 명령 실행과 코드 수정, 재실행 확인은 내가 했고, 코드 검토·해설·보고서 문장 정리에는 AI의 도움을 받았다.

오늘의 한 줄: 테스트의 실패를 없애기 전에, 내 코드의 실수인지 기대한 규칙이 다른 것인지 먼저 확인해야 한다.
