> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

   - 멈추지 않고 모두 막는 이 동작을 **닫힘 기본 값**(fail-closed · 페일 클로즈드)이라고 합니다.

### 📖 5.1 안전하게 읽고, 실패하면 빈 설정

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

```
+-----------+     +-----------+
| 설정 파일 | --> | load_json | --> 성공 --> 읽은 내용 --> 평소대로 판정
+-----------+     +-----------+
                    |
                    +--> 파일이 없음 (FileNotFoundError)
                    |       |
                    |       v
                    |    「[경고] 설정 파일 없음: 경로」 출력
                    |
                    +--> JSON 이 깨짐 (json.JSONDecodeError)
                            |
                            v
                         「[경고] 설정 파일 깨짐: 경로」 출력

                    (두 경우 모두 프로그램은 멈추지 않고 기본값 default 를 리턴한다. 오늘은 default 가 {})
                       |
                       v
                    +------------+
                    | 빈 설정 {} |
                    +------------+
                       |
                       v
                    사용자가 한 명도 없음 --> 모든 요청이 「등록되지 않은 사용자」 로 거부
```

**이 시간에 나오는 말** (이미 배운 방법입니다)

- `try:` 안에서 오류가 나면 그 종류에 맞는 `except 오류이름:` 으로 넘어갑니다(9/28(월)).
- `with open(path, encoding="utf-8") as f:` 는 파일을 열어 `f` 로 받습니다(9/28(월), 어제 `rbac.py` 와 같습니다).
- `FileNotFoundError` 는 파일이 없을 때, `json.JSONDecodeError` 는 JSON 규칙이 틀렸을 때 납니다(9/28(월)).
- 함수가 기본값을 인자(`default`)로 받으면, 부르는 쪽이 빈 딕셔너리 `{}` 나 빈 목록 `[]` 를 골라 넣을 수 있습니다.

### 📖 5.2 고장을 일부러 만들어 시험하기

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- 고장이 났을 때 어떻게 되는지는 **일부러 고장을 만들어 봐야** 압니다. 오늘 시험할 경로는 세 개입니다.

| 경로 | 상태 | 기대하는 일 |
|---|---|---|
| `config/users.json` | 정상 파일 | 사용자 여섯 명을 읽고 판정을 계속한다 |
| `config/users_typo.json` | 이름을 잘못 적은 경로(파일이 없음) | `FileNotFoundError` → 경고, 빈 설정(사용자 0명) → 이 설정으로 판정하면 모두 거부 |
| `config/users_broken.json` | 마지막 항목 뒤에 쉼표가 남은 깨진 파일 | `JSONDecodeError` → 경고, 빈 설정(사용자 0명) → 같은 결과 |

- 기본값은 원래 자료와 **같은 모양**이어야 합니다. 사용자 파일은 딕셔너리라서 빈 딕셔너리 `{}`, 예외 파일은 딕셔너리들의 목록이라서 빈 목록 `[]` 입니다. 모양이 다르면 뒤의 `for` 나 `in` 에서 또 오류가 납니다.
- 현업에서는 이런 고장 시험(장애 주입 · fault injection · 폴트 인젝션)을 미리 해 둬야 실제 고장 때 바로 대응할 수 있습니다.

### <mark>✍️ 문제 5-1 · 설정 파일을 안전하게 읽는 함수 `load_json` 만들고, 고장 두 가지로 시험하기</mark>

**📍 이런 상황이 있습니다**

- 지금 `rbac.py` 는 설정 파일을 바로 열어서, 파일이 없거나 쉼표 하나가 틀리면 오류가 나고 프로그램이 멈춥니다. 보안 담당은 설정 파일을 읽는 함수 하나를 원합니다. 읽기에 실패해도 프로그램은 멈추지 않고, 무엇이 문제인지 경고를 출력해야 합니다.
- 그 함수가 정말 그렇게 동작하는지 고장을 일부러 두 가지 만들어 확인합니다. ① 파일 이름을 잘못 쓴 경우(파일이 없음) ② 쉼표가 하나 남은 파일(JSON 규칙이 틀림). 두 경우 모두 경고가 나오고, 프로그램은 계속 실행되며, 아무것도 들어 있지 않은 빈 설정 `{}` 을 얻어야 합니다.
- 빈 설정은 사용자가 한 명도 없는 상태입니다. 이 상태로 판정하면 모든 요청이 「등록되지 않은 사용자」로 거부됩니다. 이 연결은 읽고 이해만 합니다. 6교시의 4번 테스트는 빈 설정에 `seoyeon` 이 들어 있지 않은 것까지만 확인합니다.
- 현업의 보안 장비도 설정을 읽지 못하면 「기본 거부」 상태로 켜지고 경고를 남깁니다.

**`config_loader.py`**

```python
import json                                                      # JSON 파일을 읽는 모듈을 불러온다


def load_json(path, default):                                    # 파일 경로와 실패했을 때 쓸 기본값을 받는 함수
    """JSON 파일을 읽어 리턴한다. 파일이 없거나 깨졌으면 경고를 출력하고 default 를 리턴한다."""
    # ← 아래를 직접 씁니다 (주석은 두고 각 주석 바로 아래 줄에 씁니다)
    # 1. try: 로 시작한다
    # 2.   with open(path, encoding="utf-8") as f: 로 path 를 열어
    # 3.     json.load 로 읽은 내용을 바로 리턴한다
    # 4. except FileNotFoundError: 로 파일이 없을 때를 받는다
    # 5.   "[경고] 설정 파일 없음:" 과 path 를 출력하고
    # 6.   default 를 리턴한다
    # 7. except json.JSONDecodeError: 로 JSON 이 깨졌을 때를 받는다
    # 8.   "[경고] 설정 파일 깨짐:" 과 path 를 출력하고
    # 9.   default 를 리턴한다
```

- 주석은 모두 같은 자리에 있지만, 코드는 아래 칸 수로 씁니다. 각 주석 바로 아래 줄에 씁니다.
- `load_json` 의 들여쓰기: 1번 `try:` 는 4칸, 2번 `with` 는 8칸, 3번 `return` 은 12칸, 4 · 7번 `except` 는 4칸, 5 · 6 · 8 · 9번은 8칸입니다.

### 📖 6.1 테스트 케이스와 `assert`

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- **테스트 케이스**(test case · 테스트 케이스)
  - 「이 입력이면 이 결과가 나와야 한다」 한 쌍
  - 기대 결과를 **먼저** 정하고, 실행 결과와 비교한다
- **경계값**(boundary value · 바운더리 밸류)
  - 결과가 바뀌는 바로 그 지점의 값. 예: 만료 시각 18:00 의 1분 전(17:59)과 정각(18:00)
  - 실수가 가장 많이 숨어 있는 곳이라 꼭 테스트한다

**🐍 문법 상자 — `assert` (어서트)**

`assert` 는 「이 조건은 반드시 참이어야 한다」고 적어 두는 문장입니다. 조건이 참이면 아무 일 없이 다음 줄로 가고, 거짓이면 `AssertionError` 를 내며 프로그램이 그 자리에서 멈춥니다.

| 쓰는 모양 | 조건이 거짓일 때 |
|---|---|
| `assert 조건` | `AssertionError` 로 멈춘다 |
| `assert 조건, "설명"` | `AssertionError: 설명` 으로 멈춘다. 어느 규칙이 깨졌는지 설명이 알려 준다 |
| `assert 조건 1 and 조건 2, "설명"` | 두 조건이 모두 참이어야 통과한다. 하나라도 거짓이면 멈춘다 |

아래 코드는 읽기만 합니다. 한 칸마다 한 가지만 보여 줍니다.

**① 조건이 참이면 — 아무 일 없이 다음 줄로 갑니다**

```python
assert 1 + 1 == 2                                  # 1 + 1 은 2 라서 조건이 참이다
print("다음 줄로 왔다")                                  # 참이었으니 이 줄까지 실행된다
```

실행 결과:

```
다음 줄로 왔다
```

**② 조건이 거짓이면 — `AssertionError` 로 멈추고, 아래 줄은 실행되지 않습니다**

```python
assert 1 + 1 == 3                                  # 1 + 1 은 3 이 아니라서 조건이 거짓이다
print("여기는 실행되지 않는다")                         # 위에서 멈추므로 이 줄은 실행되지 않는다
```

실행 결과:

```
Traceback (most recent call last):
  File "…/파일이름.py", line 1, in <module>
    assert 1 + 1 == 3                                  # 1 + 1 은 3 이 아니라서 조건이 거짓이다
AssertionError
```

**③ 설명을 붙이면 — 멈출 때 설명이 `AssertionError:` 뒤에 함께 나옵니다**

```python
assert 1 + 1 == 3, "1 + 1 은 3 이 아니다"            # 거짓이면 쉼표 뒤의 설명이 오류 메시지에 함께 나온다
```

실행 결과:

```
Traceback (most recent call last):
  File "…/파일이름.py", line 1, in <module>
    assert 1 + 1 == 3, "1 + 1 은 3 이 아니다"            # 거짓이면 쉼표 뒤의 설명이 오류 메시지에 함께 나온다
AssertionError: 1 + 1 은 3 이 아니다
```

**④ `and` 로 두 조건을 한 번에 — 오늘 1번 테스트의 모양입니다**

```python
ok = True                                          # 허용 여부를 담은 변수
reason = "역할 권한"                                  # 이유를 담은 변수
assert ok == True and reason == "역할 권한", "허용이고 이유도 맞아야 한다"   # 두 조건이 모두 참이어야 통과한다
print("둘 다 참이라 통과")                              # 통과하면 이 줄까지 실행된다
```

실행 결과:

```
둘 다 참이라 통과
```

**⑤ `not in` 으로 「없다」를 확인 — 오늘 4번 테스트의 모양입니다**

```python
users = {}                                         # 사용자가 한 명도 없는 딕셔너리
assert "seoyeon" not in users, "seoyeon 이 없어야 한다"  # not in 은 「안에 없다」가 참이다
print("seoyeon 이 없어서 통과")                         # 통과하면 이 줄까지 실행된다
```

실행 결과:

```
seoyeon 이 없어서 통과
```

- `==` 는 「같은가」를 묻는 비교이고, `=` 는 값을 담는 대입입니다. `assert` 의 조건에는 `==` 를 씁니다.
- `Traceback` 이 나왔다고 프로그램이 망가진 것이 아닙니다. `assert` 가 「기대와 다르다」고 정상적으로 알려 준 것입니다.

- 테스트는 **적어 둔 규칙**만 확인합니다. 네 테스트가 모두 통과해도 적지 않은 상황(다른 사람 · 다른 시각 · 다른 자원)은 확인되지 않은 것입니다.

| 4 | 설정 고장이면 아무도 없음 | 없는 파일 `config/no_such.json` 을 `load_json` 으로 읽기 | `seoyeon` 이 들어 있지 않음 |

3. 바로 코드를 고치지 않습니다. 정책이 바뀌어야 한다면 코드만이 아니라 그 규칙의 테스트와 설명 글도 함께 고칩니다.

실패 메시지는 이렇게 읽습니다. 아래는 읽기만 하는 예입니다.

```

  File "…/test_policy_extra.py", line 14, in <module>     <-- 몇 번째 줄에서 멈췄나 (폴더 경로는 PC 마다 다름)

AssertionError: 6. 만료 정각에도 허용되어야 한다(팀원 제안)           <-- assert 에 적은 설명
```

- 맨 아래 `AssertionError:` 뒤의 글자는 `assert` 에 적은 설명입니다. 설명에 번호를 붙여 두면 어느 규칙이 깨졌는지 바로 압니다.

1. `test_policy.py` 를 만들고 2 ~ 4번 테스트를 직접 씁니다.
2. 실행해서 <mark>테스트 4개 모두 통과</mark>가 나오는지 확인합니다.
3. `test_policy_extra.py` 를 만들고 실행해서 <mark>어느 테스트가 통과하고 어느 테스트가 실패하는지</mark> 읽습니다.

**`test_policy.py`**

```python
from datetime import datetime                                    # 시각을 만드는 데 쓴다
from policy import evaluate_access                               # 오전에 만든 최종 판정 함수
from config_loader import load_json                              # 5교시에 만든 안전한 읽기 함수


def at(text):                                                    # "2026-10-22 14:00" 같은 글자를 받아
    return datetime.strptime(text, "%Y-%m-%d %H:%M")             # "연-월-일 시:분" 모양 글자를 시각으로 바꿔 리턴한다


# 1. 정상 허용 — 예시로 써 둔 테스트
ok, reason = evaluate_access("junho", "SETTLE", "QUERY", at("2026-10-22 14:00"))   # 재무의 정산 조회를 판정한다
assert ok == True and reason == "역할 권한", "1. 정상 허용"       # 허용이고 이유가 「역할 권한」이어야 한다

# ← 아래를 직접 씁니다 (6.1 의 표를 보고 씁니다)
# 2. seoyeon 의 ACCOUNT CHANGE 를 14:00 에 판정해 ok, reason 으로 받고, 거부이며 이유가 "권한 없음" 인지 assert 한다
# 3. seoyeon 의 SETTLE QUERY 를 17:59 에 판정해 ok, reason 으로 받고, 허용이며 이유가 "예외 1번" 인지 assert 한다
#    같은 요청을 18:00 에 판정해 ok, reason 으로 다시 받고, 거부인지 assert 한다
# 4. load_json 으로 "config/no_such.json" 을 기본값 {} 로 읽어 users 에 담고,
#    "seoyeon" 이 users 에 없는지(in 의 반대는 not in) assert 한다

print("테스트 4개 모두 통과")                                     # 위 assert 가 모두 지나가면 출력된다
```

- 각 주석 바로 아래 줄에 씁니다. `assert 조건 1 and 조건 2, "설명"` 에서 `and` 는 두 조건을 잇고, 쉼표 뒤의 글자는 거짓일 때 나오는 설명입니다.
- `assert` 의 설명은 표의 번호와 같게 씁니다. 예: `"2. 권한 없음"`, `"3-1. 만료 1분 전 허용"`, `"3-2. 만료 정각 거부"`, `"4. 설정 고장이면 사용자 없음"`.
- 4번은 `evaluate_access` 가 아니라 5교시 `load_json` 의 기본값을 확인하는 테스트입니다. 실행하면 `[경고] 설정 파일 없음: config/no_such.json` 이 먼저 출력되는데, 5교시 `load_json` 의 경고라서 정상입니다.
- 5교시 `config_loader.py` 의 `load_json` 을 채운 상태에서, 채우기 전에 실행해도 오류 없이 돌아갑니다. 테스트가 1번 하나뿐이라 「테스트 4개 모두 통과」가 나오지만, 아직 네 개를 확인한 것이 아닙니다.

- (나) 판정 프로그램이 오류로 멈추면 정산 포털이 판정을 받지 못해 업무가 막힙니다. 그러면 현장에서는 급한 업무를 위해 판정을 끄거나 건너뛰고 **모두 통과**시키기 쉽습니다. 빈 설정을 리턴하면 프로그램은 계속 돌면서 모든 요청을 거부하므로, 열려서는 안 되는 것이 열리는 일은 없습니다. 경고가 남아서 운영자는 무엇을 고쳐야 하는지 바로 압니다.
- (다) 더할 것 예: ① 경고를 화면에만 찍지 않고 파일 로그에 남기고 담당자에게 메일 · 메신저로 알린다 ② 판정 프로그램이 지금 빈 설정으로 돌고 있는지 알려 주는 상태 확인 명령이나 화면을 둔다 ③ 마지막으로 정상이던 설정 사본을 보관해 두고 한 번에 되돌릴 수 있게 한다. 가장 먼저 할 것은 알림이 좋습니다. 모두 거부되는 상태를 모르면 업무가 왜 멈췄는지 찾는 데 시간이 걸리고, 그동안 현장에서 판정을 끄자는 요구가 커지기 때문입니다. 다른 것을 먼저 골라도 이유가 있으면 맞습니다.

**왜** — 실패를 피할 수는 없으니, 실패했을 때 어떻게 동작할지를 정해 둡니다. 접근통제는 실패하면 모두 막는 쪽이어야 합니다. 고장을 일부러 만들어 보면 실제 고장 때 어떻게 되는지 미리 알고, 기본값이 원래 자료와 같은 모양이어야 뒤의 코드가 그대로 동작합니다.

**자주 틀리는 곳** — `except JSONDecodeError:` 처럼 `json.` 을 빼서 `NameError` 가 나는 경우가 가장 많습니다. `except:` 만 써서 모든 오류를 그냥 넘기면 코드의 오타까지 숨겨져 원인을 찾기 어렵습니다. 오류 이름을 정확히 적습니다. `return default` 를 빼먹으면 `None` 이 리턴되어 시험 파일에서 `TypeError: argument of type 'NoneType' is not iterable` 이 납니다. `load_json(path)` 처럼 기본값을 빼면 `TypeError: missing 1 required positional argument` 가 납니다. 깨진 파일을 붙여 넣으면서 쉼표를 지워 정상 파일로 만들어 버리는 경우도 있습니다.

**관제에서는** — 「설정 파일 깨짐」 경고는 누군가 설정을 바꿨다는 뜻이기도 해서, 경고가 나면 최근 변경 이력(git)을 함께 봅니다. 고장 시험(장애 주입)을 정기적으로 해 두면, 실제로 모두 막혔을 때 원인을 설정에서 먼저 찾습니다.

### 정답 6-1

💻 **터미널에 입력합니다.**

```bash
python test_policy.py
```

**채운 코드** (한 예)

```python
ok, reason = evaluate_access("seoyeon", "ACCOUNT", "CHANGE", at("2026-10-22 14:00"))   # 2. 권한 없음
assert ok == False and reason == "권한 없음", "2. 권한 없음"

ok, reason = evaluate_access("seoyeon", "SETTLE", "QUERY", at("2026-10-22 17:59"))     # 3. 만료 1분 전
assert ok == True and reason == "예외 1번", "3-1. 만료 1분 전 허용"
ok, reason = evaluate_access("seoyeon", "SETTLE", "QUERY", at("2026-10-22 18:00"))     # 3. 만료 정각
assert ok == False, "3-2. 만료 정각 거부"

users = load_json("config/no_such.json", {})                     # 4. 없는 파일을 읽는다
assert "seoyeon" not in users, "4. 설정 고장이면 사용자 없음"
```

**결과**

- 위 코드는 `test_policy.py` 의 2 ~ 4번 테스트입니다. 줄 수가 달라도 주석이 말한 일을 하면 맞습니다. `python test_policy.py` 의 출력은 다음과 같습니다.

```
[경고] 설정 파일 없음: config/no_such.json
테스트 4개 모두 통과
```

- (가) 출력은 다음과 같습니다. 실패한 줄은 6번 `assert` 줄이고(아래 예에서는 `line 14`, 파일에 줄을 더하거나 빼면 숫자가 달라집니다), 설명은 「6. 만료 정각에도 허용되어야 한다(팀원 제안)」입니다. 파일 앞의 폴더 경로도 PC 마다 다릅니다.

```
5 통과
Traceback (most recent call last):
  File "…/test_policy_extra.py", line 14, in <module>
    assert ok == True, "6. 만료 정각에도 허용되어야 한다(팀원 제안)"
AssertionError: 6. 만료 정각에도 허용되어야 한다(팀원 제안)
```

- (나) **제안이 지금 정책과 다르다는 뜻입니다.** 「지금 시각이 만료 시각보다 앞일 때만 유효, 정각에는 이미 거부」로 정했고, 코드(`now < expires`)는 그대로 지키고 있습니다. 위의 3번 테스트(만료 정각 거부)도 같은 규칙을 확인해 통과했습니다. 그래서 코드를 고칠 일이 아니라, 제안을 받아들일지 정책으로 정할 일입니다.
- (다) 예: 3번 테스트(만료 17:59 허용, 18:00 거부)가 없으면, 누군가 정책 코드를 한 줄 고치다 비교를 잘못 써서 만료된 예외가 정각 뒤에도 열려 있어도 눈으로는 알아채지 못합니다. 그러면 퇴근 뒤 밤에 이미 끝난 예외로 정산 자료가 조회되고, 다음 날 감사에서야 발견됩니다. 다른 예: 4번 테스트(설정 없음)가 없으면 설정 파일 읽기를 고치다 「사용자가 없으면 허용」으로 바뀌어도 잡지 못해 모든 요청이 열립니다. 하나를 골라 구체적인 장면을 적으면 맞습니다.

**왜** — 테스트는 기대를 먼저 적고 실제와 비교합니다. 경계값을 넣어야 비교 기호 하나의 실수까지 잡습니다. 테스트 실패는 「무엇인가 서로 다르다」는 신호일 뿐, 어느 쪽이 틀렸는지는 정책을 보고 판단합니다. 실패를 없애려고 코드부터 바꾸면 정책이 알리지 않고 바뀝니다.

**자주 틀리는 곳** — `assert ok == False and reason == "권한 없음"` 에서 `and` 대신 쉼표를 써서 `assert ok == False, reason == "권한 없음"` 으로 쓰는 경우가 가장 많습니다. 그러면 뒤쪽은 설명으로 읽혀 이유를 검사하지 않습니다. 3번에서 두 번째 판정을 하지 않고 첫 `ok` 를 다시 검사하는 실수도 있습니다. 6번이 실패하자 `exception_policy.py` 의 `<` 를 `<=` 로 고치는 경우도 많은데, 그러면 3번 테스트가 깨지고 정책이 알리지 않고 바뀝니다. `Traceback` 이 나왔다고 프로그램이 망가졌다고 생각하는 경우도 있지만, 이것은 테스트가 정상적으로 차이를 알려 준 것입니다.

**관제에서는** — 정책을 바꾸는 요청에는 「바꾼 뒤에도 통과해야 하는 테스트」를 함께 붙이게 합니다. 테스트가 없는 정책 변경은 받지 않습니다. 규칙 변경 요청은 「테스트로 적은 제안」 형태로 받으면 무엇이 바뀌는지 분명해지고, 실패한 테스트는 변경 검토 회의의 출발점이 됩니다.
