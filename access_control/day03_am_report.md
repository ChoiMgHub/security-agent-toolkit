## 2교시 · 권한 요청서 만들기

### 문제 2-1 · 요청서를 만들어 목록에 모으고, 접수할 수 없는 요청 걸러 내기

- (가) 실행한 출력 전체를 붙여 넣고, 접수되지 않은 세 건이 각각 `create_request` 의 어느 `if` 조건 때문에 접수되지 않았는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 접수되지 않은 세 건 각각이 걸린 `if` 조건
  - 답:

```text
--- 단계 1: 접수 - 요청 일곱 건을 하나씩 넣는다
seoyeon SETTLE QUERY -> 접수됨, 요청 번호 1
gaeun SALES QUERY -> 접수됨, 요청 번호 2
dami SALES QUERY -> 접수됨, 요청 번호 3
junho SETTLE QUERY -> 접수됨, 요청 번호 4
hana SALES QUERY -> 접수 안 됨: 등록되지 않은 사용자
seoyeon ACCOUNT QUERY -> 접수 안 됨: 이유가 없음
gaeun ACCOUNT QUERY -> 접수 안 됨: 만료 시각이 이미 지났음
--- 단계 2: 점검 - 요청서 목록
1 seoyeon SETTLE:QUERY reviewing
2 gaeun SALES:QUERY reviewing
3 dami SALES:QUERY reviewing

```

`day03_2-1_run.py`를 실행하니 신청 일곱 건 중 네 건이 접수되고 세 건은 접수되지 않았다. 접수된 요청서에는 1번부터 4번까지 번호가 붙었고, 상태는 모두 검토 중을 뜻하는 `reviewing`이었다.

접수되지 않은 세 건이 걸린 조건은 다음과 같다.

1. **hana의 SALES:QUERY 신청**은 `if user not in USERS:`에 걸렸다. 사용자 목록에 hana가 없어서 `등록되지 않은 사용자`가 출력됐다.
2. **seoyeon의 ACCOUNT:QUERY 신청**은 `if reason == "":`에 걸렸다. 신청 이유가 빈 문자열이어서 `이유가 없음`이 출력됐다.
3. **gaeun의 ACCOUNT:QUERY 신청**은 `if until <= received_at:`에 걸렸다. 희망 만료 시각은 `2026-10-22 18:00`, 접수 시각은 `2026-10-23 09:15`였다. 접수하기 전에 이미 만료된 요청이어서 `만료 시각이 이미 지났음`이 출력됐다. 이 조건은 두 시각이 같은 경우도 접수하지 않는다.

이번 접수 단계에서는 사용자 목록에 이름이 있는지, 이유가 비었는지, 만료 시각이 접수 시각보다 늦은지를 검사했다. dami는 퇴사한 계정이지만 사용자 목록에 이름이 남아 있어 접수됐고, 이미 역할 권한이 있는 junho의 신청도 접수됐다. 접수 결과의 `True`는 요청서를 기록했다는 뜻이며, 실제 접근 허용이나 권한 부여까지 끝났다는 뜻은 아니다.

- (나) 🔍 요청서의 `until`(희망 만료 시각)은 요청자가 직접 적습니다. 요청자가 적은 기간을 그대로 믿고 승인해도 될까요? 승인하기 전에 확인할 것을 두 가지 이상 적어 주세요.
  - 쓸 내용: ① 그대로 믿어도 되는지 ② 승인 전에 확인할 것 두 가지 이상
  - 답:

요청자가 적은 희망 만료 시각을 그대로 믿고 승인하면 안 된다. 이번 함수는 만료 시각이 접수 시각보다 늦은지만 검사하므로, 미래의 날짜라는 이유만으로 업무에 적절한 사용 기간이라고 판단할 수는 없다.

승인 전에는 다음 내용을 확인해야 한다.

1. **실제 업무 기간과 필요한 사용 기간**을 확인한다. 하루 동안 필요한 업무인데 한 달 동안 권한을 신청했다면 긴 기간이 필요한 이유를 확인해야 한다.
2. **신청 이유와 요청한 권한의 범위**를 확인한다. 해당 업무에 그 권한이 필요한지, 조회만 필요한데 변경 권한까지 신청한 것은 아닌지 살펴야 한다.
3. **요청자의 현재 재직 상태와 담당 업무**를 확인한다. 접수됐다는 사실만으로 권한을 받을 수 있는 사용자라고 판단하면 안 된다.

`until`은 신청자가 바라는 시각이다. 접수 조건을 통과한 것과 그 기간의 권한 부여가 적절하다는 판단은 구분해야 한다.

## 3교시 · 승인과 반려

### 문제 3-1 · 승인 · 반려 함수 만들고, 두 번째 처리가 막히는지 확인하기

- (가) 실행한 출력 전체를 붙여 넣고, 막힌 세 줄이 각각 왜 막혔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 막힌 세 줄 각각의 이유
  - 답:

```text
--- 단계 1: 처리 - 본인 요청 시험 한 건, 승인 · 반려 여섯 건을 처리한다
1 본인 승인 -> False 본인 요청은 처리할 수 없음
1 승인 -> True 승인
2 반려 -> True 반려
3 승인 -> True 승인
4 승인 -> True 승인
1 승인 -> False 검토 중이 아님
2 승인 -> False 검토 중이 아님
--- 단계 2: 점검 - 요청서 목록
1 seoyeon approved security_manager
2 gaeun rejected security_manager
3 dami approved security_manager
4 junho approved security_manager
```

`day03_3-1_run.py`를 실행해 본인 승인 시험 한 건과 담당자의 처리 여섯 건을 확인했다. 막힌 세 줄의 이유는 다음과 같다.

1. **`1 본인 승인 -> False 본인 요청은 처리할 수 없음`**: 1번 요청자도 seoyeon이고 처리자로 전달한 이름도 seoyeon이었다. `request["user"] == approver` 조건에 걸려 본인 승인이 차단됐다. 요청서를 반려한 것이 아니라 처리 자체가 막힌 것이므로, 상태는 `reviewing`으로 유지됐다. 이후 security_manager의 정상 승인은 성공했다.
2. **`1 승인 -> False 검토 중이 아님`**: 1번 요청은 앞에서 승인해 이미 `approved` 상태였다. `request["status"] != "reviewing"` 조건에 걸려 두 번째 승인이 차단됐다.
3. **`2 승인 -> False 검토 중이 아님`**: 2번 요청은 앞에서 반려해 이미 `rejected` 상태였다. 이 요청도 `reviewing`이 아니므로 승인 시도가 차단됐고, 기존 반려 결과가 유지됐다.

최종 목록에서는 1·3·4번이 `approved`, 2번이 `rejected`였고 처리자는 모두 `security_manager`로 기록됐다. `True 반려`는 반려 처리를 정상적으로 완료했다는 뜻이며, 접근을 허용했다는 뜻은 아니다.

- (나) 🔍 이미 승인한 요청서를 다시 승인하지 못하게 막는 이유는 무엇인가요? 막지 않으면 어떤 일이 생길 수 있나요?
  - 쓸 내용: ① 막는 이유 ② 막지 않을 때 생길 수 있는 일
  - 답:

같은 요청서를 여러 번 처리하지 않고, 한 번 결정된 처리 결과와 처리자 기록을 보존하기 위해서다. 상태를 바꾸기 전에 `reviewing`인지 확인하면 이미 승인하거나 반려한 요청서는 다시 처리할 수 없다.

이 검사가 없으면 이미 승인한 요청을 재승인하거나, 반려한 요청을 나중에 승인으로 바꿀 수 있다. 처리자 정보도 나중의 처리로 덮어써질 수 있어 누가 어떤 결정을 내렸는지 추적하기 어려워진다. 이후 권한 부여 절차와 연결될 때 중복 처리의 원인이 될 수도 있다. 다만 이번 승인 함수 자체는 예외를 추가하지 않으므로, 재승인만으로 즉시 예외가 두 개 생기는 것은 아니다.

내 실행에서는 이미 승인한 1번과 이미 반려한 2번의 승인 시도가 모두 막혔다. 이번 수업의 규칙에서는 결정 변경이 필요하면 기존 결과를 덮어쓰는 대신 새 요청서를 접수한다.

- (다) 🔍 `approve_request` 에서 `request["user"] == approver` 검사를 뺀다면 어떤 위험이 생길까요? 요청자가 친구에게 대신 승인해 달라고 부탁하면 이 검사로는 막을 수 없습니다. 이런 경우를 막으려면 무엇이 더 필요할까요?
  - 쓸 내용: ① 검사를 뺐을 때의 위험 ② 더 필요한 장치 한 가지 이상
  - 답:

본인 요청 검사를 빼면 요청자가 자기 신청을 직접 승인할 수 있다. 다른 담당자의 검토 없이 신청을 통과시킬 수 있으므로 요청하는 사람과 검토하는 사람을 구분한 의미가 없어진다.

하지만 현재 검사는 요청자와 처리자의 이름이 같은지만 확인한다. 친구가 다른 계정으로 대신 승인하면 두 이름이 다르므로 이 검사만으로는 막을 수 없다. 함수에 처리자 이름을 전달하는 것만으로 실제 승인 자격이 확인되는 것도 아니다.

추가로 승인 가능한 담당자를 정하고, 실제 로그인한 사용자가 해당 신청을 처리할 권한이 있는지 검사해야 한다. 위험한 권한에는 정해진 서로 다른 담당자 두 명의 승인을 요구하고, 요청자·처리자·처리 시각과 결과를 남겨 정기적으로 대조하는 장치가 필요하다. 이런 방법은 임의 승인이나 공모 위험을 줄이는 추가 대책이며, 이번 코드에서 구현하거나 시험한 기능은 아니다.

## 4교시 · 정책 확인 후 예외 권한 부여

### 문제 4-1 · 승인된 요청서를 정책으로 확인하고 예외 권한 부여하기

- (가) 실행한 출력 전체를 붙여 넣고, 부여를 시도한 네 건이 각각 어떻게 됐는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 네 건 각각의 결과
  - 답:

```text
--- 단계 1: 판정 - 부여 전
1 seoyeon SETTLE:QUERY -> False 권한 없음
2 gaeun SALES:QUERY -> False 권한 없음
3 dami SALES:QUERY -> False 퇴사한 계정
4 junho SETTLE:QUERY -> True 역할 권한
--- 단계 2: 부여 - 요청서마다 부여를 시도한다
1 seoyeon granted -> True 부여
2 gaeun rejected -> False 승인되지 않음
3 dami approved -> False 부여하지 않음(퇴사한 계정)
4 junho approved -> False 부여하지 않음(허용)
부여된 예외 번호: 6
--- 단계 3: 점검 - 부여 후
1 seoyeon SETTLE:QUERY -> True 예외 6번
2 gaeun SALES:QUERY -> False 권한 없음
3 dami SALES:QUERY -> False 퇴사한 계정
4 junho SETTLE:QUERY -> True 역할 권한
```

`day03_4-1_run.py`를 실행해 부여 전 판정, 부여 시도, 부여 후 판정을 비교했다. 이 실행은 실제 컴퓨터 시각 대신 코드에 정한 `2026-10-23 10:00`을 기준으로 접근을 판정했다.

1. **1번 seoyeon — 예외 부여 성공**: 요청서가 `approved` 상태이고 `check_permission` 결과가 `False, "권한 없음"`이어서 예외를 추가했다. 시작할 때 예외가 5개였으므로 새 번호는 6번이었다. 요청서에는 `exception_id`가 6으로 기록되고 상태가 `granted`로 바뀌었다. 부여 전에는 거부됐지만 부여 후에는 `True 예외 6번`으로 허용됐다.
2. **2번 gaeun — 반려된 요청이라 부여하지 않음**: 요청서 상태가 `rejected`이므로 `request["status"] != "approved"` 조건에서 중단됐다. 이 요청은 부여 함수의 역할 정책 검사까지 진행하지 않았고, 부여 후 접근 판정도 계속 `False 권한 없음`이었다.
3. **3번 dami — 퇴사한 계정이라 부여하지 않음**: 승인 상태 검사는 통과했지만 `check_permission`의 이유가 `퇴사한 계정`이었다. 부여 중단 조건인 `ok or judge_reason != "권한 없음"`이 참이 돼 예외를 추가하지 않았다. 요청서는 `approved`로 남았고 접근도 계속 거부됐다.
4. **4번 junho — 이미 역할 권한이 있어 추가 부여하지 않음**: 역할 정책에서 `True, "허용"`을 반환해 예외를 추가하지 않았다. 부여 결과의 `False`는 새 예외를 추가하지 않았다는 뜻이다. 실제 접근은 기존 역할 권한으로 계속 허용됐다.

부여 전후 접근 판정이 바뀐 사람은 seoyeon 한 명이었다. 부여 판단의 `check_permission`은 사용자와 역할을 확인하고, 전후 비교의 `evaluate_access`는 유효한 예외까지 합쳐 최종 판정한다. 그래서 junho의 이유가 부여 단계에서는 `허용`, 접근 판정에서는 `역할 권한`으로 다르게 표시됐다.

- (나) 🔍 승인자가 승인한 3번 요청(`dami`)을 코드가 부여하지 않았습니다. 코드의 이 확인이 없었다면 어떤 일이 생겼을까요? 승인자가 이 문제를 미리 막기 어려운 이유도 적어 주세요.
  - 쓸 내용: ① 확인이 없을 때 생기는 일 ② 승인자가 미리 막기 어려운 이유
  - 답:

부여 단계의 정책 확인이 없으면 승인된 요청이라는 이유만으로 퇴사한 dami에게도 예외가 만들어질 수 있다. 그러면 부여하면 안 되는 계정의 예외가 목록에 남고, 회수와 감사에서 확인해야 할 잘못된 권한 정보가 생긴다.

다만 현재 `evaluate_access`는 퇴사 여부를 먼저 확인하므로, 예외가 잘못 추가돼도 dami의 실제 접근은 계속 거부된다. 부여 단계에서 잘못된 예외 생성을 막는 것과 접근 단계에서 퇴사자를 거부하는 것은 각각 필요한 검사다.

승인자는 신청 이유와 업무 필요성을 검토하더라도 최신 퇴사 정보를 모르거나 승인과 부여 사이에 바뀐 계정 상태를 놓칠 수 있다. 따라서 사람의 승인 이후에도 실제 부여 시점의 사용자·역할 정보를 코드로 확인해야 한다. 이번 출력에서도 dami는 `approved`였지만 예외가 부여되지 않아, 승인 완료와 부여 완료를 구분할 수 있었다.

- (다) 🔍 부여한 예외의 만료 시각에는 요청서의 희망 만료 시각을 그대로 썼습니다. 그 시각이 지나면 이 예외는 어떻게 될까요? 만료된 예외를 정리하는 점검은 누가 얼마나 자주 하면 좋을까요?
  - 쓸 내용: ① 만료 뒤 예외가 어떻게 되는지 ② 점검을 누가 얼마나 자주 할지
  - 답:

seoyeon에게 부여한 예외 6번의 `expires`에는 요청서의 `until` 값인 `2026-10-27 18:00`이 들어간다. 어제 만든 예외 판정은 `now < expires`일 때만 유효하므로, 10월 27일 18시 정각부터 이 예외를 사용할 수 없다. 다른 유효한 역할 권한이나 예외가 없다면 정산 조회는 다시 `권한 없음`으로 거부된다.

만료 판정이 예외 기록을 목록에서 자동으로 삭제하는 것은 아니다. 보안 담당자가 매일 아침 만료된 예외와 퇴사자의 예외를 점검하고, 회수·정리한 대상과 시각을 기록하면 좋다. 퇴사 등 계정 상태 변경이 발생했을 때는 정기 점검을 기다리지 않고 추가로 확인해야 한다. 이것은 내가 제안하는 운영 방식이며, 오늘 자동 점검 작업을 등록한 것은 아니다.

이번 실습에서는 예외를 메모리의 `EXCEPTIONS` 목록에만 추가하고 `exceptions.json`에는 저장하지 않는다. 프로그램을 종료하면 이번 실행에서 추가한 예외도 사라진다. 또한 이번에 실행한 `NOW`는 `2026-10-23 10:00`으로 고정돼 있으므로, 위의 만료 이후 결과를 실제로 시험한 것은 아니다. 만료 설명은 어제 확인한 `now < expires` 규칙을 이번 예외에 적용한 것이다.
