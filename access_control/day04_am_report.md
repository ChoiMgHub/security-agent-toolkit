## 2교시 · 지금 부여돼 있는 권한 현황 만들기

### 문제 2-1 · 역할과 예외를 합쳐 지금 부여돼 있는 권한 현황 만들기

- (가) 실행한 출력 전체를 붙여 넣고, 부여돼 있는 권한이 모두 몇 건인지, 그중 예외로 받은 권한이 몇 건인지, 현황에 권한이 하나도 없는 사용자가 있다면 누구이고 그 이유는 무엇인지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 전체 건수 ③ 예외로 받은 건수 ④ 권한이 하나도 없는 사용자와 그 이유
  - 답: 내가 실행한 결과, 현재 설정에 남아 있는 권한 부여 기록은 총 14건이었다. 역할로 받은 권한이 9건, 예외로 받은 권한이 5건이었다. 사용자별로는 seoyeon·junho·gaeun·dami가 각각 3건이고, batch-night가 2건이었다. 여기서 세는 것은 사용자 수나 서로 다른 권한 이름의 수가 아니라, 사용자·권한·부여 출처로 구분한 기록의 수이다. 예를 들어 dami의 SALES:QUERY는 역할 sales와 예외 3번에서 각각 부여됐으므로 두 기록으로 남는다.

    수업 자료의 사용자·역할 정의와 비교하면, 사용자로 등록된 tester는 현황 목록과 사용자별 집계에 나오지 않는다. tester의 역할인 intern이 역할 파일에 정의돼 있지 않아 `ROLES.get(role, [])`가 빈 목록을 반환하고, 별도로 받은 예외 권한도 없기 때문이다. 사용자가 없어진 것이 아니라 현황에 추가할 권한 기록이 없는 것이다. batch-night는 사람이 아니라 자동 집계 프로그램이 사용하는 계정이며, 이번 자료에서는 employed가 True로 설정돼 있다.

    이 목록은 USERS에서 사용자와 정보를 꺼내 역할 권한 목록을 이어 붙인 뒤, EXCEPTIONS의 예외를 한 건씩 추가해 만든 것이다. 역할과 예외의 출처를 함께 남겼기 때문에 같은 권한 이름이 나와도 어디에서 부여됐는지 구분할 수 있었다. 아래는 내가 실행해 확인한 전체 출력이다.

```text
--- 단계 1: 현황 - 부여돼 있는 권한 14 건
seoyeon SALES:QUERY <- 역할 sales | 재직 True
seoyeon SALES:CHANGE <- 역할 sales | 재직 True
junho SALES:QUERY <- 역할 finance | 재직 True
junho SETTLE:QUERY <- 역할 finance | 재직 True
gaeun ACCOUNT:QUERY <- 역할 account_admin | 재직 True
gaeun ACCOUNT:CHANGE <- 역할 account_admin | 재직 True
dami SALES:QUERY <- 역할 sales | 재직 False
dami SALES:CHANGE <- 역할 sales | 재직 False
batch-night SETTLE:QUERY <- 역할 batch | 재직 True
seoyeon SETTLE:QUERY <- 예외 1번 | 재직 True
junho SALES:CHANGE <- 예외 2번 | 재직 True
dami SALES:QUERY <- 예외 3번 | 재직 False
batch-night SALES:QUERY <- 예외 4번 | 재직 True
gaeun SETTLE:QUERY <- 예외 5번 | 재직 True
--- 단계 2: 점검 - 사용자별 권한 개수
{'seoyeon': 3, 'junho': 3, 'gaeun': 3, 'dami': 3, 'batch-night': 2}
```

- (나) 🔍 현황 목록에는 판정 함수(`check_permission` · `evaluate_access`)가 이미 거부하는 권한도 들어 있습니다. 어떤 권한이 그런지 예를 하나 들고, 거부되는 권한을 목록에서 빼지 않고 남겨 두는 것이 점검에 왜 필요한지 적어 주세요.
  - 쓸 내용: ① 이미 거부되는 권한의 예 ② 남겨 두는 이유
  - 답: 내 출력에서 dami의 SALES:QUERY와 SALES:CHANGE는 재직 여부가 False인데도 역할 sales의 권한으로 남아 있었고, 예외 3번의 SALES:QUERY도 함께 나왔다. 최종 판정 함수 evaluate_access는 퇴사한 dami의 접근을 거부하지만, 그 판단 자체가 역할·예외의 부여 기록을 삭제하는 것은 아니다. 이후 3교시에서는 기준 시각에 만료된 예외 1·2·4·5번도 확인했다.

    이번 점검의 목적은 지금 접근이 허용되는지만 확인하는 것이 아니라, 설정에 어떤 권한 부여 기록이 남아 있는지 모아서 정리할 대상을 찾는 것이다. 처음부터 퇴사자나 만료된 예외를 빼면, 오히려 다음 교시에서 찾아야 할 기록을 숨기게 된다. 따라서 출처와 재직 여부, 예외의 만료 시각을 남겨 두어야 한다. 특히 재직 여부 같은 설정이 나중에 잘못 바뀌면 남은 권한이 다시 접근에 사용될 수 있으므로, 접근을 거부하는 것과 남은 권한을 정리하는 것은 구분해야 한다. 오늘은 현황을 만들고 대상을 찾았으며 실제 권한은 회수하지 않았다.

## 3교시 · 규칙으로 필요 없어진 권한 찾기

### 문제 3-1 · 현황에서 퇴사한 계정과 만료된 예외 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 규칙에 걸린 권한이 이유별로 몇 건인지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 이유별 건수
  - 답: 전체 권한 부여 기록 14건을 검사한 결과, 규칙에 걸린 기록은 총 7건이었다. 이유가 ‘퇴사한 계정’인 것은 dami의 역할 권한 두 건과 예외 3번으로 총 3건이고, ‘만료된 예외’는 예외 1·2·4·5번으로 총 4건이었다. 퇴사한 사람이 세 명이라는 뜻이 아니라, 퇴사한 dami 한 명에게 남은 부여 기록이 세 건이라는 뜻이다. dami의 예외 3번은 만료 시각이 아직 남아 있지만 퇴사 조건에 걸린다. 점검 기준 시각은 실행 당시의 실제 시계가 아니라 실행 파일에 고정한 `2026-10-29 10:00`이다.

    처음 실행했을 때는 규칙에 걸린 권한이 0건이고 이유별 건수도 `{}`로 나왔다. 오류 메시지는 없었지만 예상 결과와 달라 AI에게 설명과 코드 검토를 요청하고, review_rules.py의 코드를 채팅에 보내 확인했다. 원인은 `return stale`이 for문 안쪽에 있어 첫 번째 권한만 검사하고 반환한 것이었다. 첫 기록인 seoyeon의 SALES:QUERY는 재직 중인 사용자의 역할 권한이어서 결과 목록에 추가되지 않았고, dami와 예외들을 검사하기 전에 빈 목록이 반환됐다.

    마지막 return을 for문과 같은 들여쓰기 위치로 옮긴 뒤 다시 실행하자 아래와 같이 7건이 나왔다. 조건 검사와 결과 추가는 반복문 안에서 하고, 전체 검사 후 반환은 반복문 밖에서 해야 한다는 점을 출력 변화로 확인했다. 함수는 원래 현황 기록을 복사한 뒤 reason을 붙여 결과 목록에 넣으므로, 원래 목록의 내용은 그대로 보존한다. 아래는 수정 후 내가 실행한 전체 출력이다.

```text
--- 단계 1: 판정 - 규칙에 걸린 권한 7 건 (전체 14 건 중)
dami SALES:QUERY <- 역할 sales | 퇴사한 계정
dami SALES:CHANGE <- 역할 sales | 퇴사한 계정
seoyeon SETTLE:QUERY <- 예외 1번 | 만료된 예외
junho SALES:CHANGE <- 예외 2번 | 만료된 예외
dami SALES:QUERY <- 예외 3번 | 퇴사한 계정
batch-night SALES:QUERY <- 예외 4번 | 만료된 예외
gaeun SETTLE:QUERY <- 예외 5번 | 만료된 예외
--- 단계 2: 점검 - 이유별 건수
{'퇴사한 계정': 3, '만료된 예외': 4}
```

- (나) 🔍 퇴사한 계정과 만료된 예외는 파일에 적힌 사실로 걸러 냈습니다. 이 규칙으로는 걸러 낼 수 없지만 필요 없을 수 있는 권한의 예를 하나 들고, 그것을 찾으려면 어떤 정보가 더 필요한지 적어 주세요.
  - 쓸 내용: ① 규칙으로 못 거르는 권한의 예 ② 찾는 데 필요한 정보
  - 답: 재직 중인 사용자가 프로젝트를 마치거나 담당 업무가 바뀌었는데도 예전에 받은 권한을 계속 가지고 있는 경우를 생각할 수 있다. 재직 여부가 True이고 예외 기한도 지나지 않았거나 역할로 받은 권한이라면, 퇴사·만료 규칙만으로는 찾을 수 없다. 이번 두 규칙에 안 걸렸다는 사실이 그 권한이 계속 필요하다는 뜻은 아니다.

    이를 확인하려면 사용자·권한별 마지막 사용 시각과 사용 이력, 현재 맡은 업무, 부서 이동이나 프로젝트 종료 여부가 더 필요하다. 이어진 4교시에서는 실제로 남은 7건을 사용 이력과 비교했고, 그중 90일 초과 미사용 또는 이력 없음에 해당하는 후보 3건을 찾았다. 다만 사용 기록만으로도 업무상 필요 여부를 확정할 수는 없으므로, 담당자에게 권한 사용 목적을 확인하는 과정이 필요하다.

- (다) 🔍 규칙에 걸린 7건을 내일 회수한다면 어떤 것부터 회수할까요? 출력의 이유(퇴사한 계정 · 만료된 예외)를 보고 기준을 하나 정해, 그 기준으로 이유를 적어 주세요.
  - 쓸 내용: ① 먼저 회수할 것 ② 그 기준과 이유
  - 답: 나는 퇴사한 dami에게 남아 있는 권한 3건부터 회수하겠다. 구체적으로는 역할 sales의 SALES:QUERY와 SALES:CHANGE, 예외 3번의 SALES:QUERY이다. 기준은 ‘현재 그 권한을 업무에 사용할 정당한 사용자가 있는가’로 정했다.

    dami는 이미 퇴사한 계정이므로 해당 직원의 업무를 위해 권한을 계속 유지할 이유가 없다. 현재는 최종 판정에서 접근을 거부하더라도, 재직 표시가 실수로 True로 바뀌면 남은 권한이 다시 사용될 수 있다. 예외 3번도 기한이 남아 있다는 이유로 유지할 것이 아니라 퇴사 사실을 기준으로 먼저 정리하겠다. 만료된 예외 4건도 정리해야 하지만, 이 기준에서는 퇴사자 권한을 먼저 처리하는 순서로 판단했다. 이것은 내일 회수한다면 어떻게 하겠다는 우선순위이며, 오늘 실제로 권한을 회수한 것은 아니다.

## 4교시 · 사용 이력으로 90일 넘게 안 쓴 권한 찾기

### 문제 4-1 · 사용 이력으로 90일 넘게 안 쓴 권한 후보 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 90일 넘게 안 쓴 후보가 몇 건인지와 후보마다 며칠째 안 쓰였는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 후보 건수 ③ 후보별 안 쓴 일 수(이력이 없으면 「이력 없음」)
  - 답: 3교시의 퇴사·만료 규칙에 걸린 7건을 제외하고, 남은 권한 7건을 마지막 사용 시각과 비교했다. 그 결과 추가 확인이 필요한 후보는 총 3건이었다. seoyeon의 SALES:CHANGE는 마지막 사용 후 120일, junho의 SALES:QUERY는 91일이 지나 기준인 90일을 초과했다. gaeun의 ACCOUNT:CHANGE는 일치하는 사용 이력이 없어 포함됐다. gaeun의 권한은 90일 초과가 계산된 것이 아니므로 미사용 일수는 ‘사용 이력 없음’으로 기록한다.

    junho의 SETTLE:QUERY는 정확히 90일이어서 후보에서 빠졌다. 조건이 ‘90일 넘게’이므로 `>`를 사용하고, `>=`로 바꾸면 이 권한까지 잘못 포함된다. batch-night의 SETTLE:QUERY는 기준일 새벽 2시에 사용했고 기준 시각이 오전 10시이므로, 아직 하루가 지나지 않아 `.days` 결과가 0이었다. 0일과 사용 이력 없음은 다른 상태이다.

    처음에는 단계 1에 7건의 사용 이력과 일수가 정상적으로 나왔지만 단계 2의 후보는 0건이었다. AI에게 access_log.json, review_unused.py, day04_4-1_run.py의 내용을 보내 검토를 요청했다. find_unused의 if·elif가 for문 밖에 있어 이력을 찾는 작업만 반복되고, 조건 검사는 마지막 권한에 대해서만 한 번 실행되고 있었다. 마지막 기록은 0일 전 사용한 batch-night의 SETTLE:QUERY였으므로 어느 조건에도 걸리지 않았다.

    if·elif와 그 안의 append 코드를 반복문 안쪽으로 들여쓰기하고, 마지막 `return unused`는 반복문 밖에 둔 뒤 다시 실행하자 아래와 같이 후보 3건이 나왔다. 3교시에서는 반환 위치 때문에 첫 기록만 검사했고, 이번에는 조건문 위치 때문에 마지막 기록만 검사했다. 두 실습을 실행하는 데는 성공했지만 들여쓰기 실수가 반복돼, 권한 한 건마다 실행할 부분과 전체 반복 후 실행할 부분을 나누어 읽는 연습이 더 필요하다. 실행 후에도 코드와 결과가 연결되는 과정을 다시 쉽게 설명해 달라고 요청하며 복습했다. 아래는 수정 후 내가 실행한 전체 출력이다.

```text
--- 단계 1: 현황 - 규칙에 안 걸린 권한 7 건의 안 쓴 일 수
seoyeon SALES:QUERY -> 2 일째 안 씀
seoyeon SALES:CHANGE -> 120 일째 안 씀
junho SALES:QUERY -> 91 일째 안 씀
junho SETTLE:QUERY -> 90 일째 안 씀
gaeun ACCOUNT:QUERY -> 9 일째 안 씀
gaeun ACCOUNT:CHANGE -> 사용 이력 없음
batch-night SETTLE:QUERY -> 0 일째 안 씀
--- 단계 2: 판정 - 90일 넘게 안 쓴 후보 3 건
seoyeon SALES:CHANGE <- 역할 sales
junho SALES:QUERY <- 역할 finance
gaeun ACCOUNT:CHANGE <- 역할 account_admin
```

- (나) 🔍 junho 의 `SETTLE:QUERY` 는 마지막 사용이 90일 전이라 후보에서 빠졌고, 같은 junho 의 `SALES:QUERY` 는 91일 전이라 후보에 들어갔습니다. 하루 차이로 나누는 기준은 합리적일까요? 경계 부근에서 담당자가 추가로 확인할 것도 적어 주세요.
  - 쓸 내용: ① 합리적인지와 이유 ② 추가로 확인할 것
  - 답: 같은 기준으로 점검을 반복하고 사람마다 후보를 다르게 고르지 않도록 하기 위해, 90일이라는 기준을 두는 것은 합리적이라고 생각한다. 이번 코드에서는 90일을 초과한 경우만 포함하므로 junho의 SETTLE:QUERY는 90일로 제외되고 SALES:QUERY는 91일로 포함됐다. 다만 하루 차이가 실제 업무상 필요성까지 바꾼다는 뜻은 아니므로, 이 기준은 자동 회수 여부를 확정하는 기준보다 추가 확인할 후보를 찾는 기준으로 사용하는 것이 적절하다.

    경계 부근의 권한은 분기·반기·연간 업무처럼 사용 주기가 긴지, 다음에 사용할 업무가 예정돼 있는지, 최근 업무나 부서가 바뀌었는지 확인해야 한다. 사용 로그의 수집 범위와 누락 여부, 기준 시각이 맞는지도 함께 확인하겠다. 90일은 이번 실습에서 정한 기준이며 모든 권한에 같은 방식으로 최종 결정을 내려도 된다는 의미는 아니다.

- (다) 🔍 사용 이력이 없는 권한을 바로 지우면 위험한 경우가 있습니다. 어떤 경우인지 예를 들고, 지우기 전에 무엇을 확인해야 하는지 적어 주세요.
  - 쓸 내용: ① 위험한 경우의 예 ② 지우기 전에 확인할 것
  - 답: 장애나 보안 사고 때만 쓰는 비상 권한, 연말 결산처럼 특정 시기에만 쓰는 권한, 곧 시작할 업무를 위해 미리 부여한 권한은 사용 이력이 없어도 필요할 수 있다. 사용했지만 로그가 누락됐거나 아직 수집되지 않은 경우도 생각해야 한다. 따라서 ‘이력 없음’을 곧바로 ‘한 번도 사용하지 않았고 앞으로도 필요 없음’으로 판단하면 필요한 업무를 막을 수 있다.

    이번에 후보로 나온 gaeun의 ACCOUNT:CHANGE도 계정 관리 업무에서 특정 상황에 필요한지 확인해야 한다. 실제로 그런 상황에 사용한다는 사실을 이번 실습에서 확인한 것은 아니므로, 가능한 사례로만 구분한다. 회수 전에는 권한을 받은 목적과 현재 담당 업무, 업무 주기와 예정된 작업, 담당자에게 계속 필요한지 여부를 확인하고, 사용 이력 파일이 정상적으로 읽혔는지와 로그 수집 범위·누락 여부도 점검하겠다. 이번 실습에서는 권한을 복사해 후보 목록에 담았을 뿐, 실제로 삭제하거나 회수하지 않았다.
