## 5교시 · 업무 시간과 접속 위치 조건으로 판정하기

### 문제 5-1 · 기본 판정 뒤에 업무 시간과 접속 위치 조건을 확인하기

- (가) 실행한 출력 전체를 붙여 넣고, 허용된 요청과 거부된 요청이 각각 몇 건인지, 조건 때문에 거부된 요청이 몇 건이고 몇 번인지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 허용 · 거부 건수 ③ 조건 때문에 거부된 요청의 건수와 번호
  - 답:

`config/conditions.json`, `conditional.py`, `day05_5-1_run.py`를 작성하고 실행했다. 기본 권한 판정 뒤에 업무 시간과 접속 위치 조건을 적용한 결과는 다음과 같다.

```text
--- 단계 1: 판정 - 요청 8 건
1 seoyeon SALES:QUERY office 10:00 -> 허용(역할 권한)
2 seoyeon SALES:CHANGE office 09:00 -> 허용(역할 권한)
3 seoyeon SALES:CHANGE office 18:00 -> 거부(업무 시간 밖)
4 seoyeon SALES:CHANGE external 10:00 -> 거부(허용되지 않은 접속 위치)
5 seoyeon SALES:CHANGE external 22:00 -> 거부(업무 시간 밖)
6 junho SETTLE:QUERY vpn 19:30 -> 허용(역할 권한)
7 gaeun ACCOUNT:CHANGE vpn 10:00 -> 거부(허용되지 않은 접속 위치)

--- 단계 2: 확인 - 조건 파일에 적힌 조건
SALES:CHANGE | 9시부터 18시 전까지 | office, vpn
SETTLE:QUERY | 8시부터 20시 전까지 | office, vpn
ACCOUNT:CHANGE | 9시부터 18시 전까지 | office
```

**허용은 1·2·6번의 3건, 거부는 3·4·5·7·8번의 5건**이었다. 이 중 **추가 조건 때문에 거부된 요청은 3·4·5·7번의 4건**이다. 3·5번은 `업무 시간 밖`, 4·7번은 `허용되지 않은 접속 위치`로 나왔다. 8번은 기본 판정에서 `퇴사한 계정`으로 거부됐으므로 조건 때문에 거부된 건수와 구분했다.

2번의 09:00은 시작 시각을 포함하므로 허용됐고, 3번의 18:00은 끝 시각을 포함하지 않으므로 거부됐다. 시간 검사는 `start <= hour < end`를 사용한다. 6번은 정산 조회의 조건이 20시 전까지이고 VPN도 허용되므로 19:30에도 허용됐다. 반면 7번의 계정 변경은 사내망만 허용하므로 VPN에서도 거부됐다.

이번 오후 실습은 오전 회수 결과를 계속 사용하는 것이 아니라 새 프로그램에서 원본 설정과 기존 `evaluate_access`를 읽어 진행한다. 추가 조건이 없는 `SALES:QUERY`는 기본 판정 결과를 유지하므로, 모든 권한에 시간·위치 제한을 적용한 것은 아니다.

- (나) 🔍 5번 요청(seoyeon, 외부, 22시)은 업무 시간도 접속 위치도 어긋나는데 거부 이유는 「업무 시간 밖」 하나만 나옵니다. 거부 이유를 하나만 알려 주는 것과 어긋난 조건을 모두 알려 주는 것 중, 요청한 사람이 정상 사용자인 경우와 계정을 가로챈 사람인 경우 각각 어느 쪽이 나은지, 판정 결과를 점검하는 관제 담당자에게는 어느 쪽이 나은지 이유와 함께 적어 주세요.
  - 쓸 내용: ① 정상 사용자에게 나은 쪽과 이유 ② 계정을 가로챈 사람에게 나은 쪽과 이유 ③ 관제 담당자에게 나은 쪽과 이유
  - 답:

5번은 외부에서 22시에 변경을 요청하므로 시간과 접속 위치 조건을 모두 어겼다. 하지만 코드가 시간을 먼저 검사하고 실패하면 즉시 `return`으로 함수를 끝내므로 `업무 시간 밖`이라는 이유 하나만 반환됐다. 위치 조건까지 통과했다는 뜻이 아니라, 그 검사에 도달하기 전에 끝난 것이다.

**정상 사용자 입장에서는 어긋난 조건을 모두 알려 주는 편이 문제 해결에 도움이 된다.** 시간뿐 아니라 접속 위치도 바꿔야 한다는 것을 한 번에 알 수 있어 같은 요청을 여러 번 수정해 보내는 일을 줄일 수 있기 때문이다.

**관제 담당자에게는 여러 위반 조건을 함께 확인할 수 있는 내부 기록이 더 도움이 된다.** 업무 시간 밖의 외부 접속이 동시에 발생했다는 상황을 알아야 요청을 분석하고 반복 패턴을 찾기 쉽기 때문이다. 단, 이런 조건 위반만으로 실제 계정 탈취라고 단정할 수는 없다.

요청자가 정상 사용자와 공격자 중 누구인지 미리 확실히 구별할 수는 없으므로, 사용자에게 보여 줄 응답과 내부 분석에 남길 정보를 나누어 설계하는 방법을 생각할 수 있다. **현재 작성한 함수는 첫 거부 사유만 반환하며, 모든 위반 조건을 수집하는 기능까지 구현하지는 않았다.**

  - 쓸 내용: ① 거부해야 하는 이유 ② 로그인 때 한 번만 확인했다면 생길 일
  - 답:

이 질문은 실제 계정 탈취를 관찰한 것이 아니라 **새벽 2시 외부 접속을 가정한 상황**이다. `SALES:CHANGE`의 추가 조건은 09:00 이상 18:00 미만, 접속 위치는 `office` 또는 `vpn`이다. 새벽 2시와 `external`은 둘 다 이 조건에 맞지 않으므로 기본 역할 권한이 있어도 요청을 거부해야 한다. 현재 코드 순서라면 시간 검사에서 먼저 `업무 시간 밖`을 반환할 것으로 예상된다.

로그인 때 한 번만 확인하고 이후 요청에서 조건을 검사하지 않으면, 로그인 이후 시간이나 접속 위치가 바뀐 상황을 반영하지 못할 수 있다. 유효한 로그인 상태와 기본 권한만 계속 신뢰하는 경우, 정상 시간에 로그인한 뒤 업무 시간 밖에서 보내는 변경 요청도 허용될 수 있다. 따라서 보호할 작업을 요청할 때마다 필요한 권한과 적용되는 조건을 확인해야 한다.

실습을 해석할 때도 한계를 구분한다. 이번 함수는 로그인이나 계정 탈취 탐지 기능을 구현한 것이 아니라 전달받은 사용자·시각·접속 위치로 접근을 판정한다. 실제 서비스에서는 신원을 검증하고, 요청자가 임의로 바꿀 수 있는 시간·위치 문자열을 그대로 신뢰하지 않도록 해야 한다.

## 6교시 · 판정 서버 만들고 요청 로그 남기기

### 문제 6-1 · 판정 서버를 만들고 요청마다 로그 남기기

- (가) 터미널 2의 출력 전체를 붙여 넣고, 응답의 상태 코드별 건수(200 · 403 · 400)와 서버가 남긴 로그 줄 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 상태 코드별 건수 ③ 로그 줄 수
  - 답:

`access_server.py`와 `send_checks.py`를 작성했다. 코드와 실행 상황을 점검하려고 AI에게 확인을 요청한 뒤, 서버와 요청 프로그램을 실행한 실제 터미널 출력을 공유해 비교했다.

서버는 `"C:/Users/User/AppData/Local/Python/pythoncore-3.14-64/python.exe" access_server.py`로 실행했고, 다른 터미널에서 같은 파이썬으로 `send_checks.py`를 실행했다. 서버 화면에는 `Serving Flask app 'access_server'`, `Debug mode: off`, 개발 서버 안내와 `Running on http://127.0.0.1:5001`이 표시됐다.

처음에는 오류가 난다고 질문했지만, 이후 공유한 화면에서 확인된 `WARNING: This is a development server.`는 로컬 개발용 서버라는 안내였다. 제공한 코드와 이 실행 기록에서 실제 오류가 발생하거나 특정 코드를 수정해 해결한 근거는 없으므로 **개발 서버 안내와 실행 오류를 구분해 확인한 과정**으로 기록한다. 요청 프로그램의 출력 전체는 다음과 같다.

```text
--- 단계 1: 응답 - 요청 9 건
1 seoyeon SALES:CHANGE -> 200 역할 권한
2 seoyeon SALES:CHANGE -> 403 업무 시간 밖
3 seoyeon SALES:CHANGE -> 403 허용되지 않은 접속 위치
4 seoyeon SALES:QUERY -> 200 역할 권한
5 junho SETTLE:QUERY -> 200 역할 권한
6 junho SETTLE:QUERY -> 403 허용되지 않은 접속 위치
7 gaeun ACCOUNT:CHANGE -> 403 허용되지 않은 접속 위치
8 dami SALES:QUERY -> 403 퇴사한 계정
9 seoyeon SALES:CHANGE -> 400 입력이 잘못됨
--- 단계 2: 로그 - 서버가 남긴 8 줄
seoyeon SALES:CHANGE office 2026-10-30T09:00 -> True 역할 권한
seoyeon SALES:CHANGE office 2026-10-30T18:00 -> False 업무 시간 밖
seoyeon SALES:CHANGE external 2026-10-30T10:00 -> False 허용되지 않은 접속 위치
seoyeon SALES:QUERY external 2026-10-30T23:00 -> True 역할 권한
junho SETTLE:QUERY vpn 2026-10-30T19:30 -> True 역할 권한
junho SETTLE:QUERY external 2026-10-30T10:00 -> False 허용되지 않은 접속 위치
gaeun ACCOUNT:CHANGE vpn 2026-10-30T10:00 -> False 허용되지 않은 접속 위치
dami SALES:QUERY office 2026-10-30T10:00 -> False 퇴사한 계정
--- 단계 3: 대조 - 판정까지 간 응답과 로그
판정까지 간 응답 8 건 / 로그에 남은 줄 8 줄
```

상태 코드별 건수는 **200이 3건(1·4·5번), 403이 5건(2·3·6·7·8번), 400이 1건(9번)**이었다. 전체 응답은 9건이고 서버가 남긴 판정 로그는 **8줄**이었다.

9번 요청은 `network`가 빠져 입력 검사에서 400으로 끝났다. 현재 코드는 이 경우 판정 함수 호출과 JSONL 기록을 하지 않으므로 로그가 없는 것이 설계된 동작이다. 판정까지 간 응답 8건과 로그 8줄이 일치했고, 출력된 사용자·권한·위치·시각·허용 여부·이유를 응답과 함께 확인했다. 다만 건수 일치만으로 모든 로그의 정확성과 보관 체계까지 검증됐다고 보지는 않는다.

4번은 밤 23시의 외부 조회인데도 허용됐다. `SALES:QUERY`에 추가 조건이 없어 기본 역할 판정대로 허용된 것으로, 서버가 모든 야간·외부 요청을 차단하는 것은 아님을 구분했다.

이번 서버는 `127.0.0.1:5001`에서 동작하는 로컬 판정 서버다. 사용자 인증은 하지 않고, `network`와 `time`도 요청자가 보내는 값을 사용한다. 로그의 시각 역시 서버가 실제 수신 시각을 측정한 것이 아니라 시험 요청에 적힌 문자열이다. 운영용 인증·네트워크 검증·자료 접근 차단 전체를 구현했다고 기록하지 않는다.

- (나) 🔍 거부는 403, 값이 빠진 요청은 400 으로 상태 코드를 다르게 답했습니다. 요청을 보내는 쪽이 이 둘을 구별해야 하는 이유와, 구별하지 않으면 생길 수 있는 일을 적어 주세요.
  - 쓸 내용: ① 구별해야 하는 이유 ② 구별하지 않을 때 생길 수 있는 일
  - 답:

**400과 403은 실패 원인과 대응 방법이 다르기 때문에 구별해야 한다.** 400은 필수 값이 빠지거나 시각 형식이 잘못되는 등 입력 문제다. 이번 9번 요청처럼 `network`가 빠졌다면 요청하는 쪽이 값을 채워 다시 보내야 한다.

403은 입력 검사를 통과해 판정까지 진행했지만 정책에 따라 거부됐다는 뜻이다. 이번에는 업무 시간 밖, 허용되지 않은 접속 위치, 퇴사한 계정 등의 이유로 403이 나왔다. 상태 코드뿐 아니라 응답의 `reason`도 같이 확인해야 한다.

둘을 구별하지 않으면 입력 누락을 권한 문제로 오해하거나, 정상적인 정책 차단을 서버 고장으로 오해할 수 있다. 원인과 관계없는 권한 변경을 요청하거나 같은 요청을 계속 반복하는 일이 생길 수 있으므로, 먼저 입력을 고칠 문제인지 접근 정책을 확인할 문제인지 구분한다.

단, **이 실습의 403이 실제 사용자 인증 완료를 뜻하지는 않는다.** 서버는 비밀번호나 토큰을 검사하지 않고 요청에 적힌 사용자 이름으로 판정하므로, 403을 받았다는 이유만으로 신원까지 검증됐다고 해석하면 안 된다.

- (다) 🔍 서버 로그를 요청마다 새로 쓰면(`"w"` 모드) 한 달 뒤에 지난주의 거부 기록을 찾으려 할 때 어떻게 되나요? 로그에는 끝에 덧붙이는 방식이 알맞은 이유를 적어 주세요.
  - 쓸 내용: ① `"w"` 모드일 때 생기는 일 ② 덧붙이는 방식이 알맞은 이유
  - 답:

로그를 요청마다 `"w"` 모드로 열면 이전 내용이 지워지고 현재 기록으로 덮어써진다. 그러면 마지막 요청 기록만 남게 되어 한 달 뒤 지난주의 거부 기록을 찾으려 해도 확인할 수 없다. 반복된 거부나 시간대별 요청 흐름도 추적하기 어렵다.

`"a"` 모드는 기존 내용 뒤에 기록을 추가하므로 요청별 기록을 누적할 수 있다. 이번 `write_log`는 딕셔너리 한 건을 JSON 문자열로 만들고 줄바꿈을 붙여 `server_log.jsonl`에 추가한다. JSONL은 파일 전체가 하나의 JSON 배열인 형식이 아니라 **한 줄에 JSON 한 건씩 기록하는 형식**이다.

다만 제공된 `send_checks.py`는 시험 시작 시 기존 `server_log.jsonl`을 삭제한다. **서버 함수는 덧붙이지만, 시험 프로그램은 이전 시험 로그를 지우는 구조**이므로 재실행해도 과거 기록이 계속 보존되는 것은 아니다. 이번 결과는 한 번의 시험에서 판정 로그 8줄을 생성하고 응답과 대조한 것으로 기록한다.

실제 서비스에서 장기간 기록을 찾으려면 시험용 삭제 동작과 구분해 로그를 보존하고 보관·접근 권한 등의 운영 정책도 마련해야 한다. 또한 이번 JSONL에는 400 요청을 남기지 않으므로 모든 HTTP 요청이 기록된 파일이라고 부르지 않고, **판정까지 진행한 요청의 로그**로 범위를 구분한다.

- (가) `git status` 를 쳤을 때 `Untracked files:` 아래에 줄이 몇 개 보였는지, 그중에 `.env` 나 `.venv` 가 있었는지 적어 주세요.
  - 쓸 내용: ① 줄 수 ② `.env` · `.venv` 가 있었는지 없었는지
  - 답:

**확인 전 — 이 보고서를 작성하는 시점의 채팅에는 오늘 업로드 전 `git status` 출력이 없다.** 따라서 `Untracked files:` 아래에 실제로 몇 줄이 보였는지와 그 목록에 `.env`·`.venv`가 있었는지는 아직 확인하지 못했다.

1. **줄 수:** 확인 전. 오늘 만든 파일의 예상 개수로 대신 적지 않고, 실제 화면에 보이는 줄 수를 확인해 기록해야 한다.
2. **`.env`·`.venv` 표시 여부:** 확인 전. 이전 날짜의 상태나 `.gitignore` 설정만으로 오늘 목록에도 없었다고 단정하지 않는다.

서버를 종료한 뒤 저장소 루트인 `security-agent-toolkit`에서 `git status`를 실행해 이 두 항목을 확인하고 갱신할 예정이다. 현재 공유된 실행 기록에는 서버를 `Ctrl + C`로 종료한 결과와 오늘 자료의 `git add`·`git commit`·`git push` 결과도 없으므로, 종료나 업로드가 완료됐다고 적지 않는다. 실습 실행 완료와 GitHub 업로드 완료는 구분해 기록한다.
