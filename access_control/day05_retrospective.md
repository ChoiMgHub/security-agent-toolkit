# 3과목 총정리 (최민기 · 2026-11-02(월))

SKT ALEPH 접근통제 수업에서 만든 코드와 실행 결과를 다시 보며, 상황이 생기면 어디를 확인해야 하는지 정리했다. 이번 4교시는 설정을 실제로 바꾸는 시간이 아니라, 앞에서 배운 기능을 이용해 원인과 처리 방법을 글로 설명하는 시간이다. 아래의 ‘고친 뒤 확인’은 그 상황을 처리할 때 확인할 내용이며, 이번에 모두 변경하고 재실행했다는 뜻은 아니다.

사용자와 회사 상황은 수업용 가상 자료다. 파일 작성·수정과 PC 실행은 내가 진행했고, 개념 설명과 코드 검토, 이 문서의 정리에는 AI의 도움을 받았다. 오늘 자료의 날짜와 고정 판정 시각을 따라 문서 날짜는 11월 2일로 적었다. Day 6 수업이지만 산출물 이름은 교재에서 지정한 `day05_retrospective.md`를 사용했다.

## 상황 1 · 새 직원이 들어옴

- **원인:** hana가 입사했지만 사용자 명단에 등록되지 않았다. `rbac.py`는 사용자 이름이 `USERS`에 없으면 역할과 권한을 보기 전에 ‘등록되지 않은 사용자’로 거부한다.
- **고칠 파일:** `config/users.json`. 사용할 역할이 있는지는 `config/roles.json`에서 확인하고, 역할 부여 함수는 `role_admin.py`의 `assign_role`을 참고한다.
- **어떻게 고치나요:** hana가 맡을 업무를 확인한 뒤 해당 역할로 등록한다. 예를 들어 영업 업무라면 `"hana": {"role": "sales", "employed": true}`를 추가할 수 있다. 없는 역할을 임의로 적거나, 접속을 성공시키려고 필요 이상의 역할을 주지는 않는다.
- **고친 뒤 확인:** 사용자 정보를 다시 읽은 상태에서 hana의 요청을 판정한다. ‘등록되지 않은 사용자’라는 이유가 사라지고, 부여한 역할의 업무는 허용되는지 확인한다. 그 역할에 없는 업무는 계속 거부돼야 한다.
- **더 써 보고 싶은 것:** 앞 수업의 `assign_role`은 프로그램 안의 사용자 딕셔너리를 바꾸는 함수다. 함수 실행만으로 `users.json`에 저장되는 것은 아니다. 또 같은 이름이 이미 있으면 기존 항목을 덮어쓰므로, 신규 등록인지 역할 변경인지 먼저 확인해야 한다.

## 상황 2 · 퇴사자 계정으로 요청이 계속 들어옴

- **원인:** dami는 퇴사했는데 점검용 사용자 명단에 남아 있다. 오늘 샘플 로그에서도 ‘퇴사한 계정’으로 네 번 거부됐다. 계정 정리가 남아 있다는 사실과, 그 계정으로 계속 요청이 들어오는 이유는 나눠서 봐야 한다.
- **고칠 파일:** `config/users.json`과 dami에게 연결된 예외가 있는 `config/exceptions.json`. 오늘 체크리스트의 입력은 별도로 모아 둔 `config/week_state.json`이다.
- **어떻게 고치나요:** 먼저 재직 값이 `false`인지 확인한다. 아직 `true`라면 퇴사 상태를 반영해야 한다. 교재의 명단 정리 예시에서는 dami의 사용자 항목을 삭제하고, 남은 역할·예외도 확인해 정리한다. 요청이 계속 발생하는 출처는 따로 조사한다. 사용자 항목을 지운다고 요청 자체가 더 이상 오지 않는 것은 아니다.
- **고친 뒤 확인:** 삭제한 사용자 정보를 읽어 판정하면 같은 요청이 ‘등록되지 않은 사용자’로 거부되는지 확인한다. 점검에 사용하는 명단도 정리했다면 퇴사자 점검에서 dami가 빠져야 한다. 예외에 dami의 권한이 남지 않았는지와 반복 요청이 계속되는지도 따로 확인한다.
- **더 써 보고 싶은 것:** `check_permission`은 재직 여부를 역할 검사보다 먼저 본다. 퇴사자는 예전 역할이나 예외가 남아 있어도 허용되면 안 되기 때문이다. 오늘 예외 3번은 만료일까지 기간이 남아 있었지만 dami의 예외였다. 만료 점검의 ‘통과’만 보고 모든 권한이 적절하다고 판단하면 놓치는 부분이다.

## 상황 3 · 다른 팀 업무를 잠시 지원함

- **원인:** seoyeon의 `sales` 역할에는 정산 조회인 `SETTLE:QUERY`가 없다. 잠깐 지원하는 업무에 필요한 권한이므로, 기본 역할이 잘못됐다고 바로 판단하지는 않는다.
- **고칠 파일:** `config/exceptions.json`. 역할 판정 뒤 예외를 확인하는 순서는 `policy.py`, 만료 여부는 `exception_policy.py`에서 읽는다.
- **어떻게 고치나요:** 지원 업무와 승인 근거, 필요한 기간을 확인한 뒤 사용자·권한·만료 시각·사유를 적은 예외를 추가한다. 번호는 기존 항목과 겹치지 않게 정한다. 이미 유효한 예외가 있다면 중복 추가하지 않는다. 잠시 지원하는 일 때문에 `sales` 역할 전체에 정산 조회를 넣지는 않겠다. 반대로 업무 자체가 계속 바뀐 경우라면 임시 예외를 반복해서 연장하기보다 역할 변경을 검토해야 한다.
- **고친 뒤 확인:** 만료 전에는 해당 요청이 예외로 허용되고, 만료 시각 정각과 그 이후에는 거부되는지 확인한다. 수업의 예외 조건은 `now < expires`이므로 만료 정각은 허용에 포함하지 않는다. 만료 뒤 남은 예외 항목은 정리 대상인지 확인한다.
- **더 써 보고 싶은 것:** 예외는 모든 거부를 뒤집는 기능이 아니다. `evaluate_access`는 역할 판정 이유가 ‘권한 없음’일 때만 예외를 찾는다. 미등록 사용자·퇴사자·존재하지 않는 역할로 거부된 경우에는 예외 검색으로 넘어가지 않는다. 앞 수업 예외 파일의 날짜와 오늘 `week_state.json`의 날짜는 서로 다른 실습 데이터이므로 섞어서 읽지 않으려고 한다.

## 상황 4 · 새 권한이 필요함

- **원인:** junho에게 `SALES:CHANGE`가 필요하지만, 누가 신청을 받고 승인하며 언제까지 처리할지 정해진 절차가 없는 상황이다. 담당자가 그때마다 파일을 직접 고치면 신청 이유와 처리 과정이 빠질 수 있다.
- **고칠 파일:** 요청 생성은 `req_create.py`, 승인·반려는 `req_review.py`, 승인 후 부여는 `req_grant.py`다. 처리 기한은 `config/sla.json`, 지연 요청 검사는 `req_sla.py`에서 확인한다. 이 수업에서는 이미 만든 파일이므로 새로 중복 작성하기보다 기존 흐름을 살펴본다.
- **어떻게 고치나요:** 사용자·권한·필요 기간·사유가 있는 요청서를 만들고, 요청자와 다른 검토자가 승인 또는 반려한다. 승인됐더라도 `grant_request`에서 사용자와 역할 상태를 다시 확인한 뒤 필요한 예외를 부여한다. 검토 중인 요청이 오래 남으면 SLA 검사로 찾아 담당자가 확인하도록 한다. 단순히 지연 표시를 없애려고 기한부터 늘리지는 않겠다.
- **고친 뒤 확인:** 정상 요청은 `reviewing → approved → granted`로 바뀌는지 확인한다. 본인 승인과 이미 처리한 요청의 재처리는 막혀야 한다. 퇴사자처럼 부여할 수 없는 계정은 승인됐어도 부여 단계에서 거부돼야 한다. SLA는 검토 중인 요청에 적용하며, 기준이 4시간이면 정확히 4시간은 초과가 아니고 4시간을 넘긴 요청이 나와야 한다.
- **더 써 보고 싶은 것:** 앞 실습에서 승인된 dami의 요청이 부여 단계에서는 막힌 결과를 봤다. 승인과 부여를 같은 것으로 읽으면 안 되는 이유였다. 현재 승인 함수는 전달받은 이름이 요청자와 같은지 확인할 뿐, 실제 로그인한 승인자의 자격까지 검증하는 기능은 없다. 부여한 예외도 메모리에 추가되며 `exceptions.json`을 자동으로 덮어쓰지는 않는다. 처리 결과로 저장한 `requests.json`과도 구별해야 한다.

## 상황 5 · 안 쓰는 권한이 쌓임

- **원인:** 한 번 부여한 권한이 계속 남아 있을 수 있다. 다만 오래 쓰지 않은 이유가 업무 종료인지, 결산이나 사고 대응처럼 드물게 쓰기 때문인지는 사용 일수만으로 알 수 없다.
- **고칠 파일:** 현황은 `review_list.py`, 퇴사·만료 점검은 `review_rules.py`, 사용 이력은 `config/access_log.json`과 `review_unused.py`에서 확인한다. 후보를 합치는 코드는 `overprivilege.py`, 회수 제외 기준은 `config/exclude_list.json`과 `report_exclude.py`다.
- **어떻게 고치나요:** 먼저 퇴사·만료와 미사용 근거를 모아 후보를 만든다. 오래 안 썼거나 이력이 없다는 이유만으로 바로 지우지 않고, 현재 업무에 필요한지 확인한다. seoyeon의 결산용 변경 권한과 gaeun의 사고 대응용 계정 변경 권한처럼 유지할 근거가 있다면 사용자·권한·제외 사유를 남긴다. 실제로 불필요한 것은 회수 대상으로 넘긴다. 퇴사자인 dami의 권한은 제외 목록에 있어도 회수 대상으로 남겨야 한다.
- **고친 뒤 확인:** 앞 수업의 같은 고정 시각·자료로 점검하면 현황 14건에서 후보 10건이 나오고, 회수 대상 8건과 회수 제외 2건으로 나뉘는지 대조한다. 미사용 기준은 ‘90일 초과’여서 91일은 후보지만 정확히 90일은 이 기준에 걸리지 않는다. 재직 상태나 입력 자료가 바뀌었다면 예전 숫자를 억지로 맞추지 않고 바뀐 이유를 확인한다.
- **더 써 보고 싶은 것:** 이 부분에서 들여쓰기를 두 번 잘못 썼다. `find_stale`의 `return`이 반복문 안에 있어 첫 기록에서 끝났고, `find_unused`에서는 조건문이 반복문 밖에 있어 마지막 기록만 검사했다. 처음에는 둘 다 후보가 0건이었지만 원인은 달랐다. 코드를 공유해 설명을 받고 위치를 고친 뒤, 퇴사·만료 7건과 규칙에 안 걸린 권한 중 미사용 후보 3건을 각각 확인했다. 함수가 끝나는 위치와 항목마다 반복할 코드를 다시 따라볼 필요가 있다.

## 상황 6 · 민감한 권한을 회수해야 함

- **원인:** 불필요한 권한을 없애야 하지만, 변경 권한을 잘못 회수하거나 역할을 통째로 해제하면 필요한 업무도 멈출 수 있다. 같은 역할을 쓰는 사람이 여럿이면 한 번의 변경이 여러 사용자에게 적용될 수도 있다.
- **고칠 파일:** 방법과 영향은 `revoke_plan.py`, 승인 조건은 `config/sensitive.json`과 `revoke_approve.py`, 실행·이력 저장은 `revoke.py`에서 확인한다. 정리할 원본 데이터는 방법에 따라 `config/users.json`, `config/roles.json`, `config/exceptions.json`이다.
- **어떻게 고치나요:** 예외에서 받은 권한은 ‘예외 삭제’, 퇴사자의 역할 권한은 ‘역할 해제’, 재직자의 불필요한 역할 권한은 ‘역할에서 권한 빼기’로 계획한다. 민감한 권한이거나 영향이 2건 이상이면 승인이 필요하다. 승인 상태가 ‘승인 대기’인 계획은 실행하지 않고 대기로 기록한다. 역할에서 권한을 빼는 경우에는 그 역할을 사용하는 사람부터 확인한다.
- **고친 뒤 확인:** 승인 대기 건이 실행되지 않았는지, 회수할 자료가 의도대로 바뀌었는지, 유지할 권한에 영향이 없는지 확인한다. 전후 판정과 `revocation_log.json`을 함께 본다. 이미 퇴사나 만료로 거부되던 요청은 자료를 정리해도 판정이 계속 거부일 수 있다. 판정이 ‘그대로’라는 이유만으로 회수 처리가 실패했다고 판단하지 않는다.
- **더 써 보고 싶은 것:** 앞 실습에서 계획 8건 중 실행 7건·대기 1건이 나왔고 이력 8건을 저장해 다시 읽었다. junho의 `SALES:QUERY`는 허용에서 거부로 바뀌었다. 다만 실행 7건은 계획별 처리 기록 수다. dami의 역할 해제처럼 같은 변경이 두 계획에 나타나므로 서로 다른 변경이 일곱 번 생겼다는 뜻은 아니다. 이 코드는 메모리의 사용자·역할·예외를 바꾸고 회수 이력만 파일로 저장했다. 원본 JSON이나 실제 운영 계정까지 변경한 실습은 아니었다. 승인 거절과 미결정도 현재 코드에서는 모두 ‘승인 대기’로 모이므로, 이력만으로 거절 사유까지 알 수는 없다.

## 상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨

- **원인:** 먼저 요청한 권한과 실제 거부 이유를 확인해야 한다. 시간·위치 조건이 빠진 경우도 있고, 현재 조건이 업무 요구와 맞지 않는 경우도 있다. 조건대로 거부된 정상 동작일 수도 있으므로 접속 실패만 보고 사용자 정보를 고치지는 않겠다.
- **고칠 파일:** `config/conditions.json`과 이를 적용하는 `conditional.py`다. 기본 역할·예외 판정은 `policy.py`를 함께 본다.
- **어떻게 고치나요:**
  - **조건이 빠졌다는 가정:** `SALES:CHANGE`에 조건이 없다면 업무에 필요한 시간과 위치를 확인해 추가한다. 교재의 예는 9시 이상 18시 미만, `office` 또는 `vpn`이다. GitHub 최종 파일에는 이 조건이 이미 있어서 현재 코드의 누락으로 적지는 않는다.
  - **gaeun의 VPN 요청:** 현재 `ACCOUNT:CHANGE`는 `office`만 허용한다. VPN에서의 계정 변경이 승인된 업무인지 확인하고, 필요할 때만 `vpn`을 추가하는 방안을 검토한다. 단순히 거부를 없애려고 `external`까지 열지는 않는다.
  - **18시 정각 거부:** `[9, 18]`은 `9 <= hour < 18`이므로 18시는 거부가 맞다. 실제 업무가 더 늦게 끝나 기준을 바꿔야 한다면 영향 범위를 확인한 뒤 수정한다. 예를 들어 종료 시각을 20으로 바꾸는 것은 별도의 규칙 변경이다.
  - **조건 없는 조회 권한:** `SALES:QUERY`는 현재 조건이 없어 기본 판정이 허용이면 외부에서도 허용된다. 버그라고 단정하지 않고 조회 업무에도 조건이 필요한지 검토한다.
- **고친 뒤 확인:** 허용해야 할 요청과 계속 거부해야 할 요청을 함께 시험한다. 예를 들어 업무 시간의 승인된 VPN 요청은 허용하되, 업무 시간 밖이나 허용하지 않은 위치는 거부돼야 한다. 종료 시각을 20으로 바꿨다면 18시는 허용되고 20시 정각은 거부되는지 확인한다. 조건을 풀어 다른 사용자까지 새로 허용되는지도 살펴본다.
- **더 써 보고 싶은 것:** 앞 실행에서 seoyeon의 변경 요청은 09시에 허용되고 18시에 거부됐다. 시간과 위치를 둘 다 어긴 요청은 시간이 먼저 검사돼 ‘업무 시간 밖’으로 나왔다. 한 가지 사유만 출력됐다고 다른 조건을 만족했다는 뜻은 아니다. 또 `load_rules`가 읽기 실패 시 빈 목록을 받으면 추가 조건이 적용되지 않을 수 있다. 기준 파일이 정상적으로 읽혔는지부터 확인해야 한다. 서버는 시작할 때 조건을 읽으므로 파일 수정만으로 실행 중 서버에 새 조건이 반영됐다고 생각하지 않겠다.

## 상황 8 · 매주 어긋남을 확인해야 함

- **원인:** 사용자 정보와 요청 로그를 눈으로 읽고 세면 오래 걸리고 빠뜨리기 쉽다. 사람마다 판단 기준이 다르면 지난 결과와 비교하기도 어렵다. 다만 오늘 만든 코드는 매주 자동 실행되는 예약 프로그램은 아니며, 실행할 때 같은 방식으로 점검하고 보고서를 만드는 코드다.
- **고칠 파일:** 오늘의 점검 자료는 `config/week_state.json`, 요청 자료는 `week_log.jsonl`, 경고 기준은 `config/alert.json`이다. `checklist.py`가 설정을 점검하고 `log_summary.py`가 로그를 집계한다. `weekly_report.py`가 보고서 문자열과 파일을 만들고 두 실행 파일이 이 과정을 호출한다. 앞서 만든 서버와 기록은 `access_server.py`, `server_log.jsonl`에서 확인한다.
- **어떻게 고치나요:** 정한 점검 항목과 집계 함수를 사용해 결과를 한 문서에 모은다. 오늘은 퇴사자·만료 예외·부서와 역할 점검, 허용·거부 수, 거부 사유, 거부율과 반복 거부 사용자를 합쳤다. 경고 기준이 맞지 않는다면 정상적인 업무와 기존 기록을 확인한 뒤 기준과 변경 이유를 남긴다. 요청이 0건인 주에는 거부율만 읽지 않고 서버와 로그 수집 상태도 확인한다.
- **고친 뒤 확인:** 입력 건수와 집계 합계, 경고 기준, 생성한 보고서 내용을 대조한다. 거부율은 소수끼리 비교하고 화면에 보여 줄 때 퍼센트로 바꾼다. 반복 거부 사용자는 원문 로그의 시간·위치·사유를 찾아 읽어야 한다. 경고 기준을 바꿔 표시가 사라져도 요청 자체가 달라진 것은 아닌지 구별한다.
- **더 써 보고 싶은 것:** 오늘 직접 실행한 결과와 준비 중 겪은 일은 아래에 남겼다.

### 오늘 확인한 점검·보고서 결과

| 확인한 내용 | 내 실행 결과 |
|---|---|
| 점검 자료 | 사용자 6명·예외 4개 |
| 퇴사자 점검 | 실패, `dami` |
| 만료 예외 점검 | 통과, 빈 목록 |
| 부서·역할 점검 | 실패, `junho` |
| 요청 집계 | 전체 40건·허용 24건·거부 16건 |
| 거부율 | 40%, 기준 30% 이상이어서 경고 |
| 거부 사유 | 역할이 없음 3건·업무 시간 밖 4건·퇴사한 계정 4건·허용되지 않은 접속 위치 5건 |
| 4번 이상 거부된 사용자 | `dami`, `gaeun` |
| 생성한 보고서 | `access_control_weekly_report_2026-11-02.md` |

로그는 교재가 제공한 10월 26일~11월 1일의 가상 요청 40건이다. 내가 실제로 일주일 동안 서버를 운영해 모은 자료는 아니다. 2교시의 점검 시각은 `2026-11-02 10:00`으로 고정돼 있다. 현재 상태를 담은 점검 자료와 과거 요청을 담은 샘플 로그는 같은 시점의 자료가 아니므로, 역할 정보가 다르게 보일 때도 먼저 입력 자료를 확인해야 한다.

만료 점검은 통과했지만 dami의 예외 3번은 아직 기간이 남은 퇴사자 권한이었다. 날짜만 검사하는 함수로는 재직 상태까지 알 수 없었다. junho도 부서가 영업이고 역할 기준 부서는 재무라는 불일치까지만 찾았다. 실제 업무와 부서·역할 중 무엇이 맞는지 확인한 뒤 조치를 정해야 한다.

샘플 로그에서 dami의 거부 네 건은 모두 퇴사한 계정이었고, gaeun은 위치 조건으로 네 건·시간 조건으로 한 건 거부됐다. 같은 반복 거부 사용자여도 먼저 확인할 것이 달랐다. 또 전체 요청이 0건이면 `deny_rate`가 나눗셈 오류를 피하려고 0.0을 반환하므로, 거부율 0%만 보고 안전했다고 판단하면 안 된다.

### 준비 과정에서 막혔던 부분

처음에는 사전 준비를 빠뜨리고 실행해서 `FileNotFoundError`가 났다. `load_state("config/week_state.json")`이 읽을 파일이 없었던 것이고, 점검 함수의 조건문이 잘못된 것은 아니었다. 준비 파일을 만든 뒤 다시 진행했다. 상대 경로는 실행 파일의 위치가 아니라 터미널의 현재 작업 위치를 기준으로 찾는다는 점도 다시 확인했다.

이후 로그 줄 수가 41로 나와 확인했더니 41번째가 빈 줄이었다. 해당 줄을 제거한 뒤 빈 줄 번호가 `[]`, 전체 줄 수가 `40`으로 나왔고 `cat -n`으로 내용도 확인했다. 줄을 세는 명령은 빈 줄도 항목으로 세기 때문에, 줄 수와 실제 요청 수가 항상 같다고 생각하면 안 됐다. 교재의 로그 읽기 함수는 빈 줄도 JSON으로 바꾸려 하므로 이 빈 줄을 정리할 필요가 있었다.

## 다시 볼 때 먼저 확인할 것

| 상황에서 확인한 결과 | 먼저 볼 대상 |
|---|---|
| 등록되지 않은 사용자 | 사용자 명단과 이름 |
| 퇴사한 계정 | 재직 상태·남은 역할과 예외·반복 요청 출처 |
| 역할이 없음 | 사용자의 역할 이름과 역할 정의 |
| 권한 없음 | 역할 권한, 해당 사용자·권한의 유효한 예외 |
| 업무 시간 밖·허용되지 않은 접속 위치 | 권한별 시간·위치 조건 |
| 후보 0건처럼 예상과 다른 집계 | 입력 자료·고정 시각·들여쓰기·반환 위치 |
| 거부율 경고 | 전체 요청 수·거부 수·기준·사유별 원문 |

앞 실습의 로컬 서버에서는 요청 9건에 응답하고 로그 8줄을 확인했다. 값이 빠진 요청 한 건은 400 응답으로 일찍 끝나 로그 작성까지 가지 않았기 때문이다. 같은 수업 코드에서 200은 허용, 403은 판정 거부, 400은 잘못된 입력이었다. 로그 수가 응답 수보다 적으면 먼저 어느 단계에서 기록하는지 살펴봐야 했다.

코드를 읽을 때는 입력 검사 → 역할·예외 판정 → 시간·위치 확인 → 로그와 응답의 흐름으로 다시 따라보려고 한다. 사용자가 함수 인자로 넘긴 이름과 위치를 실제 로그인 신원이나 검증된 접속 정보로 확인하는 운영용 인증은 이번 실습에 포함되지 않았다.

## 3과목을 마치며

처음에는 사용자와 역할 파일을 만들고 요청을 허용할지 판정했다. 이후 임시 예외, 요청과 승인, 안 쓰는 권한 점검, 회수 계획과 실행, 시간·위치 조건, 서버와 로그, 주간 보고서까지 이어졌다. 파일은 늘었지만 요청을 처리하는 기능과 설정을 정리하는 기능, 결과를 확인하는 기능으로 나눠 다시 볼 수 있었다.

수업 중에는 정상 출력이 나온 뒤에도 더 쉽게 설명해 달라고 여러 번 요청했다. 특히 반복문과 `return`, `=`와 `==`, 승인과 부여, 후보 수와 실제 변경 수를 한 번에 구별하기 어려웠다. 설명을 듣고 코드를 고쳐 실행한 기록은 남겼지만, 아직 모든 흐름을 혼자 작성하거나 설명할 정도라고 생각하지는 않는다.

다음에는 요청 한 건을 골라 사용자 상태부터 반환값까지 손으로 따라가 보려고 한다. 회수 계획도 한 건씩 보며 무엇을 지우는지와 누구에게 영향이 생기는지 말해 보고 싶다. 결과가 맞았다는 확인에서 멈추지 않고, 왜 그런 결과가 나왔는지 내 말로 설명하는 데 이 기록을 사용하려고 한다.

데이터와 규칙도 바꾸기 전에 영향 범위를 봐야 한다. 한 사람의 부서 값을 고치는 것과 공통 역할의 권한을 빼는 것은 같은 데이터 변경이라도 영향이 다르다. 시간·위치 규칙이나 경고 기준은 여러 요청의 판정을 함께 바꿀 수 있다. 먼저 원인을 확인하고, 필요한 범위만 바꾼 뒤 허용할 것과 막을 것을 함께 확인하는 순서로 복습하겠다.

LLM이나 알림을 붙인다면 보고서 문자열을 요약하거나 경고가 있을 때 담당자에게 알리는 부분을 생각해 볼 수 있다. 이것은 다음 연결 아이디어이며 오늘 구현한 결과는 아니다. 집계 숫자는 코드가 계산한 값을 기준으로 두고, 요약 문장은 원문과 비교해야 한다.
