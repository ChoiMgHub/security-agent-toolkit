## 2교시 · 웹 서버 로그를 공통 이벤트로 바꾸기

### 문제 2-1 · 웹 서버 로그 한 줄을 공통 이벤트로 바꾸기

- (가) 실행한 출력 전체를 붙여 넣고, 정규화한 이벤트 수와 읽기 실패한 줄 수, 성공과 실패 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 정규화한 이벤트 수와 읽기 실패한 줄 수 ③ 성공 · 실패 개수
  - 답: 전체 웹 로그 30줄 중 28줄이 공통 이벤트로 바뀌었고, 읽기 실패는 2줄이었다. 정규화된 28개 중 성공은 15개, 실패는 13개였다. 첫 이벤트에서는 시각이 `2026-11-02 09:01:05`로 바뀌었고, `GET /` 요청의 상태 코드 200이 성공으로 분류된 것을 확인했다. 처음 나오는 실패 이벤트는 `POST /login` 요청으로, 원본의 상태 코드 401이 실패로 바뀌었다. 읽기 실패 2줄은 이벤트를 만들지 못한 경우이고, 실패 이벤트 13개는 로그를 읽었지만 요청 결과가 실패인 경우라는 차이를 설명을 통해 정리했다.

```text
--- 단계 1: 정규화한 이벤트 28 개 · 읽기 실패 2 줄
{'time': '2026-11-02 09:01:05', 'source': 'web', 'user': None, 'ip': '198.51.100.21', 'action': 'GET /', 'result': '성공', 'raw': '198.51.100.21 - - [02/Nov/2026:09:01:05 +0900] "GET / HTTP/1.1" 200 1204 "-" "Mozilla/5.0"'}
--- 단계 2: 처음 나오는 실패 이벤트
{'time': '2026-11-02 09:12:03', 'source': 'web', 'user': None, 'ip': '203.0.113.50', 'action': 'POST /login', 'result': '실패', 'raw': '203.0.113.50 - - [02/Nov/2026:09:12:03 +0900] "POST /login HTTP/1.1" 401 312 "-" "python-requests/2.31.0"'}
--- 단계 3: 성공 · 실패별 개수
{'성공': 15, '실패': 13}
```

- (나) 🔍 시각을 `02/Nov/2026:09:00:00 +0900` 모양 그대로 문자열로 정렬하면 12월 1일 요청(`01/Dec/2026:…`)과 11월 2일 요청(`02/Nov/2026:…`) 중 어느 쪽이 앞에 놓일지 예상하고, 공통 모양(`2026-11-02 09:00:00`)으로 바꾸면 무엇이 달라지는지 이유와 함께 적어 주세요.
  - 쓸 내용: ① 어느 쪽이 앞에 놓일지 ② 공통 모양으로 바꾸면 달라지는 점과 그 이유
  - 답: 원래 모양을 문자열 그대로 정렬하면 12월 1일인 `01/Dec/2026:…`가 11월 2일인 `02/Nov/2026:…`보다 먼저 놓인다. 문자열 앞의 `01`이 `02`보다 작기 때문에 실제 날짜 순서와 달라진다. 공통 모양으로 바꾸면 `2026-11-02`가 `2026-12-01`보다 먼저 놓인다. 이번 자료처럼 같은 시간대를 기준으로 연도·월·일·시·분·초의 순서와 자릿수를 맞추면, 문자열로 정렬해도 실제 시간순으로 볼 수 있다는 점을 배웠다.

- (다) 🔍 이벤트에 원래 로그 줄(`raw`)을 그대로 남겨 두는 이유는 무엇인가요? 정규화하면 사라지는 정보를 한 가지 예로 들어 함께 적어 주세요.
  - 쓸 내용: ① `raw` 를 남겨 두는 이유 ② 정규화하면 사라지는 정보의 예
  - 답: `raw`는 정규화한 값이 맞는지 원본과 대조하고, 공통 항목에 따로 담지 않은 정보를 나중에 확인하기 위해 남긴다. 내 출력의 실패 이벤트도 `result`만 보면 정확한 상태 코드를 알 수 없지만, `raw`를 보면 401이었다는 것을 확인할 수 있다. HTTP 버전과 요청 프로그램 정보도 원본에 남아 있다. 이번 코드에서는 앞뒤 공백과 줄바꿈을 제외한 원래 줄의 내용을 보관한다.

## 3교시 · 판정 서버 로그와 SaaS 로그를 공통 이벤트로 바꾸기

### 문제 3-1 · 판정 서버 로그와 SaaS 로그를 공통 이벤트로 바꾸기

- (가) 실행한 출력 전체를 붙여 넣고, 판정 서버와 SaaS 이벤트의 수와 성공 · 실패별 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 판정 서버 이벤트 수와 성공 · 실패별 개수 ③ SaaS 이벤트 수와 성공 · 실패별 개수
  - 답: 판정 서버 이벤트는 15개였고 성공 6개, 실패 9개였다. SaaS 이벤트는 14개였고 성공 13개, 실패 1개였다. 판정 서버 첫 이벤트의 시각은 `2026-11-02T09:40`에서 `2026-11-02 09:40:00`으로 바뀌었으며, 원본에 없는 IP는 `None`으로 남았다. SaaS 첫 이벤트에서는 이메일 `jiwoo@a-corp.example`에서 이름 `jiwoo`를 꺼내고, `failure`를 실패로 바꾼 것을 확인했다. 원본 모양은 달라도 두 이벤트 모두 `time`, `source`, `user`, `ip`, `action`, `result`, `raw`의 일곱 항목으로 정리됐다.

```text
--- 단계 1: 판정 서버 이벤트 15 개
{'성공': 6, '실패': 9}
--- 단계 2: SaaS 이벤트 14 개
{'실패': 1, '성공': 13}
--- 단계 3: 각 로그의 첫 이벤트
{'time': '2026-11-02 09:40:00', 'source': 'server', 'user': 'seoyeon', 'ip': None, 'action': 'SALES:QUERY', 'result': '성공', 'raw': '{"time": "2026-11-02T09:40", "user": "seoyeon", "permission": "SALES:QUERY", "network": "office", "allowed": true, "reason": "역할 권한"}'}
{'time': '2026-11-02 02:14:08', 'source': 'saas', 'user': 'jiwoo', 'ip': '203.0.113.80', 'action': 'login', 'result': '실패', 'raw': {'time': '2026-11-02 02:14:08', 'account': 'jiwoo@a-corp.example', 'event': 'login', 'ip_address': '203.0.113.80', 'outcome': 'failure'}}
```

- (나) 🔍 판정 서버 로그에는 접속 주소가 없어서 `ip` 를 `None` 으로 두었습니다. `None` 대신 가짜 주소 `0.0.0.0` 을 넣으면 주소별로 셀 때 어떤 문제가 생길까요? 이유도 함께 적어 주세요.
  - 쓸 내용: ① 가짜 주소를 넣으면 생기는 문제 ② 그 이유
  - 답: IP를 모르는 이벤트에 임의로 `0.0.0.0`을 넣으면, 주소별 집계에서 같은 주소로 여러 요청이 발생한 것처럼 묶인다. 이번 판정 서버 이벤트 15개에 모두 이 값을 넣으면 해당 주소에서 요청 15건이 발생한 것처럼 보일 수 있다. 하지만 원본에는 IP가 없어서 실제로 같은 주소인지 알 수 없다. 접속 위치가 `office`라고 적혀 있어도 정확한 IP를 알아낼 수는 없으므로, 없는 정보는 `None`으로 남겨야 한다.

- (다) 🔍 정규화하면서 공통 이벤트의 키에 들어가지 않은 정보를 판정 서버 로그에서 찾아 적고, 그 정보를 나중에 어디서 찾을 수 있는지 적어 주세요.
  - 쓸 내용: ① 공통 이벤트의 키에 들어가지 않은 정보 ② 그 정보를 나중에 찾을 수 있는 곳
  - 답: 판정 서버의 접속 위치 `network`와 판정 이유 `reason`은 공통 이벤트의 별도 항목에 들어가지 않았다. 첫 이벤트의 `result`에서는 성공 여부만 보이지만, `raw`의 원래 JSON 줄을 보면 `network`가 `office`이고 `reason`이 `역할 권한`이었다는 것을 확인할 수 있다. 공통 항목으로 전체 기록을 비교하고, 더 자세한 이유가 필요할 때 원본을 다시 보는 방식으로 이해했다.

## 4교시 · 세 로그를 하나로 합쳐 시간순으로 저장하기

### 문제 4-1 · 세 로그의 이벤트를 합쳐 시간순으로 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, 소스별 이벤트 수와 `user` · `ip` 가 비어 있는 이벤트 수, 저장된 이벤트 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 소스별 이벤트 수 ③ `user` · `ip` 가 비어 있는 이벤트 수 ④ 저장된 이벤트 수
  - 답: 소스별 이벤트는 SaaS 14개, 웹 서버 28개, 판정 서버 15개로 총 57개였다. `user`가 `None`인 이벤트는 28개, `ip`가 `None`인 이벤트는 15개였다. 합친 이벤트 수는 `28 + 15 + 14 = 57`로 앞 교시에서 확인한 개수와 일치했다. 실행 파일이 `normalized_events.json`을 저장하고 다시 읽은 결과도 57개여서, 저장 전후의 이벤트 수가 맞는 것을 확인했다. 57개는 파일의 줄 수가 아니라 저장된 이벤트 개수라는 점도 설명을 통해 정리했다.

```text
--- 단계 1: 소스별 이벤트 수
{'saas': 14, 'web': 28, 'server': 15}
--- 단계 2: 값이 None 인 이벤트 수
user 가 비어 있는 이벤트 28 개
ip 가 비어 있는 이벤트 15 개
--- 단계 3: gaeun 의 이벤트를 시간순으로
2026-11-02 10:05:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:09:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:12:55 saas login 성공
2026-11-02 10:14:00 server ACCOUNT:CHANGE 실패
2026-11-02 16:10:00 server SALES:QUERY 성공
--- 단계 4: 저장한 파일 normalized_events.json
저장된 이벤트 57 개
```

- (나) 🔍 단계 3의 gaeun 이벤트를 시간순으로 보고, 서로 다른 소스에서 나온 이벤트가 어떻게 이어지는지 적고, 로그를 따로 볼 때와 무엇이 달라지는지 적어 주세요.
  - 쓸 내용: ① 여러 소스에 걸친 이벤트의 순서 ② 로그를 따로 볼 때와 달라지는 점
  - 답: gaeun의 기록은 10:05:00과 10:09:00의 판정 서버 `ACCOUNT:CHANGE` 실패, 10:12:55의 SaaS 로그인 성공, 10:14:00의 판정 서버 `ACCOUNT:CHANGE` 실패, 16:10:00의 판정 서버 `SALES:QUERY` 성공 순서였다. 로그를 따로 보면 로그인과 권한 요청을 각각 확인해야 하지만, 합친 결과에서는 로그인 전후에 어떤 요청이 있었는지 이어서 볼 수 있었다. SaaS 로그인 뒤에도 계정 변경 권한 요청은 실패했다. 마지막에 성공한 것은 다른 권한인 `SALES:QUERY`이므로, 계정 변경 권한 문제까지 해결됐다고 판단하면 안 된다는 점을 배웠다.

- (다) 🔍 `user` 가 비어 있는 이벤트가 28개입니다. 어느 로그(소스)의 이벤트이고 왜 비어 있는지 적어 주세요. 그리고 사용자 이름별로 개수를 세면 이 28개가 어떻게 될지 예상해 적어 주세요.
  - 쓸 내용: ① 비어 있는 이벤트의 로그(소스)와 이유 ② 사용자 이름별로 셀 때의 예상
  - 답: `user`가 비어 있는 28개는 웹 서버 로그에서 정규화한 이벤트다. 원본에 사용자 이름이 없어서 임의의 이름을 넣지 않고 `None`으로 남겼다. 사용자 이름별로 집계하면 이 28개를 seoyeon이나 gaeun 같은 특정 사용자의 건수에 포함할 수 없다. 집계 방식에 따라 사용자 미상으로 따로 묶이거나 제외될 수 있으므로, 사용자 정보가 없는 건수도 함께 살펴봐야 한다. 이 이벤트들이 삭제된 것은 아니어서 전체 57개에는 남아 있고, IP별·시간별·결과별 분석에는 사용할 수 있다.
