## 5교시 · 정규화된 이벤트를 표로 읽고 실패만 골라 세기

### 문제 5-1 · 정규화된 이벤트 표를 읽어 실패한 이벤트를 소스별로 세기

- (가) 실행한 출력 전체를 붙여 넣고, 표의 행 수와 열 수, 성공과 실패 개수, 실패한 이벤트의 소스별 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 행 수 · 열 수와 성공 · 실패 개수 ③ 소스별 실패 개수
  - 답: 내 실행 결과의 표 크기는 `(57, 7)`로, 이벤트 57개와 열 7개였다. 처음 세 시각은 `2026-11-02 02:14:08`, `2026-11-02 09:01:05`, `2026-11-02 09:01:06`이었다. 성공은 34개, 실패는 23개였고, 실패만 소스별로 세면 web 13개, server 9개, saas 1개로 합계 23개였다. 전체 소스별 개수도 web 28개, server 15개, saas 14개로 합계 57개였다. 교재는 `raw`를 뺀 6열 샘플을 사용하지만, 나는 오전에 만든 파일을 이어 사용해 7열이 나온 것으로 이해했다. 보고서에는 교재의 숫자로 바꾸지 않고 내 실제 출력인 7열을 적었다.

    실행 준비에서는 가상환경과 실행 위치 때문에 여러 번 막혔다. 처음 상위 폴더에 `.venv`가 없어 새로 만들고 판다스를 설치했지만, VS Code 실행 버튼은 `anomaly_detection/.venv`의 파이썬을 사용해 `ModuleNotFoundError`가 났다. 하위 환경에도 판다스를 설치하니 실행됐고, 이후에는 수업 안내에 맞춰 상위 `.venv`를 사용하도록 통일했다. Windows 경로를 Bash에 그대로 입력한 오류도 겪었고, AI의 안내를 받아 VS Code의 인터프리터 선택창에서 상위 파이썬을 지정했다. 그다음에는 `normalized_events.json`을 찾지 못했는데, 실행 기준 폴더가 프로젝트 상위여서 생긴 문제였다. `Execute In File Dir` 설정을 적용한 뒤 실행 버튼으로도 정상 동작하는 것을 확인했다. 파이썬 환경과 데이터 파일을 찾는 기준 폴더가 서로 다른 설정이라는 점을 설명을 통해 정리했다.

```text
--- 단계 1: 표 크기(행 수, 열 수)와 처음 3개 시각
(57, 7)
2026-11-02 02:14:08
2026-11-02 09:01:05
2026-11-02 09:01:06
--- 단계 2: 성공 · 실패별 개수
result
성공    34
실패    23
Name: count, dtype: int64
--- 단계 3: 실패한 이벤트 23 개의 소스별 개수
source
web       13
server     9
saas       1
Name: count, dtype: int64
--- 단계 4: 전체 이벤트의 소스별 개수
source
web       28
server    15
saas      14
Name: count, dtype: int64
```

- (나) 🔍 실패 개수만 보면 web 이 가장 많습니다. 그렇다면 web 이 가장 문제가 큰 소스라고 말할 수 있을까요? 단계 4의 전체 이벤트 수와 함께 보고 이유를 적어 주세요.
  - 쓸 내용: ① 말할 수 있는지 없는지 ② 소스마다 전체 이벤트 수가 다르다는 것을 근거로 한 이유
  - 답: 실패 개수만 보고 web이 가장 문제가 큰 소스라고 말할 수는 없다. web은 전체 28개 중 13개가 실패했고, server는 15개 중 9개, saas는 14개 중 1개가 실패했다. 실패율은 각각 약 46.4%, 60%, 약 7.1%여서, 건수는 web이 많지만 비율은 server가 더 높다. 소스마다 전체 이벤트 수가 다르므로 실패 건수와 비율을 함께 봐야 한다. 또 권한 없는 요청을 정상적으로 거부한 경우도 실패로 표시될 수 있으므로, 비율만으로 위험도를 확정하지 않고 실패 이유도 살펴봐야 한다고 이해했다.

- (다) 🔍 web 이벤트에는 `user` 가 비어 있습니다. 사용자 이름으로 실패를 세려 할 때 web 의 실패 13개는 어떻게 될지 예상하고, 사용자 대신 어떤 열을 보면 같은 대상이 반복했는지 알 수 있을지 이유와 함께 적어 주세요.
  - 쓸 내용: ① 사용자 이름으로 셀 때 web 실패 13개가 어떻게 될지 ② 대신 볼 열과 그 이유
  - 답: web의 실패 13개에는 사용자 이름이 없어서 특정 사용자의 실패 횟수에 포함할 수 없다. 이번처럼 기본 설정의 `value_counts()`를 사용하면 결측값은 집계에서 제외되므로, 사용자별 숫자에 이 13개가 잡히지 않을 것으로 예상했다. 대신 `ip` 열로 같은 접속 주소에서 실패가 반복됐는지 살펴볼 수 있다. `action`과 `time`도 함께 보면 어떤 요청이 어느 시각에 반복됐는지 확인할 수 있다. 다만 같은 IP를 여러 사람이 사용할 수도 있으므로, 같은 주소라는 이유만으로 같은 사람이라고 단정하면 안 된다.

## 6교시 · 실패를 사용자별 · 시간대별로 묶어 세고 저장하기

### 문제 6-1 · 실패한 이벤트를 사용자별 · 시간대별로 묶어 세고 CSV 로 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, 실패가 가장 많은 사용자와 횟수, 실패가 가장 많이 난 시간대와 횟수, 저장된 행 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 실패가 가장 많은 사용자와 횟수 ③ 가장 많이 난 시간대와 횟수 ④ 저장된 행 수
  - 답: 사용자별 실패 횟수는 dami 4개, gaeun 3개, seoyeon 2개, jiwoo 1개였다. 사용자 이름이 있는 실패 중에서는 dami가 4개로 가장 많았다. 시간대별로는 2시대 1개, 9시대 13개, 10시대 3개, 11시대 5개, 18시대 1개였고, 가장 많은 시간대는 9시대였다. 실행 파일이 `failed_events.csv`를 저장하고 다시 읽은 결과는 23행으로, 5교시의 전체 실패 23개와 일치했다. 저장된 것은 사용자별 요약표가 아니라 실패 이벤트의 상세 기록이라는 점도 설명을 통해 정리했다.

```text
--- 단계 1: 사용자별 실패 횟수
user
dami       4
gaeun      3
seoyeon    2
jiwoo      1
dtype: int64
--- 단계 2: 시간대별 실패 횟수
hour
2      1
9     13
10     3
11     5
18     1
dtype: int64
--- 단계 3: 저장한 파일 failed_events.csv
저장된 행 23 개
```

- (나) 🔍 시간대별 결과에서 실패가 가장 많이 난 시간대의 개수를 보세요. 이 개수는 5교시 단계 3의 어느 소스 개수와 같은가요? 그 실패가 어느 소스에서 났는지 적고(근거는 숫자가 같다는 것까지 쓰면 됩니다), 이어서 확인할 것도 적어 주세요.
  - 쓸 내용: ① 많이 난 실패가 어느 소스에서 난 것인지와 그 근거 ② 이어서 확인할 것
  - 답: 실패가 가장 많은 9시대의 13개는 5교시에서 확인한 web의 실패 13개와 같다. 교재 샘플 기준으로 이 시간에 몰린 실패는 web의 기록에 해당한다. 다음에는 `failed_events.csv`에서 `hour`가 9인 행의 `source`가 web인지 직접 대조하고, `ip`, `action`, 정확한 시각을 살펴보고 싶다. 같은 IP가 로그인이나 관리자 경로를 짧은 간격으로 반복 요청했는지 확인할 것이다. 숫자가 같다는 것은 확인할 단서이며, 일반적으로 건수 일치만으로 같은 이벤트 집단이라고 확정할 수는 없다고 배웠다.

- (다) 🔍 사용자별 실패 횟수를 모두 더하면 실패한 이벤트 전체보다 적습니다. 몇 개가 모자라고 왜 모자란지 적어 주세요. 그리고 이 차이를 모르고 사용자별 숫자만 보면 어떤 잘못된 판단을 할 수 있을지도 적어 주세요.
  - 쓸 내용: ① 몇 개가 모자란지 ② 모자란 이유 ③ 모르고 넘어가면 생기는 잘못된 판단
  - 답: 사용자별 실패 횟수를 더하면 `4 + 3 + 2 + 1 = 10`개여서 전체 실패 23개보다 13개 적다. 원래 사용자 이름이 없는 web 실패 13개를 기본 설정의 `groupby("user")`가 제외했기 때문이다. 이벤트가 삭제된 것은 아니므로 시간대별 집계와 CSV 저장 결과에는 23개가 모두 포함됐다. 이 차이를 모르고 사용자별 숫자만 보면 전체 실패가 10개뿐이라고 생각하거나, 이름을 알 수 있는 사용자만 살펴보다 웹 실패 13개를 놓칠 수 있다. 전체 실패 수와 사용자별 집계 합계를 함께 확인해야 한다고 이해했다.
