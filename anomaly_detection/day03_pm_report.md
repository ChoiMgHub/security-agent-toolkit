### 문제 5-1 · 웹 서버 요청을 분마다 세어 요청이 급증한 분 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 급증 기준과 요청이 급증한 분(시각과 요청 수)을 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 급증 기준 ③ 요청이 급증한 분과 요청 수
  - 답:

교재의 연습용 이벤트를 대상으로 `day03_5-1_run.py`를 실행했다. 지난 7일 기준 자료의 분당 평균은 `(2 + 2 + 3 + 2 + 1 + 2 + 2) / 7 = 2.0`건이고, 여기에 3을 곱해 급증 기준을 **1분에 6.0건 이상**으로 정했다.

실행 결과 **2026-11-02 09:12의 웹 요청 9건**이 기준 이상으로 탐지됐다. 탐지된 분은 한 곳이며, 나머지 분의 요청 수는 모두 6건보다 적었다. 09:12의 9건은 09:12:00부터 09:12:59 사이의 요청 수를 뜻한다.

출력의 `time`과 `minute`을 비교하면 09:01:05와 09:01:06이 모두 09:01:00으로 묶인다. 원래 시각을 보관하면서 집계용 열을 추가한 것이다. 웹 요청만 분별로 집계한 결과는 총 28건이며, 성공과 실패를 모두 포함한다.

## 6교시 · 알림을 한 파일로 모으기

### 문제 6-1 · 로그인 실패 알림과 트래픽 급증 알림을 alerts.json 한 파일로 모으기

- (가) 실행한 출력 전체를 붙여 넣고, `alerts.json` 의 내용도 붙여 넣은 뒤 알림이 모두 몇 건인지 적어 주세요.
  - 쓸 내용: ① 출력 전체(첫 번째 코드 상자에 붙여 넣기) ② `alerts.json` 내용(두 번째 코드 상자에 붙여 넣기) ③ 알림 건수
  - 답:

`day03_6-1_run.py`를 실행해 **로그인 실패 알림 1건과 트래픽 급증 알림 1건, 총 2건**을 `alerts.json`에 저장했다. 마지막 단계에서는 저장한 파일을 다시 읽어 두 알림이 출력되는 것을 확인했다. 두 알림 모두 `type`, `target`, `count`, `note`, `status`의 다섯 항목을 가지고 있으며, 상태는 모두 **확인 필요**이다.

로그인 실패 알림의 대상은 `203.0.113.50`, 횟수는 5건이고, 트래픽 급증 알림의 대상은 `2026-11-02 09:12:00`, 횟수는 9건이다. 이벤트 횟수와 알림 건수는 다르다. 여러 이벤트를 집계한 결과로 각각 알림 한 건을 만들었기 때문에 알림은 총 2건이다. 로그인 실패 5건은 해당 분의 웹 요청 9건에 포함되므로 두 수를 더해 서로 다른 이벤트 14건으로 해석하지 않는다.

첫 번째 코드 상자는 내가 공유한 실행 출력이다. 두 번째 JSON은 저장한 알림의 내용이다. 업로드 후 AI가 GitHub의 `alerts.json` 원본을 직접 읽어 보고서의 JSON과 대조했고, 두 알림의 전체 내용이 일치함을 확인했다. AI가 업로드된 코드와 데이터를 별도 환경에서 재실행해 생성한 알림도 GitHub 원본과 일치했다.

다만 공격 여부나 동일 인물의 행동이라고 확정한 것은 아니다. 성공한 로그인 계정과 접속 사유 등을 더 확인해야 한다. 또한 함께 조사한다는 것은 근거를 연결해서 살펴본다는 뜻이다. 이번 코드는 알림 두 건을 한 파일에 모았을 뿐 자동으로 사건을 통합하지 않으며, 알림 하나를 삭제하거나 횟수를 합치는 것도 아니다.


- (다) 🔍 203.0.113.50 알림을 조사해 보니 직원이 비밀번호를 잊어 반복해서 입력한 것이었습니다. ① `status` 를 어떤 값으로 바꿀지(안내 문서 6.1 의 처리 상태 순서를 참고), ② `note` 에 무엇을 더 적을지, ③ 알림을 지우지 않고 남겨 두는 편이 좋은 이유를 적어 주세요. 코드는 고치지 않고 글로만 적습니다.
  - 쓸 내용: ① 바꿀 `status` 이름 ② `note` 에 더 적을 내용 ③ 알림을 남겨 두는 이유
  - 답:

이 문항은 직원이 비밀번호를 잊어 반복 입력한 것으로 조사됐다는 **가정에 대한 답**이다. 실제로 내가 직원을 조사하거나 원인을 확인한 것은 아니다.

문제에서 제시한 원인 확인이 끝났다면 해당 로그인 실패 알림의 `status`를 **조사 완료**로 바꾸겠다. `note`에는 기존 탐지 이유를 남기고 **“직원이 비밀번호를 잊어 반복 입력한 것으로 확인됨”**이라는 조사 결과를 추가하겠다. 실제 기록에서는 확인한 담당자와 날짜도 함께 적되, 지금은 그 정보가 제시되지 않았으므로 임의로 넣지 않는다.

알림을 지우지 않으면 왜 탐지됐고 어떤 조사 결과로 처리를 마쳤는지 이력을 확인할 수 있다. 같은 IP에서 다시 알림이 발생했을 때 이전 결과를 참고할 수도 있다. 다만 이전에 정상적인 사유로 발생했다는 이유만으로 다음 알림도 정상이라고 단정하지는 않겠다.

‘조사 완료’는 공격 여부가 아니라 확인 절차를 마쳤다는 상태이고, 구체적인 결과는 `note`에 남긴다. 이 문항은 글로만 답하는 문제이므로 실제 `alerts.json`의 상태를 변경했다고 기록하지 않는다.

  - 답:

오늘 실습 파일을 GitHub에 업로드한 뒤, `anomaly_detection` 폴더에서 아래 세 명령을 실행해 상태를 다시 확인했다.

`git status`에는 `Your branch is up to date with 'origin/main'.`과 `nothing to commit, working tree clean`이 출력됐다. 확인한 시점에 로컬 `main`은 `origin/main`과 동기화돼 있었고, 추가로 커밋할 변경 사항은 없었다. `.env`나 `.venv`도 변경·미추적 항목으로 표시되지 않았다.

`git ls-files -- .env .venv __pycache__`는 출력이 없었다. 확인한 세 경로가 Git 추적 대상에 포함돼 있지 않다는 뜻이다. `git check-ignore -v`에서는 `.gitignore`의 1행, 2행, 4행 규칙으로 각 항목이 제외되는 것을 확인했다. 이미 제외 설정이 적용돼 있어, 이번 재확인에서는 추가로 제외 설정을 바꾸거나 추적을 해제할 필요가 없었다.

실제 실행 결과는 다음과 같다. 두 번째 명령 뒤에는 출력 없이 다음 프롬프트가 나타났다.

```text
$ git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

$ git ls-files -- .env .venv __pycache__

$ git check-ignore -v .env .venv __pycache__
.gitignore:1:.env       .env
.gitignore:2:.venv      .venv
.gitignore:4:__pycache__        __pycache__
```

업로드 결과는 AI의 GitHub 직접 검수로도 확인했다. `ChoiMgHub/security-agent-toolkit` 저장소의 `anomaly_detection` 폴더에 실습 코드, 기준 CSV, 오전·오후 보고서, `alerts.json`이 올라가 있었다. 검수한 실습 커밋은 [`131dacc7`](https://github.com/ChoiMgHub/security-agent-toolkit/commit/131dacc7cb4929f90f5dfbc0bab4a00646e771b2)이다. 해당 커밋의 저장소 파일 목록에는 `.env`, `.venv`, `__pycache__`, `.pyc`가 포함돼 있지 않았다.
