## 2교시 · 서버가 거절한 요청 중 반복된 것을 찾고 이유로 순서 정하기

### 문제 2-1 · 서버가 거절한 요청 중 반복된 것을 찾고 이유로 순서 정하기

- (가) 실행한 출력 전체를 붙여 넣고, 서버 실패 수와 먼저 확인할 이벤트 수, 1순위 사용자를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 서버 실패 수 ③ 먼저 확인할 이벤트 수 ④ 1순위 사용자
  - 답:

교재의 가상 로그를 대상으로 `day04_2-1_run.py`를 실행했다. 판정 서버의 실패 이벤트는 **9건**, 실패가 3건 이상인 사용자의 기록은 **7건**이었다. 먼저 확인할 사용자는 dami와 gaeun 두 명이고, **1순위 사용자는 dami**였다.

| 사용자 | 서버 실패 횟수 | 3건 이상 여부 | 선택된 이벤트 |
|---|---:|---|---:|
| dami | 4건 | 해당 | 4건 |
| gaeun | 3건 | 해당 | 3건 |
| seoyeon | 2건 | 해당 없음 | 0건 |

사용자별 집계는 행동 종류와 관계없이 실패를 합친다. dami의 매출 조회 실패 3건과 매출 변경 실패 1건은 합쳐 4건이다. 사용자 두 명을 고른 뒤 그 사용자의 실패 기록 전체를 가져오므로 결과는 2건이 아닌 7건이 된다.

출력 첫 숫자는 실패 횟수가 아니라 우선순위다. 11시대 dami가 10시대 gaeun보다 앞에 나온 것은 시간순보다 우선순위를 먼저 적용했기 때문이다. 실행 출력은 내가 채팅에 공유한 결과이며, 규칙 해석과 문항 답변 정리는 교재 샘플을 대조한 AI의 설명을 지원받았다.

```text
--- 단계 1: 판정 서버의 실패 이벤트 9 개
--- 단계 2: 먼저 확인할 실패 이벤트 7 개
--- 단계 3: 우선순위
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:02:00
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:03:00
1 퇴사한 계정 dami SALES:CHANGE 2026-11-02 11:05:00
1 퇴사한 계정 dami SALES:QUERY 2026-11-02 11:08:00
3 규칙은 허용인데 서버가 거절 gaeun ACCOUNT:CHANGE 2026-11-02 10:05:00
3 규칙은 허용인데 서버가 거절 gaeun ACCOUNT:CHANGE 2026-11-02 10:09:00
3 규칙은 허용인데 서버가 거절 gaeun ACCOUNT:CHANGE 2026-11-02 10:14:00
```

- (나) 🔍 ① dami 의 실패 4개는 3과목(접근통제) 규칙으로 어떤 이유로 판정됐고, 왜 1순위일까요? ② gaeun 의 실패 3개는 규칙으로는 「허용」인데 서버가 거절했습니다. 공격이라고 확정할 수 있는지 적고, 먼저 무엇을 확인해야 하는지 적어 주세요.
  - 쓸 내용: ① dami 의 판정 이유와 1순위인 까닭 ② 공격이라고 확정할 수 있는지와 먼저 확인할 것
  - 답:

dami의 요청 4건은 모두 **퇴사한 계정**으로 재판정됐다. 교재의 사용자 설정에서 dami는 `employed: false`이고, `check_permission`은 역할별 권한을 검사하기 전에 재직 여부부터 확인한다. sales 역할에 매출 조회·변경 권한이 있어도 재직 여부 검사에서 먼저 거절되는 것이다. 퇴사한 계정으로 요청이 반복된 경위와 계정 정리 상태를 우선 확인해야 하므로 교재에서는 1순위로 정했다.

gaeun은 재직 중인 account_admin 역할이고, 그 역할의 권한 목록에는 `ACCOUNT:CHANGE`가 있다. 그래서 제공된 사용자·역할 규칙으로 다시 판단하면 허용이 나오지만, 원래 서버 로그에는 실패가 기록돼 있다. 이 차이만으로 공격이라고 확정할 수는 없다. 당시 서버에 적용된 사용자·역할 설정이 재판정에 사용한 설정과 같은지, 추가 제한 조건이나 서버 설정 문제가 있었는지 먼저 확인해야 한다.

재판정의 ‘허용’은 당시 요청이 실제로 성공했다는 뜻이 아니다. 현재 제공된 규칙으로 계산한 결과이며, 원래 서버가 거절한 정확한 원인을 직접 알아낸 것은 아니다. 이번에는 판정 결과를 출력했으며, 실제 계정을 정리하거나 서버 설정을 변경한 것은 아니다.

- (다) 🔍 seoyeon 의 서버 실패 2건(11:40 `SETTLE:QUERY` · 18:20 `SALES:CHANGE`)은 먼저 확인할 이벤트에 들어가지 않았습니다. 들어가지 않은 이유를 오늘 규칙(실패 3번 이상)으로 설명하고, 이 규칙 때문에 놓칠 수 있는 경우를 한 가지 적어 주세요.
  - 쓸 내용: ① 먼저 확인할 이벤트에 들어가지 않은 이유 ② 이 규칙이 놓칠 수 있는 경우 한 가지
  - 답:

seoyeon의 서버 실패는 11:40의 `SETTLE:QUERY`와 18:20의 `SALES:CHANGE`, 총 **2건**이다. 행동은 달라도 사용자 기준으로 함께 세지만, `2 >= 3`은 거짓이므로 먼저 확인할 이벤트에서 제외됐다.

이 규칙은 적은 횟수로 발생한 중요한 요청을 놓칠 수 있다. 예를 들어 퇴사한 계정이 한두 번만 요청한다면, 권한 규칙으로는 우선 확인할 사유가 있어도 반복 횟수가 부족해 선택되지 않는다. 이는 규칙의 한계를 설명하기 위한 가정이다.

처리 순서가 ‘3건 이상인 사용자 선택 → 선택한 이벤트 재판정’이므로, 앞에서 제외된 요청은 우선순위를 붙이는 단계까지 가지 않는다. 따라서 제외됐다는 사실만으로 정상이나 안전을 확인한 것은 아니다.

## 3교시 · SaaS 로그에서 이상 사용 세 가지 찾기

### 문제 3-1 · SaaS 로그에서 이상 사용 세 가지 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 규칙마다 해당한 사용자를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 업무 시간 밖 로그인 사용자 ③ 평소와 다른 IP 사용자 ④ 대량 다운로드 사용자
  - 답:

`day04_3-1_run.py`를 실행한 결과는 다음과 같았다.

| 규칙 | 해당 사용자 | 확인 내용 |
|---|---|---|
| 업무 시간 밖 로그인 | **jiwoo** | 2026-11-02 02:14:08의 로그인 시도 1건, 결과는 실패 |
| 평소와 다른 IP | **jiwoo, seoyeon** | 각 사용자의 설정된 평소 IP와 다른 IP에서 로그인 시도 |
| 파일 다운로드 5건 이상 | **seoyeon** | 사용자별 다운로드 횟수가 기준 이상 |

업무 시간은 시(hour)가 8 이상 20 이하일 때로 정하므로 20:59까지 포함하고, 02:14는 업무 시간 밖이다. 로그인 선택에서 성공 여부를 제한하지 않아 실패한 시도도 시간·IP 검사에 포함된다.

다운로드 출력에는 사용자 이름만 나오지만, 교재 샘플에서는 seoyeon이 11:25에 1건, 17:40~17:42에 5건을 내려받아 합계 6건이다. 이번 함수는 샘플 전체의 다운로드를 사용자별로 세며 연속 여부나 파일 용량을 검사하지 않는다. 세 규칙은 각각 따로 적용하므로 같은 기록이나 사용자가 둘 이상에 해당할 수 있다.

```text
--- 단계 1: 업무 시간 밖 로그인 1 건
                  time source   user            ip action result
0  2026-11-02 02:14:08   saas  jiwoo  203.0.113.80  login     실패
--- 단계 2: 평소와 다른 IP 로 로그인한 사용자 ['jiwoo', 'seoyeon']
--- 단계 3: 파일을 5번 이상 내려받은 사용자 ['seoyeon']
```

- (나) 🔍 jiwoo 는 업무 시간 밖(02:14)과 평소와 다른 IP 두 규칙에 해당하지만 그 로그인은 실패였습니다. 이 기록만으로 계정 도용을 확정할 수 있나요? 그렇게 판단한 이유와, 샘플 로그에서 더 찾아볼 수 있는 것을 한 가지 적어 주세요.
  - 쓸 내용: ① 도용이라고 확정할 수 있는지 없는지 ② 더 확인할 정보 한 가지
  - 답:

이 기록만으로 jiwoo의 계정이 도용됐다고 확정할 수는 없다. 02:14:08에 평소 IP인 198.51.100.52와 다른 203.0.113.80에서 시도가 있었지만, 결과는 **실패**였다. 로그인에 성공해 계정에 접근했다는 근거가 아니며, 누가 시도했는지도 확인되지 않았다.

추가로 같은 사용자의 다른 로그인 시각·IP·결과를 찾아볼 수 있다. 교재 샘플에는 같은 날 16:02:18에 jiwoo가 평소 IP인 198.51.100.52에서 로그인에 성공한 기록이 있다. 이 기록을 새벽 시도와 비교할 수 있지만, 오후의 성공만으로 새벽 시도까지 정상이라고 단정할 수는 없다.

이 비교는 교재 샘플과 해설을 대조한 내용이다. 실제 사용자의 신원이나 접속 사유를 조사해 도용 여부를 확인한 것은 아니다.

- (다) 🔍 gaeun 은 평소 IP 기록이 없어 「평소와 다른 IP」 규칙에서 제외됩니다. 제외하지 않으면 어떤 일이 생기고, 제외하면 어떤 위험이 남나요?
  - 쓸 내용: ① 제외하지 않을 때 생기는 일 ② 제외했을 때 남는 위험
  - 답:

gaeun은 `USUAL_IPS`에 평소 IP가 없어 조회 결과가 `None`이다. 기준이 있는지 확인하지 않고 현재 IP인 198.51.100.77과 비교하면, IP가 `None`과 다르다는 이유만으로 ‘평소와 다른 IP’로 선택된다. 실제로 평소와 달랐는지 판단한 것이 아니므로 정상적인 접속도 불필요한 확인 대상으로 잡힐 수 있다.

반대로 제외하면 비교 근거 없는 탐지를 피할 수 있지만, 다른 사람이 gaeun의 계정을 쓰더라도 이 IP 비교 규칙으로는 발견하지 못할 위험이 남는다. 제외는 정상 판정이 아니라 **비교할 기준이 없어 이 규칙으로 판단하지 못한 것**이다.

코드는 평소 IP가 있는지(`is not None`)와 현재 IP가 다른지(`!=`)를 함께 확인한다. gaeun은 IP 비교에서만 제외되며, 업무 시간 밖 로그인과 다운로드 규칙에는 그대로 포함된다.

## 4교시 · 웹 실패 로그에서 경로를 스캔한 IP 찾기

### 문제 4-1 · 웹 실패 로그에서 경로를 스캔한 IP 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 스캔으로 본 IP 와 이유를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 스캔으로 본 IP ③ 이유
  - 답:

`day04_4-1_run.py`의 실행 결과 웹 서버 실패는 **13건**이었다. 그중 스캔으로 본 IP는 **198.51.100.90** 한 곳이며, 출력된 이유는 **‘스캐너 경로를 3번 요청’**이다.

교재 샘플에서 해당 요청은 다음과 같다. 모두 2026-11-02에 발생했고 실패로 기록됐다.

| 시각 | IP | 요청 |
|---|---|---|
| 09:20:10 | 198.51.100.90 | `GET /.env` |
| 09:20:11 | 198.51.100.90 | `GET /wp-login.php` |
| 09:20:12 | 198.51.100.90 | `GET /phpmyadmin` |

세 요청이 `SCANNER_PATTERN`에 해당해 선택됐다. 이번 규칙에는 최소 횟수 조건이 없어, 3번이라서 선택된 것이 아니라 지정한 패턴에 맞는 실패 요청이 있었기 때문에 선택된 것이다. 이 결과만으로 공격 의도나 침입 성공까지 확정할 수는 없다. 패턴에 해당하지 않은 실패 10건을 보낸 다른 IP 네 곳은 결과에서 제외됐다.

이어 `advanced_detection.py`도 실행했다. 서버 반복 실패 7건, SaaS의 업무 시간 밖 jiwoo·다른 IP jiwoo와 seoyeon·대량 다운로드 seoyeon, 웹 스캔 IP 198.51.100.90이 출력돼 각 교시에서 확인한 결과와 맞았다. 이 출력에는 이벤트 수·사용자 목록·IP 목록이 섞여 있으므로 모두 더해 탐지 건수로 해석하지 않는다. 아래에는 두 프로그램의 실제 출력을 구분해 옮겼다.

```text
$ python day04_4-1_run.py
--- 단계 1: 웹 서버의 실패 이벤트 13 개
--- 단계 2: 스캐너 경로를 요청한 IP 와 횟수
ip
198.51.100.90    3
Name: count, dtype: int64
--- 단계 3: 스캔으로 본 IP 와 이유
{'ip': '198.51.100.90', 'reason': '스캐너 경로를 3번 요청'}
--- 단계 4: 스캐너 경로가 없어 제외한 IP
203.0.113.50
198.51.100.21
198.51.100.34
198.51.100.77

$ python advanced_detection.py
판정 서버: 먼저 확인할 실패 이벤트 7 개
SaaS: 업무 시간 밖 ['jiwoo'] · 평소와 다른 IP ['jiwoo', 'seoyeon'] · 대량 다운로드 ['seoyeon']
웹 서버: 스캔으로 본 IP ['198.51.100.90']
```

- (나) 🔍 203.0.113.50 은 실패한 요청이 7번 있지만 스캔에서 제외됐습니다. 제외된 이유와, 제외하지 않으면 담당자에게 어떤 일이 생기는지 적어 주세요.
  - 쓸 내용: ① 제외된 이유 ② 제외하지 않을 때 생기는 일
  - 답:

203.0.113.50의 실패 7건은 `POST /login` 5건, `GET /admin` 1건, `GET /admin/users` 1건이다. 하지만 이 요청들은 현재 패턴인 `/.env`, `/wp-login`, `/phpmyadmin`에 해당하지 않아 경로 스캔 결과에서 제외됐다.

실패가 많다는 이유만으로 이 IP에도 스캔 이유를 붙이면, 담당자는 로그인 실패와 특정 경로를 찾아본 요청을 구분하기 어려워진다. 불필요한 스캔 확인이 늘어날 수도 있다. 이 IP의 반복 로그인 실패는 어제의 로그인 실패 규칙에서 따로 다룬 대상이다.

같은 IP가 여러 규칙에 해당하는 것 자체가 문제는 아니지만, 각 규칙에 맞는 근거로 선택해야 한다. 이번 스캔 결과에서 제외됐다는 사실만으로 이 IP가 안전하다고 판단하지는 않는다.

- (다) 🔍 198.51.100.21 의 `GET /board/99` 실패 1건은 이 규칙에서 어떤 조건 때문에 제외되나요? 그리고 해킹 도구가 `SCANNER_PATTERN` 에 없는 경로(예: `/backup.zip`)를 요청하면 이 규칙이 탐지하지 못한다는 점을 설명해 주세요.
  - 쓸 내용: ① 한 번의 실패가 제외되는 과정 ② 목록에 없는 경로를 요청하면 탐지하지 못한다는 점
  - 답:

198.51.100.21의 `GET /board/99`는 웹 서버의 실패이므로 처음 고른 웹 실패 표에는 포함된다. 이후 `action`에 `SCANNER_PATTERN`이 포함되는지 검사할 때 해당하지 않아 `is_scanner`가 거짓이 되고, 스캐너 요청 표에서 제외된다. **실패가 한 번뿐이어서 제외된 것은 아니다.** 현재 규칙에는 요청 횟수가 몇 건 이상이어야 한다는 조건이 없다.

해킹 도구가 `/backup.zip`처럼 현재 패턴에 해당하지 않는 경로를 요청해도 그 요청은 이 규칙으로 찾아내지 못한다. 요청자의 의도를 알아서 판단하는 코드가 아니라, 지정한 패턴에 맞는 문자열을 찾는 코드이기 때문이다. 따라서 이번 결과는 정해 둔 패턴의 범위 안에서 해석해야 한다.
