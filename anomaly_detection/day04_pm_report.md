## 5교시 · 서로 다른 로그를 한 사용자 기준으로 연결해 60분 안의 사건 찾기

### 문제 5-1 · 서로 다른 로그를 한 사용자 기준으로 연결해 60분 안의 사건 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 연결된 사건의 사용자와 이유를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 연결된 사건의 사용자 ③ 이유
  - 답: `anomaly_detection` 폴더에서 오전 탐지 함수 세 묶음이 오류 없이 불러와지는지 확인한 뒤 `correlation.py`와 `day04_5-1_run.py`를 작성하고 실행했다. 실행 결과 gaeun이 한 사건으로 연결됐다. 서로 다른 로그가 3종류이고, 코드에서 계산한 첫 이벤트부터 마지막 이벤트까지의 간격이 41분이어서 ‘로그 2종류 이상’과 ‘60분 이내’라는 두 조건을 모두 만족했다. 연결 이유는 `서로 다른 로그 3종류 · 41분 안`으로 출력됐다.

```text
--- 단계 1: IP 로 사용자를 알 수 있는 웹 실패 이벤트 1 개
--- 단계 2: 사용자별로 시간순으로 놓은 이벤트 24 개
gaeun 의 이벤트 (시각 · 로그 · 행동 · 결과)
2026-11-02 09:33:51 web GET /admin 실패
2026-11-02 10:05:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:09:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:12:55 saas login 성공
2026-11-02 10:14:00 server ACCOUNT:CHANGE 실패
--- 단계 3: 60 분 안에 서로 다른 로그로 연결된 사건
{'user': 'gaeun', 'reason': '서로 다른 로그 3종류 · 41분 안'}
--- 단계 4: 로그 종류는 여럿이지만 시간 차가 60분을 초과해 연결되지 않은 사용자
{'user': 'seoyeon', 'source_count': 2, 'span_minutes': 555}
```

  사용자를 연결할 수 있는 웹 실패 이벤트는 1개였다. 판정 서버의 실패 전체 9개, SaaS 전체 14개와 이 웹 이벤트 1개를 합쳐 총 24개가 됐다. 오전에 먼저 확인 대상으로 고른 서버 이벤트 7개만 사용한 것은 아니다. 사용자별로 여러 로그의 기록을 함께 보기 위해 서버 실패 전체를 가져왔다.

  웹 로그에는 사용자 이름이 없어서 SaaS의 성공 로그인으로 만든 IP→사용자 대응표를 사용했다. 교재의 대응표에서 `198.51.100.77`은 gaeun에 연결되므로 해당 IP의 웹 이벤트에 사용자 이름을 붙일 수 있었다. 대응표에 없는 IP는 이번 사용자별 연결에서 제외됐지만, 그 기록을 정상으로 판정했다는 뜻은 아니다.

- (나) 🔍 단계 2에 나온 gaeun 의 이벤트 5개는 어느 로그(`source`)에서 왔고, 왜 한 사건으로 연결됐나요? 이 사건만으로 공격이라고 확정할 수 있는지도 적어 주세요.
  - 쓸 내용: ① gaeun 이벤트 5개의 로그(source) ② 연결된 까닭 ③ 공격이라고 확정할 수 있는지와 그 근거(단계 2 의 action · result 와 오전 2교시 판정 이유)
  - 답: gaeun의 이벤트 5개는 웹(`web`) 1개, 판정 서버(`server`) 3개, SaaS(`saas`) 1개였다. 09:33:51의 웹 `GET /admin` 실패, 10:05·10:09·10:14의 서버 `ACCOUNT:CHANGE` 실패 3개, 10:12:55의 SaaS 로그인 성공이 시간순으로 출력됐다. 이벤트는 5개지만 서로 다른 로그의 종류는 3개이므로, 이벤트 수와 로그 종류 수를 구분해야 한다.

  로그 종류가 3종류로 기준인 2종류 이상이었고, 코드의 분 단위 계산으로 처음부터 마지막까지 41분이어서 한 사건으로 연결됐다. 이 코드는 초를 제외하고 `09:33 → 573분`, `10:14 → 614분`으로 바꾼 뒤 차이를 구한다. 실제 시각 차이는 40분 9초지만 코드에서는 41분으로 출력된다.

  다만 이 결과만으로 공격이라고 확정할 수는 없다. 웹의 `/admin` 실패는 1건이고 SaaS 로그인은 성공했다. 판정 서버의 `ACCOUNT:CHANGE` 실패 3건은 오전에 현재 권한 규칙으로 다시 판정했을 때 ‘허용’으로 나왔다. 가까운 시간에 여러 로그의 활동이 확인된 것은 알 수 있지만, 서버가 당시 요청을 거절한 원인이나 공격 여부까지 밝혀진 것은 아니다. 관련 기록을 함께 살펴볼 대상으로 이해했다.

  또한 IP로 사용자 이름을 붙이는 방식은 이번 실습의 연결 기준이다. 09:33의 웹 기록에 10:12의 성공 로그인에서 얻은 IP 대응을 적용한 것이므로, 웹 요청 시각의 실제 사용자가 gaeun이었다고 별도로 인증한 결과는 아니다. 로그인 성공 기록이 나중에 있다고 해서 웹 요청이 그 뒤에 발생한 것처럼 시간순서를 바꾸지도 않았다.

- (다) 🔍 seoyeon 은 서로 다른 로그에 나오지만 연결되지 않았습니다. 단계 4 의 두 숫자(로그 종류 수와 처음부터 마지막까지의 분)로 두 조건을 비교해 연결되지 않은 이유를 설명하고, 하나의 사건으로 연결하지 않아서 탐지하지 못할 수 있는 것을 오전 3교시 출력에서 seoyeon 이 나온 규칙과 연결해 적어 주세요.
  - 쓸 내용: ① 연결되지 않은 이유(두 조건과 단계 4 의 두 숫자) ② 연결하지 않아서 탐지하지 못할 수 있는 것
  - 답: seoyeon은 `source_count: 2`로 판정 서버와 SaaS의 로그 2종류에 등장해 첫 번째 조건인 ‘서로 다른 로그 2종류 이상’을 만족했다. 하지만 `span_minutes: 555`로 첫 이벤트 09:05부터 마지막 이벤트 18:20까지의 간격이 555분이었다. 두 번째 조건인 ‘60분 이내’를 만족하지 못했으므로, 두 조건을 모두 요구하는 이번 규칙에서는 한 사건으로 연결되지 않았다.

  연결되지 않았다고 seoyeon의 이상 징후가 사라지는 것은 아니다. 오전 SaaS 분석에서는 seoyeon이 ‘평소와 다른 IP’와 ‘대량 다운로드’ 규칙에 해당했다. 이를 하나의 사건으로 연결하지 못하면 판정 서버의 `SETTLE:QUERY` 거절과 SaaS의 다른 IP 사용·대량 다운로드를 같은 사용자의 관련 활동으로 함께 파악하기 어려울 수 있다.

  이번 코드는 사용자별 전체 기록의 첫 시각과 마지막 시각을 비교한다. 긴 시간에 걸친 기록 안에서 가까운 60분 구간만 따로 찾아내는 방식은 아니다. 따라서 전체 간격이 길면 그중 일부 활동이 가까운 시간에 모여 있어도 연결 결과에서 빠질 수 있다는 한계가 있다. 실습에서는 정해진 2종류·60분 기준을 그대로 사용했다.

## 6교시 · 탐지된 규칙에 점수를 매겨 등급과 이유를 day03_risk_scores.json 에 저장하기

### 문제 6-1 · 탐지된 규칙에 점수를 매겨 등급과 이유를 day03_risk_scores.json 에 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, high · mid · low 에 각각 어떤 대상이 들어갔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② high 에 들어간 대상 ③ mid 에 들어간 대상 ④ low 에 들어간 대상
  - 답: `day04_6-1_run.py`를 실행한 결과, 탐지된 대상·규칙 조합은 8건이었고 이를 대상별로 합산해 `day03_risk_scores.json`에 5건을 저장했다는 출력이 나왔다. high에는 dami 60점, mid에는 seoyeon 45점·gaeun 40점·jiwoo 35점, low에는 198.51.100.90 30점이 들어갔다. 각 대상의 점수와 등급뿐 아니라 해당한 규칙 이름도 함께 출력됐다.

```text
--- 단계 1: 탐지된 규칙 8 건
--- 단계 2: 대상별 점수
entity
dami             60
seoyeon          45
gaeun            40
jiwoo            35
198.51.100.90    30
Name: points, dtype: int64
--- 단계 3: day03_risk_scores.json 에 5 건 저장
--- 단계 4: 등급 · 대상 · 점수 · 이유
high dami 60 ['퇴사한 계정']
mid seoyeon 45 ['평소와 다른 IP', '대량 다운로드']
mid gaeun 40 ['규칙은 허용인데 서버가 거절', '여러 로그 연결']
mid jiwoo 35 ['업무 시간 밖 로그인', '평소와 다른 IP']
low 198.51.100.90 30 ['경로 스캔']
```

  점수는 dami의 ‘퇴사한 계정’ 60점, seoyeon의 ‘평소와 다른 IP’ 20점과 ‘대량 다운로드’ 25점, gaeun의 ‘규칙은 허용인데 서버가 거절’ 10점과 ‘여러 로그 연결’ 30점, jiwoo의 ‘업무 시간 밖 로그인’ 15점과 ‘평소와 다른 IP’ 20점, 스캔 IP의 ‘경로 스캔’ 30점으로 구성됐다. 등급은 60점 이상 high, 35점 이상 60점 미만 mid, 35점 미만 low이므로 60점은 high에, 35점은 mid에 포함됐다.

  단계 1의 8건은 원본 이벤트 8개나 서로 다른 규칙 이름 8종류를 뜻하지 않는다. 중복을 제거한 대상·규칙 조합의 수로, dami 1건·seoyeon 2건·gaeun 2건·jiwoo 2건·스캔 IP 1건을 합친 값이다. 이를 사용자 4명과 IP 1개로 묶었기 때문에 최종 기록은 5건이 됐다. 출력 파일의 `day03`은 교재에서 지정한 이름이라 Day 4 실습에서도 그대로 사용했다.

- (나) 🔍 seoyeon 의 점수가 어떤 규칙의 점수를 더해 나왔는지 적고, 점수만 저장하지 않고 이유(`reasons`)를 함께 저장하는 까닭을 적어 주세요.
  - 쓸 내용: ① seoyeon 점수를 이룬 규칙과 점수 ② 이유를 함께 저장하는 까닭
  - 답: seoyeon은 ‘평소와 다른 IP’ 20점과 ‘대량 다운로드’ 25점을 더해 45점이 됐다. 35점 이상이고 60점 미만이므로 mid로 분류됐다. 같은 대상에게 같은 규칙이 여러 이벤트에서 해당해도 한 번만 반영하므로, 다운로드 이벤트 수만큼 25점을 반복해서 더하지 않았다.

  5교시에서 seoyeon은 전체 시간 간격이 555분이어서 연결되지 않았으므로 ‘여러 로그 연결’ 30점은 붙지 않았다. 또한 이번 점수 수집은 서버 실패가 3번 이상인 사용자만 가져오므로, 서버 실패가 2번인 seoyeon의 ‘권한 없음’은 점수에 들어가지 않았다. 오전 SaaS 분석의 두 규칙이 반영된 결과가 45점이다.

  점수만 저장하면 왜 45점인지, 어떤 활동을 확인해야 하는지 알기 어렵다. `reasons`에 `['평소와 다른 IP', '대량 다운로드']`를 함께 남기면 담당자가 등급이 나온 근거를 이해하고 해당 로그를 찾아볼 수 있다. 다만 여기에 저장되는 것은 규칙 이름이므로, 실제 요청 시각·행동·결과를 조사할 때는 원본 로그도 함께 확인해야 한다.

- (다) 🔍 198.51.100.90 은 경로 스캔 하나에 해당하지만 low 입니다. low 는 점수 기준상 낮은 등급이라는 뜻입니다. low 인 이유를 점수와 기준으로 설명하고, 이 IP 의 기록을 무시해도 되는지 샘플의 값(그 IP 의 요청 3개의 `result`)으로 판단해 적어 주세요.
  - 쓸 내용: ① low 인 이유(점수와 기준) ② 무시해도 되는지(오전 4교시 find_scan_ips 결과나 normalized_events.json 의 이 IP 요청 시각 · 경로 · 결과를 근거로)
  - 답: 198.51.100.90은 ‘경로 스캔’ 규칙 하나에 해당해 30점을 받았다. mid 기준인 35점보다 낮으므로 low로 분류됐다. 오전에 스캐너 경로 요청이 3개로 나왔지만, 같은 대상의 같은 규칙은 한 번만 반영하므로 30점씩 세 번 더한 90점이 아니라 30점이다.

  low라고 해서 이 기록을 무시해도 된다고 판단할 수는 없다. 오전 샘플에서 이 IP가 09:20에 요청한 `/.env`, `/wp-login.php`, `/phpmyadmin`의 결과는 모두 ‘실패’였다. 이 세 요청에서 자료 접근에 성공했다고 볼 근거는 없지만, 스캐너가 자주 찾는 경로를 요청한 사실은 남아 있다. 따라서 확인할 기록이며, 다른 시각의 요청이나 다른 경로의 성공 여부까지 조사하려면 추가 로그가 필요하다.

  이번 등급은 정해진 규칙과 점수에 따른 확인 순서다. low는 안전 확정, high는 공격 확정을 뜻하지 않는다. 이 실습은 제공된 샘플 로그에 규칙을 적용한 것이며 실제 운영 서비스의 침해 여부를 확정한 결과로 쓰지 않는다.

  - 답: 확인 예정 — 오후의 로그 연결과 위험 점수 프로그램 실행은 마쳤다. 다만 이 보고서 작성에 사용할 이번 마무리의 `git status` 출력과 `.env`·`.venv`의 표시 여부, 표시됐다면 실제로 한 조치는 아직 기록에 없다. 업로드 전에 실제 상태를 확인해 이 항목을 보완해야 한다. `ls`에 폴더가 보이는 것과 Git이 추적하는 것은 다르므로, 폴더 목록만으로 제외 여부를 알 수는 없다. 이번 오후 실습의 GitHub 업로드 완료 여부도 아직 기록하지 않았다.
