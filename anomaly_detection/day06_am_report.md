- (다) 🔍 AI 호출이 실패해도 파이프라인이 멈추지 않고 대체 문장을 쓰게 만든 이유를 적어 주세요. 대체 문장이 들어간 대상을 담당자가 어떻게 처리해야 하는지도 적어 주세요.

## 4교시 · 4과목 총정리: 상황마다 원인과 고치는 방법 정리하기

### 문제 4-1 · 상황 8개의 원인과 고치는 방법을 내 말로 정리하기

**상황 정리** — 상황 1·2·3·4·7·8 여섯 개를 정리했다. 상황 5·6은 교재의 본보기다. 아래의 개선 계획과 이전 실측 결과를 구분해 적었다.

#### 상황 1 · 설정 파일 주소를 연달아 요청했는데 「의심」이 아니라 「오류」로 분류됨
- 원인: 규칙 문제다. `log_classify.py`의 `is_suspicious`는 401·403 상태 코드 또는 `/admin`이 포함된 경로를 의심으로 본다. 샘플의 `/.env`, `/wp-login.php`, `/phpmyadmin` 요청은 모두 404이고 이 조건에 해당하지 않아 일반 오류로 분류된다. 중요한 파일이나 관리 경로를 탐색하는 행동을 현재 조건이 충분히 보지 못한 것이다.
- 고칠 파일: `log_classify.py`의 `is_suspicious`. 여러 요청을 묶어 탐색을 찾는 기능은 기존 `malicious_detection.py`의 `find_scan_ips`도 확인한다.
- 어떻게 고치나요: 제안: 설정 파일·관리 도구 경로를 의심 조건에 추가한다. 반복 탐색은 요청을 IP별로 묶는 기존 경로 스캔 규칙과 함께 확인한다. 모든 404를 의심으로 바꾸면 일반적인 잘못된 주소 요청까지 알림이 될 수 있으므로 경로와 반복 행동을 구분한다. 이번 4교시에는 분류 코드를 수정하지 않았다.
- 고친 뒤 확인: 계획: 같은 샘플을 다시 분류해 해당 IP의 세 요청이 의심에 포함되고 일반적인 404까지 일괄적으로 의심 처리되지 않는지 확인한다. 교재의 경로 조건을 추가한 예에서는 정상 15·오류 2·의심 11을 예상하지만, 이번에 직접 실행한 결과로 적지는 않는다.
- 담당자가 가장 먼저 할 일(선택): 같은 IP가 같은 시간대에 요청한 다른 경로와 성공 응답이 있었는지 원본 로그에서 확인한다. 예시 상황이며 실제 공격을 확정하는 것은 아니다.

#### 상황 2 · 로그 30줄이 이벤트 28개가 됨
- 원인: 데이터 문제다. 교재의 원본 웹 로그 30줄 중 두 줄은 형식이 깨져 `normalize_web`이 `None`을 반환한다. 따라서 정상적으로 읽힌 웹 이벤트는 28개다. 두 줄이 이유 없이 사라진 것이 아니라 읽기 실패로 구분된 것이다.

- 담당자가 가장 먼저 할 일(선택): 시험 상황에서는 해당 사용자의 권한과 정산 조회가 발생한 업무 경위를 확인한다. 조회 시도와 실제 자료 열람 성공을 구분한다.

#### 상황 8 · 서버가 같은 네트워크에 열려 있고, 지우면 접속 기록도 사라짐

- 담당자가 가장 먼저 할 일(선택): 현재 포트 공개 범위를 먼저 확인하고 접속 기록을 보존한다. Docker 내부 주소만 보고 외부 사용자나 공격자라고 단정하지 말고 요청 시각·경로와 접속 경로를 함께 확인한다.

    이벤트 57개는 원본 기록의 수이고, 탐지 8건은 대상별로 규칙에 걸린 결과다. seoyeon은 ‘평소와 다른 IP’와 ‘대량 다운로드’ 두 규칙에 해당하므로 탐지 결과는 두 건이지만 대상별 점수 기록에서는 한 건이다. 이렇게 사용자와 IP별로 묶으면 기록은 5건이 되고, 그중 조건에 맞는 앞의 세 대상만 AI 요약을 받는다. 앞 함수의 반환값을 다음 함수에 넘긴다는 설명과 실제 출력 숫자를 연결해 이해했다.

## 실습 준비와 기록 범위

- Windows의 VS Code UCRT64 터미널에서 `anomaly_detection`을 작업 위치로 사용했고, `sys.executable`로 기존 `.venv\Scripts\python.exe` 사용을 확인했다.
- 처음에는 판다스 `sparse`를 불러올 때 Windows 애플리케이션 제어 정책의 차단 오류가 났지만, 이후 같은 구성 요소를 불러오는 명령에서 판다스 3.1.0이 정상 출력됐다. 최초 차단의 정확한 원인은 확인하지 못했다.
- `llm_client.py`를 `agent_core`에서 복사했다. `requests`가 없다는 오류는 같은 가상환경에서 `python -m pip install requests`를 실행해 해결했고, API 키 읽기 결과 `True`를 확인했다. 이어 2·3교시에서 실제 Gemini 응답을 받았다.
- 교재와 AI 안내를 참고해 파일을 작성하고 로컬에서 실행했다. 이 보고서의 실행 결과는 내가 공유한 터미널 출력이며, AI의 별도 검토와 내가 실행한 결과를 구분했다. 샘플의 사용자 이름·IP·사건을 대상으로 한 교육용 실습이다.
- 4교시 개선안은 문서로 정리한 계획이다. 이번 시간에 새 탐지 규칙을 구현하거나 변경 전후 성능을 재측정하지 않았다. 오전 작업은 `e634c32`로 업로드했고, 이후 AI가 GitHub에서 파일과 결과를 검수했다.
