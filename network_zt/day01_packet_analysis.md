## 2교시 · ping

### 문제 2-1 · 결과 화면 읽기

- 보냄 · 받음 · 손실 · 평균: **보냄 4회 · 받음 3회 · 손실 1회(25%) · 평균 47ms**
- 결과의 성격: 이 문제는 **수업에 제시된 예시 결과**를 읽는 연습이다. 내 PC에서 새로 측정한 결과와 구분해 기록한다.
- 손실 %는 보낸 수와 받은 수로 어떻게 계산했나요?
  - 답: 예시에서는 목적지 `1.1.1.1`에 ping 확인용 메시지를 4번 보냈고, 그중 3번의 답장을 받았다. 응답을 받지 못한 횟수는 `4 - 3 = 1`회이므로 손실률은 `1 ÷ 4 × 100 = 25%`이다.
  - 평균 47ms는 답장이 돌아온 3번의 평균 왕복 시간이다. `47 ÷ 1000 = 0.047초`이므로, 메시지가 나갔다가 답장이 돌아오는 데 평균 0.047초 걸렸다는 뜻이다.
  - 처음에는 “서버까지 가는 데 47ms”라고 생각할 수 있었지만, 실제로는 **갔다가 돌아오는 시간인 RTT(Round-Trip Time)**라는 점을 이해했다. 응답하지 않은 1회의 대기 시간을 이 평균에 넣는 것은 아니다.
  - 응답이 없었다는 결과만으로 어디에서 메시지가 사라졌는지는 알 수 없다. 요청이나 응답 경로의 문제, 상대의 ICMP 응답 정책 등을 추가로 확인해야 한다.

### 문제 2-2 · 구글 DNS 서버에 `ping` 열 번 보내기

- 실행 대상: `8.8.8.8`
- 기록한 결과:

| 항목 | 내 보고서에 기록한 값 |
|---|---:|
| 보냄 | 10회 |
| 받음 | 10회 |
| 손실 | 0회, 0% |
| 최소 왕복 시간 | 35ms |
| 최대 왕복 시간 | 440ms |
| 평균 왕복 시간 | 212ms |
| 응답의 TTL | 당시 기록하지 못함. 현재 공유한 결과에는 응답 줄의 TTL 값이 없어 확인할 수 없음 |

- 해석: 열 번 모두 답장을 받았으므로 이 측정에서는 손실이 없었다. 다만 최소 35ms와 최대 440ms의 차이가 크고 평균도 212ms이므로, 응답 시간이 매번 일정하지 않았다는 점을 읽을 수 있다.
- 추가 이해: DNS 서버 주소에 ping을 보냈더라도, 이 명령이 DNS 이름 조회를 시험하는 것은 아니다. 여기서는 **해당 IP가 ICMP Echo 요청에 응답하는지와 왕복 시간**을 확인한 것이다.
- 복습할 때 확인할 것: TTL은 평균 통계가 아니라 각 응답 줄의 `TTL=숫자`에서 읽어야 한다. 다시 실행한 값은 오늘의 미기록 값과 구분해 새 측정으로 남긴다.

### 문제 2-3 · 이름으로 `ping` 보내기

- `google.com`의 IP 주소: **142.250.197.110 — 이번 실습에서 표시된 값**
- 이름만 입력했는데 IP 주소가 나온 이유는 무엇인가요?
  - 답: 사람이 기억하기 쉬운 도메인 이름 `google.com`을 IP 주소로 바꾸는 **이름 해석(Name Resolution)**이 먼저 이루어졌기 때문이다. DNS 또는 이미 저장된 이름 해석 정보 등을 통해 IP를 얻은 뒤, 그 주소로 ping을 보낸다.
  - 쉽게 이해하면 “이름을 주소록에서 숫자 주소로 찾은 뒤 메시지를 보낸 것”이다. 이 과정을 통해 도메인 이름과 IP 주소가 서로 다른 역할을 한다는 점을 알게 됐다.
  - 같은 도메인이라도 조회 시점이나 위치 등에 따라 표시되는 IP가 달라질 수 있으므로, 이 숫자를 google.com의 영구적인 단일 주소로 외우지는 않는다.

### 문제 2-4 · 두 가지 실패를 구별하기

- 두 실패 결과:
  - `ping abc.nowhere-not-exist`: “Ping 요청에서 abc.nowhere-not-exist 호스트를 찾을 수 없습니다. 이름을 확인하고 다시 시도하십시오.”
  - `ping 192.0.2.1`: 보냄 4회 · 받음 0회 · 손실 4회(100%). 기록한 결과는 응답을 받지 못했다는 통계이며, 개별 실패 문구는 별도로 보존하지 못했다.
- 두 실패는 각각 어디에서 멈춘 것인가요?
  - 답: 첫 번째는 **이름을 IP로 바꾸는 단계**에서 실패했다. 목적지 IP를 얻지 못했으므로 그 목적지에 대한 ping 요청을 보내는 단계로 진행하지 못했다.
  - 두 번째는 IP를 직접 입력했으므로 목적지 이름을 조회할 필요가 없다. 그 IP로 통신을 시도했지만 제한 시간 안에 응답을 받지 못한 것이다.
  - 내가 구분해야 하는 핵심은 **“목적지 주소를 못 찾았는가”와 “주소는 정했지만 응답을 못 받았는가”**이다.
  - `192.0.2.1`은 문서 예시에 쓰는 예약 주소 범위에 속한다. 이 실습 결과를 실제 운영 중인 서버의 장애로 해석하지 않는다.

### ⭐ 도전 2-5 · `ping` 결과를 파이썬으로 판정하기

- 기록한 출력:

```text
[정상] 8.8.8.8 34ms
[느림] 1.1.1.1 120ms
[실패] 192.0.2.1 응답 없음
```

- 복습 기록: 수업의 분류 예시에서는 응답 시간이나 응답 여부에 따라 정상·느림·실패를 구분했다. 이 출력의 34ms와 120ms는 도전 문제에 기록한 값이며, 문제 2-2에서 측정한 평균 212ms와 섞지 않는다.
- “느림”의 기준은 코드에서 정한 조건이다. 어떤 환경에서도 120ms가 반드시 장애라는 뜻은 아니므로 기준과 측정 환경을 함께 봐야 한다.

### 찾아본 것

- TTL(Time to Live)의 뜻과 라우터를 지날 때 바뀌는 방식:
  - IPv4 패킷이 잘못된 경로에서 끝없이 돌아다니는 것을 막기 위한 제한 값이다. 라우터는 전달하면서 TTL을 줄이고, 0이 되면 해당 패킷을 버린다.
  - 실습에서는 “라우터를 지날 때마다 보통 1씩 줄어드는 값”으로 이해했다. 이름에 Time이 들어 있지만 화면의 `TTL=128`을 “128초 동안 유효하다”라고 읽지 않는다.
  - 응답에 남은 TTL만 보고 실제 거친 라우터 수를 바로 계산할 수는 없다. 처음 설정된 TTL도 알아야 하기 때문이다.

### 이 교시에 새로 안 것

- ping 결과는 보냄·받음·손실·왕복 시간으로 나누어 읽을 수 있다는 것을 배웠다.
- 처음에는 숫자를 보는 것부터 어려웠지만, “4번 보냈는데 3번 돌아왔다”로 풀어 생각하니 25% 손실 계산을 이해할 수 있었다.
- 도메인 이름 해석 실패와 ping 응답 실패는 원인을 살펴볼 출발점이 다르다. 앞으로 오류가 나오면 먼저 문구를 읽고 어느 단계까지 진행됐는지 구분하려고 한다.

## 3교시 · IP와 MAC

### 문제 3-1 · 결과 화면 읽기

- 예시 화면의 IPv4 주소: **192.168.0.15**
- 예시 화면의 MAC 주소: **A4-B1-C2-D3-E4-F5**
- 예시 화면의 기본 게이트웨이: **192.168.0.1**
- 복습 기록: 이 세 값은 수업의 **예시 화면**에 나온 값이다. 다음 문제에서 직접 확인한 내 PC의 주소와 구분했다.
- IPv4는 IP 통신에 사용하는 주소, MAC은 네트워크 인터페이스의 링크 계층 주소, 기본 게이트웨이는 별도 경로가 없는 목적지로 보낼 때 사용하는 다음 홉이다.

### 문제 3-2 · 내 IP 주소·게이트웨이·MAC 주소 찾기

- 사용한 명령: Git Bash에서 `ipconfig //all`
- 찾은 인터페이스 이름: **이더넷 2 — 이후 Wireshark에서 실제 통신을 확인하고 선택한 이름**
- 기록한 IPv4 주소: **192.168.100.89**
- 기록한 기본 게이트웨이: **192.168.1.1**
- 기록한 MAC 주소(물리적 주소): **D8-BB-C1-40-37-26**
- 네트워크 어댑터의 제품명(Description): 당시 별도로 기록하지 못함. 인터페이스 이름과 제품명은 같은 항목이 아니므로 추측해 채우지 않는다.
- 복습 기록: 여러 어댑터가 표시되더라도 실제 통신하는 인터페이스의 항목을 함께 읽어야 한다. 연결되지 않은 어댑터의 MAC과 사용 중인 어댑터의 IP를 섞지 않도록 주의한다.
- 이번 기록에서는 IP와 게이트웨이의 세 번째 숫자가 다르다. 같은 망인지 판단하려면 서브넷 마스크와 경로 정보가 필요하므로, 오늘은 숫자 모양만으로 설정 오류라고 단정하지 않는다.

### 문제 3-3 · 게이트웨이까지 `ping`

- 게이트웨이까지 평균: **실제 측정값을 기록하지 못함**
- 문제 2-2의 `8.8.8.8` 평균: **212ms**
- 기록 보완: 원래 적어 둔 “보통 1~5ms”는 일반적인 예시 설명이었다. 내 PC에서 측정한 값으로 확인되지 않았으므로 실제 결과로 쓰지 않는다.
- 게이트웨이까지가 더 짧은 이유는 무엇인가요?
  - 답: 기본 게이트웨이는 외부 네트워크로 나가는 가까운 다음 홉이다. 인터넷의 먼 목적지까지 통신할 때보다 일반적으로 거치는 경로와 장비가 적어 왕복 시간이 짧을 수 있다.
  - 다만 응답 시간은 거리뿐 아니라 혼잡이나 장비 상태, 응답 처리에도 영향을 받는다. 이번에는 실제 게이트웨이 평균이 남아 있지 않으므로 “실제로 몇 ms 더 짧았다”는 비교는 하지 못했다.
- 재확인 방법: `ping 192.168.1.1`을 실행하고 마지막 통계의 평균을 새 측정으로 기록한다.

### 문제 3-4 · ARP 캐시 보기 — `arp -a`

- 게이트웨이 줄의 IP: **192.168.1.1**
- MAC 주소·유형: **00-10-f3-a3-fc-96 · 동적**
- ARP는 무엇을 알아내려고 쓰나요?
  - 답: IPv4 통신에서 같은 링크에 있는 다음 전달 대상의 **IP 주소에 대응하는 MAC 주소**를 알아내기 위해 사용한다.
  - 내 결과에서는 기록한 게이트웨이 IP `192.168.1.1`에 대응하는 MAC이 `00-10-f3-a3-fc-96`으로 표시됐다. 외부 서버에 보낼 때도 로컬 링크에서는 게이트웨이로 프레임을 전달해야 하므로 이 MAC 정보가 필요하다.
  - “동적”은 PC가 통신 과정에서 자동으로 학습하여 ARP 캐시에 저장한 항목이라는 뜻이다.
- 처음에 헷갈렸던 점: `arp -a`의 첫 줄이 무조건 게이트웨이라는 뜻은 아니다. `ipconfig`에서 확인한 게이트웨이 IP와 같은 줄을 찾아야 한다. 또한 `ff-ff-ff-ff-ff-ff`는 브로드캐스트 MAC이므로 게이트웨이의 개별 MAC으로 적지 않는다.

### ⭐ 도전 3-5 · 주소 모양으로 IP와 MAC 구별하기

- 기록한 분류 결과:

```text
IP 192.168.0.15
MAC a8-5e-45-01-2b-3c
MAC ff-ff-ff-ff-ff-ff
모름 192.168.0
```

- 복습 기록: 일반적인 IPv4 표기는 점으로 나눈 네 부분이고, MAC은 여섯 묶음의 16진수로 표시한다. `192.168.0`은 완전한 일반 IPv4 표기로 보기 어려워 수업 코드에서 “모름”으로 분류했다.
- 주소 모양을 대략 분류하는 것과 값의 범위까지 엄격하게 검증하는 것은 다르다는 점도 기억한다.

### 이 교시에 새로 안 것

- IP·MAC·게이트웨이가 모두 “주소”와 관련되어 있지만 맡은 역할이 다르다는 것을 배웠다.
- 특히 외부 서버의 IP와 로컬 링크에서 전달할 MAC은 같은 대상을 가리키지 않을 수 있다. 인터넷 서버로 향하는 패킷도 첫 전달 단계에서는 게이트웨이의 MAC을 사용한다.
- 긴 출력에서 값을 무작정 복사하기보다 먼저 실제 인터페이스를 고르고, 같은 항목 안에서 IP·MAC·게이트웨이를 읽어야 한다는 것을 알게 됐다.

## 4교시 · 포트

### 문제 4-1 · 직접 실행해 보기

- 출력 두 줄:

```text
HTTPS
모름
```

- `3389`는 사전에 없는데도 에러 없이 둘째 줄이 나온 이유는 무엇인가요?
  - 답: 수업 코드가 사전의 `get()`을 사용하면서, 키가 없을 때 반환할 기본값을 “모름”으로 지정했기 때문이다. 예를 들어 `port_names.get(3389, "모름")`은 해당 키가 사전에 없으면 “모름”을 돌려준다.
  - `사전[3389]`처럼 없는 키를 직접 찾으면 `KeyError`가 날 수 있지만, `get()`은 기본값으로 처리할 수 있다.
  - 여기서 “모름”은 **이 코드의 사전에 정보가 없다는 뜻**이다. 3389에 대응하는 실제 서비스가 없다는 뜻은 아니다. 3389는 일반적으로 RDP 원격 데스크톱에 사용된다.

### 문제 4-2 · 지금의 연결 보기 — `netstat -n`

- 선택한 연결:

```text
TCP  192.168.100.89:49572  140.82.114.25:443  ESTABLISHED
```

- 외부 포트 → 서비스 이름: **443 → HTTPS**
- 내 PC의 로컬 주소: `192.168.100.89:49572`
- 상대의 외부 주소: `140.82.114.25:443`
- 상태: **ESTABLISHED — TCP 연결이 성립되어 유지 중**
- 복습 기록: 주소의 콜론 앞은 IP이고 뒤는 포트다. 문제에서 “외부 포트”를 묻기 때문에 로컬 포트 49572가 아니라 상대의 포트 443을 읽었다.
- 443은 HTTPS의 일반적인 포트다. 포트 번호는 서비스 판단의 단서이며, 번호 하나만으로 실제 통신 내용을 모두 확정하지는 않는다.

### 문제 4-3 · 그 연결은 어느 프로그램의 것인가

- PID → 프로그램 이름: **14472 → chrome.exe**
- 확인에 사용한 명령:

```bash
netstat -ano | grep ESTABLISHED
tasklist | grep 14472
```

- 실제로 확인한 프로그램 줄:

```text
chrome.exe                   14472 Console                   14     59,508 K
```

- 이해한 과정: `netstat -ano`의 마지막 숫자는 **PID(Process ID)**다. 그 번호를 `tasklist`에서 찾아야 연결을 사용한 프로세스를 확인할 수 있다.
- 처음에는 예시 숫자인 1234를 그대로 넣으려 했지만, 내가 선택한 연결의 실제 PID인 14472를 사용해야 한다는 것을 이해했다.
- PID는 실행 중인 프로세스의 번호다. 프로그램을 다시 실행하면 달라질 수 있고, Chrome처럼 한 프로그램이 여러 프로세스로 실행되는 경우도 있다. IP만 보고 프로그램을 추측하지 않고 연결의 PID를 확인하는 이유를 배웠다.

### 문제 4-4 · 내 PC의 LISTENING 포트 찾기

- 확인한 명령: `netstat -an | grep LISTENING`
- 수업 표에 있는 LISTENING 포트 → 서비스 이름:
  - **135 → RPC**
  - **445 → SMB(파일 공유)**
- 실제 확인한 예:

```text
TCP  0.0.0.0:135  0.0.0.0:0  LISTENING
TCP  0.0.0.0:445  0.0.0.0:0  LISTENING
```

- LISTENING과 ESTABLISHED는 무엇이 다른가요?
  - 답: **LISTENING**은 새로운 TCP 연결 요청을 기다리는 상태이고, **ESTABLISHED**는 특정 상대와 연결이 성립된 상태다.
  - `0.0.0.0:135 LISTENING`은 모든 로컬 IPv4 주소를 대상으로 135번 포트에서 연결 요청을 받도록 대기한다는 뜻이다.
  - `192.168.100.89:49572 ↔ 140.82.114.25:443 ESTABLISHED`는 두 끝점 사이의 연결이 성립되어 있다는 뜻이다.
- 주소 표기에서 추가로 이해한 점:
  - `127.0.0.1`은 내 컴퓨터 내부의 IPv4 루프백 주소다.
  - `[::1]`은 IPv6 루프백 주소이고, `[::]`는 모든 로컬 IPv6 주소를 나타내는 대기 주소로 쓰인다.
  - LISTENING이라고 해서 인터넷 어디에서나 접속할 수 있다는 뜻은 아니다. 방화벽과 네트워크 경로 등도 영향을 준다.
  - LISTENING 줄의 외부 주소 `0.0.0.0:0`은 아직 특정 상대와 연결되지 않았다는 표기다.

### 문제 4-5 · 증상으로 층 좁히기

| 증상 | 먼저 확인할 범위 | 판단한 이유 |
|---|---|---|
| ① 숫자 IP로 ping은 되지만 도메인 이름을 찾지 못함 | DNS 이름 해석, 수업의 OSI 분류로 7계층 | IP 대상의 응답은 받았지만 이름을 IP로 바꾸는 단계가 실패함 |
| ② 기본 게이트웨이 ping도 응답하지 않음 | 로컬 연결과 IP 설정, 1~3계층 | 가까운 다음 홉과의 통신부터 확인할 필요가 있음 |
| ③ ping은 되지만 특정 웹사이트가 열리지 않음 | TCP 포트 연결·TLS·웹 서비스 등 4계층 이상 | ping 성공만으로 웹 서비스의 정상 동작까지 확인한 것은 아님 |

- 판단의 한계: 위 범위는 원인을 좁히는 출발점이다. 게이트웨이가 ICMP 응답을 막을 수도 있으므로 ping 실패만으로 랜선 고장을 확정하지 않는다. 웹사이트가 안 열리는 경우에도 DNS, 브라우저 설정 등 여러 원인이 있을 수 있다.
- 복습 기록: “증상 하나를 보고 원인을 확정하기”보다 **어디까지 성공했고 어느 단계에서 실패했는지**를 먼저 구분해야 한다.

### 찾아본 것

- 3389의 위험:
  - RDP 원격 데스크톱의 기본 포트다. 외부에 노출된 원격 접속 서비스는 비밀번호를 반복해서 시도하는 공격이나 계정 탈취의 대상이 될 수 있다.
  - 번호 자체가 악성이라는 뜻은 아니다. 실제 원격 접속 서비스의 노출 범위와 인증 설정 등을 확인해야 한다.
- 445를 이용해 퍼진 랜섬웨어:
  - 대표적인 과거 사례는 **2017년 WannaCry/WannaCrypt**다. 패치되지 않은 Windows SMBv1 취약점을 악용하여 전파했고, 관련 보안 업데이트는 **MS17-010**이다.
  - 내가 보는 445 LISTENING 한 줄만으로 감염됐다고 판단할 수는 없다. 서비스의 취약 여부와 보안 업데이트, 실제 통신·행위 등 추가 근거가 필요하다.
- 확인 자료: 보고서 끝의 Microsoft 공식 문서를 참고했다. 이 부분은 수업 후 복습에서 보완한 내용이다.

### 이 교시에 새로 안 것

- IP는 통신할 컴퓨터를 가리키고, 포트는 그 컴퓨터에서 통신하는 서비스나 연결의 끝점을 구분한다는 것을 배웠다.
- `netstat`의 연결 정보에서 PID를 찾고 `tasklist`로 프로그램을 확인하면 “어느 프로그램의 연결인지”를 근거를 가지고 설명할 수 있다.
- LISTENING과 ESTABLISHED를 구분하니 대기 중인 서비스와 이미 성립된 연결을 같은 것으로 보지 않게 됐다.

## 5교시 · TCP

### 문제 5-1 · 직접 실행해 보기

- 출력 세 줄:

```text
True
False
443
```

- 탐지 코드에서 플래그를 `==`로 검사하면 어떤 일이 생기나요?
  - 답: 수업 예시의 `packet["flags"]`는 `["SYN", "ACK"]`라는 리스트다. `"ACK" in packet["flags"]`는 그 안에 ACK가 있는지 묻기 때문에 True가 나온다.
  - 반면 `packet["flags"] == "ACK"`는 리스트 전체와 문자열 하나가 같은지 비교하므로 False가 나온다. ACK가 실제로 들어 있어도 이 조건으로는 탐지하지 못한다.
  - 비교 자체가 오류 없이 실행되므로, 에러 메시지가 없는데도 탐지가 누락될 수 있다. “실행된다”와 “원하는 의미로 판단한다”는 다르다는 것을 배웠다.
  - `==`가 항상 잘못된 연산자는 아니다. 이 문제에서는 **포함 여부를 확인하려는데 전체 값의 같음을 검사한 것**이 문제였다. 값이 리스트인지 문자열인지 확인하고 비교 방식을 골라야 한다.

### 문제 5-2 · TCP일까 UDP일까

- 수업의 대표 사례 분류:
  - ① 사진 파일 보내기 → **TCP**
  - ② 실시간 방송 → **UDP**
  - ③ `requests.post` 웹 요청 → **TCP**
  - ④ 일반적인 DNS 조회 → **UDP**
  - ⑤ `ping` → **ICMP**
- 사진 파일 보내기가 TCP인 이유는 무엇인가요?
  - 답: 파일은 데이터를 빠짐없이 받아 원본을 복원하는 것이 중요하다. TCP는 손실된 데이터를 재전송하고 바이트 전달 순서를 보장하는 방식이므로 이런 전송에 적합하다.
- 복습 기록:
  - TCP는 신뢰성 있는 전달, UDP는 연결 설정 없이 데이터그램을 보내는 방식이라는 차이를 이해하는 것이 핵심이다.
  - “방송이면 언제나 UDP”처럼 실제 서비스 전체를 단정하지 않는다. 웹 영상은 TCP나 QUIC 등 여러 방식을 사용할 수 있고 DNS도 TCP를 사용할 수 있다.
  - ping은 TCP도 UDP도 아닌 ICMP를 사용하며, 이 실습의 ICMP Echo 요청에는 TCP·UDP 포트 번호가 없다.

### 문제 5-3 · 세 번의 순서 맞히기

- 세 패킷의 순서와 방향:
  1. **(나) SYN:** 내 PC → 서버
  2. **(다) SYN, ACK:** 서버 → 내 PC
  3. **(가) ACK:** 내 PC → 서버
- 연결을 맺을 때는 세 번인데, 끝낼 때는 왜 네 번인가요?
  - 답: 연결 시작 때 서버는 내 요청의 확인인 ACK와 자신의 연결 요청인 SYN을 한 패킷에 함께 보내므로 보통 세 패킷으로 진행된다.
  - 정상 종료에서는 양쪽이 각자 **“나는 더 보낼 데이터가 없다”**는 FIN을 보내고, 상대는 이를 ACK로 확인한다. 한쪽이 전송을 끝냈더라도 반대쪽은 아직 전송할 데이터가 남아 있을 수 있어 양방향을 따로 종료한다.
  - 대표적인 설명은 `FIN → ACK → FIN → ACK`의 네 단계다. 다만 ACK와 FIN이 함께 실리는 등 실제 패킷 수는 달라질 수 있다.
  - 실제 7교시 캡처에서는 9번 FIN, ACK → 10번 FIN, ACK → 11번 ACK로 종료가 보였다. **네 단계라는 설명을 무조건 네 줄의 패킷으로 외우면 안 된다**는 점을 연결해서 이해했다.

### 문제 5-4 · 같은 서버로 간 두 연결은 무엇이 다른가

- 비교 대상: 수업의 두 연결 예시

```text
TCP  192.168.0.15:51234  142.250.196.110:443  ESTABLISHED
TCP  192.168.0.15:51240  142.250.196.110:443  ESTABLISHED
```

- 두 연결에서 같은 것:
  - TCP 프로토콜
  - 내 PC의 IP `192.168.0.15`
  - 상대 IP `142.250.196.110`
  - 상대 포트 `443`
  - ESTABLISHED 상태
- 다른 것: 내 PC의 임시 포트가 **51234와 51240**으로 다르다.
- 같은 서버로 간 두 연결을 무엇으로 구별하나요?
  - 답: 이 예시의 TCP 연결은 **출발지 IP·출발지 포트·목적지 IP·목적지 포트**의 조합으로 구분한다. 이 중 출발지 포트가 다르므로 목적지가 같아도 서로 다른 연결이다.
  - 이 네 값은 흔히 **4-tuple**이라고 부른다. 여러 프로토콜을 함께 다룰 때는 프로토콜까지 더한 **5-tuple**을 사용하기도 한다.
  - “같은 서버에 연결했다”는 사실만으로 연결 하나라고 판단하지 않는다. 브라우저가 같은 서버와 여러 연결을 사용할 때 로컬 임시 포트를 비교하는 이유를 알게 됐다.

### 이 교시에 새로 안 것

- TCP 연결은 통신 상대와 연결을 설정한 뒤 데이터를 주고받으며, 양쪽의 전송 종료를 확인하는 과정이 있다는 것을 배웠다.
- SYN·ACK·FIN을 단어로만 외울 때는 이해하기 어려웠지만 “시작 요청·확인·전송 종료”로 나누어 생각하니 역할이 조금씩 연결됐다.
- 파이썬에서는 실제 데이터 형태에 맞게 `in`과 `==`를 골라야 한다. 네트워크 지식뿐 아니라 탐지 코드의 조건을 정확히 쓰는 것도 중요하다는 것을 배웠다.

## 6교시 · Wireshark

### 실습 1 · 캡처하고 통신 방향 읽기

#### 문제 6-1 · Wireshark 실행하기

- 고른 인터페이스 이름: **이더넷 2**
- Wireshark는 무엇인가: 통신 패킷을 캡처하고 각 패킷의 프로토콜과 주소, 헤더 등을 확인하는 **패킷 분석 도구**다.
- 인터페이스를 고르는 이유: 실제 통신 중인 네트워크 통로에서 수집해야 내가 관찰하려는 패킷이 잡히기 때문이다.
- 첫 사용에서 이해한 점: `netstat`은 연결 상태를 한 줄씩 보여 주지만, Wireshark의 패킷 목록은 **개별 패킷을 한 줄씩** 보여 준다.

#### 문제 6-2 · 캡처한 통신의 방향 읽기

- 전체 Packets: **186,929개**
- 관찰한 Protocol 이름 세 개: **TCP · ARP · TLSv1.2**
- 관찰한 연결:
  - 내 PC: `192.168.100.89:56750`
  - 상대: `172.64.155.209:443`
- 어느 줄이 요청 방향인가요?
  - 답: `56750 → 443`이 내 PC에서 서버로 향하는 요청 방향이다. Source IP가 내 PC인 `192.168.100.89`이고 Destination IP가 상대 서버인 `172.64.155.209`이기 때문이다.
  - 반대로 `443 → 56750`은 서버에서 내 PC로 돌아오는 방향이다. 같은 두 IP와 포트가 출발지·목적지에서 서로 뒤바뀐다.
- 정확히 구분한 점: 선택한 3번 패킷은 `[ACK]`, `Len=0`이다. 방향은 클라이언트 → 서버지만 **실제 HTTP 요청 내용을 담은 패킷이 아니라 TCP 수신 확인 패킷**이다. 통신 방향과 개별 패킷의 역할을 구분해야 한다.
- 첫 사용에서 헷갈렸던 점:
  - example.com에 같은 안내 문구만 나와서 캡처가 안 되는 줄 알았다. 웹사이트 화면이 그대로여도 그 페이지를 불러오는 통신은 별도로 발생할 수 있다.
  - Wireshark는 웹페이지 내용을 바꾸는 도구가 아니다. 패킷 목록에 줄이 쌓이는지로 캡처 상태를 확인해야 한다.
  - 이번 큰 캡처에는 여러 프로그램과 다른 통신도 포함되어 있다. 이 IP가 example.com인지 캡처 화면만으로 확정하지 않았다.

### 실습 2 · 패킷 내용을 해석하고 필터로 확인하기

#### 문제 6-3 · 패킷 하나를 층별로 펼치기

- 선택한 패킷: **6교시 캡처의 3번 TCP ACK 패킷**
- 직접 찾아 기록한 값:

| 계층 | 항목 | 확인한 값 |
|---|---|---|
| 2계층 · Ethernet II | Source MAC | d8:bb:c1:40:37:26 |
| 3계층 · IPv4 | Source IP | 192.168.100.89 |
| 3계층 · IPv4 | Destination IP | 172.64.155.209 |
| 3계층 · IPv4 | Time to Live | 128 |
| 4계층 · TCP | Source Port | 56750 |
| 4계층 · TCP | Destination Port | 443 |
| 4계층 · TCP | Flags | 0x010 (ACK) |

- 이 패킷은 내 PC가 보낸 것인가요, 받은 것인가요?
  - 답: **내 PC가 보낸 패킷**이다. 출발지 IP인 `192.168.100.89`가 내 PC의 IP와 같기 때문이다.
  - Source Port 56750은 이 연결에서 내 PC가 사용한 임시 포트이고, Destination Port 443은 상대의 포트다.
  - Flags의 `0x010`은 16진수 표현이고 `ACK`는 그 의미를 이름으로 표시한 것이다.
- 이해한 조작: 패킷 목록에서 한 줄을 선택하고, **패킷 상세(Packet Details)**에서 Ethernet II·IPv4·TCP 항목을 **펼치기(Expand)**로 열었다.
- 복습 기록: MAC은 Ethernet에서, IP와 TTL은 IPv4에서, 포트와 TCP 플래그는 TCP에서 찾는다. IPv4에도 Flags가 있으므로 이번 문제의 TCP Flags와 혼동하지 않는다.

#### 문제 6-4 · 필터 결과와 뜻 비교하기

- 공유한 화면과 대화에서 확인 가능한 결과:

| 조건 | 값 | 확인 상태 |
|---|---:|---|
| 전체 Packets | 186,929개 | 6교시 캡처 중지 화면에서 확인 |
| `dns`의 Displayed | 미기록 | 해당 필터의 결과 화면을 남기지 못함 |
| `udp`의 Displayed | 미기록 | 해당 필터의 결과 화면을 남기지 못함 |
| `tcp.port == 443`의 Displayed | 23,374개, 12.5% | 실제 필터 적용 화면에서 확인 |

- 필터를 걸어도 Packets는 그대로인데 Displayed만 바뀌는 이유는 무엇인가요?
  - 답: **표시 필터(Display Filter)**는 이미 캡처한 패킷을 삭제하지 않고 조건에 맞는 것만 화면에 보여 주기 때문이다. 전체 수집량인 Packets는 그대로이며, 화면에 보이는 수인 Displayed만 바뀐다.
  - `tcp.port == 443`은 TCP의 출발지 또는 목적지 포트가 443인 패킷을 고른다. TLS가 TCP 위에서 동작하므로 Protocol 열에 TLSv1.2라고 표시된 패킷도 이 조건에 맞을 수 있다.
  - 입력 칸의 초록색은 문법이 유효하다는 뜻이다. 실제 적용은 Enter 또는 적용 버튼으로 하고, 적용 결과는 표시된 패킷과 Displayed 값으로 확인한다.
- 재확인할 것: 같은 6교시 캡처가 남아 있다면 `dns`와 `udp`를 각각 적용해 Displayed를 기록한다. 새로 만든 7교시 캡처는 수집 조건과 전체 개수가 다르므로 그 결과를 이 표의 빈 측정값 대신 넣지 않는다.
- 추가 관찰: 화면의 Dropped는 0으로 표시됐다. 이는 Wireshark가 보고한 **캡처 누락**이며, 인터넷 경로 전체에서 패킷 손실이 없었다는 뜻은 아니다.

### 이 교시에 새로 안 것

- 처음에는 화면에 줄이 많이 쌓이는 것부터 낯설었지만, 패킷 목록에서 한 줄을 선택하면 그 패킷의 상세 정보를 볼 수 있다는 화면 구조를 익혔다.
- 버튼 모양만 기억하는 대신 정식 이름도 함께 익히려고 했다.

| 기능·영역 이름 | 내가 사용한 역할 |
|---|---|
| 캡처 시작 · Start Capture | 새 패킷 수집 시작 |
| 캡처 중지 · Stop Capture | 빨간 네모 버튼으로 새 수집 중지 |
| 표시 필터 · Display Filter | 조건에 맞는 패킷만 화면에 표시 |
| 패킷 목록 · Packet List | 패킷 번호·출발지·목적지·Info 확인 |
| 패킷 상세 · Packet Details | 선택한 패킷의 헤더 정보 펼치기 |
| 패킷 바이트 · Packet Bytes | 패킷의 실제 바이트 확인 |
| 상태 표시줄 · Status Bar | 전체·표시·캡처 누락 개수 확인 |

- IP와 포트를 함께 읽으면 통신 방향을 설명할 수 있고, 플래그를 보면 그 패킷이 어떤 역할을 하는지도 구분할 수 있다는 것을 배웠다.

### 문제 7-1 · 내 HTTP 연결 하나만 잡기

- 캡처 인터페이스: **이더넷 2**
- 캡처 필터: **`tcp port 80`**
- 요청을 발생시킨 명령:

```bash
curl "http://example.com/?q=network_day1"
```

- 실제 관찰 결과: 터미널에 Example Domain의 HTML이 출력됐고, Wireshark에서는 **1~11번, 총 11개 패킷**이 잡혔다.
- 연결 설정 세 패킷:

| 번호 | Source → Destination | Info에서 확인한 포트·신호 |
|---:|---|---|
| 1 | 192.168.100.89 → 172.66.147.243 | 52337 → 80 [SYN] |
| 2 | 172.66.147.243 → 192.168.100.89 | 80 → 52337 [SYN, ACK] |
| 3 | 192.168.100.89 → 172.66.147.243 | 52337 → 80 [ACK] |

- 세 줄 Info의 신호 순서: **SYN → SYN, ACK → ACK**
- 이미지 기록: 연결 설정 세 단계가 보이는 화면을 [handshake.png](handshake.png)로 저장하고, GitHub의 `network_zt` 폴더에 업로드했다.
- 이해가 막혔던 부분과 해결:
  - 캡처 시작 직후 화면이 비어 있어 이상한 것인지 물었다. Wireshark는 통신을 관찰하는 도구이므로, 80번 통신이 없으면 빈 화면일 수 있다. 캡처 중에 curl을 실행하자 패킷이 나타났다.
  - `tcp.flags.syn == 1`을 입력하면 1번 SYN과 2번 SYN, ACK만 보였다. 3번 ACK는 SYN이 없기 때문에 숨겨진다.
  - 필터를 지운 후 찾을 대상은 **3번 ACK**였다. “첫 번째 SYN과 비교하라”는 설명을 처음에는 “첫 번째 줄을 고르라”는 뜻으로 이해했지만, 실제 뜻은 **1번과 같은 IP·포트 쌍을 사용하는 마지막 확인 패킷을 찾으라**는 것이었다.
  - 이번에는 처음 세 줄에 모두 보여 필터 없이도 찾을 수 있었다. 그래도 필터를 사용한 이유는 패킷이 많을 때 특정 신호를 찾는 방법을 익히기 위해서였다.
  - 8번과 11번도 ACK지만, 각각 데이터 수신과 연결 종료를 확인하는 패킷이다. 모든 ACK가 연결 설정의 마지막 단계는 아니다.

### 문제 7-2 · HTTP 요청과 연결 종료 찾기

- HTTP 표시 필터: `http`
- 요청 줄의 Info: **4번 `GET /?q=network_day1 HTTP/1.1`**
- 응답 줄의 Info: **7번 `HTTP/1.1 200 OK (text/html)`**
- 종료 표시 필터: `tcp.flags.fin == 1`
- FIN 줄 수: **2개 — 9번, 10번**

| 번호 | 방향 | 신호와 역할 |
|---:|---|---|
| 9 | 내 PC → 서버 | 52337 → 80 [FIN, ACK] — 내 PC의 전송 종료 알림 |
| 10 | 서버 → 내 PC | 80 → 52337 [FIN, ACK] — 서버의 전송 종료 알림과 확인 |
| 11 | 내 PC → 서버 | 52337 → 80 [ACK] — 서버의 종료 알림 확인, FIN 개수에는 포함하지 않음 |

- 요청 내용 해석:
  - `GET`은 해당 자원의 내용을 요청하는 HTTP 메서드다.
  - `/`는 경로이며, `q=network_day1`은 URL에 붙인 쿼리 값이다.
  - 이번 값은 요청을 쉽게 알아보기 위해 붙인 표시다. example.com에서 실제 검색을 했다는 뜻은 아니다.
- 같은 요청을 HTTPS로 보냈다면 어떻게 보였을까요?
  - 답: 요청 내용이 TLS로 암호화되므로 별도의 복호화 설정 없이 캡처만 보면 `network_day1`이나 GET 요청 내용을 그대로 읽을 수 없다. TLS Application Data처럼 암호화된 데이터로 보일 수 있다.
  - HTTPS도 패킷 자체는 캡처할 수 있고 IP 등 일부 통신 정보는 확인할 수 있다. “내용이 암호화된다”와 “패킷이 전혀 안 보인다”는 다르다.
- 복습 기록: SYN은 연결 시작, FIN은 해당 방향의 전송 종료를 나타낸다. `[FIN, ACK]`에도 FIN이 들어 있으므로 두 줄을 세면 됐다.

## 최종 분석 — 내가 만든 HTTP 연결 정리

> 6교시의 큰 캡처와 7교시의 11개 패킷 캡처는 서로 다른 자료다. 아래 최종 분석은 **7교시 curl로 만든 HTTP 연결**로 통일했다. 6교시의 56750 → 443 값을 이 연결의 포트로 사용하지 않는다.

### 1. 연결이 열리는 순간 — 3-way handshake

- 세 줄의 Source → Destination과 Info:
  1. **192.168.100.89 → 172.66.147.243**  
     `52337 → 80 [SYN]` — 내 PC가 연결 설정을 요청했다.
  2. **172.66.147.243 → 192.168.100.89**  
     `80 → 52337 [SYN, ACK]` — 서버가 요청을 확인하고 자신의 연결 설정 정보를 보냈다.
  3. **192.168.100.89 → 172.66.147.243**  
     `52337 → 80 [ACK]` — 내 PC가 서버의 응답을 확인했다.
- 세 줄이 오간 뒤 두 컴퓨터는 어떤 상태가 되나요?
  - 답: 정상적인 연결 설정이 완료되면 양쪽 TCP는 **ESTABLISHED** 상태가 된다. 내 PC가 서버의 응답을 받은 뒤 마지막 ACK를 보내고, 서버가 그것을 받으면 양쪽의 연결 설정이 완료된다.
  - 그다음 4번에서 실제 HTTP 요청이 전송됐다. 따라서 연결을 시작하는 SYN과 웹 요청인 GET은 서로 다른 단계라는 것을 실제 패킷에서 확인했다.

### 2. 패킷 하나를 열어 본 값 — 6-3에서 배운 방법 적용

- 선택한 패킷: **7교시 캡처의 1번 SYN**
- 출발지·목적지 IP(3층), TTL, 출발지·목적지 포트(4층):

| 항목 | 값 |
|---|---|
| Source IP | 192.168.100.89 |
| Destination IP | 172.66.147.243 |
| Time to Live | 128 |
| Source Port | 52337 |
| Destination Port | 80 |
| TCP 신호 | SYN |
| 방향 | 내 PC → 서버 |

- 값의 근거: IP·포트·SYN은 첨부한 7교시 화면의 1번 패킷에서 확인했다. TTL 128은 같은 화면의 Packet Bytes에 있는 IPv4 헤더의 TTL 바이트 `0x80`을 확인해 복습 과정에서 보완한 값이다. 이전 6교시 패킷의 TTL을 그대로 복사한 것은 아니다.
- 목적지 포트를 보고 어떤 서비스로 가는 패킷인지 알 수 있나요?
  - 답: 목적지 포트 80은 일반적으로 HTTP 웹 서비스에 사용된다. 이번에는 포트 번호 외에도 4번의 GET 요청과 7번의 HTTP 응답을 확인했으므로 **실제 HTTP 웹 통신**임을 설명할 수 있다.
  - 다른 상황에서는 포트 번호만 보고 내용을 확정하지 않고 Protocol과 상세 정보도 함께 확인한다.
- 이 패킷은 내 PC가 보냈다. Source IP가 내 PC의 주소 `192.168.100.89`이기 때문이다.

### 3. HTTP 요청 — 7-2

- 요청 줄에서 그대로 보인 내용:

```http
GET /?q=network_day1 HTTP/1.1
```

- 이것이 보안에서 문제가 되는 이유는 무엇인가요?
  - 답: 암호화되지 않은 HTTP 통신은 패킷을 관찰할 수 있는 위치에서 요청 경로와 쿼리 값 등을 읽을 수 있다. 이번에는 실습용 `network_day1`만 넣었지만, 민감한 내용이 포함되어 있다면 노출될 수 있다.
  - HTTPS는 TLS로 HTTP 내용을 암호화한다. 별도의 복호화 설정 없이 같은 방식으로 캡처하면 이 요청 문자열을 그대로 읽을 수 없다.
- 응답과 종료까지 관찰한 순서:
  - 1~3번: TCP 연결 설정
  - 4번: 내 HTTP GET 요청
  - 5~8번: 서버의 확인·데이터 응답과 내 수신 확인
  - 9~11번: 양쪽 전송 종료와 마지막 확인
- FIN이 포함된 것은 9번과 10번 두 패킷이다. ACK는 연결 설정뿐 아니라 데이터를 받았을 때와 종료를 확인할 때도 쓰인다는 점을 이해했다.

- 오늘 배운 것 가운데 가장 중요하다고 생각하는 것과 그 이유:
  - 가장 중요한 것은 **출력과 패킷을 근거로 통신 과정을 설명하는 방법**이라고 생각한다. 이전에는 “인터넷이 안 된다”, “웹페이지가 안 바뀐다”, “ACK가 있다” 정도로만 봤지만, 오늘은 이름 해석·IP 통신·TCP 연결·HTTP 요청을 나누어 생각하기 시작했다.
  - 오전의 `netstat`에서 ESTABLISHED라고 표시된 연결이 오후에는 SYN → SYN, ACK → ACK라는 과정으로 만들어진다는 것을 확인했다. 명령어의 상태 이름과 실제 패킷이 연결된 점이 기억에 남는다.
- 가장 어려웠던 부분:
  - Wireshark 화면 구조와 필터의 역할이 처음에는 낯설었다. 특히 첫 SYN을 기준으로 마지막 ACK를 찾는다는 설명을 처음에는 “첫 번째 줄을 선택하라”는 의미로 받아들였다.
  - 내 화면의 실제 1·2·3번 패킷을 함께 비교하고, 필터가 3번을 숨긴다는 사실을 확인하면서 이해가 나아졌다. 추상적인 설명보다 실제 IP·포트와 패킷 번호를 함께 보는 것이 도움이 됐다.
- 앞으로 적용할 방법:
  - 주소를 읽을 때 Source와 Destination을 먼저 확인하고, 포트와 Flags로 역할을 구분한다.
  - 필터를 사용할 때 “처음부터 수집을 제한하는가”와 “수집한 것 중 일부를 보여 주는가”를 구분한다.
  - 실습 결과와 수업 예시를 섞지 않고, 실제 측정값을 남긴다. 확인하지 않은 숫자는 정답처럼 채우지 않는다.
  - 오류가 나오면 무작정 명령을 다시 입력하기보다 어느 단계까지 성공했는지와 오류 문구를 기록한다.
