## 2교시 · nslookup

### 문제 2-1 · 도메인 이름을 IP 주소로 — 두 DNS 서버에 묻기

- (가-1) 처음 `nslookup example.com` 을 쳤을 때, 내가 물어본 DNS 서버의 주소와 example.com 의 IPv4 주소를 적어 주세요.
  - 쓸 내용: 화면 맨 위 `Address` 줄의 주소 하나, 아래쪽 `Addresses` 에서 숫자 네 개를 점으로 이은 주소 하나 — 두 개를 「서버: … / example.com: …」처럼. 맥북은 맨 위 `Address`, 아래 `Name:` 다음 `Address` 줄
  - 답: 
    - 서버: 168.126.63.1 / example.com: 104.20.23.154
- (가-2) `nslookup example.com 8.8.8.8` 을 쳤을 때, 맨 위 `서버` 줄에 나온 이름과 example.com 의 IPv4 주소를 적어 주세요.
  - 쓸 내용: `서버` 줄의 이름 하나(맥북은 `Server`), IPv4 주소 하나. 시간 초과가 났으면 「시간 초과」라고 적어도 됩니다
  - 답: 
    - 서버 이름: dns.google / example.com의 IPv4 주소: 104.20.23.154
- (나) 🔍 화면 위쪽 `Address` 와 아래쪽 `Addresses` 는 각각 무엇의 주소일까요? 두 화면을 비교해서 적어 주세요.
  - 쓸 내용: ① 두 화면에서 바뀐 쪽과 그대로인 쪽 ② 그렇게 된 이유 — 위쪽 · 아래쪽이 각각 무엇의 주소인지를 근거로 쓰기
  - 답: 위쪽 Address는 내가 질문한 DNS 서버의 주소이고, 아래쪽 Addresses는 조회한 example.com에 대해 받은 IP 주소이다. 두 번째 명령에서는 질문할 서버를 8.8.8.8로 지정했으므로 위쪽 서버 정보가 바뀐다. 아래쪽은 계속 같은 이름을 조회한 결과이므로 같은 IP가 나올 수 있다.
- (다-1) 회사 PC 가 회사 DNS 서버 대신 `8.8.8.8` 같은 외부 DNS 서버에 직접 묻고 있다면, 관제 담당자는 왜 이것을 확인해야 할까요?
  - 쓸 내용: ① 회사 DNS 서버가 평소에 하는 일(검색해서 찾아도 됩니다) ② 외부 DNS 에 직접 물으면 그 일을 거치지 않게 되는 까닭
  - 답: 회사 DNS 서버는 이름에 해당하는 주소를 알려 주는 것뿐 아니라, 설정에 따라 위험한 도메인을 차단하고 PC의 조회 기록을 남긴다. 회사 PC가 외부 DNS 서버에 직접 질문하면 회사 DNS의 차단과 기록을 거치지 않을 수 있으므로, 관제 담당자는 회사 정책에 맞는 조회인지와 외부 DNS를 사용하는 이유를 확인해야 한다.
- (다-2) 내 PC 의 DNS 서버 설정이 나도 모르게 낯선 주소로 바뀌어 있다면, 어떤 일이 생길 수 있을까요?
  - 쓸 내용: ① 그 낯선 DNS 서버가 내 질문에 어떤 답을 줄 수 있는지 ② 그 답 때문에 내가 어디로 접속하게 되는지
  - 답: DNS 서버 설정이 나도 모르게 낯선 주소로 바뀌었다면, 그 서버가 정상 도메인에 대해 공격자 서버의 IP 같은 잘못된 주소를 답할 수 있다. 내 PC는 받은 주소를 이용해 접속을 시도하므로 의도한 서버와 다른 곳으로 연결될 위험이 있다. 따라서 DNS 설정이 변경된 이유와 해당 서버가 신뢰할 수 있는 서버인지 확인해야 한다.

### 문제 2-2 · URL 에서 이름을 꺼내 묻기 — 없는 이름이면

- (가-1) `day03_2-2_url_example.py` 를 실행했을 때 나온 두 줄을 그대로 옮겨 적어 주세요.
  - 쓸 내용: 터미널에 나온 출력 두 줄을 복사해 붙여 넣기
  - 답:
    - ['https:', '', 'example.com', 'news', 'today']
    - example.com → 172.66.147.243
- (가-2) `day03_2-2_url_nowhere.py` 의 맨 마지막 줄에 나온 에러 이름과, 같은 이름을 `nslookup` 했을 때 나온 문구를 적어 주세요.
  - 쓸 내용: 에러 이름은 마지막 줄의 `:` 앞부분 하나, `nslookup` 문구는 `Non-existent domain` 이 든 줄 하나(맥북은 `NXDOMAIN` 이 든 줄)
  - 답:
    - 오류 이름: socket.gaierror
    - nslookup 문구:
    - *** kns.kornet.net이(가) abc.nowhere-not-exist.com을(를) 찾을 수 없습니다. Non-existent domain
- (나-1) `parts[2]` 를 꺼냈더니 도메인 이름이 나왔습니다. 왜 번호 2 칸에 도메인 이름이 있을까요?
  - 쓸 내용: ① (가-1) 첫 줄의 리스트를 0 번부터 세어 각 칸에 무엇이 있는지 ② `//` 사이에 무엇이 생겼는지
  - 답: `split("/")`로 URL을 나누면 0번에는 `'https:'`, 1번에는 빈 문자열 `''`, 2번에는 `'example.com'`, 3번에는 `'news'`, 4번에는 `'today'`가 들어간다. `https://`의 두 슬래시 사이에는 글자가 없어서 빈 문자열이 한 칸 생긴다. 리스트는 0번부터 세므로 `parts[2]`를 꺼내면 세 번째 요소인 도메인 이름이 나온다.
- (나-2) 두 번째 파일은 왜 마지막 줄에서 에러가 나며 멈췄을까요? `nslookup` 결과와 이어서 적어 주세요.
  - 쓸 내용: ① `gethostbyname()` 이 DNS 서버에 무엇을 물었는지 ② DNS 서버가 어떤 답을 했는지 ③ 그래서 왜 에러가 났는지
  - 답: ['https:', '', 'abc.nowhere-not-exist.com', 'login']
- (다) 🔍 `Non-existent domain`(NXDOMAIN) 이 나왔다고 인터넷이 끊긴 걸까요? 아니라면 왜 아닌지 적어 주세요.
  - 쓸 내용: ① DNS 서버가 답을 했는지 안 했는지 ② 인터넷이 정말 끊겼다면 화면이 어떻게 달랐을지
  - 답: NXDOMAIN이 나왔다고 인터넷이 끊긴 것은 아니다. 내 결과에서는 DNS 서버가 응답하지 않은 것이 아니라, `abc.nowhere-not-exist.com`이라는 이름이 존재하지 않는다는 답을 했다. DNS 서버에 연결할 수 없어 응답을 받지 못했다면 시간 초과 같은 결과가 나올 수 있다. 따라서 이름이 없다는 응답과 응답 자체를 받지 못한 상황을 구분해야 한다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요. (「이 교시에 새로 안 것」 칸)
  - 쓸 내용: 새로 안 것 하나와, 그게 왜 기억에 남는지
  - 답: 이번에 새로 알게 된 것은 DNS 조회 화면에서 질문을 받은 서버와 조회해서 얻은 주소를 구분해서 읽어야 한다는 점이다. 처음에는 example.com의 IPv4가 두 개 나오는데 왜 104.20.23.154를 답으로 골랐는지 궁금해서 질문했다. 확인해 보니 104.20.23.154와 172.66.147.243 모두 조회 결과였고, 문제에서 하나를 요구해서 그중 하나를 선택한 것이었다. 위쪽의 168.126.63.1은 example.com의 주소가 아니라 내가 질문한 DNS 서버의 주소였다. 구글 DNS에 물었을 때는 그 위쪽 주소가 8.8.8.8로 바뀌어서 두 역할을 구분할 수 있었다.

    이름을 찾지 못한 결과도 다시 질문하며 이해했다. URL을 나누는 코드는 성공했지만 abc.nowhere-not-exist.com의 IP를 알아내는 단계에서 socket.gaierror가 났고, nslookup에서도 Non-existent domain이라는 답을 받았다. 이름을 찾지 못한 것과 DNS 서버의 응답 자체를 받지 못한 것은 다르다는 점까지 연결됐다. 같은 화면에 서버 주소, 조회 결과, 오류가 함께 나와도 각각 무엇을 뜻하는지 따로 읽어야 한다는 점을 이번 실습으로 이해했다.

## 3교시 · DNS 계층

### 문제 3-1 · 레이블로 나누고 권한 있는 네임서버 찾기

- (가-1) `day03_3-1_labels_kr.py`(`mail.google.co.kr`)를 실행했을 때 나온 세 줄을 그대로 옮겨 적어 주세요.
  - 쓸 내용: 터미널 출력 세 줄을 복사해 붙여 넣기
  - 답:
    - kr
    - co.kr
    - ['kr', 'co', 'google', 'mail']
- (가-2) `nslookup -type=ns example.com` 에서 `nameserver =` 뒤에 나온 이름을 모두 적고, 몇 개였는지도 적어 주세요.
  - 쓸 내용: 네임서버 이름들과 개수. `internet address` 줄의 IP 는 적지 않습니다
  - 답: `example.com`의 권한 있는 네임서버는 `hera.ns.cloudflare.com`과 `elliott.ns.cloudflare.com`이며, 조회 결과에서 확인한 이름은 총 2개이다.
- (나) 두 번째 파일의 둘째 줄은 `google.co.kr` 이 아니라 `co.kr` 로 나왔습니다. 왜 그럴까요?
  - 쓸 내용: ① `[-2:]` 가 몇 개의 레이블을 꺼내는지 ② `.kr` 아래에 어떤 계층이 하나 더 있는지(안내 3.1 절 참고)
  - 답: `parts[-2:]`는 리스트의 마지막 두 요소만 꺼낸다. `mail.google.co.kr`을 점으로 나누면 `['mail', 'google', 'co', 'kr']`이므로 마지막 두 요소는 `'co'`와 `'kr'`이다. 이 둘을 점으로 연결해서 `co.kr`이 출력됐다. 이 이름에는 `kr` 아래에 `co.kr`이라는 중간 단계가 있으므로, `google.co.kr`까지 꺼내려면 마지막 세 요소가 필요하다.
- (다-1) (가-2) 에서 본 것처럼 한 도메인에 네임서버를 둘 이상 두는 이유는 무엇일까요?
  - 쓸 내용: 네임서버가 하나뿐일 때 그 서버가 멈추면 무슨 일이 생기는지
  - 답: 권한 있는 네임서버가 하나뿐이면 그 서버가 멈추거나 연결되지 않을 때 해당 도메인의 DNS 정보를 새로 조회하기 어려워진다. 네임서버를 둘 이상 두면 하나가 응답하지 못해도 다른 서버에 조회할 수 있어, DNS 조회가 중단될 가능성을 줄일 수 있다.
- (다-2) 어떤 회사 도메인의 네임서버가 갑자기 낯선 서버로 바뀌었다면, 어떤 일이 생길 수 있을까요?
  - 쓸 내용: ① 권한 있는 네임서버가 그 도메인에 대해 정하는 것 ② 그 서버를 공격자가 관리하게 되면 웹 · 메일 접속이 어떻게 되는지
  - 답: 권한 있는 네임서버는 담당 도메인의 IP 주소나 메일 서버 같은 DNS 정보를 제공한다. 그 담당 서버가 공격자가 관리하는 서버로 바뀌면, 공격자가 웹이나 메일에 관한 정보를 잘못된 대상으로 안내할 수 있다. 따라서 네임서버가 갑자기 낯선 서버로 변경됐다면 정상적인 변경인지, 도메인 관리 권한이 탈취된 것인지 확인해야 한다.

### 문제 3-2 · 권한 있는 네임서버에게 직접 묻기

- (가-1) `nslookup example.com`(리졸버에 물은 화면)에 `권한 없는 응답:` 줄이 있었는지, 그리고 IPv4 주소를 적어 주세요.
  - 쓸 내용: 「있음 / 없음」 하나와 IPv4 주소 하나. 맥북은 `Non-authoritative answer:` 줄
  - 답: 있음 / IPv4 주소: 104.20.23.154
- (가-2) 권한 있는 네임서버에 직접 물은 화면에 `권한 없는 응답:` 줄이 있었는지, 그리고 IPv4 주소를 적어 주세요.
  - 쓸 내용: 「있음 / 없음」 하나와 IPv4 주소 하나(맥북은 `Non-authoritative answer:` 줄). 시간 초과면 「시간 초과」라고 적어도 됩니다
  - 답: 없음 / IPv4 주소: 104.20.23.154
- (나-1) 🔍 두 화면에서 `권한 없는 응답:` 줄이 한쪽에만 나온 이유는 무엇일까요?
  - 쓸 내용: ① 첫 화면은 누가 답했는지 ② 둘째 화면은 누가 답했는지 ③ 그 차이가 왜 그 줄로 나타나는지
  - 답: 첫 번째 조회에는 리졸버인 `kns.kornet.net`이 답했다. 이 서버는 `example.com`의 DNS 정보를 직접 담당하는 서버가 아니라, 조회해서 얻었거나 캐시에 저장한 정보를 대신 답하므로 `권한 없는 응답`이 표시됐다. 두 번째 조회에는 `example.com`의 권한 있는 네임서버인 `hera.ns.cloudflare.com`이 직접 답했기 때문에 해당 표시가 없었다.
- (나-2) 「권한 없는 응답」이라는 이름 때문에 틀린 답처럼 들립니다. 정말 틀린 답일까요?
  - 쓸 내용: ① 리졸버가 그 답을 어디서 받아 왔는지 ② (가-1) · (가-2) 의 IPv4 가 같았는지
  - 답: `권한 없는 응답`이라는 표시만으로 틀린 답이라고 판단할 수 없다. 리졸버는 권한 있는 네임서버에서 얻은 정보나 그 정보를 저장한 캐시를 이용해 답한다. 내 두 조회 결과에는 모두 `104.20.23.154`와 `172.66.147.243`이 나왔으므로 IPv4 주소들은 같았다. 두 번째 화면에서는 표시 순서만 달랐다.
- (다) 리졸버가 준 답이 이상해 보일 때, 권한 있는 네임서버에 직접 물어보면 무엇을 알 수 있을까요?
  - 쓸 내용: 두 답이 같을 때와 다를 때 각각 무엇을 알 수 있는지
  - 답: 권한 있는 네임서버에 직접 조회하면, 리졸버가 준 주소 정보가 담당 서버의 주소 정보와 일치하는지 비교할 수 있다. 두 답이 같다면 현재 비교한 주소 정보가 일치한다는 것을 확인할 수 있다. 다르다면 리졸버의 캐시에 이전 정보가 남았는지, 응답이나 설정에 다른 차이가 있는지 추가로 확인해야 한다. 내 결과에서는 IPv4 두 개가 모두 같고 표시 순서만 달랐다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요. (「이 교시에 새로 안 것」 칸)
  - 쓸 내용: 새로 안 것 하나와, 그게 왜 기억에 남는지
  - 답: 이번에 새로 알게 된 것은 ‘권한 없는 응답’이 틀린 답이라는 뜻이 아니라, 그 도메인의 정보를 직접 담당하는 서버가 아닌 리졸버가 답했다는 표시라는 점이다. DNS와 리졸버의 뜻을 다시 설명해 달라고 했고, 리졸버는 내 PC가 바쁠 때만 대신하는 서버가 아니라 평소 이름 조회를 맡아 주는 역할이라는 것을 이해했다. 권한 있는 네임서버는 그 도메인의 정보를 직접 담당하고, 리졸버는 필요한 정보를 찾아오거나 저장한 답을 이용해 알려 준다.

    실제로 kns.kornet.net에 물었을 때는 ‘권한 없는 응답’이 있었고, hera.ns.cloudflare.com에 직접 물었을 때는 그 표시가 없었다. 그런데 두 결과에 나온 IPv4는 104.20.23.154와 172.66.147.243으로 같았고 순서만 달랐다. 표시의 이름만 보고 잘못된 답이라고 생각하지 말고, 누가 답했는지와 어떤 주소가 나왔는지를 함께 봐야 한다는 점을 알게 됐다. 이름의 순서나 주소 목록의 첫 줄만 보는 대신 역할과 결과를 나눠 읽는 방식으로 복습하려고 한다.

## 4교시 · 레코드와 캐시

### 문제 4-1 · 메일 서버와 별칭 — MX · CNAME

- (가-1) `nslookup -type=mx google.com` 에서 메일 서버 이름(`mail exchanger =` 뒤)과 우선순위 숫자(`MX preference`)를 적어 주세요.
  - 쓸 내용: 메일 서버 이름 하나, 숫자 하나. 아래에 같이 나오는 IP 는 적지 않습니다
  - 답: 메일 서버 이름: smtp.google.com / 우선순위: 10
- (가-2) `nslookup www.naver.com` 에서 `Aliases:` 줄의 이름과 `이름:` 줄의 최종 이름을 적어 주세요.
  - 쓸 내용: `Aliases:` 에 나온 이름, `이름:` 에 나온 이름. 맥북은 `canonical name =` 뒤가 최종 이름입니다
  - 답:
    - 별칭: www.naver.com
    - 최종 이름: www.naver.com.nheos.com
- (나-1) MX 레코드는 왜 IP 가 아니라 서버 이름으로 답할까요? 그 서버의 IP 는 어떻게 알아낼까요?
  - 쓸 내용: ① 서버 이름으로 적어 두면 좋은 점(서버 IP 가 바뀌는 경우를 생각해 보세요) ② IP 를 알아내는 방법(안내 4.1 절의 표 참고)
  - 답: MX 레코드에 메일 서버 이름을 적어 두면, 그 서버의 IP가 바뀌어도 같은 이름을 유지하면서 주소 정보를 바꿀 수 있다. 내 조회에서는 메일 서버 이름으로 `smtp.google.com`이 나왔다. 이 서버의 IP가 필요하면 해당 이름의 A 레코드로 IPv4를, AAAA 레코드로 IPv6를 조회하면 된다.
- (나-2) `www.naver.com` 은 왜 다른 이름(정식 이름)을 가리키고 있을까요?
  - 쓸 내용: ① CDN 이 무엇인지 한 줄 ② 큰 사이트가 CNAME 으로 CDN 이름을 가리키게 하는 까닭
  - 답: CDN은 콘텐츠를 여러 지역의 서버에서 제공해 전송 속도를 높이고 부하를 분산하는 서비스이다. 큰 사이트는 사용자가 입력하는 이름을 유지하면서 CDN 등 서비스를 제공하는 쪽의 이름으로 연결하기 위해 CNAME을 사용할 수 있다. 내 결과에서는 `www.naver.com`이 별칭이고, 최종 이름은 `www.naver.com.nheos.com`으로 조회됐다.
- (다) 🔍 의심스러운 메일을 받았을 때, 보낸 쪽 도메인의 MX 레코드를 확인하면 무엇을 알 수 있을까요?
  - 쓸 내용: ① 정상 회사 도메인의 MX 는 보통 어떤지 ② MX 가 없거나 낯설면 무엇을 의심할 수 있는지
  - 답: 메일을 받는 정상 회사 도메인은 보통 MX 레코드로 수신 서버를 지정한다. 의심스러운 메일의 보낸 쪽 도메인을 조회하면 메일 수신 서버가 설정돼 있는지와 어떤 서버를 가리키는지 확인할 수 있다. MX가 없거나 회사와 관계를 확인하기 어려운 낯선 서버를 가리키면 도메인의 용도와 설정을 추가로 조사할 단서가 된다. 다만 MX의 유무나 서버 이름만으로 피싱 여부를 확정할 수는 없다.

### 문제 4-2 · 내 PC 의 DNS 캐시와 TTL

- (가-1) `ipconfig //displaydns` 에서 본 `example.com` 의 TTL 숫자와, `//flushdns` 뒤에 그 항목이 남아 있었는지 적어 주세요.
  - 쓸 내용: 숫자 하나와 「남음 / 없어짐」 하나. 맥북은 「건너뜀」, 「표시할 수 없습니다」가 나오면 옆 사람 화면의 값
  - 답: DNS 확인자 캐시를 플러시했습니다.
- (가-2) `day03_4-2_ttl_60.py`(`ttl = 60`)를 실행했을 때 나온 네 줄을 그대로 옮겨 적어 주세요.
  - 쓸 내용: 터미널 출력 네 줄을 복사해 붙여 넣기
  - 답:
    - 30 초: 캐시의 답을 쓴다
    - 100 초: DNS 서버에 새로 묻는다
    - 299 초: DNS 서버에 새로 묻는다
    - 300 초: DNS 서버에 새로 묻는다
- (나) 첫 파일과 두 번째 파일에서 100초 줄의 결과가 다릅니다. 왜 그럴까요?
  - 쓸 내용: ① 두 파일의 만료 시각(저장한 시각 + TTL)을 각각 계산 ② 100 이 각 만료 시각보다 작은지 큰지
  - 답: 두 파일 모두 저장 시각은 0초이다. 첫 파일의 만료 시각은 `0 + 300 = 300초`이고, 두 번째 파일은 `0 + 60 = 60초`이다. 100초는 300초보다 이르므로 첫 파일에서는 캐시를 사용한다. 반면 100초는 60초를 지났으므로 두 번째 파일에서는 DNS 서버에 새로 묻는다고 출력된다.
- (다-1) 🔍 사이트가 서버 IP 를 바꿨는데도, 한동안은 옛 IP 로 접속되는 사람이 있습니다. 왜 그럴까요?
  - 쓸 내용: ① 캐시에 무엇이 저장되는지 ② TTL 이 지나기 전에는 어떻게 동작하는지
  - 답: PC나 리졸버의 DNS 캐시에는 이전에 조회한 이름과 IP 주소 등의 정보가 저장된다. 사이트가 권한 있는 네임서버의 IP 정보를 변경했더라도, 캐시의 유효 시간이 남아 있으면 저장해 둔 옛 IP를 사용할 수 있다. 그래서 변경 직후에는 한동안 옛 IP로 접속을 시도하는 사용자가 있을 수 있다.
- (다-2) 어떤 PC 가 계속 이상한 주소로 접속된다면, 관제 담당자는 왜 `ipconfig //flushdns` 부터 해 볼까요?
  - 쓸 내용: ① 캐시에 어떤 답이 남아 있을 수 있는지 ② 비운 뒤에는 PC 가 어떻게 다시 묻는지
  - 답: PC의 DNS 캐시에 이전 주소나 잘못된 조회 결과가 남아 있으면, 그 정보를 반복해서 사용할 수 있다. `ipconfig //flushdns`로 PC의 DNS 캐시를 비우면 저장된 답을 제거하고, 다음 조회에서 DNS 서버에 다시 질문하도록 할 수 있다. 이를 통해 문제가 PC에 남은 캐시와 관련된 것인지 확인할 수 있다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요. (「이 교시에 새로 안 것」 칸)
  - 쓸 내용: 새로 안 것 하나와, 그게 왜 기억에 남는지
  - 답: 이번에 새로 알게 된 것은 캐시가 ‘작은 데이터’라는 뜻이 아니라, 받은 정보를 저장했다가 다시 사용하는 방식이고 DNS에서는 TTL이 그 답을 사용할 수 있는 시간을 정한다는 점이다. 브라우저에서 보던 캐시와 같은 것인지 질문했는데, 저장해 재사용하는 기본 원리는 같고 저장하는 내용과 위치가 다르다고 이해했다. DNS 캐시는 이름과 IP 같은 조회 정보를 저장하며, 캐시의 크기는 저장하는 내용에 따라 달라진다.

    TTL 코드에서도 저장 시각과 유효 시간을 함께 봐야 했다. 0초에 저장했다고 가정하면 TTL 300의 만료 시각은 300초, TTL 60은 60초여서 같은 100초에도 결과가 달랐다. 또 300 < 300은 False이므로 만료 시각과 같을 때도 새 조회가 필요하다고 출력됐다. 실제 PC에서 본 ping의 TTL 51과 다른 이름의 DNS TTL 15는 example.com의 캐시 TTL로 적을 수 없다는 점도 구분했다. 캐시를 비우기 전 example.com의 TTL은 아직 기록하지 못했으므로 따로 확인해야 한다. 숫자가 보인다고 바로 답에 옮기기보다 어느 정보의 값인지 먼저 확인하는 것이 중요하다는 점을 알게 됐다.
