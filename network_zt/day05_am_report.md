## 2교시 · 클라우드 · SaaS

### 문제 2-1 · 서비스 형태 네 개 가르고 먼저 볼 기록 정하기

- (가-1) 서비스 A · B · C · D 는 각각 IaaS · PaaS · SaaS 중 무엇인가요?
  - 쓸 내용: 「A: … / B: … / C: … / D: …」 네 개
  - 답: **A: IaaS / B: PaaS / C: SaaS / D: PaaS**
  - 이해한 이유: A는 가상 서버의 운영체제와 보안 설정을 회사가 관리한다. B는 업체가 관리하는 실행 환경에 회사의 코드를 올린다. C는 완성된 메일·문서 협업 프로그램을 사용한다. D도 회사가 직접 만든 프로그램을 올리므로 PaaS이다. 직원 계정과 권한을 관리한다는 설명만 보고 D를 SaaS로 판단하면 안 된다.

- (가-2) 서비스 C 에서 회사가 직접 맡는 것 세 가지를 적어 주세요.
  - 쓸 내용: 안내 2.1 의 SaaS 줄에 나온 「내가 맡는 것」 세 가지
  - 답: **직원 계정, 접근 권한, 서비스에 넣은 데이터**이다.
  - 이해한 이유: 프로그램을 업체가 운영해도 누가 사용하고, 어떤 자료까지 접근하며, 회사 자료를 어떻게 보관하고 공유할지는 회사가 관리해야 한다. 예를 들어 퇴사자의 접근 권한을 회수하거나 중요한 문서의 외부 공유를 제한하는 일이다.

- (나) 🔍 서비스 C 에는 방화벽 규칙을 직접 걸 수 없습니다. 그러면 회사에 남는 통제 수단은 무엇일까요?
  - 쓸 내용: ① 남는 통제 수단 한 가지 ② 그것으로 정할 수 있는 것 한 가지
  - 답: **① 계정별 접근 권한 설정 ② 특정 문서를 허가받은 직원만 열람하도록 정하는 것**이다.
  - 이해한 이유: 회사가 SaaS 업체의 기반 서버 방화벽을 직접 관리하지 않더라도 계정과 자료의 접근 범위는 통제할 수 있다. 서비스가 제공하는 보안 설정까지 전혀 없다는 뜻은 아니다.

- (다) 서비스 A 와 서비스 C 에서 사고가 났을 때, 회사가 먼저 볼 기록은 각각 무엇인가요?
  - 쓸 내용: 「서비스 A: … / 서비스 C: …」
  - 답: **서비스 A: 서버의 운영체제 로그와 방화벽 로그 / 서비스 C: 해당 SaaS 서비스의 로그인 기록**이다.
  - 이해한 이유: A는 회사가 서버 안쪽을 직접 관리하므로 서버와 통신 기록을 확인한다. C는 외부에서 서비스에 바로 로그인할 수도 있으므로 서비스가 남긴 계정·시각·접속 IP 기록을 먼저 확인한다. 로그인 이후 무엇을 열람하거나 다운로드했는지는 활동 기록으로 추가 확인한다.

### 문제 2-2 · 방화벽 로그에 없는 접속 찾고 조치 보고 평가하기

- (가) 방화벽 로그에 짝이 없는 로그인은 몇 건이고, 번호는 무엇인가요?
  - 쓸 내용: 「… 건 / 번호: …」 번호는 `1, 4, 6` 처럼 숫자로 써도 됩니다
  - 답: **3건 / 번호: 1, 4, 6**이다.
  - 이해한 이유: 회사 방화벽에는 09:02, 09:15, 11:30 기록이 있어 각각 2·3·5번과 대응한다. 1·4·6번은 대응하는 기록이 없고 접속 IP도 회사 공인 IP인 `203.0.113.10`과 다르다. 이 문제에서는 회사 밖에서 SaaS에 직접 접속한 경우로 해석한다.

- (나) 🔍 방화벽 로그에 없는 접속 중 가장 수상한 것은 몇 번이고, 그렇게 본 근거는 무엇인가요?
  - 쓸 내용: ① 번호 하나 ② 근거 두 가지 이상(시각 · 접속한 IP · 같은 계정의 다른 접속 중에서 골라서)
  - 답: **1번**이다. **첫째, 접속 시각이 새벽 03:12이다. 둘째, 회사 공인 IP가 아닌 `192.0.2.88`에서 접속했다. 셋째, 같은 lee 계정의 3번 접속은 09:15에 회사 공인 IP인 `203.0.113.10`에서 이루어져 시각과 접속 위치를 비교할 필요가 있다.**
  - 이해한 이유: 회사 밖 접속이라는 이유만으로 1·4·6번을 전부 공격으로 확정하는 것은 아니다. 재택근무일 수도 있다. 1번을 우선 확인할 대상으로 고르되, 새벽 접속이나 퇴사 예정이라는 사실만으로 실제 접속자를 공격자라고 단정하지 않는다.

- (다) 담당자 보고에서 **확인된 것**과 **확인하지 못한 것**을 각각 적어 주세요.
  - 쓸 내용: 「확인된 것: … / 확인하지 못한 것: … (두 가지 이상)」
  - 답: **확인된 것: 예시의 담당자가 오전 10시에 lee 계정의 비밀번호를 변경했다는 사실이다. / 확인하지 못한 것: ① 새벽 03:12 접속을 실제로 누가 했는지 ② 그 접속에서 어떤 자료를 열람하거나 다운로드했는지 ③ 다른 계정에도 관련된 접속이 있었는지이다.**
  - 이해한 이유: 비밀번호 변경은 대응 조치이고, 변경 전에 있었던 행동의 조사 결과는 아니다. 새벽에 자료가 내려받아졌다면 오전에 비밀번호를 바꿨다고 그 일이 사라지는 것은 아니다. 따라서 이 조치만으로 “이제 안전하다”거나 “열람한 자료가 없다”고 확정할 수 없다.

- (라) 🔍 확인하지 못한 것을 확인하려면 어느 기록에서 무엇을 봐야 하나요?
  - 쓸 내용: ① 볼 기록 이름 ② 그 기록에서 찾을 것 두 가지(시각 · 접속 IP · 계정 중에서)
  - 답: **SaaS 서비스의 활동 기록**에서 **03:12 전후의 시각, lee 계정, 접속 IP `192.0.2.88`**을 대조해 자료 열람·다운로드 기록을 확인한다. 같은 IP와 관련된 다른 계정의 로그인 여부는 로그인 기록도 함께 확인한다.
  - 이해한 이유: 로그인 기록은 들어온 사실을, 활동 기록은 들어온 뒤의 행동을 확인하는 자료이다. lee는 09:15에도 접속했으므로 계정 이름만 보고 모든 활동을 새벽 접속의 행동으로 묶지 않아야 한다. 실제 사용자가 누구인지는 필요에 따라 계정 주인에게도 확인해야 한다.

- (한 줄) 고객에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 고객이 바로 읽을 수 있는 한 문장(확인된 것과 확인 중인 것을 함께)
  - 답: **lee 계정의 새벽 로그인은 회사 방화벽을 지나지 않은 SaaS 직접 접속으로 보이며, 비밀번호는 변경했지만 자료 열람·다운로드 여부는 아직 확인되지 않아 해당 시각·계정·IP의 서비스 기록을 추가 확인해야 합니다.**
  - 작성 기준: 수업의 가상 상황에서 작성한 보고 문장이다. 내가 실제 회사 계정의 비밀번호를 변경하거나 사고 조사를 수행했다는 뜻은 아니다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: **회사 업무용 서비스라도 모든 접속이 회사 방화벽을 지나는 것은 아니라는 점을 배웠다.** 외부에서 SaaS에 직접 접속하면 회사 방화벽에는 없고 서비스 로그인 기록에는 있을 수 있다. 기록이 없다는 말은 어느 장비의 기록인지 함께 봐야 한다.

### 이 교시에 새로 안 것

처음에는 IaaS·PaaS·SaaS를 설명대로 외우기보다, 이름이 왜 그렇게 붙었는지 궁금해서 풀네임을 질문했다. `aaS`는 `as a Service`이고, 앞의 단어가 무엇을 서비스로 제공받는지 나타낸다는 설명을 들었다.

| 명칭 | 풀네임 | 내가 이해한 핵심 |
|---|---|---|
| IaaS | Infrastructure as a Service | 서버·저장 공간·네트워크 같은 기반을 제공받는다. |
| PaaS | Platform as a Service | 내가 만든 프로그램을 올려 실행할 환경을 제공받는다. |
| SaaS | Software as a Service | 업체가 완성해서 운영하는 프로그램을 사용한다. |

일반 사용자는 SaaS를 사용하고 관련 실무자는 IaaS·PaaS를 쓰는 것인지도 질문했다. 일반 사용자는 완성된 서비스를 접할 일이 많지만, 이것은 사람의 직업을 나누는 분류가 아니라는 설명을 들었다. 개발자도 문서 작성이나 협업에 SaaS를 사용할 수 있고, 개인도 프로젝트를 위해 IaaS·PaaS를 사용할 수 있다. **누가 쓰느냐보다 무엇을 제공받고 어디까지 직접 관리하느냐가 기준**이라고 정리했다.

어제는 VPN과 방화벽을 통해 회사 네트워크로 들어오는 통신을 배웠는데, 오늘은 회사 네트워크 밖의 업무 서비스까지 시야를 넓혔다. 집에서 직접 SaaS에 접속하면 회사 방화벽을 지나지 않는다는 경로를 이해하는 것이 중요했다. 다만 VPN으로 해당 통신을 회사로 보내는 구성이라면 경로가 달라질 수 있으므로, 재택 접속은 무조건 회사에서 볼 수 없다고 일반화하지 않기로 했다.

로그를 읽을 때는 **로그인 사실, 실제 접속자, 자료 열람·다운로드 여부, 대응 조치**를 각각 나눠 봐야 한다. 비밀번호를 변경한 것과 과거에 자료가 유출되지 않았음을 확인한 것은 별개의 일이라고 배웠다.

## 3교시 · 망 구성도 읽고 고치기

### 문제 3-1 · 구성도 두 개를 읽고 DMZ 판정하기

- (가) 구성도 가 와 나 에서 웹 서버가 있는 구역을 각각 적어 주세요.
  - 쓸 내용: 「가: … / 나: …」
  - 답: **가: INSIDE(내부망) / 나: DMZ**이다.
  - 이해한 이유: 가는 `INSIDE ( WEB · DB )`이므로 두 서버가 같은 내부망에 있다. 나는 `DMZ ( WEB )`과 `INSIDE ( DB )`로 나뉘어 있다. 괄호 안의 서버 이름과 괄호 앞의 구역 이름을 함께 읽어야 한다.

- (나) 🔍 두 구성도 중 DMZ 가 있는 것은 어느 것이고, 그렇게 본 근거는 무엇인가요?
  - 쓸 내용: ① DMZ 가 있는 구성도 이름 ② 웹 서버가 있는 구역을 써서 근거
  - 답: **구성도 나**이다. 공개 웹 서버 WEB은 DMZ에, DB는 내부망에 있어 **서로 다른 구역으로 분리**돼 있기 때문이다.
  - 이해한 이유: 방화벽은 가와 나 모두 한 대이다. 방화벽 수가 아니라 공개 서버를 내부 서버와 분리했는지, 구역 사이의 통신이 방화벽을 거치는지를 봐야 한다.

- (다) 웹 서버가 해킹당했을 때, 가 와 나 에서 각각 내부 서버로 가려면 방화벽을 몇 번 지나야 하나요?
  - 쓸 내용: 「가: … 번 / 나: … 번」
  - 답: **가: 0번 / 나: 1번**이다.
  - 이해한 이유: 출발점은 인터넷이 아니라 이미 해킹당한 WEB이다. 가에서는 WEB과 DB가 같은 구역에 있어 오늘의 단순화된 구성상 중간 방화벽이 없다. 나에서는 DMZ의 WEB에서 FW를 거쳐 내부망의 DB로 가므로 한 번 지난다. 방화벽을 한 번 지난다는 것은 통제할 경계가 있다는 뜻이지, 공격이 반드시 막힌다는 뜻은 아니다.

- (라) 🔍 구성도 나 에서 `FW` 와 DMZ 를 잇는 선이 끊기면 영향받는 접속과 영향 없는 접속은 각각 무엇인가요?
  - 쓸 내용: 「영향받는 것: … / 영향 없는 것: …」
  - 답: **영향받는 것: 인터넷에서 DMZ의 WEB으로 가는 접속과 WEB–DB 사이의 통신이다. / 영향 없는 것: 내부망 안에서 이루어지는 통신이다.** 내부망에서 FW를 거쳐 인터넷으로 나가는 경로도 DMZ 연결을 지나지 않아 이 선의 단절로 직접 끊기지는 않는다.
  - 이해한 이유: 끊어진 곳은 FW 전체나 FW–INSIDE 연결이 아니라 FW–DMZ 연결이다. 그 선을 지나야 하는 통신인지 확인하면 된다. 다만 DMZ의 웹 서비스를 이용하는 내부 업무는 영향을 받을 수 있으므로 “내부 업무가 전부 정상”이라고까지 말하지는 않는다.

### 문제 3-2 · 경보 로그와 구성도를 함께 읽고 고치기

- (가) 🔍 로그 다섯 줄 중 이상한 줄은 몇 번이고(여러 개면 모두), 왜 이상한가요? 구성도를 근거로 적어 주세요.
  - 쓸 내용: 「이상한 줄: … 번 / 이유: …」 출발 · 도착 구역을 써서

### 이 교시에 새로 안 것

DMZ가 처음에는 잘 이해되지 않아 더 쉽게 설명해 달라고 여러 번 질문했다. 서버를 격리해서 보호한다는 의미인지 물었고, 여기서 격리는 모든 연결을 끊는 것이 아니라 **구역을 나누고 필요한 통신만 허용하는 것**이라고 설명받았다. DMZ는 프로그램이나 서버 자체의 이름이 아니라 공개 서버를 두는 네트워크 구역이다.

군대의 DMZ와 완충 구역이라는 점이 비슷하다고 느껴 풀네임도 질문했다. 네트워크의 DMZ도 `Demilitarized Zone`이라는 이름을 사용한다는 것을 알았다. 외부와 중요한 내부망 사이의 완충 구역이라는 이미지로 이해하는 데 도움이 됐다. 다만 비무장지대라는 이름이 방화벽이나 보안 검사를 없앤다는 뜻은 아니다. 방화벽 한 대로도 외부·DMZ·내부망을 나눌 수 있다.

3-2는 설명과 답을 보고도 바로 이해되지 않아 다시 쉽게 설명을 요청했다. **외부 PC는 손님, WEB은 접수대, DB는 창고**라는 가게 비유로 설명을 들었다. 손님이 접수대에 오는 것과 접수대 직원이 창고를 이용하는 것은 필요하지만, 손님에게 창고 직접 출입까지 허용하면 안 된다는 식이다. 이 비유를 실제 문제에 연결하면 2·3번은 외부 PC의 DB 직접 접근이 허용된 것이고, 5번은 WEB이 필요한 DB 통신을 하는 것이다.

아직 구성도와 로그를 처음부터 혼자 빠르게 연결해서 읽는 것은 더 연습해야 한다. 우선 **출발 구역 → 도착 구역 → 포트 → 허용·차단 결과** 순서로 읽고, 그 길이 원래 허용돼야 하는지를 확인하는 방식으로 복습하려고 한다. DMZ가 있어도 모든 경로를 허용하면 분리의 효과가 줄어든다는 점을 함께 기억해야 한다.

## 4교시 · 구역 규칙 코드

### 문제 4-1 · 규칙 판정 코드 읽고 설명하기

- (가) 함수 `default_policy` · `match_rule` · `judge` 가 각각 무엇을 하는지 적어 주세요.
  - 쓸 내용: 「default_policy: … / match_rule: … / judge: …」 함수마다 자유롭게
  - 답:
    - **default_policy:** 규칙표에 맞는 규칙이 없을 때 기본 동작을 정한다. 이 코드에서는 같은 구역끼리, inside에서 출발, outside로 나가는 통신을 허용하고 나머지는 차단한다.
    - **match_rule:** 규칙 한 줄의 출발·도착·포트가 요청과 모두 같은지 비교해 True 또는 False를 반환한다.
    - **judge:** RULES를 위에서부터 확인해 첫 번째 일치 규칙의 동작과 번호를 반환한다. 일치하는 규칙이 없으면 기본 정책의 동작과 번호 0을 반환한다.
  - 이해한 이유: 규칙 한 줄을 비교하는 역할, 규칙표를 순서대로 확인하는 역할, 끝까지 맞는 규칙이 없을 때 처리하는 역할을 나눠 둔 것이다.

- (나) `judge` 가 리턴하는 값 두 개는 무엇이고, 어느 줄이 만드나요?
  - 쓸 내용: 「값 ①: … / 값 ②: … / 만드는 줄: …」
  - 답: **값 ①: 동작인 permit 또는 deny / 값 ②: 적용 규칙 번호 / 만드는 줄: 일치하면 `return rule[4], rule[0]`, 일치하는 규칙이 없으면 `return default_policy(src, dst), 0`이다.**
  - 이해한 이유: 규칙 튜플은 `(번호, 출발, 도착, 포트, 동작)` 순서이고 인덱스가 0부터 시작하므로 `rule[4]`는 동작, `rule[0]`은 번호이다. 반환한 두 값은 `action, no = judge(src, dst, port)`로 나눠 받는다. 번호 0은 기본 정책을 사용했다는 표시이다.

- (다) 🔍 `judge` 의 `for` 는 맞는 규칙을 찾으면 바로 `return` 합니다. 같은 요청에 규칙이 둘 이상 맞는다면 어느 규칙이 적용되나요? 왜 `return` 으로 바로 끝내도록 만들었나요?
  - 쓸 내용: ① 규칙이 둘 이상 맞을 때 적용되는 규칙 ② 방화벽이 「첫 번째로 맞는 규칙」을 쓴다는 점과 이어서 `return` 으로 바로 끝내는 이유
  - 답: **RULES 목록에서 위쪽에 있는 첫 번째 일치 규칙이 적용된다.** 이 코드가 첫 번째 일치 규칙을 적용하는 방식을 구현하므로, 일치하면 return으로 판정 결과를 돌려주고 judge 전체를 끝내 뒤의 규칙이나 기본 정책이 적용되지 않게 한다.
  - 이해한 이유: return은 반복문만 멈추는 것이 아니라 함수를 종료한다. 코드가 번호순으로 정렬하는 것은 아니므로 적용 순서는 규칙 번호의 크기보다 리스트에 놓인 순서로 결정된다.

```python
def allowed_ports(src, dst, ports):

    return result
```

  - 쓸 내용: ① `result = []` 를 `for` 위에 두는 이유 ② `for` 안에 두면 달라지는 점
  - 답: **허용된 포트를 계속 누적하려면 반복문 시작 전에 빈 리스트를 한 번만 만들어야 하기 때문이다.** 반복문 안에 두면 매번 result가 빈 목록으로 초기화되어 앞에서 모은 포트가 사라지고 마지막 포트의 처리 결과만 남는다.
  - 이해한 이유: 바구니를 한 번 준비한 뒤 계속 담아야 하는데, 매번 새 빈 바구니로 바꾸는 것과 같다. 시험 포트가 `[22, 80, 443, 445, 3389]`일 때 inside→DMZ는 원래 모두 모아야 하지만, 반복문 안에서 초기화하면 마지막 `[3389]`만 남는다. outside→DMZ에서는 중간에 담은 443이 다음 반복에서 지워져 마지막에 `[]`가 된다. 또한 `return result`도 for 밖에 있어야 모든 포트 검사를 마친 뒤 결과를 반환한다.

- (한 줄) 고객에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 고객이 바로 읽을 수 있는 한 문장(요구사항이 지켜졌는지)
  - 답: **코드를 직접 실행해 시험한 다섯 포트에서 인터넷→DMZ는 443만, DMZ→내부망은 445만 허용되고, 내부망→DMZ는 모두 허용되며 인터넷→내부망은 모두 차단되어 요구사항과 일치함을 확인했습니다.**
  - 확인 범위: 내 PC에서 실행한 학습 코드의 판정 결과를 요구사항과 비교했다. 실제 회사 방화벽의 설정이나 인터넷 서버의 열린 포트를 검사한 것은 아니다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: **judge는 요청 하나를 판정하고, allowed_ports는 그 판정을 여러 포트에 반복해 허용된 것만 리스트에 모으는 함수**라는 점을 배웠다. 코드를 수정한 뒤에도 이해가 덜 돼 전체 설명을 다시 요청했고, 포트를 꺼내고 판정하고 바구니에 담는 흐름으로 다시 정리했다. 아직 스스로 작성하고 설명하는 연습이 더 필요하다.

### 이 교시에 새로 안 것

어제는 IP와 포트를 기준으로 통신을 판정했는데, 오늘은 outside·DMZ·inside라는 구역을 기준으로 같은 원리를 적용했다. match_rule은 규칙 한 줄이 맞는지 비교하고, judge는 규칙표 전체를 순서대로 확인하며, default_policy는 끝까지 일치하는 규칙이 없을 때 쓰는 정책이라는 역할을 나눠서 설명받았다. 이 기본 정책은 수업 코드가 정한 것이므로 실제 방화벽이 모두 내부망 출발을 허용한다고 일반화하면 안 된다.

실습을 하면서 보안 코드에 조건문이 많이 보인다고 질문했다. 실무에서도 대부분 조건문인지, AI가 코드를 작성하고 사람이 검수하게 되는 것 아닌지도 물었다. 지금 배우는 것은 허용·차단을 판정하는 부분이라 조건 비교가 눈에 많이 띄지만, 보안 코드 전체가 대부분 if문이라고 단정할 수는 없다는 설명을 들었다. 로그를 수집하고 정리하거나 횟수를 계산하고, 암호·통신 데이터를 처리하는 작업도 필요하다.

대표적으로 어떤 구문을 사용하는지도 질문해 다음과 같이 연결했다.

| 구문·자료구조 | 수업과 연결해서 정리한 역할 |
|---|---|
| if / elif / else | 조건에 따라 동작을 나눈다. |
| for | 규칙, 로그, 포트를 하나씩 꺼낸다. |
| def / return | 작업을 함수로 묶고 결과를 돌려준다. |
| 리스트·튜플 | 규칙이나 포트처럼 여러 값을 담는다. |
| 딕셔너리 | IP별·계정별 횟수를 저장한다. 이전 NXDOMAIN 집계 결과도 이 형태였다. |
| set | 중복을 없애 서로 다른 계정 수 등을 구분한다. |
| try / except | 잘못된 입력이나 변환 오류가 생겼을 때의 처리를 정한다. |
| with open | 파일을 열어 기록을 읽거나 쓴다. |

위 구문을 모두 오늘 실습에서 작성했다는 뜻은 아니다. 실무 코드에 관한 질문에서 설명받은 예시이다. 오늘은 구역 규칙 판정 코드를 직접 실행했고, 허용 포트 함수도 초기 상태를 실행한 뒤 수정했다. 수정 후 다시 실행한 `[443]`, `[445]`, `[22, 80, 443, 445, 3389]`, `[]` 네 줄을 직접 확인해 채팅에 공유했다.

AI가 코드 초안을 만들어도 문법이 맞고 실행된다는 것만으로 요구사항까지 맞는 것은 아니라는 설명이 중요했다. 예를 들어 외부의 DB 접근만 막아야 하는데 DB로 가는 모든 접근을 차단하면 WEB의 업무 통신도 막는다. 검수하려면 무엇을 막고 무엇을 유지해야 하는지와 코드의 조건을 이해해야 한다.

4-2에서는 코드 수정과 이해가 별개라는 점도 느꼈다. 수정하고 문제를 풀어봤지만 전체 흐름이 덜 이해돼 다시 설명을 요청했다. **for가 포트를 꺼내고 → judge가 판정하고 → if가 허용인지 확인하고 → append가 담고 → 마지막 return이 목록을 돌려준다**는 순서로 정리했다. 리스트를 만드는 위치와 return의 들여쓰기는 결과를 바꾸므로 다시 살펴볼 부분이다.

### 제출까지 확인한 것과 추가로 배운 것

오전 과제의 별도 결과물인 `day05_diagram.md`는 오후 GitHub 제출 과정에서 위치를 다시 확인했다. 저장소 루트에서 `cat day05_diagram.md`가 실행됐으므로 파일은 그 위치에 있었지만, git add에는 `network_zt/day05_diagram.md`를 지정해 찾지 못했던 것이다. 파일 이름이 같아도 현재 폴더와 하위 폴더의 경로는 다르다는 것을 실제 오류와 연결했다.

파일 위치를 찾는 find는 이때 추가로 설명받은 명령어이다. cat은 지정한 파일의 내용을 읽고, find는 조건에 맞는 파일이 어디 있는지 찾는다. `find . -type f -iname '*diagram*'`에서 점은 현재 폴더부터의 검색, `-type f`는 파일, `-iname`은 대소문자 구분 없는 이름 비교이고, 별표는 앞뒤에 다른 글자가 있어도 찾도록 하는 패턴이다. 정확한 전체 이름을 찾을 때는 별표가 반드시 필요한 것은 아니다.

GitHub에 오전·오후 보고서, 구성도, 파이썬 파일 네 개를 제출했다. 이후 검수에서 구성도 양식과 코드 설명을 보완하고 다시 올렸으며, `21c6072` 커밋의 제출 파일 7개와 파이썬 파일 4개의 실행 결과가 확인됐다. 오전 4-1의 여섯 줄과 4-2의 네 줄도 내가 공유한 출력과 일치했다. 상세한 제출 과정과 오류 해결 기록은 오후 보고서의 7-3에 정리했다.
