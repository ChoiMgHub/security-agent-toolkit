### 문제 5-1 · 지연 · 지터 · 손실을 직접 계산하기

- (가) 회선 X 와 Y 의 평균 지연과 지터(이웃한 두 값의 차이의 평균), 회선 Z 의 손실률을 각각 구해 적어 주세요.
  - 쓸 내용: 「X: 평균 … ms · 지터 … ms / Y: 평균 … ms · 지터 … ms / Z: 손실 … %」
  - 답: **X: 평균 30ms · 지터 1ms / Y: 평균 26ms · 지터 38ms / Z: 손실 40%**이다.
  - 계산을 이해한 과정: 평균은 받은 시간의 합을 받은 개수로 나누고, 지터는 이웃한 값의 차이 크기를 평균 낸다. X·Y는 응답 5개이므로 차이는 4개이다. Z는 5번 보내고 2번 응답이 없어 전체 보낸 개수 5로 나눈다.

```text
X 응답: 30, 31, 29, 30, 30ms
X 평균: (30 + 31 + 29 + 30 + 30) / 5 = 150 / 5 = 30ms
X 이웃한 차이: 1, 2, 1, 0ms
X 지터: (1 + 2 + 1 + 0) / 4 = 1ms

Y 응답: 10, 50, 12, 48, 10ms
Y 평균: (10 + 50 + 12 + 48 + 10) / 5 = 130 / 5 = 26ms
Y 이웃한 차이: 40, 38, 36, 38ms
Y 지터: (40 + 38 + 36 + 38) / 4 = 38ms

Z: 5번 요청 중 2번 응답 없음
Z 손실률: 2 / 5 * 100 = 40%
```

- (나) 🔍 평균 지연만 보면 Y 가 더 좋아 보입니다. 화상회의에는 어느 회선이 더 나쁠까요? 왜 그런가요?
  - 쓸 내용: ① 회선 이름 하나 ② 지연 · 지터 숫자를 써서 이유
  - 답: **회선 Y가 더 나쁘다.** 평균 지연은 Y가 26ms로 X의 30ms보다 작지만, 지터는 Y가 38ms로 X의 1ms보다 훨씬 크다. 응답 시간이 크게 흔들리므로 실시간 음성·영상의 재생이 불안정해질 가능성이 더 크다.
  - 이해한 이유: 평균적으로 빠른 것과 매번 일정하게 도착하는 것은 다르다. 그렇다고 느려도 일정하기만 하면 좋다는 뜻은 아니다. 평균 지연과 지터를 함께 봐야 한다.

  - 쓸 내용: 자유롭게

### 이 교시에 새로 안 것

지연은 응답까지 걸리는 시간, 지터는 그 시간의 변동, 손실은 응답을 받지 못한 비율로 나눠 이해했다. ping의 시간은 편도 시간이 아니라 왕복 시간인 RTT(Round Trip Time)이다. 회선은 인터넷이나 네트워크 연결 하나를 가리키는 표현이고, 오늘의 회선 X·Y·Z는 계산 방법을 배우기 위한 예시이다.

5-1 설명을 듣고 “무작정 낮은 것보다 일정한 것이 중요한가”라고 질문했다. 지연이 크게 흔들리고 평균 지연도 높으면 어떻게 판단하는지도 물었다. **평균 지연이 작고 지터도 작은 상태가 바람직하며, 둘 중 하나만 보고 전체를 판단하지 않는다**고 설명받았다. 평균은 높지만 일정하면 꾸준히 늦는 것이고, 평균은 작아도 지터가 크면 도착 시간이 불규칙한 것이다.

5-2에서는 내 PC에서 ping을 직접 실행해 결과 전체를 공유하고, 실제 값으로 계산 설명을 받았다. 최댓값이 37ms이고 최솟값이 35ms라고 해서 그 차이 2ms가 바로 오늘의 지터가 되는 것은 아니다. **이웃한 차이 아홉 개의 합을 구해 평균을 내야 약 0.44ms**가 된다. 화면 요약의 평균 35ms와 표시된 열 값의 산술평균 35.3ms도 구분해 기록했다.

패킷 손실을 어제 본 재전송과 연결해서 배웠지만, ping이 TCP 재전송을 하는 것은 아니다. 프로토콜과 서비스에 따라 손실 처리 방식이 다르다. 실시간 음성·영상은 누락이나 늦은 도착에 영향을 받을 수 있으므로 평균 하나로 품질을 판단하지 않는다.

## 6교시 · 코드로 계산과 판정

### 문제 6-1 · 지터 함수 직접 만들기

- (가) 직접 만든 `jitter` 함수를 독스트링과 함께 아래 코드 블록에 붙여 넣어 주세요.
  - 쓸 내용: 독스트링을 쓴 함수를 복사해 아래 코드 블록에 붙여 넣기
  - 답: 설명받은 계산 방식으로 정리한 함수는 다음과 같다. 내가 공유한 실행 결과는 이 계산 방식의 결과와 일치했다. 독스트링은 함수가 하는 일·받는 값·리턴하는 값을 설명하는 글이고, 그 아래 네 줄이 실제 계산 코드이다.

```python
def jitter(got):
    """받은 응답 시간으로 지터를 계산한다.

    입력: 응답을 받은 시간 리스트 got(ms, 2개 이상)
    리턴: 이웃한 두 값 차이의 절댓값을 평균 낸 지터(ms)
    """
    total = 0
    for i in range(1, len(got)):
        total = total + abs(got[i] - got[i - 1])
    return total / (len(got) - 1)
```

| 코드 | 설명을 듣고 정리한 역할 |
|---|---|
| `total = 0` | 차이를 더할 합계를 한 번 준비한다. |
| `range(1, len(got))` | 위치 1부터 마지막 위치까지 비교한다. 첫 값에는 바로 앞 값이 없으므로 1부터 시작한다. |
| `got[i]`, `got[i - 1]` | 현재 값과 바로 앞 값을 꺼낸다. 위치 번호는 0부터 시작한다. |
| `abs(...)` | 차이가 음수여도 크기를 양수로 구한다. |
| `total = total + ...` | 차이를 계속 누적한다. |
| `return total / (len(got) - 1)` | 이웃한 차이의 개수로 나눠 평균을 돌려준다. |

- (나) 함수를 채운 뒤 실행해 나온 세 줄을 그대로 옮겨 적어 주세요.
  - 쓸 내용: 터미널 출력 세 줄을 복사해 붙여 넣기
  - 답: **내 PC에서 `day05_6-1_measure.py`를 실행하고 공유한 실제 출력**은 다음과 같다.

```text
회선 A | 지연 21.9 ms | 지터 1.1 ms | 손실 0 %
회선 B | 지연 42.3 ms | 지터 54.3 ms | 손실 0 %
회선 C | 지연 41.0 ms | 지터 1.7 ms | 손실 30 %
```

| 회선 | 출력의 의미 |
|---|---|
| A | 평균 응답 시간과 변동이 작고 응답 손실이 없다. |
| B | 손실은 없지만 19→95, 18→110처럼 큰 변화가 있어 지터가 크다. |
| C | 받은 값끼리의 변동은 작지만 응답 10개 중 3개가 빠졌다. |

이 출력은 내 PC에서 실행한 실제 프로그램 출력이다. 다만 계산의 입력인 회선 A·B·C의 목록 자체는 내가 새로 측정한 회선이 아니라 수업에서 제공한 연습 데이터이다.

- (다) `jitter` 함수의 리턴값은 무엇이고, `measure` 의 어느 줄에서 어떻게 쓰이나요?
  - 쓸 내용: ① 리턴하는 값이 무엇인지 ② 그 값을 받는 줄(`measure` 안)
  - 답: **응답 시간의 이웃한 차이를 평균 낸 지터 값(ms)을 반환하며, `measure` 안의 `jitter_value = jitter(got)`에서 그 값을 받는다.** 이후 `round(jitter_value, 1)`로 소수점 첫째 자리까지 표시해 다른 지표와 함께 출력한다.
  - 이해한 이유: jitter는 숫자를 계산해 돌려주고, measure가 그 숫자를 받아 화면에 출력하는 구조이다. 예를 들어 A의 계산값은 약 1.111…ms이고 출력은 1.1ms이다. 이 6-1의 measure는 세 숫자를 출력하며, 6-2의 measure가 세 값을 반환하는 구조와 구분한다.

### 문제 6-2 · 세 회선을 화상회의 기준으로 판정하기

- (가) 세 회선의 판정 결과(적합 · 부적합)와 걸린 기준을 각각 적어 주세요.
  - 쓸 내용: 「A: … / B: … (걸린 기준 …) / C: … (걸린 기준 …)」
  - 답: **A: 적합 / B: 부적합(걸린 기준: 지터) / C: 부적합(걸린 기준: 손실)**이다. 지연 150ms 이하·지터 30ms 이하·손실 1% 이하라는 수업 기준을 모두 만족해야 한다.

**수정 전 직접 실행하고 공유한 실제 출력**

```text
회선 A → 부적합 (걸린 기준: )
회선 B → 부적합 (걸린 기준: 지터)
회선 C → 부적합 (걸린 기준: 손실)
```

처음에는 `ok = False`가 임시로 들어 있어 세 회선을 모두 부적합으로 표시했다. 기준을 넘은 항목을 찾는 부분은 이미 작동하므로, A는 걸린 항목이 없어 괄호가 비어 있었다. 이것은 예외 오류가 아니라 판정식이 미완성인 상태였다.

**설명에 따라 수정한 판정식**

```python
ok = delay <= MAX_DELAY and jitter <= MAX_JITTER and loss <= MAX_LOSS
```

**수정 후 내 PC에서 직접 실행하고 공유한 실제 출력**

```text
회선 A → 적합
회선 B → 부적합 (걸린 기준: 지터)
회선 C → 부적합 (걸린 기준: 손실)
```

수정 후에는 세 기준을 모두 만족하는 A만 적합으로 바뀌었다. 이 결과는 예상 출력만 적은 것이 아니라 내가 직접 확인한 실행 결과이다.

| 회선 | 지연 ≤150ms | 지터 ≤30ms | 손실 ≤1% | 판정 |
|---|---|---|---|---|
| A | 21.9ms, 충족 | 1.1ms, 충족 | 0%, 충족 | 적합 |
| B | 42.3ms, 충족 | 54.3ms, 초과 | 0%, 충족 | 부적합 |
| C | 41.0ms, 충족 | 1.7ms, 충족 | 30%, 초과 | 부적합 |

- (나) 회선 C 는 지연과 지터가 작은데도 왜 부적합인가요? 어제(10/15) 오후 문제 5-2 에서 본 것과 연결해 적어 주세요.
  - 쓸 내용: ① C 의 손실률과 기준 ② 손실이 통신에 주는 영향 한 가지
  - 답: **C의 손실률은 30%로 기준 1%를 초과하기 때문이다.** 받은 응답의 시간이 일정해도 데이터가 빠지면 품질이 나빠질 수 있다. 어제 응답이 없어 SYN이 재전송되던 것을 본 것처럼, TCP 통신에서는 재전송과 대기로 추가 시간이 들 수 있고 실시간 음성·영상에서는 누락이나 끊김이 생길 수 있다.
  - 이해한 이유: 오늘 ping의 응답 없음과 어제 TCP 재전송은 같은 프로토콜의 동작은 아니다. 손실이나 응답 부재가 통신에 영향을 준다는 점을 연결했다. C는 받은 값만 보면 40~43ms로 비슷하지만 10개 중 3개를 못 받았다. 응답 없음인 None을 0ms로 넣으면 안 된다.

- (다) 🔍 `ok` 를 `and` 로 이은 이유는 무엇인가요? `or` 로 이으면 회선 B 의 판정이 어떻게 달라지나요?
  - 쓸 내용: ① `and` 로 이은 이유 ② `or` 로 이으면 B 의 판정이 어떻게 달라지는지
  - 답: **세 기준을 모두 만족해야 적합이므로 and로 연결한다. or로 연결하면 하나만 만족해도 통과하므로, 지터 기준을 초과한 B도 적합으로 잘못 판정된다.**
  - 이해한 이유: B는 지연 조건 True, 지터 조건 False, 손실 조건 True이다. `True and False and True`는 False이고, `True or False or True`는 True이다. 출력이 실행된다는 것뿐 아니라 요구사항을 맞게 표현했는지도 확인해야 한다.

- (한 줄) 고객에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 고객이 바로 읽을 수 있는 한 문장(어느 회선이 되고 안 되는지, 이유 한 가지)
  - 답: **수업의 화상회의 기준으로 회선 A는 적합하며, B는 지터 54.3ms가 기준 30ms를 초과하고 C는 손실률 30%가 기준 1%를 초과해 부적합한 것을 코드 실행으로 확인했습니다.**
  - 확인 범위: 준비된 연습 데이터와 수업의 기준을 적용한 결과이다. 실제 회선이나 모든 화상회의 서비스의 품질을 보증하는 판정은 아니다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: **숫자를 계산하는 일과 기준을 붙여 판정하는 일이 다르다는 점**을 배웠다. 평균 지연이 작아도 지터나 손실이 기준을 넘으면 부적합이고, 세 조건 모두를 요구할 때는 and를 써야 한다.

### 이 교시에 새로 안 것

5교시의 수작업 계산을 코드로 옮기면 같은 방법을 여러 회선에 적용할 수 있다. abs는 두 시간 차이의 크기를 구하고, for는 이웃한 값을 반복해서 비교하며, total은 차이를 누적한다. 오전에 허용된 포트를 모으던 것과 마찬가지로 누적값은 반복문 전에 준비하고, 최종 반환은 반복이 끝난 뒤에 한다.

6-1 출력이 나왔어도 jitter 함수가 무슨 역할인지 더 쉽게 설명해 달라고 다시 질문했다. **입력은 응답 시간 여러 개이고, 출력은 지터 숫자 하나**라는 설명을 들었다. 예를 들어 `[30, 31, 29]`이면 차이 1·2의 평균 1.5를 돌려준다. jitter가 평균 지연이나 손실률까지 계산하거나 적합 판정까지 하는 것은 아니라는 역할 구분으로 다시 정리했다.

독스트링은 함수 바로 아래 처음에 쓰는 설명 문자열이며, 함수의 하는 일·입력·리턴을 적는다. 독스트링 자체가 계산을 하는 것은 아니지만 함수를 다시 읽거나 다른 사람이 사용할 때 무엇을 넣고 무엇을 받는지 설명한다.

회선 C에서 지터 1.7ms와 손실 30%가 함께 나오는 이유도 정리했다. 수업 코드는 None을 제외해 받은 값끼리 지터를 계산하므로, 지터가 작아도 누락이 많을 수 있다. 이 계산은 주어진 연습 자료를 위한 단순화된 방식이며, 모든 상황의 네트워크 지터를 그대로 대표하는 것은 아니다.

6-2는 처음 실행했을 때 A도 부적합이고 걸린 기준은 비어 있어 설명을 받았다. `ok = False`를 세 비교식과 and로 바꾸고 다시 실행해 **A만 적합, B는 지터로 부적합, C는 손실로 부적합**인 결과를 직접 확인했다. 문법 오류가 없어도 임시 값이나 잘못된 논리 연산자가 있으면 의도와 다른 판정이 나올 수 있다는 점을 확인했다.

### 문제 7-1 · tracert 표에서 느려진 구간 찾기

- (가-1) 표 1 에서 지연이 처음 크게 뛴 구간은 몇 번 홉과 몇 번 홉 사이인가요?
  - 쓸 내용: 「… 번 홉과 … 번 홉 사이」 하나
  - 답: **4번 홉과 5번 홉 사이**이다.
  - 이해한 이유: 4번의 왕복 시간이 6ms이고 5번은 48ms이며, 뒤의 6·7번도 49·50ms로 크게 유지된다. 48−6=42ms는 두 왕복 측정값의 차이로, 실제 연결선 하나에서 정확히 42ms가 발생했다고 단정하는 값은 아니다.

- (가-2) 그 구간은 우리 회사 쪽일까요, 바깥(통신사)일까요? 근거를 적어 주세요.
  - 쓸 내용: ① 「사내 / 바깥」 하나 ② 근거(사내 홉의 시간 또는 장비 이름)
  - 답: **바깥 구간**이다. 4번은 통신사 중계 장비, 5번은 해외 연결 지점이므로 회사 내부 구간이 아니다. 사내 공유기와 방화벽은 각각 1ms와 2ms로 작게 관찰됐다.
  - 이해한 이유: 장비 이름과 위치를 근거로 조사할 범위를 나눈다. 사내 두 홉의 값이 작다는 것이 회사 안의 모든 서비스와 장비가 정상임을 입증하는 것은 아니다.

- (나) 🔍 표 2 의 4번 홉은 60 ms 로 큰데 실제 장애가 아니라고 봅니다. 그 근거는 무엇인가요?
  - 쓸 내용: ① 4번 홉의 뒤 홉 시간 ② 그것이 무엇을 뜻하는지
  - 답: **4번은 60ms이지만 뒤의 5번은 7ms, 6번은 8ms로 다시 작아지기 때문이다.** 그 장비의 통신 전달 전체가 느려졌다기보다 진단 응답 자체가 늦게 처리됐을 가능성을 생각해야 하므로, 그 한 줄만으로 실제 경로 장애라고 판단하지 않는다.
  - 이해한 이유: 장비가 패킷을 전달하는 일과 자기 진단 응답을 만드는 일은 다를 수 있다. 뒤의 홉과 목적지까지 큰 값이 이어지는지 확인해야 한다. tracert의 별표도 해당 진단 응답을 못 받았다는 표시이지 곧바로 모든 통신의 차단을 뜻하지 않는다.

**두 표를 읽으며 비교한 부분 — 수업에서 제공한 값**

| 구분 | 시간 변화 | 정리한 해석 |
|---|---|---|
| 표 1의 4~7번 | 6 → 48 → 49 → 50ms | 크게 증가한 뒤에도 이어져 해당 경로를 조사한다. |
| 표 2의 3~6번 | 5 → 60 → 7 → 8ms | 한 홉만 큰 값으로 실제 전달 지연과 진단 응답 지연을 구분한다. |

### 문제 7-2 · SaaS 접속이 느린 고객 진단하기

- (가) 이 고객의 SaaS 접속이 느린 원인 구간은 어디인가요?
  - 쓸 내용: 「… 번 홉과 … 번 홉 사이」 + 어떤 장비 구간인지
  - 답: **4번 홉과 5번 홉 사이, 통신사 중계 장비와 해외 연결 지점 사이가 의심 구간**이다.
  - 이해한 이유: 고객 예시의 ping은 평소 평균 22ms에서 이번 52ms로 커졌고 지터는 2ms·손실은 0%이다. tracert는 4번 6ms에서 5번 48ms로 커진 뒤 목적지 쪽까지 큰 값이 이어진다. 한 번의 표로 고장 위치를 확정하기보다는 지연이 늘어나는 경로를 우선 조사하는 근거로 읽었다.

- (나) 🔍 그 구간은 우리가 고칠 수 있나요? 고칠 수 없다면 고객에게 무엇을 말하고 무엇을 요청하나요?
  - 쓸 내용: ① 「고칠 수 있다 / 없다」 ② 고객에게 할 말 한 문장 ③ 요청할 곳과 붙일 자료
  - 답:
    - **직접 고칠 수 없다.** 회사가 관리하는 장비가 아니라 통신사 측 외부 구간이기 때문이다.
    - **고객에게 할 말:** “이번 측정에서는 사내 구간의 지연은 작고, 통신사 중계 장비와 해외 연결 지점 사이부터 왕복 시간이 크게 증가해 외부 구간 확인이 필요합니다.”
    - **요청할 곳과 자료:** 이용 중인 통신사에 측정 시각·대상 주소·ping 결과·tracert 결과·평소 측정값을 첨부해 경로와 지연 증가 여부를 확인 요청한다.
  - 이해한 이유: 통신사 문제라고 책임을 넘기는 것이 아니라 관찰한 자료를 전달해 운영자가 확인할 수 있게 하는 것이다. 여기서는 요청 방법을 작성했으며 실제 통신사에 문의를 보낸 것은 아니다.

- (다) 이 측정은 한 시각의 값입니다. 이 값만으로 원인을 단정할 수 없는 이유와, 추가로 잴 것 한 가지를 적어 주세요.
  - 쓸 내용: ① 단정할 수 없는 이유 한 가지(한 시각의 값) ② 추가로 잴 것 한 가지
  - 답: **한 시각의 값만으로는 일시적인 혼잡인지 지속적인 지연인지 구분하기 어렵기 때문이다. 같은 PC·대상·연결 방식을 유지하고 시간대를 바꿔 ping과 tracert를 반복 측정한다.**
  - 이해한 이유: 경로 변화나 장비의 진단 응답 처리, 이동 거리도 왕복 시간에 영향을 줄 수 있다. 해당 구간부터 지연이 반복해서 커지는지와 목적지 지연이 평소보다 계속 큰지 확인하고, 운영자의 확인도 받아야 한다.

- (한 줄) 고객에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 고객이 바로 읽을 수 있는 한 문장(우리 구간 상태, 원인 구간, 요청할 곳)
  - 답: **이번 측정에서 사내 공유기·방화벽의 왕복 시간은 1~2ms로 작고 4번 통신사 중계 장비와 5번 해외 연결 지점 사이부터 지연이 커져, 통신사에 측정 자료로 확인을 요청하고 반복 측정으로 지속 여부를 확인하겠습니다.**
  - 작성 기준: 수업의 고객 상황을 가정한 보고 문장이다. 한 번의 진단으로 통신사 장비 고장이나 공격을 확정하지 않았다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: **tracert에서 가장 큰 값 하나만 보지 말고 뒤의 홉에서도 큰 시간이 이어지는지 봐야 한다는 점**을 배웠다. 각 행은 내 PC에서 해당 홉까지의 왕복 시간이며 행끼리 더해 전체 시간을 구하는 것이 아니다.

### 이 교시에 새로 안 것

ping으로 목적지까지의 품질을 보고, tracert로 중간 경로의 어느 지점부터 왕복 시간이 커지는지 살펴보는 순서로 배웠다. 홉은 경로의 단계이고, 실제 Windows 출력의 한 줄에 나오는 세 시간은 같은 홉에 대한 세 번의 측정이다. 중간 장비가 진단 응답을 하지 않아도 뒤의 홉이 응답할 수 있으므로 별표만으로 장애를 단정하지 않는다.

7-1과 7-2는 제공된 표를 읽고 설명을 받아 정리한 것이다. 내 PC에서 직접 실행한 tracert 출력은 이번 대화에 공유하지 않았다. 따라서 고객 예시의 52ms·지터 2ms·손실 0%나 표의 4→5번 구간을 내 실제 인터넷 측정 결과로 기록하지 않았다.

“단순히 지연이 커지는 것도 판단 범위에 들어가는가”라고 질문했다. 품질 진단에서는 증가 자체가 조사할 신호이지만, 장애나 공격으로 확정하는 것은 아니라는 설명을 들었다. **6교시 기준 150ms 이하를 만족하는 것과, 평소 22ms에서 52ms로 달라진 이유를 조사하는 것은 다른 판단**이다. 기준을 넘지 않았어도 평소와 달라졌다면 확인할 수 있다는 점을 정리했다.

서비스를 필요할 때 사용할 수 있도록 유지하는 가용성과도 연결된다는 설명을 들었다. 다만 모든 지연 증가를 보안 사고라고 부르지 않는다. 일반적인 회선·장비 문제와 공격 가능성을 기록과 추가 측정으로 구분하고, 조직에 따라 네트워크 운영 담당과 보안 담당이 함께 확인할 수 있다.

### 문제 7-3 · 품질 진단 리포트 완성하고 올리기

- (가) `git status` 를 쳤을 때 빨간 목록에 줄이 몇 개였는지, 그 가운데 `.env` · `.venv` 가 있었는지 적어 주세요.
  - 쓸 내용: 「줄 … 개 / `.env` 있음 · 없음 / `.venv` 있음 · 없음」
  - 답: **목록 줄 수: Git 상태 확인 전으로 미확인 / `.env`: 미확인 / `.venv`: 미확인.** 이 보고서는 업로드 전 정리 단계에서 작성했고, 오늘 오후의 git status 출력을 아직 공유하지 않았다. 따라서 줄 수를 임의로 쓰거나 비밀 파일이 없다고 단정하지 않았다.
  - 다음 작업: 저장소 루트에서 `git status`로 실제 목록을 확인한 뒤 이 답을 관찰한 값으로 바꾸고 저장한다. `.env`·`.venv` 등 올리지 않을 항목이 섞였는지도 확인한 후 제출 파일을 커밋·업로드하고 원격 저장소에서 확인한다. 지금 이 문서만으로 업로드 완료를 기록하지 않는다.

## 최종 품질 진단 리포트 — 7교시에 완성합니다

> 오늘 측정과 판정을, 처음 보는 사람도 이해할 수 있게 정리합니다. 강의계획서의 5일 차 산출물(`day05_quality_report.md`)의 역할을 이 칸이 합니다. 위에서 적은 5 · 6 · 7교시의 답을 다시 보며 씁니다.

### 1. 측정 요약 — 문제 5-2

- 5-2 에서 내 PC 로 잰 `8.8.8.8` 의 지연 · 손실 · 지터를 적어 주세요.
  - 쓸 내용: 「평균 … ms · 손실 … % · 지터 … ms」
  - 답: **평균 35ms · 손실 0% · 지터 약 0.44ms**이다. 내 PC에서 `ping -n 10 8.8.8.8`을 실행해 응답 10개를 모두 받았고, 응답 시간은 37, 35, 35, 35, 35, 35, 35, 36, 35, 35ms였다. 평균은 ping 요약값을 사용했고 표시된 값의 산술평균은 35.3ms이다. 지터는 이웃한 차이 아홉 개의 합 4ms를 9로 나눠 구했다.

이번 표본에서는 응답 누락이 없고 시간 변동도 작았다. 8.8.8.8은 DNS 서버 주소이지만 이번 명령은 이름 조회가 아니라 ping 측정이다. 이 측정만으로 모든 서비스의 속도나 다른 시간대의 품질까지 확인한 것은 아니다.

### 2. 세 숫자 판정 — 문제 6-2

- 세 회선의 판정과 걸린 기준을 적고, 세 숫자의 차이를 정리해 주세요.
  - 쓸 내용: ① A · B · C 의 판정과 걸린 기준 ② 지연 · 지터 · 손실이 각각 무엇을 나타내는지
  - 답: **A: 적합 / B: 부적합(지터 54.3ms > 기준 30ms) / C: 부적합(손실 30% > 기준 1%)**이다. 수업에서 정한 평균 지연 150ms 이하·지터 30ms 이하·손실 1% 이하를 모두 만족해야 한다. 코드를 수정한 뒤 직접 실행해 세 판정이 맞게 출력된 것을 확인했다.

| 지표 | 나타내는 것 | 단위 |
|---|---|---|
| 지연 | 요청을 보내고 응답을 받기까지 걸린 왕복 시간으로, 여기서는 그 평균을 사용한다. | ms |
| 지터 | 응답 시간이 얼마나 흔들리는지이며, 여기서는 이웃한 응답 시간 차이 크기의 평균이다. | ms |
| 손실 | 보낸 요청 중 응답받지 못한 비율이다. | % |

실행한 프로그램의 입력은 수업이 제공한 A·B·C 자료이다. 내 PC에서 세 회선을 새로 측정한 것은 아니다. B는 받은 시간이 크게 흔들리고, C는 받은 시간은 일정해도 누락이 많아 평균 지연만으로 품질을 판단할 수 없었다.

### 3. 지연 원인 — 문제 7-1 · 7-2

- SaaS 접속이 느린 원인 구간과 그 근거를 적어 주세요.
  - 쓸 내용: ① 원인 구간 ② 근거(tracert 에서 뛴 값) ③ 사내 구간이 정상이라는 근거
  - 답: **고객 예시의 우선 조사 구간은 4번 홉과 5번 홉 사이인 통신사 중계 장비→해외 연결 지점이다.** 왕복 시간이 4번 6ms에서 5번 48ms로 커지고 6번 49ms·7번 50ms로 이어진다. 사내 공유기·방화벽은 1ms·2ms로 이번 표에서 큰 지연이 보이지 않았다.

고객 예시의 ping은 평소 평균 22ms에서 이번 52ms로 커졌지만 지터는 2ms, 손실은 0%이다. 자료에서는 외부 경로의 지연 증가를 우선 확인할 근거가 있으나 특정 장비 고장이나 공격을 확정한 것은 아니다. 직접 관리할 수 없는 구간이므로 측정 시각·대상·ping·tracert·평소 값을 통신사에 전달해 확인을 요청하는 방식으로 정리했다.

표 2처럼 4번만 60ms이고 이후 7ms·8ms로 작아지는 경우에는 진단 응답 자체가 늦었을 가능성을 고려한다. 고객 예시와 표는 수업 자료이며 내 PC의 직접 tracert 결과가 아니다.

### 4. 한계와 다음 확인

- 이 진단으로 알 수 없는 것 하나와, 다음에 확인할 것 하나를 적어 주세요.
  - 쓸 내용: ① 알 수 없는 것(예: 한 시각의 값이라는 점) ② 다음 확인(시간대를 바꿔 다시 재기 · 구간 운영자에게 확인 요청)
  - 답: **한 시각의 짧은 측정만으로 지연 증가가 지속되는지, 정확한 원인이 혼잡·경로 변화·장비 문제 등 무엇인지 확정할 수 없다. 같은 PC·대상·연결 방식을 유지하고 시간대를 바꿔 ping과 tracert를 반복 측정하며, 외부 구간은 운영자에게 측정 자료로 확인을 요청한다.**

내 PC의 실제 측정 대상인 8.8.8.8과 고객 예시의 SaaS 서버는 다르므로 두 수치를 한 경로의 진단처럼 연결하지 않는다. 무선·유선 차이를 확인할 때는 반대로 다른 조건을 최대한 맞추고 연결 방식만 바꿔 각각 10번씩 측정해야 한다. 질문에 따라 무엇을 고정하고 무엇을 바꿔야 하는지를 구분한다.

## 오늘 오후 학습 정리

### 수업이 이어진 흐름

1. **5교시:** 느리거나 끊기는 현상을 지연·지터·손실로 나누고, 실제 ping 출력으로 계산했다.
2. **6교시:** 같은 계산을 함수로 만들고 세 기준을 모두 만족하는지 코드로 판정했다.
3. **7교시:** 제공된 경로 표에서 지연이 커지는 위치를 읽고, 근거·한계·다음 확인을 구분해 보고하는 연습을 했다.

오전에는 어느 경로를 허용할지 배웠고, 오후에는 연결된 경로의 품질을 어떻게 측정하고 해석할지 배웠다. 둘 다 숫자나 로그가 있다는 이유만으로 결론을 앞서 내리지 않고, 어떤 조건과 범위에서 관찰한 것인지 이해하는 것이 필요했다.

### 질문하면서 다시 정리한 부분

- **평균과 일정함:** 일정하기만 하면 되는지 질문했고, 평균 지연·지터·손실을 함께 봐야 한다고 정리했다.
- **직접 측정과 예시 구분:** 5-2의 내 실제 출력은 35ms·0%·약 0.44ms이고, 7-2 고객 예시는 52ms·2ms·0%이다. 서로 다른 자료를 섞지 않는다.
- **jitter 함수의 역할:** 출력이 나와도 함수가 하는 일을 다시 질문했다. 여러 응답 시간을 받아 변동의 크기인 숫자 하나를 돌려준다는 설명으로 정리했다.
- **임시 판정값:** 6-2의 A가 이유 없이 부적합인 것은 ok가 False로 고정돼 있었기 때문이다. 직접 고친 뒤 A만 적합으로 출력되는 것을 확인했다.
- **단순 지연 증가도 조사 대상인지:** 기준 이하라도 평소와 달라졌다면 조사할 수 있지만, 그것만으로 장애나 공격을 뜻하지는 않는다고 배웠다.

### 내가 직접 확인한 실행 결과

| 실습 | 실제로 공유한 결과 |
|---|---|
| 5-2 ping | 10개 전부 응답, 요약 평균 35ms·손실 0%, 응답값에서 구한 지터 약 0.44ms |
| 6-1 계산 코드 | A 21.9/1.1/0, B 42.3/54.3/0, C 41.0/1.7/30(지연ms/지터ms/손실%) |

| 6-2 수정 후 | A 적합, B 지터로 부적합, C 손실로 부적합 |

7교시는 제공된 표를 해석했고, 실제 tracert 실행 결과나 통신사 문의 기록은 남기지 않았다. Git 상태 확인·커밋·푸시는 아직 진행 전이므로 업로드 완료로 적지 않았다.

### 아직 더 복습할 것

- jitter 함수를 보지 않고도 현재 값과 앞 값, 차이의 합계, 개수에서 1을 빼는 이유를 설명해본다.
- 같은 평균이어도 지터와 손실이 다르면 품질 해석이 달라지는 예를 다시 비교한다.
- and와 or를 바꾸면 판정이 달라지는 이유를 B의 True·False·True로 설명해본다.

- 업로드 전 7-3의 실제 Git 상태를 확인해 줄 수와 .env·.venv 유무를 기록하고, 저장한 최종 파일을 올린 뒤 저장소에서 확인한다.
