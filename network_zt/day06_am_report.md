### 문제 2-1 · 새벽 대량 조회 사건 추적하고 단정할 수 있는지 따지기

- (가) 의심스러운 접근 기록은 몇 번이고, 이상해 보이지만 정상인 줄은 몇 번인가요? 한 줄씩은 정상 같지만 모아서 보면 이상한 줄이 있으면 함께 적어 주세요.
  - 쓸 내용: 「의심: 번호 … / 이상해 보이지만 정상: 번호 … (정상으로 본 이유) / 모으면 이상한 줄: 번호 … (이유)」
  - 답:

    **의심: 2·3·4·5번 / 이상해 보이지만 정상: 1번 / 반복을 함께 볼 기록: 12·14·15·16·17번.**

    설명을 들으며 등록 정보와 접근 기록을 대조하는 방법을 배웠다. 2번은 seoyeon 계정이 새벽 02:14에 자신의 등록 기기 NB-0417과 다른 NB-7741에서 비밀번호만으로 로그인한 기록이다. 이어지는 3·4·5번에서는 영업 담당 자원 SALES가 아닌 정산 자료 SETTLE을 40건씩 세 번, 합계 120건 조회했다.

    1번은 새벽에 320건을 조회해 가장 이상해 보일 수 있지만, batch-night는 원래 매일 02:00에 정산을 집계하는 서비스 계정이다. 기기 SRV-BATCH와 자원 SETTLE도 등록 정보에 맞으므로 제공된 자료에서는 정상 작업으로 볼 수 있다.

    12·14·15·16·17번은 등록 기기를 이용한 낮 시간의 조회이며 앞선 8번에는 MFA 로그인도 기록돼 있다. 그러나 영업팀 계정이 담당 외 자원 SETTLE을 19건씩 다섯 번 조회했다. 건수만 보면 평소 영업 조회량과 비슷하지만, 담당 자원이 다르고 합계는 95건이다. 이 수치는 조회 건수의 합계이며 서로 다른 자료 95개인지, 중복 조회가 있는지는 알 수 없다.

    | 근거 필드 | 기록의 값과 비교 기준 |
    |---|---|
    | 기기 | 새벽의 NB-7741은 seoyeon의 등록 기기 NB-0417과 다르다. 낮 기록은 NB-0417이다. |
    | 시각 | 새벽 기록은 02:14~02:15이고, 같은 계정의 다른 이용 기록은 낮 시간대에 있다. 시각만으로 악성이라고 확정하지는 않는다. |
    | 자원 | 담당 자원은 SALES인데 새벽과 낮의 의심 조회는 SETTLE이다. 정상적인 영업 조회 기록 9·11·18번은 SALES이다. |

- (다) 🔍 방화벽이 막지 못하고 통과한 이유를 5대 원칙의 어느 칸이 비어 있었는지로 설명해 주세요.
  - 쓸 내용: ① 비어 있던 칸 두 개 이상 ② 칸마다 확인했어야 할 것
  - 답:

    - **ID:** 새벽에는 비밀번호만 확인한 로그인이다. 필요한 MFA 등 본인 확인을 접속 경로별로 빠짐없이 적용해야 한다.
    - **Device:** 접속 기기가 해당 계정의 등록 기기인지 대조해야 한다. NB-7741은 seoyeon의 등록 기기와 다르다.
    - **Application:** 영업팀 계정에 정산 자료 SETTLE 조회 권한이 있는지 확인하고, 담당 외 자원 접근은 별도 승인 없이는 제한해야 한다.
    - **Policy:** 새벽 접속, 짧은 시간의 반복 조회, 일정 시간의 누적 조회량을 확인해 추가확인 또는 제한에 반영해야 한다.

    낮의 12·14·15·16·17번은 기기와 로그인 방식만 보면 정상에 가깝지만, 담당 자원과 누적 행동을 확인하는 Application·Policy 문제가 남는다. 방화벽이나 VPN을 사용하면 반드시 내부가 전부 열리는 것은 아니며, 여기서는 경계 통과만으로 넓게 신뢰하는 구성의 한계를 배우는 것이다. 실제 설정 전체가 제시되지는 않았으므로 구체적인 장애 원인까지 확정하지 않는다.

- (라) 🔍 이 기록만으로 「seoyeon 계정이 도용됐다」고 단정할 수 있나요? 기록으로 확인된 것과 확인하지 못한 것, 그것을 확인하려면 볼 자료를 적어 주세요.
  - 쓸 내용: ① 단정할 수 있는지 ② 기록으로 확인된 것 ③ 확인하지 못한 것 ④ 확인하려면 볼 자료

    - **확인된 것:** seoyeon 계정으로 새벽에 등록 기기와 다른 기기에서 비밀번호 단독 로그인이 기록됐고, 이어 정산 자료 합계 120건이 조회됐다. 낮에도 등록 기기를 사용한 계정에서 SETTLE을 19건씩 다섯 번, 합계 95건 조회했다.

    기록의 QUERY는 조회를 의미한다. 조회됐다는 사실을 외부 유출로 바꾸어 쓰거나, 다른 기기라는 이유만으로 공격자의 기기라고 단정하면 안 된다는 점을 배웠다.

### 문제 2-2 · 접속 요청 여섯 개를 5대 원칙의 칸으로 분류하기

- (가) 요청 ① ~ ⑥ 은 각각 5대 원칙 중 어느 칸에서 걸리나요? 걸리지 않고 통과하면 「통과」라고 적어 주세요.
  - 쓸 내용: 「①: … / ②: … / ③: … / ④: … / ⑤: … / ⑥: …」 여섯 개
  - 답:

    **①: ID / ②: Device / ③: Application / ④: Network / ⑤: Policy / ⑥: 통과**

    ①은 관리자 기능에 접근하면서 비밀번호만 사용해 문제의 본인 확인 기준이 부족하다. ②는 백신이 꺼져 있고 패치가 오래 적용되지 않아 기기 상태가 문제다. ③은 인사 앱 이용 권한이 없고, ④는 앱을 거치지 않는 DB 직접 연결 경로가 문제다. ⑤는 정상 인증·기기·앱 권한과 별개로 상황을 확인해야 한다. ⑥은 제시된 조건에서 걸리는 항목이 없다.

    이번 문제는 ID → Device → Network → Application → Policy 순서로 처음 걸리는 칸을 고르는 연습이다. 걸린다는 말은 곧 공격 확정이라는 뜻이 아니며 정책에 따라 추가확인이나 거부로 이어질 수 있다.

- (나) 🔍 요청 ⑤ 는 ID · Device · Application 이 모두 정상인데 왜 Policy 칸에서 걸리나요?
  - 쓸 내용: ① 정상인 것 ② 평소와 달라진 상황 ③ Policy 칸이 하는 일
  - 답:

    ⑤는 비밀번호와 MFA를 사용했고, 최신 상태의 회사 노트북이며 영업 앱 이용 권한도 있다. 하지만 평소 서울에서만 접속하던 계정이 해외 IP에서 새벽 03:00에 접속했다. Policy는 시간·위치·위험도처럼 달라진 상황을 반영해 추가 인증이나 접근 제한을 결정하는 칸이다. 출장이나 특별 업무일 수도 있으므로 공격이라고 단정하지 않고 추가로 확인해야 한다.

- (다) 요청 ③ 과 ④ 는 둘 다 가면 안 되는 곳에 닿으려는 시도인데 왜 서로 다른 칸에서 걸리나요?
  - 쓸 내용: ① ③ 이 확인하는 것 ② ④ 가 확인하는 것
  - 답:

    ③은 마케팅팀 계정이 인사 시스템 앱을 사용할 권한이 있는지 확인하는 문제여서 **Application**이다. ④는 직원 기기에서 서버 구역의 DB로 직접 통신하도록 허용할지, 정해진 앱을 거치는 경로인지 확인하는 문제여서 **Network**이다.

    둘 다 접근 제한과 관련되지만, 전자는 앱·기능의 이용 권한이고 후자는 연결 경로·통신 범위에 초점이 있다. 실제로는 두 통제를 함께 적용할 수 있다. DB 직접 접속도 승인된 관리 목적 등으로 허용할 수 있으므로 모든 직접 접속이 본질적으로 공격이라는 뜻은 아니다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답:

    로그인 성공과 자료 이용 권한은 다른 확인이라는 것을 배웠다. 지난주에는 VPN·방화벽·DMZ를 중심으로 경로와 구역을 배웠는데, 이번에는 사용자 신원, 기기 상태, 연결 범위, 앱 권한, 현재 상황을 함께 봐야 한다는 설명을 들었다.

    특히 사내 IP라고 등록 기기인 것은 아니며, MFA를 통과했다고 모든 자료를 볼 수 있는 것도 아니다. 새벽 작업이라도 batch-night처럼 정상 사유가 있을 수 있고, 낮의 정상 로그인 이후에도 담당 외 자료의 반복 조회가 있을 수 있다. 기록의 값과 그 값으로 추정한 이유를 나누어 쓰는 방법을 복습했다. 이 과정의 다섯 칸은 수업에서 사용하는 분류이며, 다른 문서의 명칭·구성과 꼭 같지는 않다.

## 3교시 · 점수로 판단하는 함수 (PDP)

### 문제 3-1 · 권한 변경 판단 함수의 점수 직접 정하기

- (가) 내가 채운 코드 여덟 줄을 붙여 넣어 주세요.
  - 쓸 내용: `# ←` 여덟 곳에 채운 코드(점수 세 개 · 역할 검사 두 줄 · MFA 점수 블록 세 줄)
  - 답:

    설명을 참고해 점수 세 줄, 역할 검사 두 줄, MFA 검사 세 줄을 수정했고 수정 코드를 직접 실행했다. 아래는 실제로 수정한 여덟 줄을 위치별로 나눈 것이다.

    파일 위쪽의 점수 설정 세 줄:

    ```python
    HEALTH_POINTS = 50
    MFA_POINTS = 20
    COUNTRY_POINTS = 30
    ```

    등록 기기 검사 다음, 점수 계산 전의 역할 검사 두 줄:

    ```python
        if account["role"] != "account_admin":
            return "거부", ["관리자 역할이 아님"]
    ```

    기기 보안 상태 검사 다음의 MFA 검사 세 줄:

    ```python
        if req["mfa"] == False:
            score = score + MFA_POINTS
            reasons.append("MFA 안 함")
    ```

- (나) 🔍 실행해서 나온 요청 A ~ F 의 결정을 적어 주세요. 모두 기대 결정과 같은지도 함께 적어 주세요.
  - 쓸 내용: 「A: … / B: … / C: … / D: … / E: … / F: …」 여섯 개와 「기대 결정과 같음 · 다름」
  - 답:

    **A: 허용 / B: 거부 / C: 추가확인 / D: 거부 / E: 추가확인 / F: 거부. 직접 재실행한 결과 여섯 요청 모두 기대 결정과 같았다.**

    처음 기본 코드를 실행했을 때는 A~F 모두 허용이었다. 관리자 역할 검사가 없고 점수도 0이며 MFA 검사도 없던 상태였다. 설명을 참고해 수정한 뒤 내 PC에서 확인한 실제 출력은 다음과 같다.

    ```text
    A ('허용', [])
    B ('거부', ['관리자 역할이 아님'])
    C ('추가확인', ['MFA 안 함'])
    D ('거부', ['기기 보안 상태 이상'])
    E ('추가확인', ['해외에서 접속'])
    F ('거부', ['MFA 안 함', '해외에서 접속'])
    ```

    ```python

        counts[decision] = counts[decision] + 1

            print("[거부]", req["id"], req["user"], reasons)

            print("[추가확인]", req["id"], req["user"], reasons)

    print("허용", counts["허용"], "건 / 추가확인", counts["추가확인"], "건 / 거부", counts["거부"], "건")

    ```

    점수가 낮은 두 항목은 **세그멘테이션 0점, 위험 기반 인증 0점**이다. 비율 항목 중에서는 **기기 점검이 5점**으로 낮다.

    설명받은 개선안에서는 **Device를 우선 개선하는 방안**으로 정리했다. 새벽 사건에서 해당 계정의 등록 기기와 다른 기기의 접근이 허용됐고, 제공된 직원 12명 중 기기 점검 통과 직원도 3명뿐이기 때문이다. 등록 기기 대조와 보안 상태 점검을 접근 조건에 반영해야 한다.

    등록된 기기인지와 현재 보안 상태가 정상인지는 서로 다른 확인이다. 점수가 가장 낮은 항목만 기계적으로 고르는 것이 아니라, 사건 기록과 개선 필요성을 연결해 우선순위를 설명해야 한다는 안내를 받았다. 비밀번호 유출 후 해외 로그인 성공 기록을 근거로 ID·MFA를 우선하는 방안도 가능하다.

    PDP는 허용 여부를 결정하고, PEP는 그 결정을 실제 요청에 적용한다는 차이를 배웠다. 파이썬 함수가 ‘거부’를 반환했다고 실제 서버 접근까지 자동으로 차단되는 것은 아니며, 오늘 작성하는 방안 역시 실제 운영 환경에 배포한 결과가 아니다.

    4-1의 코드를 수정해 30점이 나온 뒤에도 공식이 이해되지 않아 다시 질문했다. STAFF의 직원 정보를 한 명씩 읽어 count로 인원을 세고, score로 점수를 계산한다는 설명을 들었다. 6명/12명은 전체의 절반이므로 20점 만점의 절반인 10점을 준다는 방식이다. 비율에 100을 곱하면 백분율, 20을 곱하면 20점 만점의 점수가 된다. len(STAFF)는 목록의 현재 인원을 자동으로 구하며, round는 결과를 정수로 반올림한다.

    한 사람이 MFA·기기 점검·최소권한 조건을 동시에 충족할 수 있으므로 세 조건을 각각 if로 세는 이유도 설명받았다. 최소권한은 초과 권한 개수의 합이 아니라 초과 권한이 없는 직원 수를 세는 것이다. SEGMENTED와 RISK_AUTH는 실제 현황이 False라 0점이며, 점수를 올리려고 임의로 True로 바꾸는 것이 아니다.

    3교시 위험 점수는 높을수록 주의할 신호가 많고, 4교시 성숙도 점수는 높을수록 도입 수준이 높다는 차이도 정리했다. 실행 결과를 확인한 것과 코드를 충분히 이해하는 것은 별개여서, 인원 집계 → 적용 비율 → 항목 점수 → 총점의 순서를 다시 따라가며 복습하고 싶다. 교시 전체 설명에서는 개념에 집중하고 문제는 따로 요청할 때 풀어 달라고 학습 방식도 요청했다.
