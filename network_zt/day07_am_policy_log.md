# <mark style="display:block; background:#c8e6c9; color:#1a1a1a; padding:6px 12px; border-radius:4px">2교시 (10:00–10:50) · 지속 검증 · 세션 만료</mark>

> A사 보안 담당이 보낸 메시지: 「정산 포털에 로그인한 직원이 자리를 비워도 접속이 계속 유지됩니다. 로그인할 때만 확인하지 말고 접속하는 동안에도 확인하고, 시간이 지나면 허용을 취소할 수 있나요?」
> - 이 교시에서 하는 일: 자원마다 접속 유지 시간이 다르게 세션 상태를 판정하는 함수를 직접 만들고, 접속 중에 생긴 변화마다 어떤 조치를 할지 고릅니다.
> - 끝나면 쓰는 것: **새로 알게 된 것** 하나(보고서의 마지막 칸)

### 왜 필요한가

1. 어제 만든 판단 함수는 요청이 들어오는 **그 순간**만 판단합니다. 로그인한 뒤 기기 상태가 바뀌거나 직원이 퇴사 처리돼도 접속이 유지되면 계속 허용됩니다.
2. 접속이 오래 유지되면 자리를 비운 사이 다른 사람이 쓰거나, 탈취된 세션이 계속 쓰일 수 있습니다.
3. 위험한 자원일수록 접속 유지 시간을 짧게 둡니다. 어제 배운 **최소권한**을 시간에도 적용하는 것입니다.

### 2.1 세션과 지속 검증

- **세션**(session · 세션)
  - 로그인한 뒤 서버가 그 접속의 상태(누가 언제부터 접속했는지)를 저장해 두는 것
  - 서버가 준 **토큰**(token · 토큰, 로그인했다는 표시용 문자열)을 요청마다 보여 주면 로그인된 접속으로 본다
- **지속 검증**(continuous verification · 컨티뉴어스 베리피케이션)
  - 로그인할 때만이 아니라 접속하는 동안에도 계속 다시 확인하는 것
- **세션 만료**(expiration · 익스퍼레이션)
  - 정해진 유지 시간이 지나면 허용이 끝나서 다시 로그인해야 하는 것
- **재인증**(re-authentication · 리오센티케이션)
  - 본인 확인을 다시 하는 것
  - 예: 비밀번호나 MFA 를 한 번 더 입력
- **회수**(revoke · 리보크)
  - 허용을 중간에 취소하고 세션을 끝내는 것

접속 중에 상황이 바뀌면 조치를 세 가지 중에서 고릅니다. 고르는 기준은 **허용했던 근거가 어떻게 되었는가**입니다.

| 조치 | 언제 | 예 |
|---|---|---|
| 유지 | 허용했던 근거가 그대로다 | 평소와 같은 기기 · 위치 · 업무 |
| 재인증 | 근거가 불확실해졌지만 **본인 확인으로 해결될 수 있다** | 만료 시각이 가까워짐 |
| 종료(회수) | 근거가 없어졌고 **본인 확인으로 해결되지 않는다** | 계정이 비활성화됨 |

**현실에서 마주치는 곳**

- **Microsoft Entra 조건부 액세스**의 **로그인 빈도**(sign-in frequency): 사용자가 다시 로그인하라는 요청을 받기 전까지 자원에 접근할 수 있는 시간을 정합니다.
- **Cloudflare Access** 의 **세션 지속 시간**(session duration): 앱마다 접속 상태를 얼마나 유지할지 정합니다.

### 2.2 자원마다 다른 유지 시간

| 자원 | 유지 시간(분) | 이유 |
|---|---|---|
| 정산 내역 조회 | 30 | 읽기 중심이라 위험이 중간 |
| 계정 권한 변경 | 5 | 계정을 바꿀 수 있어 위험이 큼 |

세션의 상태는 **접속한 지 지난 시간(경과 분)** 과 유지 시간으로 정합니다.

| 상태 | 조건 |
|---|---|
| 종료 | 경과 분이 유지 시간보다 **크다** |
| 재인증 | 경과 분이 유지 시간의 **0.8배 이상**이다 (만료가 가까워 본인 확인을 다시 요구) |
| 유지 | 위 둘이 아니다 |

정산 조회(유지 시간 30분)에서 경과 분에 따른 상태입니다. 0.8배는 `30 * 0.8` 처럼 소수와 곱하면 `24.0` 입니다.

| 경과 분 | 비교 | 상태 |
|---|---|---|
| 10 | 24 보다 작다 | 유지 |
| 24 | 24 이상, 30 이하 | 재인증 |
| 30 | 30 보다 크지 않다 | 재인증 |
| 31 | 30 보다 크다 | 종료 |

- 먼저 **종료**를 검사하고, 그다음 **재인증**을 검사합니다. 31분은 두 조건에 모두 맞지만 먼저 검사한 종료가 적용됩니다. 함수는 `return` 을 만나면 그 자리에서 끝납니다(어제 배운 방식).

### <mark>✍️ 문제 2-1 · 세션 상태를 판정하는 함수 직접 만들기</mark>

**📍 이런 상황이 있습니다**

- A사는 정산 조회 세션의 유지 시간을 30분, 권한 변경 세션을 5분으로 정했습니다. 지금 열려 있는 세션 7개를 보고 **유지 · 재인증 · 종료** 중 어느 상태인지 판정해야 합니다.
- 담당자는 `session_state` 함수를 완성하고, 같은 경과 시간이라도 자원에 따라 다르게 판정되는지 확인해야 합니다.
- 현업에서는 세션이 수천 개입니다. 오늘은 **7개로 줄였습니다.**

**🎯 할 일**

1. 아래 코드를 `day07_2-1_session_state.py` 로 만듭니다.
2. `# ←` 표시가 있는 <mark>두 곳</mark>을 채웁니다.
3. 실행해서 세션 7개의 <mark>상태</mark>를 확인합니다.
4. 같은 경과 시간이 <mark>자원마다 다르게 판정되는 이유</mark>와 경계값에서의 판정을 설명합니다.

**받은 자료**

세션 7개

| 번호 | 계정 | 자원 | 경과 분 |
|---|---|---|---|
| 1 | `junho` | 정산 조회 | 10 |
| 2 | `junho` | 정산 조회 | 26 |
| 3 | `junho` | 정산 조회 | 41 |
| 4 | `gaeun` | 권한 변경 | 3 |
| 5 | `gaeun` | 권한 변경 | 4 |
| 6 | `gaeun` | 권한 변경 | 12 |
| 7 | `seoyeon` | 정산 조회 | 30 |

```python
SESSION_LIMITS = {"settlement": 30, "admin": 5}              # 자원별 세션 유지 시간(분). 위험한 자원일수록 짧다

SESSIONS = [                                                                                   # 지금 열려 있는 세션 7개
    {"id": 1, "user": "junho",   "resource": "settlement", "age": 10},                          # 접속한 지 10분 지난 정산 조회 세션
    {"id": 2, "user": "junho",   "resource": "settlement", "age": 26},                          # 26분 지난 정산 조회 세션
    {"id": 3, "user": "junho",   "resource": "settlement", "age": 41},                          # 41분 지난 정산 조회 세션
    {"id": 4, "user": "gaeun",   "resource": "admin",      "age": 3},                           # 3분 지난 권한 변경 세션
    {"id": 5, "user": "gaeun",   "resource": "admin",      "age": 4},                           # 4분 지난 권한 변경 세션
    {"id": 6, "user": "gaeun",   "resource": "admin",      "age": 12},                          # 12분 지난 권한 변경 세션
    {"id": 7, "user": "seoyeon", "resource": "settlement", "age": 30},                          # 30분 지난 정산 조회 세션
]

def session_state(session):                                  # 세션 하나의 상태를 판정하는 함수
    """세션이 '유지' '재인증' '종료' 중 어느 상태인지 리턴한다"""
    limit = SESSION_LIMITS[session["resource"]]              # 이 세션의 자원에 정해진 유지 시간(분)
    # 1. session["age"] 가 limit 보다 크면 "종료" 를 리턴한다   # ←
    if session["age"] > limit:
      return "종료"
    # 2. session["age"] 가 limit * 0.8 이상이면 "재인증" 을 리턴한다   # ←
    if session["age"] >= limit * 0.8:
      return "재인증"
    return "유지"                                             # 위 둘이 아니면 유지한다

for session in SESSIONS:                                     # 세션을 하나씩 꺼낸다
    print(session["id"], session["user"], session["resource"], session["age"], "->", session_state(session))   # 번호 · 계정 · 자원 · 경과 분 -> 상태 를 출력한다
```

- 채울 줄의 앞 공백은 바로 위 `limit =` 줄과 같은 깊이(4칸)로 시작하고, `if` 안쪽 줄은 4칸 더 들어갑니다.
- 채우기 전에 실행해도 오류 없이 돌아갑니다. 빈 곳이 있어서 모든 세션이 「유지」로 나오는 것이 정상입니다.

### 3.1 정책 로그와 앱 접근 기록

- **PDP**(Policy Decision Point · 폴리시 디시전 포인트)
  - 요청을 보고 점수를 계산해 「허용 · 추가확인 · 거부」를 정하는 곳
  - 정하기만 하고 막거나 통과시키지는 않는다
  - 월요일 3교시에 만든 점수 판단 함수가 이 일을 한다
- **PEP**(Policy Enforcement Point · 폴리시 인포스먼트 포인트)
  - PDP 의 결정대로 요청을 통과시키거나 막는 곳
  - 앱보다 먼저 요청을 받는다
- **요청 번호**(`rid`, request ID · 리퀘스트 아이디)
  - 요청마다 붙는 번호
  - 정책 로그와 앱 접근 기록에서 같은 요청에는 같은 `rid` 가 붙어 있다
  - 그래서 `rid` 가 같은 줄끼리 맞춰 보면, 한 요청이 정책 로그에서는 어떻게 결정되고 앱에서는 어떻게 처리됐는지 비교할 수 있다
- **정책 로그**(policy log · 폴리시 로그)
  - PDP 가 요청마다 남기는 결정 기록. 어제 3교시 함수가 리턴한 `(결정, 이유 목록)` 을 기록해 둔 것이다
  - 필드: `rid` · `time`(시각) · `user`(계정) · `decision`(결정) · `score`(점수) · `reasons`(이유)
- **앱 접근 기록**(access log · 액세스 로그)
  - 앱이 요청을 실제로 처리한 결과. PEP 가 집행한 뒤의 결과가 여기에 남는다
  - 필드: `rid` · `time` · `user` · `status`(응답 번호)
- **응답 번호**(status code · 스테이터스 코드)
  - 서버가 요청에 답하며 붙이는 번호
  - `200` 은 처리됨
  - `401` 은 추가 확인 요구
  - `403` 은 차단됨
  - 세기는 `200`(통과) < `401`(추가 확인) < `403`(차단) 순서다

PDP 의 결정마다 앱이 내야 하는 응답 번호가 정해져 있습니다.

| PDP 결정 | 앱이 내야 하는 응답 번호 |
|---|---|
| 허용 | 200 |
| 추가확인 | 401 |
| 거부 | 403 |

정책 로그와 앱 기록을 요청 번호(`rid`)로 맞춰 보면 어긋난 유형이 네 가지로 나뉩니다.

| 유형 | 모양 | 뜻 | 위험 |
|---|---|---|---|
| 일치 | 결정에 맞는 응답 번호 | 결정대로 집행됨 | 없음 |
| 집행 누락 | 앱이 결정보다 약한 번호를 냄 (거부인데 200 · 401, 추가확인인데 200) | 결정이 집행되지 않았거나 약하게 집행됨 | 높음 |
| 과집행 | 앱이 결정보다 센 번호를 냄 (허용인데 401 · 403, 추가확인인데 403) | 정상 요청을 막음 | 업무 불편 |
| 우회 | 앱 기록에만 있고 정책 로그에는 없음 | PDP 를 거치지 않은 경로 | 높음 |

**이 시간에 나오는 말** (이미 배운 방법입니다)

- `d[키] = 값` 으로 딕셔너리에 담고, `d.get(키)` 로 꺼냅니다. 없으면 `None` 이 나옵니다(10/12(월) · 10/13(화)).
- `리스트.append(…)` 로 목록에 더하고, `값 not in 리스트` 로 목록에 없는지 검사합니다(10/15(목)).
- `counts[키] = counts.get(키, 0) + 1` 로 키별 건수를 셉니다(10/19(월)).
- `for 키, 값 in d.items():` 로 딕셔너리의 키와 값을 함께 꺼냅니다(9/28(월)).

요청 번호 `101` 한 건을 맞춰 보면 이렇습니다.

| 기록 | 값 |
|---|---|
| 정책 로그 `101` | 결정 `거부` → 앱이 내야 하는 응답 번호 `403` |
| 앱 접근 기록 `101` | 응답 번호 `200` |
| 판정 | `200` ≠ `403` → **어긋남**(집행 누락) |

### 왜 필요한가

1. 정상 직원에게 추가 확인이 자주 뜨면 업무가 멈추고, 결국 규칙이 무시되거나 꺼집니다. 기준을 바꾸기 전에 바꾼 결과를 숫자로 확인해야 합니다.
2. 정상 요청을 덜 막도록 규칙의 기준을 낮추면 위험한 요청을 놓칠 수 있습니다. 오탐과 미탐을 **같이 세어** 비교해야 합니다.

### 4.1 오탐 · 미탐과 점수 규칙 조정

- **오탐**(false positive · 폴스 포지티브)
  - 실제로는 정상 요청인데, 규칙이 「추가확인」이나 「거부」로 판정한 경우
  - 결과: 정상 직원의 업무가 막히거나 늦어진다
  - 예: 마감 주간에 조회를 많이 한 junho 의 정상 요청이 점수 규칙 때문에 추가확인이 된다
- **미탐**(false negative · 폴스 네거티브)
  - 실제로는 위험한 요청인데, 규칙이 「허용」이나 더 약한 판정(거부 대신 추가확인)을 한 경우
  - 결과: 위험한 요청이 막히지 않거나 약하게만 막힌다
  - 예: 대량 조회 점수의 기준을 20건에서 50건으로 올리면, 해외에서 49건을 조회한 위험한 요청이 대량 조회 점수를 받지 못해 거부 대신 추가확인에 그친다

| 규칙의 판정 | 실제 정상 요청 | 실제 위험 요청 |
|---|---|---|
| 허용 | 맞음 | **미탐** |
| 추가확인 · 거부 | **오탐** | 거부면 맞음, 추가확인이면 **미탐** |

오늘 연습에서는 위험한 요청의 맞는 결정을 「거부」로 봅니다.

점수 규칙은 어제 3교시 함수와 같습니다. 오늘 junho 의 요청은 모두 등록 기기 · MFA 함이라, 아래 두 점수만 계산합니다.

| 구분 | 기준 |
|---|---|
| 점수 | 해외에서 접속 +30 · **20건 이상 조회 +30** |
| 결정 | 50점 이상 거부 · 20점 이상 추가확인 · 그 아래 허용 |

조정안 세 가지

| 안 | 바꾸는 것 |
|---|---|
| A | 대량 조회 기준을 **20건 이상에서 50건 이상**으로 올린다 (점수는 +30 그대로) |
| B | 대량 조회 점수를 **+30 에서 +10** 으로 낮춘다 (기준은 20건 그대로) |
| C | 정산 마감 주간 동안 재무팀 계정의 **대량 조회 점수를 0** 으로 한다 |

**이 시간에 나오는 말** (이미 배운 방법입니다)

- `for 이름, 기준, 점수 in 목록:` 으로 튜플 하나를 이름 셋으로 풀어 꺼냅니다(10/14(수)).
- `조건1 and 조건2` 로 두 조건이 모두 맞는지 봅니다(10/15(목)).
- `def` 함수가 `return` 으로 값을 리턴합니다(10/19(월)).

- (다) 정산 조회의 유지 시간은 30분이라 12분은 `24`(30 × 0.8) 보다 작아 「유지」입니다. 권한 변경은 5분이라 12분은 5 보다 커서 「종료」입니다. 권한 변경은 계정을 바꿀 수 있는 더 위험한 자원이라 유지 시간을 짧게 두었기 때문입니다(최소권한을 시간에 적용).

**왜** — 세션은 시간이 지날수록 위험이 커지므로 만료 전에 본인 확인을 다시 요구하고, 위험한 자원일수록 유지 시간을 짧게 둡니다.

**관제에서는** — 세션 유지 시간은 자원의 위험에 맞춰 정하고, 오래 유지된 세션이 만료 직전에 하는 행동을 유심히 봅니다.

  - PEP 가 결정을 기다리지 않고 요청을 먼저 통과시켰을 수 있습니다 → PEP(프록시나 앱보다 먼저 요청을 받는 곳)의 설정과 처리 순서, 요청 처리 시각을 봅니다.
  - PEP 가 PDP 의 결정을 받지 못했을 때 기본으로 통과시키게 설정돼 있을 수 있습니다 → 그 시각 PDP 의 응답 기록, PEP 의 오류 기록을 봅니다.
  - 기록하는 쪽이 어긋나 로그에만 200 으로 남았을 수도 있습니다 → 실제 데이터가 내려갔는지 앱의 처리 기록을 봅니다.
- (한 줄) 예: 「12건 중 집행 누락 2건(101 · 108)과 과집행 1건(112), 판단을 거치지 않은 우회 1건(201)이 확인되었고, 거부했는데 통과한 101 번부터 조사하겠습니다.」

**왜** — PDP 의 결정은 PEP 가 집행해야 효력이 생깁니다. 정책 로그는 결정의 기록일 뿐이라 앱 기록과 맞춰 봐야 실제로 막혔는지 알 수 있고, 유형별로 세면 어디부터 조사할지 정할 수 있습니다.

**자주 틀리는 곳** — 정책 로그만 보고 「모두 정상적으로 막혔다」고 답하는 경우가 많습니다. 우회(201)를 놓치는 경우도 많은데, 정책 로그를 기준으로만 반복하면 앱 기록에만 있는 요청이 보이지 않습니다. `STRENGTH[status] < STRENGTH[expected]` 의 부등호를 거꾸로 쓰면 집행 누락과 과집행이 서로 바뀝니다. `if` 안쪽 줄의 들여쓰기를 빼면 `IndentationError` 가 납니다.

**관제에서는** — 결정 로그와 집행 로그를 같은 요청 번호로 대조하는 점검을 정기적으로 하고, 어긋난 요청을 유형별로 세어 일간 보고에 올립니다. 거부로 기록된 요청이 성공한 경우와 결정 기록이 없는 요청은 우선 조사하고, 개수의 변화는 설정이 바뀌었다는 신호로 봅니다.
