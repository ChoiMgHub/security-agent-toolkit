## 5교시 · 어제 명령 복습 · 서버 두 대 켜고 접속 기록 구분해 읽기

### 문제 5-1 · 어제와 같은 명령으로 서버 두 대를 켜고 접속 기록을 구분해 읽기

- (가) 내가 `web-three` 와 `web-four` 를 켠 `docker run` 명령 두 개를 붙여 넣어 주세요.
  - 쓸 내용: 윈도는 `MSYS_NO_PATHCONV=1` 부터, 맥북은 `docker run` 부터 친 그대로 두 줄
  - 답: 내가 사용한 명령은 다음과 같다. 처음에는 실수로 `day06_docker`에서 실행했지만, 두 컨테이너를 정리한 뒤 오늘 만든 폴더를 `day07_docker`로 옮겼다. `ls site-three site-four`로 각각 index.html이 있는 것을 확인하고, 올바른 위치에서 같은 명령으로 두 서버를 다시 만들었다.

```bash
MSYS_NO_PATHCONV=1 docker run -d --name web-three -p 8082:80 -v "$(pwd)/site-three:/usr/share/nginx/html:ro" nginx:1.28
MSYS_NO_PATHCONV=1 docker run -d --name web-four -p 8083:80 -v "$(pwd)/site-four:/usr/share/nginx/html:ro" nginx:1.28
```

    이름·내 PC 포트·연결 폴더를 달리하고, 이미지는 같은 nginx:1.28을 사용했다. `$(pwd)`는 명령을 입력한 현재 위치로 바뀌므로 작업 폴더가 실제 연결 경로를 결정한다.
- (나) 🔍 `docker ps` 에서 `web-three` 와 `web-four` 줄의 `PORTS` 값을 각각 적어 주세요.
  - 쓸 내용: 「web-three: … / web-four: …」
  - 답: web-three: `0.0.0.0:8082->80/tcp, [::]:8082->80/tcp` / web-four: `0.0.0.0:8083->80/tcp, [::]:8083->80/tcp`. 처음 실행 때 `docker ps`에서 두 PORTS 값과 Up 상태를 직접 확인했다. 이후 day07_docker에서 재실행한 명령도 각각 8082:80, 8083:80으로 동일하게 지정했고 각 서버의 응답 기록을 확인했다. 내 PC의 8082는 web-three의 80으로, 8083은 web-four의 80으로 연결된다.
- (다) 🔍 8082 로 세 번, 8083 으로 한 번 접속했을 때 `docker logs web-three` 와 `docker logs web-four` 의 `"GET / HTTP/1.1"` 줄은 각각 몇 개였고, 왜 그렇게 나뉘나요?
  - 쓸 내용: ① web-three 의 줄 수 ② web-four 의 줄 수 ③ 그렇게 나뉘는 이유(어느 포트로 온 요청이 어느 서버에 기록되는지)
  - 답: 최종 재실행에서 web-three는 3개, web-four는 2개였다. 교재는 3회·1회 접속을 요구했지만 내 실제 기록에는 직원용 요청이 한 번 더 남아 있었으므로 3개·1개로 바꾸어 적지 않았다. 추가 요청이 어떤 브라우저 조작으로 생겼는지는 로그만으로 확정하지 못했다. 각 포트가 다른 컨테이너로 연결되어 8082 요청은 web-three에, 8083 요청은 web-four에 따로 남는 것을 확인했다. 다음은 긴 브라우저 정보 등을 생략한 실제 첫 페이지 요청 부분이다.

```text
web-three:
[20/Oct/2026:05:45:49 +0000] "GET / HTTP/1.1" 304 0
[20/Oct/2026:05:45:50 +0000] "GET / HTTP/1.1" 304 0
[20/Oct/2026:05:45:50 +0000] "GET / HTTP/1.1" 304 0

web-four:
[20/Oct/2026:05:45:53 +0000] "GET / HTTP/1.1" 304 0
[20/Oct/2026:05:45:54 +0000] "GET / HTTP/1.1" 304 0
```

    처음 day06_docker에서 실행했을 때는 두 서버가 각각 GET / 1건·200 응답을 남겼고 사이트 두 개도 잘 표시되는 것을 확인했다. 아이콘 요청인 /favicon.ico의 404도 있었지만 첫 페이지 접속 실패는 아니었다. 위치 수정 후의 위 기록은 304 응답으로, 내용이 바뀌지 않아 브라우저가 보관한 내용을 사용하라는 뜻이다. 본문 크기 0이어도 요청은 서버에 도착해 응답했으므로 건수에 포함했다.
- (라) 🔍 `stop` 뒤에 `docker ps` 와 `docker ps -a` 에서 두 서버가 각각 어떻게 보였고, `rm` 뒤에는 어떻게 되었나요?
  - 쓸 내용: 「stop 뒤 ps: … / stop 뒤 ps -a: … / rm 뒤 ps -a: …」
  - 답: stop 뒤 ps: 두 서버가 보이지 않고 제목 줄만 나왔다. / stop 뒤 ps -a: 두 서버가 Exited (0)으로 남아 있었다. / rm 뒤 ps -a: 두 서버가 사라지고 기존 hello-world 컨테이너 sad_euclid·gifted_chaplygin만 남았다. 이 차이는 첫 실행에서 직접 출력으로 확인했다. 올바른 폴더에서 재실행한 뒤에도 `docker stop web-three web-four`와 `docker rm web-three web-four`를 실행해 두 이름이 출력됐고, 마지막 ps -a에서 hello-world 두 개만 남은 것을 다시 확인했다. 추가로 `docker exec web-four ls /usr/share/nginx/html`의 출력에서 index.html을 확인했다.
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(서버를 몇 대 어떻게 켰고 기록이 어떻게 남았는지)
  - 답: 고객용·직원용 서버 두 개를 각각 8082·8083 포트로 실행해 페이지를 확인했고 최종 첫 페이지 요청이 각 서버에 3건·2건으로 따로 기록되는 것을 확인한 뒤, 두 컨테이너를 중지·삭제했습니다.
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: 같은 이미지로 만든 서버도 컨테이너 이름·호스트 포트·연결 폴더를 구분하면 서로 다른 페이지와 로그를 가질 수 있다는 점을 배웠다. 처음에는 day06_docker에서 실습한 것이 큰 문제인지 걱정했지만, `$(pwd)`가 그 위치의 폴더를 연결한 덕분에 서버는 정상 작동했다. 오늘 파일만 day07_docker로 옮기고 확인한 뒤 재실행하면서 상대 경로와 현재 위치의 관계를 이해했다.

    로그 횟수가 교재와 다른 이유를 질문한 뒤, 서버 설정 오류와 추가 요청 기록을 구분했다. 페이지가 잘 나오는지는 한 번 접속해도 확인할 수 있지만, 새로고침을 반복하는 것은 요청이 누적되고 서버별로 분리되는 모습을 보기 위한 것이라는 설명을 들었다. 서버가 ‘새로고침 버튼 클릭’ 자체를 적는 것이 아니라 그 때문에 도착한 HTTP 요청을 기록한다는 점도 알았다. 따라서 로그 3건은 방문자 3명과 같지 않고, 시작 메시지나 favicon 요청도 첫 페이지 요청과 구분해서 세어야 한다. 304 역시 오류가 아니라 캐시 재사용을 알리는 응답이었다.
## 6교시 · 내 이미지 만들기 (Dockerfile)

### 문제 6-1 · Dockerfile 두 줄을 써서 내 이미지 만들기

- (가) 내가 쓴 Dockerfile 두 줄을 붙여 넣어 주세요.
  - 쓸 내용: Dockerfile 두 줄(`FROM` 줄 · `COPY` 줄)
  - 답: day07_docker에서 Vim으로 Dockerfile을 작성하고 빌드했다. Dockerfile에 쓴 두 줄은 다음과 같다.

```dockerfile
FROM nginx:1.28
COPY site-three/index.html /usr/share/nginx/html/index.html
```

- (나) 🔍 `FROM` 과 `COPY` 가 각각 하는 일을 적어 주세요.
  - 쓸 내용: ① FROM 이 하는 일 ② COPY 가 하는 일
  - 답: FROM은 새 이미지의 기반으로 기존 nginx:1.28을 지정한다. nginx를 직접 개발하는 것이 아니라 이미 준비된 프로그램과 기본 구성을 바탕으로 내 파일을 추가하는 것이다. COPY는 빌드 자료의 site-three/index.html을 이미지 안의 /usr/share/nginx/html/index.html로 복사한다. 앞쪽은 원본 파일이고 뒤쪽은 이미지 안의 목적지다. 이번에는 `docker build`의 마지막 점으로 day07_docker를 빌드 자료의 기준 위치로 지정했으므로 그 안의 site-three/index.html을 찾았다. 기존 nginx 이미지를 덮어쓰는 것이 아니라 my-nginx:1이라는 새 이미지를 만드는 방식이다.
- (다) 🔍 5교시와 달리 `docker run` 에 `-v` 가 없는데도 내 화면이 나오는 이유는 무엇인가요?
  - 쓸 내용: ① 어제 파일이 컨테이너에 닿던 방법 ② 오늘 파일이 서버에 있는 위치와 시점
  - 답: 5교시에는 페이지 파일이 내 PC에 있고 `-v`로 폴더를 연결해 컨테이너가 읽게 했다. 이번에는 docker build 때 페이지 파일을 이미지 안에 복사해 두었으므로 원본 폴더를 연결하지 않아도 컨테이너에 해당 파일이 들어 있다. 실제로 `docker run -d --name my-site -p 8090:80 my-nginx:1`로 실행하고, ps에서 IMAGE my-nginx:1·Up 상태·8090→80 연결을 확인했다. 첨부한 브라우저 화면에서도 127.0.0.1:8090에 제목 site-three와 ‘고객 안내 페이지입니다’가 표시되는 것을 확인했다. 실행 중인 컨테이너 ID는 a10d3b5fd9bb였다.
- (라) 🔍 `docker build` 출력에서 `[2/2] COPY` 줄과 `naming to` 줄을 붙여 넣고, 각각 무엇을 알려 주는지 적어 주세요.
  - 쓸 내용: ① 두 줄 ② 각 줄이 알려 주는 것
  - 답: 내 빌드 출력의 해당 두 줄은 다음과 같다.

```text
=> [2/2] COPY site-three/index.html /usr/share/nginx/html/index.html  0.6s
=> => naming to docker.io/library/my-nginx:1  0.0s
```

    COPY 줄은 내 페이지를 이미지 안에 넣는 두 번째 단계를 처리했음을 보여 준다. naming to 줄은 결과에 my-nginx:1이라는 이름과 태그를 붙였다는 뜻이다. Docker Hub에 업로드했다는 뜻은 아니다. 내 전체 빌드는 2.8초 만에 FINISHED로 끝났고, 이미지 목록에서 my-nginx:1·ID 2d8d946a7969가 생긴 것을 확인했다. Dockerfile 전송 크기는 114B였다.

    6교시에서 나는 Docker의 이미지가 사진·그림·캡처를 말하는지 질문했다. 여기서는 프로그램과 필요한 파일·기본 설정을 담아 컨테이너를 만들 수 있게 준비한 원본 묶음이라는 설명을 들었다. 왜 image라는 이름을 쓰는지, 영어권에서는 호칭이 다른지도 다시 물었다. 영어에서도 image라는 단어를 쓰며 문맥이나 Docker image·disk image 같은 표현으로 구분한다는 것을 알았다. 사진으로 이해한 채 따라가기보다 용어의 의미를 다시 확인한 것이 도움이 됐다. Dockerfile은 제작 설명서, build는 이미지 제작, image는 제작된 실행 기반, run은 컨테이너 생성·실행으로 구분했다.
## 7교시 · 이미지 버전 다루기 · 되돌리기 · 정리 · 올리기

### 문제 7-1 · 파일을 고쳐 보고, 이미지를 다시 만들어 반영하기

- (가) 파일을 고친 직후 새로 고침했을 때 화면에 무엇이 나왔나요?
  - 쓸 내용: 새로 고침했을 때 보인 화면의 큰 제목
  - 답: 확인 기록 구분: 원본 HTML만 수정한 직후, 이미지 교체 전 브라우저 화면은 대화에 공유하지 않아 직접 확인한 값으로 확정하지 않는다. 코드 구조상 기존 my-nginx:1을 사용하는 동안에는 제목이 site-three로 남는다는 설명을 들었다. 내가 화면을 첨부해 직접 확인한 것은 새 이미지로 교체한 뒤의 site-three v2였다.
- (나) 🔍 파일을 고쳤는데도 화면이 바뀌지 않은 이유와, 바꾸려면 무엇을 해야 하는지 적어 주세요.
  - 쓸 내용: ① 바뀌지 않은 이유(서버가 보는 파일이 어디 있는지) ② 바꾸려면 할 일
  - 답: 서버가 사용하는 파일은 my-nginx:1 안에 빌드 시점에 복사된 파일이고 내 PC 원본 폴더는 연결되어 있지 않기 때문이다. 원본을 고치거나 새 이미지를 만들기만 해서는 기존 컨테이너가 자동으로 바뀌지 않는다. 나는 수정한 파일로 `docker build -t my-nginx:2 .`를 실행했고, 기존 my-site를 삭제한 뒤 새 이미지로 실행했다.

```bash
docker build -t my-nginx:2 .
docker rm -f my-site
docker ps -a
docker run -d --name my-site -p 8090:80 my-nginx:2
```

    빌드는 0.7초 만에 FINISHED로 끝났고 기반 FROM 단계는 CACHED였지만 COPY는 새로 처리됐다. 결과는 my-nginx:2·ID a1dda04ea60e였다. 기존 my-site가 ps -a에서 사라진 것을 확인한 뒤 새 컨테이너 b5c95835a29c를 만들었고, 브라우저 제목이 site-three v2로 바뀐 화면을 공유했다. 같은 이름 my-site를 다시 붙였어도 새 컨테이너이며, 기존 이미지는 이 컨테이너 삭제 명령으로 지워지지 않는다.
- (다) 🔍 5교시의 `-v` 방식과 6교시의 이미지에 넣는 방식은 파일을 고쳤을 때 반영되는 방법이 어떻게 다른가요?
  - 쓸 내용: ① -v 방식의 반영 방법 ② 이미지에 넣는 방식의 반영 방법
  - 답: ① -v 방식: 내 PC 폴더를 컨테이너에 연결하므로 원본을 수정하면 서버가 변경된 파일을 읽을 수 있고, 브라우저 새로고침과 캐시 상태를 확인한다. ② 이미지에 넣는 방식: 빌드 때 복사한 파일을 사용하므로 원본 저장만으로 기존 이미지와 컨테이너는 바뀌지 않는다. 이미지를 다시 빌드하고 그 이미지로 컨테이너를 교체한 뒤 화면을 확인해야 한다. 단순히 기존 컨테이너를 중지했다 다시 시작하는 것은 새 이미지로 교체하는 것과 다르다.
### 문제 7-2 · 이전 버전으로 되돌리고 쓰지 않는 이미지 지우기

- (가) 이전 버전으로 되돌린 뒤 `docker ps` 의 `IMAGE` 칸 값과 브라우저에 나온 제목을 적어 주세요.
  - 쓸 내용: 「IMAGE: … / 브라우저 제목: …」
  - 답: IMAGE: my-nginx:1 / 브라우저 제목: site-three. v2 컨테이너를 삭제하고 `docker run -d --name my-site -p 8090:80 my-nginx:1`로 다시 실행했다. ps에서 새 컨테이너 52546186a245가 my-nginx:1을 사용하고 Up 상태인 것을 확인했다. 원본 index.html의 v2를 지우지 않았는데도 이전 화면으로 돌아오는 점이 궁금해 그 이유를 질문했다. 원본 파일이 복원된 것이 아니라 예전 페이지가 들어 있는 이미지를 선택해 실행한 것이었다.
- (나) 🔍 쓰고 있는 `my-nginx:1` 을 `docker rmi` 로 지우려 했을 때 에러 문구의 핵심과, 어떻게 해결했는지 적어 주세요.
  - 쓸 내용: ① 에러 문구의 핵심 ② 지워지지 않은 이유 ③ 해결한 순서
  - 답: 오류의 핵심은 `container 52546186a245 is using its referenced image 2d8d946a7969`였다. 실행 중인 my-site가 my-nginx:1을 참조하고 있어 일반적인 이미지 삭제가 거절된 것이다.

```text
Error response from daemon: conflict: unable to delete my-nginx:1 (must be forced) - container 52546186a245 is using its referenced image 2d8d946a7969
```

    사용하지 않는 my-nginx:2를 먼저 삭제한 다음 my-site 컨테이너를 삭제하고, my-nginx:1을 다시 삭제해 해결했다.

```bash
docker rmi my-nginx:2
docker rm -f my-site
docker ps -a
docker rmi my-nginx:1
docker images
```

    두 이미지에서 Untagged와 Deleted 메시지를 확인했다. 마지막 컨테이너 목록에는 기존 hello-world 두 개만, 이미지 목록에는 hello-world:latest와 nginx:1.28만 남아 실습용 컨테이너와 내 이미지 두 개를 정리한 것을 확인했다.
- (다) 🔍 이미지에 `:1` · `:2` 같은 태그를 붙여 두면 문제가 생겼을 때 어떤 점이 좋은가요?
  - 쓸 내용: ① 되돌리는 방법 ② 어느 버전이 켜져 있는지 아는 방법
  - 답: 이전 구성과 새 구성을 서로 다른 태그로 보관하면, 새 버전에 문제가 있을 때 이전 태그의 이미지로 컨테이너를 다시 만들어 되돌릴 수 있다. 어떤 버전으로 실행 중인지는 docker ps의 IMAGE 칸에서 확인한다. 다만 태그는 사람이 붙이는 이름표이므로 :1을 지정한다고 과거 내용이 자동 생성되는 것은 아니다. 이전 이미지나 이전 원본 파일이 실제로 남아 있어야 하며, 수정된 원본으로 :1이라는 이름을 붙여 재빌드하면 내용은 수정본이 된다. 이번에는 복구 확인 뒤 두 이미지를 모두 삭제했으므로 이 실습 이미지가 계속 남아 있다고 쓰지 않는다.
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(되돌린 일과 정리한 일)
  - 답: 서버를 이전 이미지 my-nginx:1로 되돌려 사용 버전을 확인했고, 사용 중인 이미지의 삭제 거절을 읽은 뒤 컨테이너와 내 실습 이미지 두 개를 순서대로 정리했습니다.
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: 원본 HTML을 예전 내용으로 고치지 않아도 이전 이미지로 서버를 만들면 그 안에 남은 예전 페이지가 보일 수 있다는 것을 직접 경험했다. 처음에는 ‘v2를 안 지웠는데 어떻게 복구되는가’가 이해되지 않았고, 수정 전 HTML을 복사해 뒀다가 복원하는 방법도 안 되는 것인지 질문했다. 백업한 HTML로 복구하는 방법도 가능하지만, 이번 COPY 방식에서는 원본 복원 뒤 이미지 재빌드와 컨테이너 교체가 필요하다는 설명을 들었다. 반대로 원하는 내용이 들어 있는 이전 이미지가 있으면 재빌드 없이 그 이미지로 컨테이너를 만들 수 있다.

    파일 수정·이미지 제작·실행 컨테이너 교체는 다른 작업이다. `docker rm`은 컨테이너, `docker rmi`는 이미지를 지운다는 차이도 실제 오류와 삭제 결과로 확인했다. 이미지가 다른 컨테이너에서 참조되는지 살펴야 하며 중지된 컨테이너도 참조를 남길 수 있다. 이미지 목록의 U도 반드시 실행 중이라는 뜻만은 아니다. 태그를 남기는 것과 Git에 소스 변경을 기록하는 일도 구분해야 한다. 오늘은 AI의 설명을 받아 질문하며 개념을 이해했고, 내가 공유한 출력과 화면으로 확인한 범위만 완료로 기록했다.
