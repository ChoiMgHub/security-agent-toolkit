### 📖 왜 필요한가

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

1. 현업에서 알림은 어떤 유형인지 적혀 오지 않습니다. 증상을 보고 아래 세 유형 중 하나로 짐작하고, 짐작이 맞는지는 **기록으로 확인**해야 합니다. 이 교시에서는 서버 알림 세 건을 내 PC 에서 재현해 확인합니다.
   - **장애**: 정상 요청이 안 되거나 느림
   - **위협**: 악의적인 시도
   - **접근통제**: 권한 · 정책의 문제(서버가 누구에게 열려 있는지도 여기에 듭니다)
2. `-p 8080:80` 처럼 `127.0.0.1:` 없이 연결하면 **내 PC의 모든 주소(`0.0.0.0`)로 열립니다.** 켜 두기만 한 개발용 서버가 이렇게 열려 사내 다른 PC에서 접속되는 일이 흔하고, 이것을 점검하는 것이 열린 포트 점검입니다.
3. 서버는 포트만 보면 끝이 아닙니다. 켜진 서버 **안쪽**에 비밀번호가 평문으로 들어 있거나 서버가 `root` 로 실행되면, 포트를 닫아도 한 번 뚫렸을 때 피해가 커집니다. `docker inspect` · `docker exec` 로 안쪽을 점검합니다.
4. 서버 응답 번호가 `000` 이거나 `404` 가 쌓여도 번호만으로는 원인을 모릅니다. `docker ps` 의 `STATUS` · `PORTS` 와 `docker logs` 의 접속 기록 줄을 읽어야 압니다.

### 📖 2.1 어디까지 열려 있나

> ⚠ **읽기만 합니다 — 따라 치지 않습니다.** 아래 「✍️ 문제 2-1」에서 칩니다.

```
-p 127.0.0.1:8081:80  (닫힘)
  내 PC 안에서 (127.0.0.1)  : 접속됨
  내 PC 의 IP 주소:8081     : 거부됨
  다른 PC                   : 거부됨

-p 8082:80  (열림)
  내 PC 안에서 (127.0.0.1)  : 접속됨
  내 PC 의 IP 주소:8082     : 접속됨
  다른 PC                   : 접속됨
```

- 위는 닫은 서버로 내 PC 안에서만 접속됩니다. 아래는 연 서버로 내 PC의 IP 주소로도, 다른 PC에서도 접속됩니다.

- `127.0.0.1` 은 내 PC 자신을 가리키는 주소입니다(1일 차). `-p 127.0.0.1:8081:80` 은 그 주소로 온 요청만 서버에 넘깁니다.
- `docker run` 의 `-p` 옵션은 `-p [주소:]내PC포트:컨테이너포트` 모양이고, 맨 앞의 `주소:` 는 생략할 수 있습니다.
  - `-p 127.0.0.1:8081:80` 처럼 `127.0.0.1:` 을 쓰면 내 PC 안에서 온 요청만 받습니다(닫힘).
  - `-p 8082:80` 처럼 `주소:` 를 생략하면 `0.0.0.0`(내 PC의 모든 주소)으로 연결되어 다른 PC에서 온 요청도 받습니다(열림).
- 켠 뒤 `docker ps` 의 `PORTS` 열에 `127.0.0.1:8081->80/tcp` 로 나오면 닫힌 것이고 `0.0.0.0:8082->80/tcp` 로 나오면 열린 것입니다.
- 오늘은 내 PC의 **IP 주소**(같은 네트워크 안에서 다른 PC가 내 PC에 접속할 때 쓰는 주소, 1일 차)로 접속해 봅니다. 다른 PC가 접속할 때와 같은 주소입니다.
- 오늘 켜는 두 서버에는 `--name` 옵션으로 이름을 붙입니다. 닫힌 서버는 `closed-web-8081`, 열린 서버는 `open-web-8082` 입니다.
  - 이름은 Docker 가 정해 둔 명령이 아니라 **내가 정하는 컨테이너 이름**입니다. 어제 `--name web-three` 로 `web-three` 라는 이름을 붙인 것과 같습니다.
  - 이름에 「닫힘/열림 · 서버 종류 · 포트」를 넣었습니다: `closed`(닫힘) · `web`(웹 서버) · `8081`(포트 번호). 이름만 보고 어느 서버가 닫혔고 열렸는지 알아보기 위해서입니다.
  - 이 문서 뒤쪽의 명령이 이 이름으로 적혀 있으므로 그대로 씁니다.

- **`docker inspect 이름`**(도커 인스펙트 · 컨테이너의 설정 값을 JSON 으로 보여 줌)
  - `docker ps` 의 `PORTS` 열은 요약이고, `inspect` 는 원본 설정입니다. 포트 연결 부분만 뽑으면 `"HostIp":"127.0.0.1"` 이면 닫힘이고 `"HostIp":""`(비어 있음)이면 **모든 주소로 열림**입니다.
  - 안쪽이 JSON 이라 9/28(월)에 배운 모양과 같습니다. 필요한 부분만 `--format` 으로 뽑습니다.
- **환경변수**(environment variable · 인바이런먼트 배리어블 · `이름=값` 으로 프로그램에 넘기는 설정)
  - API 키를 `.env` 에 넣었던 것과 같은 방식입니다. 서버에는 `docker run -e 이름=값` 으로 넘깁니다.
  - 편리하지만 서버에 `docker exec` 로 들어올 수 있는 사람은 `env` 로 값을 그대로 읽습니다. `docker inspect` 에도 그대로 보입니다.
- **실행 사용자**
  - 컨테이너 안의 프로그램도 어떤 사용자로 실행됩니다. 따로 정하지 않으면 모든 권한을 가진 `root` 입니다.
  - `docker exec 이름 whoami` 로 확인합니다. 서버가 뚫리면 공격자가 `root` 권한을 얻으므로, 6일 차에 배운 최소권한과 같은 문제입니다.
- `docker exec` 는 어제 배운 명령입니다. 오늘은 컨테이너 안에 들어가지 않고 명령 하나만 실행합니다.

### <mark>✍️ 문제 2-1 · 알림 A 확인 — 서버 두 대로 열려 있는지 재고, 설정 값 · 비밀번호 · 실행 사용자까지 점검하기</mark>

**📍 이런 상황이 있습니다**

- 알림 A: 개발용 서버(8082 포트)가 사내 다른 PC에서도 접속된다는 신고입니다. 담당자는 서버 두 대를 켭니다. 한 대는 내 PC 안에서만 접속되게(`-p 127.0.0.1:포트:80`), 다른 한 대는 다른 PC도 접속되게(`-p 포트:80`) 켭니다. 그다음 내 PC의 IP 주소로 접속해서 어느 쪽이 열려 있는지 판정합니다.
- 보안 담당이 두 가지를 더 물었습니다. 「그 서버에는 DB 비밀번호가 환경변수로 들어 있다는데, 서버 안에서 읽히나요?」 「그 서버는 어떤 사용자로 실행되나요?」
- 현업에서는 켜 두기만 한 개발용 서버가 `0.0.0.0` 으로 열려 사내 다른 PC에서 접속되는 일이 흔하고, 이것을 점검하는 것이 열린 포트 점검입니다.

**🎯 할 일**

1. 8081 · 8082 포트를 쓰는 <mark>컨테이너를 정리</mark>합니다.
2. <mark>닫힌 서버(8081)와 열린 서버(8082)</mark>를 켭니다. 열린 서버에는 연습용 비밀번호를 환경변수로 넣습니다.
3. 내 PC의 <mark>IP 주소</mark>로 두 포트에 접속해 <mark>`PORTS` 열과 접속 결과</mark>를 짝지어 판정합니다.
4. <mark>`docker inspect`</mark> 로 같은 결론을 설정 값에서 확인합니다.
5. <mark>`docker exec`</mark> 로 환경변수의 비밀번호와 실행 사용자를 확인합니다.

**순서**

1. **[터미널]** Docker Desktop 이 켜져 있는지 확인하면서 지금 있는 컨테이너 목록을 봅니다.
   ```bash
   docker ps -a
   ```
   - 명령 풀이: `docker ps` 켜져 있는 컨테이너 목록 · `-a` 꺼진 것까지 모두
   - 에러가 나면 Docker Desktop 을 실행하고 **Engine running** 이 될 때까지 기다린 뒤 다시 칩니다.
2. **[터미널]** 어제 켠 컨테이너를 지웁니다. 같은 포트는 한 번에 한 컨테이너만 쓸 수 있어서, 어제 켠 `web-three` 가 8082 를 쓰고 있으면 오늘 서버가 `port is already allocated` 에러로 켜지지 않습니다.
   ```bash
   docker rm -f web-three web-four my-site
   ```
   - 명령 풀이: `docker rm` 컨테이너를 지움 · `-f` 켜져 있어도 끄고 지움 · `web-three` · `web-four` · `my-site` 지울 컨테이너 이름 세 개
   - 목록에 없는 이름은 `No such container` 에러가 나지만 나머지는 지워지므로 무시해도 됩니다.
   - 1번 목록의 `PORTS` 열에 `8081` 또는 `8082` 가 들어간 다른 이름의 줄이 남아 있으면 그 이름도 `docker rm -f` 뒤에 적어 지웁니다. `hello-world` 와 수업에서 만들지 않은 컨테이너는 지우지 않습니다.
3. **[터미널]** 서버 두 대를 켭니다. `--name` 뒤의 `closed-web-8081` · `open-web-8082` 는 내가 붙이는 컨테이너 이름입니다(어제 `web-three` 처럼). 이름에 「닫힘/열림 · 서버 종류 · 포트」를 넣어 이름만 보고 알아보게 했고, 뒤쪽 명령이 이 이름으로 적혀 있으므로 그대로 씁니다.
   - `closed-web-8081` 을 켭니다. `127.0.0.1:` 이 붙어 **내 PC 안에서만** 접속되게 8081 을 엽니다.
     ```bash
     docker run -d --name closed-web-8081 -p 127.0.0.1:8081:80 nginx:1.28
     ```
     - 명령 풀이: `docker run` 이미지로 컨테이너를 만들어 켬 · `-d` 백그라운드로 실행(터미널을 계속 쓸 수 있음) · `--name closed-web-8081` 컨테이너 이름 붙이기 → `closed-web-8081` · `-p 127.0.0.1:8081:80` 내 PC 안(`127.0.0.1`)에서만 8081 포트로 들어온 요청을 컨테이너 80 포트로 연결 · `nginx:1.28` 쓸 이미지(이름:태그)
   - `open-web-8082` 를 켭니다. 주소를 붙이지 않아 **모든 주소로** 8082 를 열고, 연습용 비밀번호를 환경변수로 넣습니다.
     ```bash
     docker run -d --name open-web-8082 -e DB_PASSWORD=dev-pass-1234 -p 8082:80 nginx:1.28
     ```
     - 명령 풀이: `docker run` 이미지로 컨테이너를 만들어 켬 · `-d` 백그라운드로 실행 · `--name open-web-8082` 컨테이너 이름 붙이기 → `open-web-8082` · `-e DB_PASSWORD=dev-pass-1234` 컨테이너 안에 환경변수 `DB_PASSWORD` 를 연습용 값으로 만듦 · `-p 8082:80` 내 PC 8082 포트를 컨테이너 80 포트에 연결(모든 주소로 열림) · `nginx:1.28` 쓸 이미지(이름:태그)
   - 에러가 나면 읽고 고칩니다.
     - `port is already allocated` — 2번에서 놓친 컨테이너가 8081 또는 8082 를 쓰고 있습니다. `docker ps -a` 로 `PORTS` 열을 다시 보고 그 이름을 `docker rm -f` 로 지운 뒤 다시 켭니다.
     - `container name "/closed-web-8081" is already in use` — 방금 실패한 컨테이너가 이름을 잡고 있습니다. `docker rm -f closed-web-8081 open-web-8082` 으로 지우고 다시 켭니다.
4. **[터미널]** 두 서버의 `PORTS` 열을 읽습니다. `closed-web-8081` 은 `127.0.0.1:8081->80/tcp`, `open-web-8082` 는 `0.0.0.0:8082->80/tcp` 로 나옵니다.
   ```bash
   docker ps
   ```

### 📖 2.2 서버가 켜져 있는데 응답이 없을 때 · 접속 기록 한 줄 읽기

> 📖 **읽을거리** — 다음 문제의 배경지식입니다. 읽고 나서 아래 「✍️ 문제 2-2」으로 갑니다. 여기 나오는 명령은 **따라 치지 않습니다.**

```
서버가 응답하지 않는다
   |
   v
docker ps        <-- 켜져 있나?  (있으면: PORTS 열 확인)
   |  없다
   v
docker ps -a     <-- 꺼진 채 남아 있나?  (Created 또는 Exited 로 있을 수 있다)
   |
   v
docker logs 이름 <-- 요청 줄과 에러가 있나?
```

- **응답 번호 `000`** 은 서버가 답을 하지 않아 연결 자체가 안 됐다는 뜻입니다. 서버가 꺼졌거나, 내 PC 안에서만 열려 있거나, 포트 연결이 잘못돼도 모두 `000` 이 나오므로 **번호만으로는 원인을 알 수 없습니다.**
- `-p 내PC포트:컨테이너포트` 에서 **컨테이너포트**는 컨테이너 안에서 프로그램이 기다리는 번호입니다. nginx 는 `80` 에서 기다리므로 `-p 8084:8080` 처럼 다른 번호를 쓰면 포트는 연결됐는데 받는 프로그램이 없습니다. 포트 연결은 서버를 켤 때 정해지므로, 틀리게 켠 서버는 `docker rm -f 이름` 으로 지운 뒤 다시 켜야 합니다.
- **`docker logs` 에 요청 줄이 남는지**가 단서가 됩니다. 서버가 요청에 답했다면(`200` · `404` 등) 접속 기록 줄이 남습니다. 요청이 서버에 닿지 못했다면 기록이 남지 않습니다.
- 접속 기록 한 줄은 이렇게 읽습니다. 학생 PC 에서는 맨 앞 주소가 `172.17.0.1` 처럼 도커가 PC 안에서 쓰는 주소로 보일 수 있습니다.

```
192.168.65.1 - - [20/Oct/2026:12:14:23 +0000] "GET /admin HTTP/1.1" 404 153 "-" "curl/8.7.1" "-"
```

| 칸 | 뜻 |
|---|---|
| `192.168.65.1` | 요청을 보낸 곳(출처) |
| `[20/Oct/2026:12:14:23 +0000]` | 요청을 받은 시각 |
| `"GET /admin HTTP/1.1"` | 요청한 내용: `GET`(내용 달라는 요청) `/admin`(경로) |
| `404` | 응답 번호 |
| `"curl/8.7.1"` | 요청을 보낸 프로그램 이름. 브라우저가 보내면 `Mozilla/5.0 …` 로 시작합니다 |

- `[error]` 로 시작하는 줄은 nginx 가 이유를 따로 적은 오류 기록입니다. 10/19(월)에 `favicon.ico` 의 `404` 접속 기록 줄과 함께 있던 것과 같은 종류의 줄입니다.

> ✍️ **여기부터 문제입니다.** 위는 읽을거리였고, 아래에서 직접 합니다.

### <mark>✍️ 문제 2-2 · 알림 B · C 확인 — 응답이 없는 서버와 연달아 남은 404 읽기</mark>

**📍 이런 상황이 있습니다**

- 알림 B: 개발 서버(8084 포트)가 `docker ps` 에 `Up` 으로 켜져 있는데 접속하면 응답 번호가 `000` 입니다. 서버가 켜져 있는데 왜 답을 하지 않는지 원인을 찾아야 합니다.
- 알림 C: 같은 출처에서 1초 안에 없는 주소를 연달아 요청해 `404` 가 다섯 번 남았습니다. 단순 오류인지 공격 시도인지 기록으로 판단해야 합니다.
- 두 알림을 내 PC 에서 그대로 재현합니다. 응답 번호만 보고 단정하지 않고 `docker ps` 와 `docker logs` 를 근거로 씁니다.

**🎯 할 일**

1. 알림 B 의 서버를 <mark>신고된 설정 그대로</mark> 켜고 응답 번호를 봅니다.
2. <mark>`docker ps` 의 `PORTS` 열</mark>과 <mark>`docker logs`</mark> 로 원인을 찾고, 컨테이너 포트를 `80` 으로 켠 서버와 비교해 확인합니다.
3. 알림 C 처럼 <mark>없는 주소를 연달아 요청</mark>하고, 접속 기록 줄의 <mark>출처 · 시각 · 경로 · 프로그램</mark>을 읽어 판단합니다.

### 📖 3.1 JSON 줄 로그와 상관 분석

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

- **JSON 줄**(JSON Lines · 제이슨 라인즈)
  - 한 줄이 JSON 하나인 로그 형식
  - 줄 하나를 `json.loads(글자)` 로 딕셔너리로 바꿔서 읽는다(9/28(월))
- **상관 분석**(correlation analysis · 코릴레이션 애널리시스)
  - 여러 줄의 사건을 이어서 보고 패턴을 찾는 것
  - 오늘은 「같은 계정이 거부된 뒤 10분 안에 허용되는 것」을 찾는다
- 이 패턴은 의심 후보일 뿐 확정이 아닙니다. MFA 를 한 뒤 다시 시도해 허용되는 정상 재시도도 같은 모양입니다. **거부 이유와 기기가 바뀌었는지**로 가릅니다.

#### MFA 와 2차 인증 — 로그의 「MFA 안 함」은 무엇을 안 했다는 뜻인가

- **MFA**(multi-factor authentication · 엠에프에이, 다요소 인증)
  - 서로 **다른 종류**의 인증 요소를 **두 개 이상** 함께 쓰는 로그인 방식(10/19(월)에 배움)
  - 인증 요소는 세 종류입니다.

| 종류 | 뜻 | 예 |
|---|---|---|
| 지식 | 아는 것 | 비밀번호, PIN |
| 소유 | 가진 것 | 휴대폰 OTP(일회용 인증 번호), 보안키 |
| 존재 | 나 자신 | 지문, 얼굴 |

- **2차 인증**(2FA · two-factor authentication · 투 팩터 오센티케이션, 2요소 인증)
  - 서로 다른 종류의 요소를 **정확히 두 개** 쓰는 MFA
  - 그래서 **2차 인증은 MFA 의 한 경우**이고, MFA 가 모두 2차 인증인 것은 아닙니다. 비밀번호(지식) + 휴대폰 OTP(소유) + 지문(존재)처럼 요소가 셋이면 MFA 이지만 2차 인증은 아닙니다.
- **같은 종류를 두 번 쓰면 MFA 가 아닙니다.** 비밀번호 + 보안 질문은 둘 다 「아는 것」이라 단계만 둘일 뿐 다요소가 아닙니다.
- **단계와 요소는 다릅니다.** 「2단계 인증」은 로그인 단계가 두 번이라는 뜻이고, 「2요소 인증」은 서로 다른 종류의 요소가 둘이라는 뜻입니다. 한국어에서는 둘 다 「2차 인증」이라고 뭉뚱그려 부르는 일이 많습니다.
- 이 문서에서는 **「MFA(흔히 2차 인증)」** 로 씁니다. 오늘 로그의 이유 「MFA 안 함」은 비밀번호 말고 추가 인증(보통 휴대폰 인증)을 하지 않아서 거부됐다는 뜻이고, junho 처럼 추가 인증을 마친 뒤 다시 시도하면 허용됩니다.

계정마다 **마지막 결정과 그 시각(분)**을 딕셔너리에 기억해 두고, 새 줄을 읽을 때마다 비교합니다. 시각 `"09:10"` 은 `to_min` 함수로 분(550)으로 바꿔 뺄셈합니다(`.split(":")` 은 10/13(화)에 배웠습니다).

로그 두 줄을 따라가면 이렇습니다.

| 읽는 줄 | `last` 에 기억된 값 | 판정 |
|---|---|---|
| `02:10 seoyeon 거부` | (없음) | 처음 보는 계정 → 기억만 한다: `last["seoyeon"] = ("거부", 130)` |
| `02:13 seoyeon 허용` | `("거부", 130)` | 마지막이 거부이고 지금은 허용이고 `133 - 130 = 3` 분 → **거부 후 허용** |

- `last[user]` 는 그 계정에 기억해 둔 괄호 묶음(튜플) 하나입니다. 번호를 붙여 값을 하나씩 꺼냅니다. 번호는 0 부터 셉니다.
  - `last[user][0]` : 첫째 값 = 마지막 결정(`"거부"` 또는 `"허용"`)
  - `last[user][1]` : 둘째 값 = 그 결정의 시각(분)

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

| 유형 | 뜻 | 예 | 먼저 볼 기록 |
|---|---|---|---|
| 장애 | 정상 요청이 안 되거나 느림 (연결 장애 · 성능 저하 · 서비스 장애) | 특정 사이트만 안 열림, 응답이 느림, 서버가 켜지자마자 꺼짐 | `ping` · `tracert` · `nslookup`, 서버 상태, `docker ps -a` · `docker logs` |

- **과다권한**: 업무에 필요한 것보다 큰 권한을 가진 상태. **노출 범위**: 그 서버나 자료에 누가 접속할 수 있는지의 범위
- **무차별 대입**(brute force · 브루트 포스)
  - 비밀번호를 계속 바꿔 가며 로그인을 시도하는 공격
  - 10/15(목)에 한 IP 의 로그인 실패 기록으로 찾아봤다
- **DNS 스푸핑**(DNS spoofing · 디엔에스 스푸핑)
  - 가짜 DNS 응답으로 이름을 엉뚱한 IP 에 연결하는 공격
  - 사용자는 사이트가 열리는 것처럼 보인다
- **SYN Flood**(신 플러드)
  - 연결 요청(SYN)을 한꺼번에 마구 보내 서버가 새 연결을 받지 못하게 만드는 공격
  - 10/12(월)에 배운 handshake 의 첫 단계를 악용한다
- 한 증상이 두 유형에 걸칠 수 있습니다. 증상만으로 정하지 말고 **기록으로 가릅니다.**

### 📖 4.5 닫힘 기본 값 — 판단 서버가 응답하지 않을 때

> 📖 **읽을거리 — 읽기만 합니다.** 문제가 아닙니다. 답할 질문도, 따라 칠 명령도 없습니다.

6일 차에 PDP(판단)와 PEP(집행)를 나눴습니다. 그런데 PEP 가 PDP 에 물었는데 **답이 오지 않으면** 어떻게 해야 할까요?

- **닫힘 기본 값**(fail-closed · 페일 클로즈드)
  - 판단 서버가 응답하지 않으면 요청을 **막는** 설정
- **열림 기본 값**(fail-open · 페일 오픈)
  - 판단 서버가 응답하지 않으면 요청을 **통과시키는** 설정
- **거절과 통신 실패는 다릅니다.** 거절은 PDP 가 「거부」라고 **답한** 것이고, 통신 실패는 PDP 가 **답을 못 한** 것입니다. 중요한 자원은 두 경우 모두 막아야 합니다.
- 닫으면 판단 서버 장애가 곧 업무 중단이 되고, 열면 장애 동안 검사 없이 통과합니다. 그래서 **자원마다 다르게** 정합니다. 최소권한에서 자원마다 기준이 달랐던 것과 같은 생각입니다.
- **그래서 어느 쪽을 고르나 — 기본은 닫힘입니다.** Zero Trust 는 확인하지 못한 요청을 믿지 않기 때문입니다.
  - 닫힘을 고르는 자원: 정산 포털 · 관리자 화면 · 개인정보처럼 **잘못 통과하면 피해가 큰 것**. 잠깐 못 쓰는 불편보다 뚫리는 피해가 큽니다.
  - 열림을 예외로 고르는 자원: 사내 공지 게시판처럼 **누가 봐도 문제없고, 멈추면 업무가 서는 것**. 잠깐 검사 없이 통과해도 피해가 작습니다.
- 오늘 2교시 2-1 에서 `127.0.0.1:` 을 붙여 서버를 닫아 켜는 것도 같은 생각입니다. 기본은 닫아 두고 필요한 곳만 엽니다.

### 정답 2-1

💻 **터미널에 입력합니다.**

```bash
docker rm -f web-three web-four my-site
docker run -d --name closed-web-8081 -p 127.0.0.1:8081:80 nginx:1.28
docker run -d --name open-web-8082 -e DB_PASSWORD=dev-pass-1234 -p 8082:80 nginx:1.28
docker ps
curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://내주소:8081
curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://내주소:8082
curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8081
docker inspect closed-web-8081 open-web-8082 --format '{{.Name}} {{json .HostConfig.PortBindings}}'
docker exec open-web-8082 env | grep DB_
docker exec open-web-8082 whoami
docker rm -f closed-web-8081 open-web-8082
```

**결과**

- (가) `closed-web-8081` 은 `127.0.0.1:8081->80/tcp`, `open-web-8082` 는 `0.0.0.0:8082->80/tcp` 로 나옵니다. 앞에 `127.0.0.1:` 이 붙어 있는지가 다릅니다.
- (나) `closed-web-8081` 은 `000`(연결 거부), `open-web-8082` 는 `200` 입니다.
- (다) `closed-web-8081` 은 `127.0.0.1`(내 PC 자신)로 온 요청만 받도록 연결돼 있어서, 내 PC 안에서 `127.0.0.1` 로 접속하면 `200` 이지만 `내주소` 로 오는 요청은 받지 않아 거부됩니다. 다른 PC가 내 PC의 IP 주소로 접속하는 것도 같은 경로이므로 똑같이 거부됩니다.
- (라) `-p 127.0.0.1:포트:80` 으로 켭니다. 필요한 곳에만 열고 나머지는 닫는 방화벽 허용 목록(4일 차)과 같은 생각입니다.
- (마) 실행 결과는 다음과 같습니다.

```
/closed-web-8081 {"80/tcp":[{"HostIp":"127.0.0.1","HostPort":"8081"}]}
/open-web-8082 {"80/tcp":[{"HostIp":"","HostPort":"8082"}]}
```

  - `closed-web-8081` 의 `HostIp` 는 `127.0.0.1` 이고, `PORTS` 열의 `127.0.0.1:8081->80/tcp` 와 같은 뜻입니다(내 PC 안에서만).
  - `open-web-8082` 의 `HostIp` 는 비어 있고(`""`), `PORTS` 열의 `0.0.0.0:8082->80/tcp` 와 같은 뜻입니다(모든 주소로 열림).
- (바) 한 예: `docker exec open-web-8082 env | grep DB_` 로 `DB_PASSWORD=dev-pass-1234` 가 그대로 나옵니다. 서버에 `docker exec` 로 들어올 수 있는 사람이나 `docker inspect` 를 칠 수 있는 사람은 누구나 비밀번호를 알게 됩니다. 다룰 때는 ① 비밀번호를 코드 · 이미지 · 저장소에 직접 쓰지 않고(`.env` 도 올리지 않음) ② 필요한 서버에만 넘기고 ③ 운영에서는 비밀번호를 따로 보관하는 기능(도커의 시크릿, 클라우드의 비밀 관리 서비스)을 씁니다. 오늘의 값은 연습용입니다.
- (사) `whoami` 는 `root` 입니다. 서버가 침해되면 공격자가 `root` 의 모든 권한을 얻어 서버 안의 파일 · 환경변수 · 설정을 마음대로 바꿀 수 있어 피해가 커집니다. 일하는 데 필요한 권한만 주는 최소권한(6일 차)과 반대 상태입니다. 서버를 일반 사용자로 실행하도록 정해야 합니다.

**왜** — `-p` 에 주소를 쓰지 않으면 서버가 모든 주소로 열립니다. 개발용 · 관리용 서버를 이렇게 켜 둔 채 잊는 것이 열린 포트의 흔한 원인입니다. 포트를 닫아도 서버 안에 평문 비밀번호가 있고 `root` 로 실행되면 한 번 뚫렸을 때 피해가 커서, 안쪽도 같이 점검합니다.

**자주 틀리는 곳** — `내주소` 를 글자 그대로 쳐서 에러가 나는 경우가 가장 많습니다. 실제 숫자로 바꿉니다. 맥북에서 `en0` 가 아닌 인터페이스를 쓰고 있어 주소가 비어 나오는 경우도 있습니다. 윈도에서 `172.` 로 시작하는 도커용 주소로 접속해 둘 다 열리는 것처럼 보이는 경우도 있습니다. `내주소` 가 잘못되면 둘 다 거부로 나옵니다. 가장 확실한 판정은 `PORTS` 열이나 `HostIp` 입니다. `--format` 뒤의 `'…'` 를 큰따옴표로 바꾸거나 `{{` 를 빼먹으면 에러가 나거나 전체 설정이 길게 나옵니다. `HostIp` 가 비어 있는 것을 「설정이 없다」로 읽으면 반대로 판단하게 됩니다. 비어 있다는 것은 모든 주소입니다.

**관제에서는** — 서버를 켤 때 `docker ps` 의 `PORTS` 열에 `0.0.0.0` 이 있는 서버를 찾는 것이 열린 포트 점검의 첫 단계입니다. 열려 있어도 되는 서버인지 확인하고, 아니면 `127.0.0.1:` 을 붙여 다시 켭니다. 이어서 설정 값에서 환경변수의 비밀번호와 `root` 실행 여부까지 같이 보면 서버 한 대의 점검이 끝납니다.

**결과**

- (가) 원인은 **컨테이너 쪽 포트를 `8080` 으로 연결한 것**입니다. nginx 는 컨테이너 안에서 `80` 을 기다리는데 8084 로 들어온 요청은 `8080` 으로 가서 받을 프로그램이 없습니다.
  - `docker ps` 에서 `STATUS` 는 `Up`, `PORTS` 는 `0.0.0.0:8084->8080/tcp` 입니다. 서버는 켜져 있습니다.
  - `docker logs wrongport-web-8084` 에는 시작 메시지뿐이고 요청 줄이 없습니다. 요청이 nginx 에 닿지 못했다는 뜻입니다.
  - 컨테이너 포트만 `80` 으로 바꾼 `compare-web-8085` 는 `200` 이고 `"GET / HTTP/1.1" 200` 접속 기록 줄이 남았습니다. 두 서버의 차이는 그 하나뿐이라 원인이 확인됩니다.
  - 포트 연결은 켤 때 정해지므로 지우고 `-p 8084:80` 으로 다시 켜야 합니다.
- (나) 한 예: **위협**(경로 탐색)에 가깝습니다. 근거는 ① 출처가 여섯 줄 모두 같고 ② 모두 같은 초(`12:14:23` 처럼)에 들어왔고 ③ 경로가 `/admin` · `/login` · `/.env` · `/wp-login.php` · `/backup.zip` 처럼 관리 · 설정 · 백업 파일을 찾는 것이고 ④ 프로그램이 브라우저가 아니라 `curl` 이라는 점입니다. 10/19(월)의 `favicon.ico` 404 는 브라우저가 스스로 한 번 보내는 정상 요청이고, 프로그램 이름이 `Mozilla/5.0 …` 이며 경로도 아이콘 하나입니다. 다만 이 기록만으로 누가 왜 했는지는 알 수 없으므로 「탐색 시도로 의심」이라고 쓰고, 출처의 다른 기록을 확인합니다. 학원 PC 에서는 출처가 도커의 PC 안 주소(`172.17.0.1` 등)로 보여 진짜 출처를 알 수 없지만, 실제 서버에서는 요청한 쪽의 주소가 찍힙니다.
- (답장) 한 예:

```

B 장애(포트 연결 오류) — 8084 서버는 Up 이지만 컨테이너 쪽 포트가 8080 이라 nginx(80)에 요청이 닿지 않습니다. -p 8084:80 으로 다시 켜겠습니다.
C 위협 의심(경로 탐색) — 같은 출처가 같은 초에 /admin · /.env 등 다섯 경로를 curl 로 요청했습니다. 그 출처의 다른 기록과 방화벽 로그를 확인하겠습니다.
```

**왜** — 알림은 짐작으로 나누고, 짐작은 기록으로 확인합니다. 응답 번호가 같아도 원인이 다르므로 `PORTS` · `STATUS` 와 `docker logs` 의 요청 줄을 함께 봐야 합니다.

**자주 틀리는 곳** — `000` 을 모두 「서버가 꺼졌다」로 읽는 경우가 가장 많습니다. `Up` 인데 컨테이너 쪽 포트가 틀려도 `000` 입니다. 404 를 서버 고장으로 읽는 경우도 있는데, 서버는 정상이고 없는 파일을 요청한 것입니다. 답장에 확인한 근거(`PORTS` 값 · 응답 번호 · 기록 줄)를 빼고 유형만 쓰면 보안 담당이 판단을 다시 해야 합니다.

**관제에서는** — 404 가 한꺼번에 많이 쌓이면 존재하지 않는 주소를 차례로 요청해 보는 시도일 수 있어서 4과목에서 분석할 대상이 됩니다. 답장은 「유형 · 근거 · 먼저 할 일」 순서로 써야 받는 사람이 바로 움직입니다.
