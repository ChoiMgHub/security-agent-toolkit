## 2교시 · 도커로 서버 알림 세 건 직접 확인 · 보안 담당에게 답장

### 문제 2-1 · 알림 A 확인 — 서버 두 대로 열려 있는지 재고, 설정 값 · 비밀번호 · 실행 사용자까지 점검하기

- (가) `docker ps` 의 `PORTS` 열에서 두 서버가 각각 어떻게 나왔는지 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 PORTS 값 ② open-web-8082 의 PORTS 값
  - 답:

    직접 실행한 `docker ps`에서 `closed-web-8081`의 PORTS는 `127.0.0.1:8081->80/tcp`였고, `open-web-8082`는 `0.0.0.0:8082->80/tcp, [::]:8082->80/tcp`였다. 두 서버 모두 Up이었다. 같은 nginx 이미지라도 앞에 호스트 주소를 지정했는지에 따라 공개 범위가 달라졌다.

- (나) 🔍 `내주소` 로 접속했을 때 `closed-web-8081` 과 `open-web-8082` 의 결과(응답 번호)를 각각 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 응답 번호 ② open-web-8082 의 응답 번호
  - 답:

    처음에는 `내주소`를 실제 IP로 바꾸지 않고 그대로 입력해 두 요청 모두 000이 나왔다. 이 결과는 공개 범위를 비교한 결과로 사용할 수 없었다. 이후 `ipconfig` 전체 출력에서 이더넷 2의 IPv4가 `192.168.100.89`, WSL 가상 어댑터의 IPv4가 `172.25.16.1`임을 확인했다. 실제 네트워크 주소 `192.168.100.89`로 다시 요청하니 8081은 000, 8082는 200이 나왔다. 이번에는 내가 직접 수정하고 확인한 결과다. 000은 HTTP 응답 코드를 얻지 못했다는 표시이며, 번호 하나로 원인을 확정하지 않고 PORTS와 설정을 함께 봤다.

- (다) 🔍 `closed-web-8081` 은 `127.0.0.1` 로 접속하면 열려 있는데 `내주소` 로는 거부되는 이유는 무엇인가요? 다른 PC가 접속하는 경우와 어떻게 같은가요?
  - 쓸 내용: ① 127.0.0.1 로는 열리는 이유 ② 내주소로는 거부되는 이유 ③ 다른 PC가 접속하는 경우와 같은 점
  - 답:

    `closed-web-8081`은 `-p 127.0.0.1:8081:80`으로 실행했으므로, 설정 원리상 `127.0.0.1:8081`로 들어온 요청을 컨테이너 80번으로 전달한다. `192.168.100.89:8081`처럼 다른 목적지 주소로 온 요청은 이 연결에 해당하지 않는다. 같은 PC에서 실행해도 목적지 주소가 다르면 결과가 달라질 수 있다. 다른 PC 역시 내 PC의 네트워크 주소로 접속해야 하므로 이 주소 제한의 영향을 받는다. 이번에 직접 공유한 응답 결과는 실제 네트워크 IP에 대한 000·200이며, 127.0.0.1 접속 가능 여부는 이 항목에서 설정 원리로 설명했다. 다른 실제 PC에서 접속을 시험한 것은 아니다.

- (라) 🔍 사내 PC에서 접속되면 안 되는 관리용 서버를 켠다면 `-p` 를 어떻게 쓰고, 이것이 4일 차의 어떤 원칙과 같은가요?
  - 쓸 내용: ① -p 에 쓸 형태 ② 같은 생각을 말하는 4일 차 원칙
  - 답:

    내 PC 내부에서만 사용할 관리용 서버라면 `docker run`에 `-p 127.0.0.1:8081:80`처럼 호스트 주소를 지정한다. 4일 차에 배운 허용 목록처럼 필요한 접속 범위만 허용하는 접근통제 원칙과 이어진다. 포트 바인딩과 방화벽 규칙은 구현 방식이 다르지만, 불필요하게 넓은 접근을 줄인다는 목적을 연결해 이해했다. `-p`는 독립 명령이 아니라 `docker run`에 붙는 옵션이다. 나는 옵션만 따로 실행해 `bash: -p: command not found`가 났고, 이 점을 설명받았다.

- (마) 🔍 `docker inspect` 결과에서 두 서버의 `HostIp` 는 각각 무엇이고, `PORTS` 열의 어느 표시와 같은 뜻인가요?
  - 쓸 내용: ① closed-web-8081 의 HostIp ② open-web-8082 의 HostIp ③ 각각 `PORTS` 열의 어느 표시와 같은 뜻인지
  - 답:

    직접 확인한 설정은 다음과 같다.

    ```text
    /closed-web-8081 {"80/tcp":[{"HostIp":"127.0.0.1","HostPort":"8081"}]}
    /open-web-8082 {"80/tcp":[{"HostIp":"","HostPort":"8082"}]}
    ```

    `closed-web-8081`의 HostIp `"127.0.0.1"`은 PORTS의 `127.0.0.1:8081->80/tcp`에 대응한다. `open-web-8082`의 HostIp `""`는 호스트 주소를 특정하지 않은 요청 설정이며, 이번 실행에서는 PORTS의 `0.0.0.0:8082->80/tcp, [::]:8082->80/tcp`로 나타났다. 빈 문자열을 ‘포트가 닫혀 있다’는 뜻으로 읽으면 안 된다. 0.0.0.0은 바인딩 표시이고 접속할 브라우저 목적지 주소로 쓰는 값은 아니다.

- (바) 🔍 `open-web-8082` 의 비밀번호가 `docker exec` 로 그대로 읽혔습니다. 왜 문제이고, 비밀번호를 환경변수에 넣을 때 어떻게 다뤄야 하나요?
  - 쓸 내용: ① 읽힌 값 ② 왜 문제인지 ③ 다룰 때 지킬 것 두 가지 이상
  - 답:

    `docker exec open-web-8082 env | grep DB_`를 실행해 `DB_PASSWORD=dev-pass-1234`가 그대로 출력되는 것을 확인했다. 환경변수는 설정 전달 방식이지 값을 자동 암호화하는 보관함은 아니므로, 도커 설정을 조회하거나 컨테이너 안에서 명령을 실행할 권한이 있는 사람이 값을 볼 수 있다. 실제 값은 ① 코드·이미지·공개 저장소에 직접 넣지 않고 ② 출력·로그·캡처를 공유할 때 노출하지 않으며 ③ 관리·조회 권한을 제한하고 필요한 서비스에만 전달해야 한다. 이번 값은 교재의 연습용 값이다. 웹페이지에 접속할 수 있다는 것과 환경변수를 조회할 수 있다는 것은 별개의 권한이다. 환경변수를 넣었다고 실제 DB를 연결한 것도 아니다.

- (사) 🔍 `whoami` 결과는 무엇이고, 이 서버가 침해되면 왜 위험이 커지나요? 6일 차 최소권한과 어떻게 이어지나요?
  - 쓸 내용: ① whoami 결과 ② 위험이 커지는 이유 ③ 최소권한과 이어지는 점
  - 답:

    `docker exec open-web-8082 whoami`의 실제 출력은 `root`였다. 이번 exec 명령이 컨테이너 내부의 높은 권한으로 실행됐다는 뜻이다. 침해된 프로그램이나 공격 코드가 높은 권한으로 실행된다면 파일·설정·중요한 값에 영향을 줄 수 있는 범위가 커지므로, 6일 차 최소권한 원칙에 따라 필요한 권한만 부여해야 한다. 다만 이 출력 하나로 nginx의 모든 프로세스가 root라고 확정하거나, 컨테이너의 root를 Windows 호스트 전체 관리자 권한과 같다고 해석하지는 않는다.

### 문제 2-2 · 알림 B · C 확인 — 응답이 없는 서버와 연달아 남은 404 읽기

- (가) 🔍 `wrongport-web-8084` 가 `Up` 인데 응답이 `000` 인 원인은 무엇인가요? `PORTS` 값, `docker logs` 에 요청 줄이 있었는지, `compare-web-8085` 와 비교한 결과를 근거로 적어 주세요.
  - 쓸 내용: ① 원인 ② `PORTS` 값 ③ `docker logs` 에 요청 줄이 있었는지 ④ `compare-web-8085` 와 비교한 결과
  - 답:

    원인은 내 PC 8084번을 컨테이너의 8080번으로 잘못 연결한 것이다. 이번 nginx 기본 설정은 컨테이너의 80번에서 요청을 기다린다. `docker ps`에서는 Up이었지만 PORTS가 `0.0.0.0:8084->8080/tcp, [::]:8084->8080/tcp`였고, curl은 000을 출력했다. 공유한 `docker logs wrongport-web-8084`에는 시작 메시지만 있고 GET 접속 기록은 없었다. 반면 `8085:80`으로 연결한 비교 서버는 200을 반환했고, `05:52:10 +0000`에 `"GET / HTTP/1.1" 200` 기록이 남았다. 컨테이너가 실행 중인 것과 웹서비스가 정상 이용 가능한 것은 다르며, 이번에는 포트 설정·응답·로그를 함께 비교해 원인을 확인했다. 8084라는 내 PC 포트 자체가 문제인 것은 아니다.

- (나) 🔍 `probe-web-8087` 의 접속 기록은 장애 · 위협 · 접근통제 중 무엇인가요? 출처 · 시각 · 경로 · 프로그램 중 세 가지 이상을 근거로 적고, 10/19(월)의 `favicon.ico` `404` 와 무엇이 다른지 적어 주세요.
  - 쓸 내용: ① 유형 ② 근거 세 가지 이상 ③ `favicon.ico` 404 와의 차이
  - 답:

    유형은 위협 의심, 구체적으로 관리·설정·백업 경로 탐색 형태다. 근거는 ① 여섯 접속 기록의 출처가 모두 `172.17.0.1`로 보이고 ② 모두 `2026-10-21 05:52:32 +0000` 같은 초에 남았으며 ③ `/admin`, `/login`, `/.env`, `/wp-login.php`, `/backup.zip`을 연속 요청했고 ④ 프로그램 정보가 모두 `curl/8.21.0`이라는 점이다. 다섯 경로는 404, `/index.html`은 200이었다. UTC 05:52:32는 한국 시각 14:52:32다.

    이전 `favicon.ico` 404는 브라우저가 아이콘을 자동 요청했지만 파일이 없었던 경우다. 이번에는 여러 관리·민감 파일 경로를 빠르게 찾았다는 차이가 있다. 다만 curl을 썼다는 사실 자체가 악의의 증거는 아니고, 이번 요청은 내가 명령으로 만든 연습이다. 172.17.0.1도 도커 환경에서 보이는 출처여서 실제 사람의 신원을 뜻하지 않는다. 404는 서버가 ‘찾지 못함’으로 응답한 것이며 자동으로 공격 차단을 의미하지 않는다. `/.env`가 404였으므로 앞 실습의 환경변수 비밀번호를 웹으로 읽은 것도 아니다.

- (답장) 보안 담당에게 보낼 답장을 씁니다. A · B · C 마다 유형 · 확인한 근거 · 먼저 할 일을 적어 주세요.
  - 쓸 내용: A · B · C 마다 ① 유형 ② 확인한 근거(`PORTS` 값 · 응답 번호 · 기록 줄) ③ 먼저 할 일
  - 답:

    보안 담당에게 전달하는 연습용 답장은 다음과 같이 정리했다. 실제 발송이나 계정·서버 변경 조치를 수행한 것은 아니다.

    - **A — 접근통제(공개 범위):** 8081은 `127.0.0.1:8081`, 8082는 `0.0.0.0:8082`로 공개돼 있었고 실제 네트워크 IP로 요청했을 때 각각 000과 200이었다. inspect도 이를 뒷받침했다. 담당자 PC 내부에서만 사용할 개발 서버라면 127.0.0.1로 공개 범위를 제한하는 것을 우선 검토한다. 실제 비밀정보의 취급과 실행 권한도 함께 점검한다. 다른 물리 PC에서 접속을 시험하거나 인터넷 공개 여부까지 확인한 것은 아니다.
    - **B — 장애(포트 연결 오류):** Up 상태여도 `8084:8080`으로 잘못 연결해 nginx의 80번으로 요청이 전달되지 않았다. 000과 접속 기록 부재, 정상 비교 서버의 200을 확인했다. `8084:80`으로 연결해 재생성하고 응답을 확인하는 것이 먼저다.
    - **C — 위협 의심(경로 탐색):** 같은 출처가 같은 초에 관리·설정·백업 관련 경로를 curl로 연속 요청했다. 실제 운영에서 발견했다면 로그를 보존하고 승인된 점검인지 확인한 뒤, 다른 요청과 민감한 자원의 응답을 조사한다. 이번에는 직접 재현한 요청이므로 실제 외부 침입으로 확정하지 않는다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답:

    오늘은 명령어만 먼저 따라 하다가 Windows에서 맥북용 명령을 실행하고, `내주소`를 그대로 입력하거나 `-p` 옵션만 실행하는 실수를 했다. AI 설명을 받은 뒤 실제 IP로 바꿔 000·200을 직접 확인했고, inspect 값과 연결해 이해했다. 명령어 앞뒤의 문제 설명, 운영체제, 현재 위치와 바꿔 넣을 값을 먼저 확인해야 한다는 것을 배웠다.

    또한 Up만 보고 정상이라고 판단하거나 404만 보고 공격이라고 판단하면 안 된다는 점을 배웠다. 오류 기록과 접속 기록이 같은 요청에 대해 각각 남을 수 있으므로, 이번 다섯 오류 줄과 다섯 404 줄을 열 번의 요청으로 세지 않는다. 2-1의 두 서버와 2-2의 세 서버는 삭제했고, 마지막 목록에 기존 hello-world 두 개만 남은 것을 확인했다.

### 문제 3-1 · 거부 직후 허용 찾고 이유별 막대그래프 그리기

- (가) 내가 채운 코드를 붙여 넣어 주세요.

    ```python
    last = {}
    deny_reasons = {}

    for text in LOG:
        line = json.loads(text)  # 1. JSON 문자열을 딕셔너리로 읽기
        user = line["user"]
        now = to_min(line["time"])

        # 2. 같은 계정의 직전 거부 뒤 10분 이내 허용인지 비교
        if (
            user in last
            and last[user][0] == "거부"
            and line["decision"] == "허용"
            and now - last[user][1] <= 10
        ):
            print("[거부 후 허용]", user, line["time"], line["device"])

        last[user] = (line["decision"], now)  # 3. 비교 후 현재 기록 기억

        if line["decision"] == "거부":
            deny_reasons[line["reason"]] = deny_reasons.get(line["reason"], 0) + 1

    for reason in deny_reasons:
        count = deny_reasons[reason]
        print(reason, "#" * count, count)  # 4. 건수만큼 글자 반복
    ```

    내가 직접 확인한 출력:

    ```text
    [거부 후 허용] seoyeon 02:13 NB-0417
    [거부 후 허용] junho 09:44 NB-0522
    미등록 기기 ## 2
    퇴사 계정 #### 4
    MFA 안 함 # 1
    해외 접속 # 1
    ```
