## 5교시 · SOAR 와 플레이북 4요소 이해하고, 알림 두 건을 수동 처리해 보기

### 문제 5-1 · 경로 스캔 플레이북을 쓰고, 알림 두 건을 수동 처리하기

- (가) 내가 쓴 PB-003 의 액션과 승인을 적고, 5번 확인 명령의 출력을 붙여 넣어 주세요.
  - 쓸 내용: ① PB-003 의 액션 ② PB-003 의 승인 ③ 확인 명령의 출력(코드 상자에 붙여 넣기)
  - 답: 교재와 AI의 안내를 참고해 PB-003의 액션을 ‘IP 차단’과 ‘티켓 생성’, 승인 값을 ‘담당자 승인 필요’로 작성했다. 등록 파일에서 PB-001·PB-002·PB-003을 읽을 수 있는지와 PB-003의 액션·승인을 확인했다.

    수동 실습에서는 담당자가 승인했다고 가정하고 INC-001과 INC-005를 처리했다. 확인 출력은 잠긴 계정 dami, 차단한 IP 198.51.100.90, 티켓 2건이었다. 파일로 표현한 모의 상태이며 실제 계정 잠금이나 네트워크 차단을 실행한 것은 아니다.

```text
['dami'] ['198.51.100.90'] 2
```

- (나) 🔍 알림 두 건을 수동 처리하면서 `system_state.json` 을 직접 고친 곳이 모두 몇 군데였는지 적고, 알림이 100건이면 어떤 문제가 생길지 적어 주세요.
  - 쓸 내용: ① 고친 곳의 개수 ② 알림이 100건일 때 생길 문제
  - 답: 추가한 기록을 기준으로 네 군데다. INC-001에서는 `locked_users`에 dami를 넣고 `tickets`에 TCK-1을 추가했다. INC-005에서는 `blocked_ips`에 198.51.100.90을 넣고 `tickets`에 TCK-2를 추가했다. 바뀐 최상위 항목 이름은 세 개지만, 사건별 티켓 두 건을 각각 추가하므로 기록 추가는 총 네 건으로 셌다.

    알림이 100건이면 같은 작업을 반복하면서 사건 번호나 대상을 잘못 입력하거나, 조치는 했는데 티켓을 빠뜨릴 수 있다. 승인 여부와 액션 순서도 건마다 확인해야 하므로 사람마다 처리 결과가 달라질 수 있다. 이번에는 입력 예시를 참고해 수동 처리했으며 실제 타이핑 횟수나 소요 시간을 측정한 것은 아니다.

- (다) 🔍 PB-003 의 승인 값을 그렇게 정한 이유를 적어 주세요. 대상이 사용자 계정이 아니라 IP 라는 점과 잘못 차단했을 때의 영향을 근거로 쓰세요.
  - 쓸 내용: ① 승인 값 ② 대상이 IP 라는 점을 근거로 한 이유 ③ 잘못 차단했을 때의 영향
  - 답: 승인 값은 ‘담당자 승인 필요’로 정했다. PB-003의 대상은 계정이 아니라 IP다. 같은 IP를 여러 정상 사용자가 함께 쓸 수도 있어, 경로 스캔 알림만 보고 차단하면 정상 사용자의 접속과 업무까지 막을 수 있다. 따라서 담당자가 해당 요청과 차단 영향을 확인하고 승인한 뒤 실행하도록 했다.

    사건의 위험 등급과 조치를 자동으로 실행해도 되는지는 다른 기준이다. low 등급이라고 해서 차단 영향까지 작다고 판단하지 않았다. 이 설정은 AI가 제시한 예시와 해설을 참고해 작성했다. 실제 IP 공유 여부나 차단 영향을 별도로 측정한 결과는 아니다.

## 6교시 · 플레이북으로 알림 5건을 한 번에 처리하고 감사 기록 남기기

### 문제 6-1 · 플레이북 실행기로 알림 5건 처리하고 감사 기록 읽기

- (가) 실행한 출력 전체를 붙여 넣고, 실행 후 잠긴 계정 · 차단한 IP · 티켓의 개수와 승인 대기 건수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 잠긴 계정 ③ 차단한 IP ④ 티켓 수 ⑤ 승인 대기 건수
  - 답: 인시던트 5건과 플레이북 3개를 읽었다. 실행 후 잠긴 계정은 dami 1개, 차단한 IP는 0개, 티켓은 1건, 담당자 알림은 0건이었다. 승인 대기는 INC-002와 INC-005 두 건이었다. 감사 기록 4건을 `action_log.json`에 저장했다는 메시지가 출력됐다.

    INC-001은 자동으로 실행됐고, INC-002·INC-005는 승인 대기로 멈췄다. INC-003·INC-004는 맞는 플레이북이 없었다. 맞는 플레이북이 없다는 결과를 정상 또는 해결 완료로 해석하지 않았다. 실제 실행 출력 전체는 아래와 같다.

```text
--- 단계 1: 불러온 인시던트 5 건 · 등록된 플레이북 3 개
--- 단계 2: 실행 전 모의 시스템 상태
잠긴 계정: []
차단한 IP: []
티켓: 0 건 · 담당자 알림: 0 건
--- 단계 3: 인시던트마다 플레이북 실행
INC-001 dami high -> PB-001 실행 완료 (상태: 조치됨)
INC-002 seoyeon mid -> PB-002 승인 대기 (상태: 분류됨)
INC-003 gaeun mid -> 맞는 플레이북 없음 (상태: 탐지됨)
INC-004 jiwoo mid -> 맞는 플레이북 없음 (상태: 탐지됨)
INC-005 198.51.100.90 low -> PB-003 승인 대기 (상태: 분류됨)
--- 단계 4: 실행 후 모의 시스템 상태
잠긴 계정: ['dami']
차단한 IP: []
티켓: 1 건 · 담당자 알림: 0 건
--- 단계 5: 승인 대기 2 건
INC-002 seoyeon PB-002 · 담당자 승인 필요
INC-005 198.51.100.90 PB-003 · 담당자 승인 필요
--- 단계 6: 감사 기록 4 건을 action_log.json 에 저장
INC-001 PB-001 계정 잠금 : 계정 dami 잠금 완료
INC-001 PB-001 티켓 생성 : 티켓 TCK-1 생성
INC-002 PB-002 전체 : 승인 대기
INC-005 PB-003 전체 : 승인 대기
```

- (나) 🔍 5교시에서 INC-005 를 수동 처리할 때와 달리, 실행기는 INC-005 를 어떻게 처리했는지 적어 주세요. 근거는 단계 3 · 4 · 5 의 출력으로 쓰고, 그렇게 처리한 이유도 적어 주세요.
  - 쓸 내용: ① 실행기가 INC-005 를 처리한 방식 ② 단계 3 · 4 · 5 에서 찾은 근거 ③ 그 이유
  - 답: 5교시에는 담당자가 승인했다고 가정하고 INC-005의 IP 차단과 티켓 생성을 상태 파일에 수동 입력했다. 6교시에는 실행기가 PB-003의 ‘담당자 승인 필요’를 확인하고 두 액션을 모두 실행하지 않았다.

    단계 3에서 INC-005는 ‘PB-003 승인 대기’, 상태는 ‘분류됨’으로 나왔다. 단계 4의 차단한 IP는 빈 목록이고 티켓도 INC-001에서 만든 1건뿐이었다. 단계 5에서는 INC-005와 PB-003이 승인 대기 목록에 포함됐다. 단계 6의 ‘INC-005 PB-003 전체 : 승인 대기’도 이를 뒷받침한다.

    IP 차단은 정상 사용자에게 영향을 줄 수 있으므로 승인 전에 멈춰야 한다. 코드의 `return False`는 오류가 아니라 더 이상 액션을 실행하지 않고 승인 대기로 넘긴다는 뜻이다. 이번 실행기는 사람에게 승인을 받는 화면이나 승인 후 재개 기능을 구현한 것은 아니다. 또한 실행 파일은 빈 모의 상태에서 시작하므로 5교시 결과에 누적하지 않고 이번 실행 결과로 `system_state.json`을 새로 저장한다.

- (다) 🔍 감사 기록(단계 6)에서 INC-002 의 한 줄을 읽고, 그 인시던트에 실제로 무엇이 일어났고 무엇이 일어나지 않았는지 적어 주세요. 이런 기록이 현업에서 필요한 이유도 적어 주세요.
  - 쓸 내용: ① INC-002 에 일어난 일 ② 일어나지 않은 일 ③ 기록이 필요한 이유
  - 답: INC-002의 감사 기록은 `INC-002 PB-002 전체 : 승인 대기`였다. ‘대량 다운로드’ 규칙과 mid 등급에 맞는 PB-002를 찾았지만 담당자 승인이 필요해 실행이 중단됐다. 단계 3에서 상태는 ‘분류됨’이었고 단계 5의 승인 대기 목록에도 남았다.

    PB-002의 ‘담당자 알림’과 ‘티켓 생성’은 모두 실행되지 않았다. 단계 4의 담당자 알림은 0건이고 티켓은 INC-001의 1건만 있었다. 여기서 ‘전체’는 모든 액션을 실행했다는 뜻이 아니라 플레이북 전체가 승인 대기로 멈췄다는 표시다.

    이런 기록은 대응을 누락한 것인지 승인 때문에 멈춘 것인지 구분하고, 어떤 사건에 어떤 절차가 적용됐는지 나중에 확인하는 데 필요하다. 코드상 감사 기록에는 시각·인시던트·플레이북·액션·결과가 들어간다. 다만 내가 공유한 콘솔 출력에는 시각이 없고, 저장된 JSON의 `time` 항목을 다시 읽은 결과도 아직 공유하지 않았다. 따라서 파일의 시각 항목 검증은 미확인으로 남긴다.

    감사 기록 4건은 INC-001의 액션 두 건과 INC-002·INC-005의 승인 대기 각 한 건이다. 현재 코드는 맞는 플레이북이 없는 INC-003·INC-004에 감사 기록을 추가하지 않으므로, 이 파일에 모든 인시던트의 전체 이력이 있다고 해석하지 않는다.

## 실습 준비와 확인 과정

- 작업 위치는 `security-agent-toolkit/soar_response`이고, 설정 파일은 `config/playbook_registry.json`에 두었다. 오늘 오후에는 Gemini API나 판다스를 사용하지 않았다.
- 처음에는 두 JSON 파일의 내용을 서로 바꿔 넣어 `incident_samples.json`의 개수가 4로 나왔다. 인시던트 네 건이 아니라 모의 상태 딕셔너리의 키 네 개를 센 것이었다. AI의 첨부 파일 검수로 원인을 확인한 뒤 임시 파일 이름을 이용해 두 파일 이름을 교환했다. 이후 `list 5`, INC-001부터 INC-005까지의 번호와 빈 초기 상태를 확인했다.
- PB-003에 ‘내가 정한 액션 이름들’ 같은 안내 문구를 그대로 남겼다가 AI와 검토했다. `actions`는 실제 액션 이름을 큰따옴표로 감싼 목록으로, `approval`은 정해진 승인 값으로 바꾸고 이유도 작성했다. 등록 확인 결과는 다음과 같았다.

```text
['PB-001', 'PB-002', 'PB-003']
['IP 차단', '티켓 생성'] 담당자 승인 필요
```

- 등록 확인 후 상태가 `[] [] 0`으로 나와 질문했다. 플레이북은 대응 절차를 적은 설정이고 확인 명령은 읽기만 하므로 아직 액션이 실행되지 않은 초기 상태라는 설명을 들었다. 이후 안내한 모의 상태를 직접 입력·저장하고 수동 처리 결과를 확인했다.
- 6교시에는 `incident.py`, `playbook_runner.py`, `day01_6-1_run.py`를 작성해 실행했다. 공유한 실행 경로는 기본 Python 3.14였으며 오전의 `anomaly_detection/.venv` 실행 경로와 달랐다. 실행 결과 오류는 없었고, 실제 시스템이 아닌 파일 기반 모의 대응이었다.
- 교재와 AI의 코드·해설을 참고해 실습하고 결과를 공유했다. 보고서도 이 대화와 실제 출력에 근거해 AI의 작성 지원을 받았다.

## 수동 처리와 자동 실행 비교

| 항목 | 5교시 수동 처리 | 6교시 자동 실행 |
| --- | --- | --- |
| 시작 상태 | 비어 있는 상태 파일을 직접 수정 | 코드가 빈 상태를 새로 생성 |
| 승인 전제 | INC-005는 승인받았다고 가정 | INC-002·INC-005는 승인 필요로 중단 |
| 잠긴 계정 | dami 1개 | dami 1개 |
| 차단한 IP | 198.51.100.90 1개 | 없음 |
| 티켓 | INC-001·INC-005, 2건 | INC-001, 1건 |
| 담당자 알림 | 선택한 액션에 없어 빈 목록 유지 | PB-002가 승인 대기로 멈춰 0건 |
| 감사 기록 | 별도의 감사 기록 생성은 하지 않음 | 저장 메시지와 기록 네 줄 확인 |

5교시 수동 결과가 6교시 뒤에도 그대로 남는 구조가 아니다. 두 결과의 차이는 승인 전제와 실행 방식의 차이이며, IP 차단과 티켓이 줄었다고 해서 오류라고 판단하지 않았다.

## 아직 확인하지 않은 항목

- 저장된 `action_log.json`을 다시 읽어 네 기록에 실제 시각 값이 들어 있는지 확인한 출력은 아직 공유하지 않았다.
- 저장된 `system_state.json`을 6교시 실행 뒤 별도로 재열람한 출력은 아직 공유하지 않았다. 현재 실행 후 상태의 근거는 단계 4 출력이다.
- 오후 작업의 `git status`·커밋·업로드 결과는 아직 공유하지 않았다.
